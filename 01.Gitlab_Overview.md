# 1. GitLab Platform Overview

## Quick Summary
- GitLab is a single-application DevOps platform: source control (Git), CI/CD, security scanning, issue/project tracking, container registry, and Kubernetes/agent integration.
- Everything lives in one data model (project -> pipelines -> environments -> deployments), unlike stitching together separate SCM + CI + registry tools.
- CI/CD is native — no separate "Actions marketplace" install step; a `.gitlab-ci.yml` in the repo root is enough to get a pipeline.
- Available as GitLab.com (SaaS), self-managed (any infra), and GitLab Dedicated (single-tenant managed).
- Tiers (Free / Premium / Ultimate) gate advanced security, compliance, and governance features, not basic Git/CI usage.
- Interview framing: GitLab is usually compared against GitHub (SCM + Actions) and Jenkins/CircleCI (CI-only) — know what's bundled vs bolted-on.

## Core Concepts
- **Core building blocks**
  - Project: a Git repo plus its issues, MRs, CI/CD config, wiki, registry namespace.
  - Group: a container for multiple projects; permissions and settings cascade down to subgroups/projects.
  - Namespace: either a personal namespace (your username) or a group namespace (`gitlab.com/my-group/my-project`).
- **Source control**
  - Standard Git under the hood — any `git` client works; GitLab adds Merge Requests (MRs) as the review/merge workflow (GitLab's term for what GitHub calls Pull Requests).
  - Protected branches, push rules, and approval rules layer on top of plain Git.
- **CI/CD**
  - Defined in `.gitlab-ci.yml` at the repo root (or included from elsewhere via `include:`).
  - Runs on Runners (shared/instance runners provided by GitLab.com, or self-hosted runners you register).
  - Pipeline = collection of stages; stage = collection of jobs; jobs in a stage run in parallel by default.
- **Security / DevSecOps scanning**
  - SAST and Secret Detection are available even on Free tier for many project types.
  - DAST, Container Scanning, Dependency Scanning, and License Compliance require Ultimate (verify current tier gating on the docs page below — this shifts between releases).
- **Container Registry**
  - Every project gets its own registry namespace at `registry.gitlab.com/<namespace>/<project>` once enabled.
  - Auth uses the same PAT/CI job token mechanism as Git, not separate registry credentials.
- **Kubernetes / GitLab Agent**
  - Older "Kubernetes cluster integration via CI/CD settings" (certificate-based) is deprecated.
  - ⚠️ Deprecated / Changed: the certificate-based Kubernetes integration under Settings > CI/CD > Kubernetes described in older tutorials is removed. Current mechanism is the **GitLab agent for Kubernetes**, installed via `gitlab-agent` chart/CLI and configured with an `agents/<name>/config.yaml` file in the repo, connecting outbound from the cluster instead of GitLab holding cluster credentials.
- **GitLab vs GitHub (interview-relevant deltas)**
  - CI/CD: native in GitLab vs. a separate product (Actions) bolted onto GitHub.
  - Built-in Container Registry vs GitHub Container Registry (also built-in now, historically separate).
  - Merge Request approvals + built-in security dashboards vs GitHub's branch protection + third-party/Advanced Security add-ons.
  - Both offer self-hosted runners/agents; both have free tiers with usage-based CI minute limits.

## Hands-On Labs

### Lab 1: Create a GitLab.com account and first project
- **Goal:** Get a working namespace to practice in.
- **Steps:**
  1. Sign up at `gitlab.com` (or reuse existing account).
  2. Click **New project > Create blank project**.
  3. Name it `gitlab-overview-lab`, set visibility to **Private**, uncheck "Initialize with a README" is fine either way.
  4. Click **Create project**.
- **Expected result:** You land on an empty project page with a clone URL shown.
- **What this teaches:** Namespaces, project creation, where the clone URL/visibility toggle live.

### Lab 2: Clone the project and push a commit
- **Goal:** Confirm basic Git plumbing works end to end.
- **Steps:**
  1. `git clone https://gitlab.com/<your-namespace>/gitlab-overview-lab.git`
  2. `cd gitlab-overview-lab && echo "hello" > README.md`
  3. `git add README.md && git commit -m "init"`
  4. `git push origin main`
- **Expected result:** Commit appears in the project's **Repository > Commits** view.
- **What this teaches:** GitLab is just a Git remote with a UI layered on top.

### Lab 3: Add a minimal `.gitlab-ci.yml` and watch a pipeline run
- **Goal:** See native CI/CD trigger without any extra setup.
- **Steps:**
  1. In the repo root, create `.gitlab-ci.yml`:
     ```yaml
     stages: [build, test]
     build_job:
       stage: build
       script: [echo "Compiling code..."]
     test_job:
       stage: test
       script: [echo "Running tests..."]
     ```
  2. Commit and push to `main`.
  3. Go to **Build > Pipelines** in the UI.
- **Expected result:** A pipeline appears automatically with 2 stages, both green.
- **What this teaches:** Any push with a valid `.gitlab-ci.yml` auto-triggers a pipeline — no separate "enable CI" step.

### Lab 4: Open a Merge Request
- **Goal:** Practice the GitLab code-review workflow.
- **Steps:**
  1. `git checkout -b feature/login`
  2. Make a small change, commit, `git push origin feature/login`.
  3. GitLab UI shows a banner "Create merge request" — click it, or go to **Code > Merge requests > New merge request**.
  4. Fill title/description, click **Create merge request**.
- **Expected result:** MR page shows diff, pipeline status, and a **Merge** button (enabled once pipeline passes, if required).
- **What this teaches:** MR = GitLab's PR equivalent; pipeline status gates merging when configured.

### Lab 5: Create and label an issue
- **Goal:** Use built-in project management instead of an external tracker.
- **Steps:**
  1. Go to **Plan > Issues > New issue**.
  2. Title: `Add login feature`.
  3. Add labels `frontend`, `urgent`; set an assignee.
  4. Submit.
- **Expected result:** Issue appears in the issue board/list with labels visible.
- **What this teaches:** Issue tracking is part of the same project, referenceable from commits/MRs (`Closes #1`).

### Lab 6: Build and push a Docker image to the GitLab Container Registry
- **Goal:** Use the built-in registry end to end.
- **Steps:**
  1. Ensure Container Registry is enabled: **Settings > General > Visibility, project features, permissions**.
  2. `docker login registry.gitlab.com`
  3. `docker build -t registry.gitlab.com/<namespace>/gitlab-overview-lab:latest .` (any trivial Dockerfile works, e.g. `FROM alpine`)
  4. `docker push registry.gitlab.com/<namespace>/gitlab-overview-lab:latest`
- **Expected result:** Image visible under **Deploy > Container Registry**.
- **What this teaches:** Registry auth reuses your GitLab credentials/PAT — no separate account.
- **CI equivalent to note:**
  ```yaml
  docker_build:
    stage: build
    image: docker:latest
    services: [docker:dind]
    script:
      - docker build -t myapp:latest .
  ```

### Lab 7: Run a Node.js test pipeline
- **Goal:** See a language-specific CI example, not just `echo`.
- **Steps:**
  1. Add `.gitlab-ci.yml`:
     ```yaml
     image: node:20
     stages: [install, test]
     install_dependencies:
       stage: install
       script: [npm install]
     unit_tests:
       stage: test
       script: [npm test]
     ```
  2. Push a minimal `package.json` with a `test` script (even `"test": "echo ok"` works).
- **Expected result:** Pipeline runs both jobs against the `node:20` image.
- **What this teaches:** `image:` pins the container each job runs in; stages define ordering.

### Lab 8: Enable a security scan (SAST)
- **Goal:** See DevSecOps scanning without buying a license.
- **Steps:**
  1. Go to **Secure > Security configuration**.
  2. Click **Configure** next to Static Application Security Testing (SAST).
  3. Accept the generated MR that adds an `include:` for the SAST template.
  4. Merge it, then check the next pipeline for a `sast` job.
- **Expected result:** Pipeline gains a SAST job; results land under **Secure > Vulnerability report**.
- **What this teaches:** Many scanners are template `include:`s, not separate tools — and several work on Free tier.

### Lab 9: Compare GitLab.com vs a self-managed/Dedicated mental model
- **Goal:** Understand deployment options for interview purposes.
- **Steps:**
  1. Read **Settings > General** on your GitLab.com project and note what's admin-controlled vs instance-controlled (you can't see instance-level admin settings on SaaS).
  2. Note: this project lives on shared multi-tenant infrastructure (GitLab.com).
  3. Contrast mentally with a self-managed install (you'd control the whole instance, Omnibus/Helm install, your own runners by default) and GitLab Dedicated (single-tenant SaaS, GitLab-operated).
- **Expected result:** You can articulate the 3 deployment models without needing to provision one.
- **What this teaches:** "GitLab" is software, not just gitlab.com — a common interview clarifying point.

### Lab 10: Trace a full DevOps lifecycle in one project
- **Goal:** Tie everything together end to end.
- **Steps:**
  1. Create issue "Add health endpoint".
  2. Branch `feature/health`, commit code referencing `Closes #<issue-number>` in the commit message.
  3. Push, open MR, let pipeline run (build/test).
  4. Merge MR — confirm the issue auto-closes.
  5. Check **Deploy > Environments** if you added a deploy stage; otherwise confirm pipeline history under **Build > Pipelines**.
- **Expected result:** One traceable thread from issue -> branch -> MR -> pipeline -> merge -> closed issue.
- **What this teaches:** This traceability is GitLab's core "single application" pitch versus stitching together separate tools.

## Common Pitfalls
- Assuming Kubernetes integration still works via the old **Settings > CI/CD > Kubernetes** cert-based flow — it's removed; use the GitLab agent instead.
- Assuming all security scanners are free — SAST/Secret Detection are broadly available, but DAST/Container/Dependency scanning are typically Ultimate-gated (verify current gating, it changes).
- Confusing "Merge Request" with "Pull Request" in conversation with GitHub-background teammates — functionally equivalent, different name.
- Forgetting that pushing without a `.gitlab-ci.yml` simply does nothing — there's no error, just no pipeline.
- Assuming GitLab.com and self-managed GitLab always have identical default settings (e.g., instance runners only exist on GitLab.com / instances that configure them).

## Interview Questions & Answers
- **What is GitLab, in one sentence?**
  - A single DevOps platform combining Git hosting, CI/CD, issue tracking, container registry, and security scanning.
- **How does GitLab CI/CD differ from GitHub Actions?**
  - Native to every project via `.gitlab-ci.yml`, no marketplace install step; concepts are stages/jobs/runners vs workflows/jobs/actions.
- **What is a Runner?**
  - An agent process that executes CI/CD jobs; can be shared (GitLab-provided) or self-hosted/registered per project or group.
- **What's the difference between a project and a group in GitLab?**
  - A project is a single repo + its CI/issues/etc.; a group is a namespace that holds multiple projects and cascades settings/permissions.
- **What is a Merge Request?**
  - GitLab's code review/merge mechanism, equivalent to a GitHub Pull Request.
  - Can be gated by pipeline success, required approvals, and merge checks.
- **Name three deployment models for GitLab.**
  - GitLab.com (SaaS, multi-tenant), self-managed (you host it), GitLab Dedicated (single-tenant, GitLab-operated).
- **What replaced the old certificate-based Kubernetes integration?**
  - The GitLab agent for Kubernetes — cluster connects outbound to GitLab instead of GitLab holding a cluster API token.
- **Is GitLab CI/CD free to use?**
  - Yes, with a monthly compute-minutes quota on shared runners for Free tier namespaces; self-hosted runners aren't metered against that quota.
- **Scenario: a teammate says "there's no pipeline running" after they pushed code. First things to check?**
  - Does `.gitlab-ci.yml` exist at repo root (or is correctly included)? Is it valid YAML (check the pipeline editor's lint)? Are there `rules:`/`only:`/`except:` conditions excluding this branch/event? Are runners available/not paused for this project?
- **Scenario: your org wants full control over data residency and infra but doesn't want to run GitLab's control plane. Which deployment model fits?**
  - GitLab Dedicated — single-tenant SaaS, GitLab-operated, but isolated infra with more control over region than gitlab.com.
- **What's the difference between SAST and DAST?**
  - SAST scans source code statically (no running app needed); DAST tests a running deployed instance for vulnerabilities dynamically.
- **What is the Container Registry tied to?**
  - Each project gets its own registry path under `registry.gitlab.com/<namespace>/<project>`, authenticated with the same GitLab credentials/tokens as Git.
