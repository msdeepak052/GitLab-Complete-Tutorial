# 4. Private vs Public Repositories & Tier Limits

## Quick Summary
- GitLab projects/groups have one of three visibility levels: Public, Internal, Private — each controls who can view/clone without being an explicit member.
- Internal visibility is not selectable on GitLab.com for new projects/groups — it only exists on self-managed and GitLab Dedicated instances.
- Free tier lets you create unlimited public and private projects, but private top-level namespaces are capped at 5 users before going read-only.
- CI/CD minutes were renamed "compute minutes" in the docs; Free tier includes 400/month, Premium 10,000/month, Ultimate 50,000/month (verify at gitlab.com/pricing — these numbers change with pricing updates).
- The old blanket "public projects get a 0.008 cost-factor discount" rule is gone — the default compute-minute cost factor is now 1 regardless of visibility; the steep discounts (0.5, 0.008) are scoped specifically to the GitLab for Open Source program, not public projects in general.
- Interview framing: know the visibility model (who can see/clone) separately from the tier/billing model (how much compute you get) — they're independent axes people often conflate.

## Core Concepts
- **Visibility levels**
  - **Public** — anyone, including anonymous/logged-out users, can view and clone.
  - **Private** — only explicit project/group members can view or clone; nothing is visible to non-members.
  - **Internal** — any authenticated user on the instance can view/clone; not available for new projects/groups on GitLab.com.
  - ⚠️ Deprecated / Changed: Internal visibility is effectively self-managed/Dedicated-only now — don't expect to set it on a fresh GitLab.com project.
- **Inheritance rule**
  - A project's visibility must be at least as restrictive as its parent group's visibility (a private group cannot contain a public project).
- **What differs, public vs private, in practice**
  - Anonymous clone/view over HTTPS: allowed for public, blocked for private.
  - Issues/wiki/README visible to the world: yes for public, members-only for private.
  - Search-engine indexing / discoverability: public projects are discoverable, private are not.
  - Not subject to the same billing seat pressure — see next point.
- **Free tier user limit (private namespaces only)**
  - Top-level **private** namespaces on GitLab.com Free are capped at 5 users.
  - Exceeding 5 puts the namespace in a read-only state (no new commits, LFS uploads, package/registry pushes) until you remove members or upgrade to a paid tier.
  - Public top-level groups and personal namespaces are not subject to this 5-user cap.
  - Community programs (Open Source, Education, Startups) can lift this limit for qualifying projects without a paid plan.
- **Compute minutes (the current name for "CI/CD minutes")**
  - ⚠️ Deprecated / Changed: docs.gitlab.com now uses "compute minutes," not "CI/CD minutes," for the shared/instance-runner quota — same underlying concept, renamed.
  - Free: 400 compute minutes/month. Premium: 10,000/month. Ultimate: 50,000/month. (Confirm current figures at gitlab.com/pricing before relying on them — GitLab has changed these before and will again.)
  - Self-hosted/project runners are **not** metered against this quota — only GitLab-provided shared/instance runners consume compute minutes.
- **Cost factor (multiplier applied to job runtime)**
  - Default cost factor for standard instance-runner jobs is **1**, regardless of project visibility (public, private, internal all charged the same by default) — this is the key correction versus older material claiming a blanket public-project discount.
  - Steep discounts (0.5, and 0.008 for forks) apply specifically to projects enrolled in the **GitLab for Open Source program**, not to "any public project."
  - Different hosted runner classes have different cost factors, e.g. Linux x86-64 small = 1, Linux x86-64 medium = 2, Linux + GPU medium = 7, macOS runners = 6-12 (beta pricing, verify current values) — heavier compute classes cost more per minute of wall-clock job time.
- **Tier gating beyond minutes/seats**
  - Free: core Git, CI/CD, issues, MRs, basic SAST/Secret Detection on many project types.
  - Premium: higher compute quota, multiple approval rules, code owners enforcement, more advanced CI features.
  - Ultimate: full security/compliance suite (DAST, dependency/container scanning, compliance frameworks), custom roles, higher compute quota.

## Hands-On Labs

### Lab 1: Inspect a project's current visibility setting
- **Goal:** Find where visibility lives in the UI.
- **Steps:**
  1. Open any project you own > **Settings > General**.
  2. Expand **Visibility, project features, permissions**.
  3. Note the current **Project visibility** radio selection.
- **Expected result:** You see Public/Internal/Private options, with Internal grayed out or absent on GitLab.com.
- **What this teaches:** Visibility is a per-project setting independent of billing tier.

### Lab 2: Change a project from Private to Public and observe anonymous access
- **Goal:** See the practical effect of visibility change.
- **Steps:**
  1. In a throwaway project, switch visibility to **Public** and save.
  2. Open the project's URL in an incognito/private browser window (logged out).
  3. Try `git clone <https-url>` from a machine with no stored GitLab credentials.
- **Expected result:** The repo, README, and issues are viewable/clonable with no login.
- **What this teaches:** Public means literally anonymous, unauthenticated access — not just "any GitLab user."

### Lab 3: Confirm a Private project blocks anonymous clone
- **Goal:** Contrast with Lab 2.
- **Steps:**
  1. Switch the same project back to **Private**.
  2. Retry the incognito view and the credential-less clone from Lab 2.
- **Expected result:** Incognito view returns a 404 (GitLab doesn't reveal private project existence); clone prompts for/rejects auth.
- **What this teaches:** Private projects don't even leak their existence to non-members — a 404, not a 403.

### Lab 4: Check project visibility via the REST API
- **Goal:** Confirm/automate visibility checks without the UI.
- **Steps:**
  1. `curl --header "PRIVATE-TOKEN: <your_pat>" "https://gitlab.com/api/v4/projects/<project_id>"`
  2. Inspect the `"visibility"` field in the JSON response.
- **Expected result:** Returns `"public"`, `"private"`, or `"internal"` matching the UI setting.
- **What this teaches:** Visibility is a scriptable/auditable attribute — useful for compliance checks across many projects.

### Lab 5: Change visibility via the REST API
- **Goal:** Automate what Lab 2 did manually.
- **Steps:**
  1. `curl --request PUT --header "PRIVATE-TOKEN: <your_pat>" --data "visibility=private" "https://gitlab.com/api/v4/projects/<project_id>"`
  2. Reload the project's **Settings > General** page to confirm.
- **Expected result:** UI reflects the API-driven change.
- **What this teaches:** Bulk visibility audits/enforcement (e.g., "ensure no project is accidentally public") are realistically done via API/script, not by clicking through every project.

### Lab 6: Check remaining compute minutes for a namespace
- **Goal:** Find where usage/quota is surfaced.
- **Steps:**
  1. Go to your personal namespace or group > **Settings > Usage Quotas** (or **Settings > Usage Quotas > Pipelines**).
  2. Note "Compute minutes" used vs quota for the current billing period.
- **Expected result:** A used/total number, e.g. `12 / 400 minutes`.
- **What this teaches:** Quota is tracked per top-level namespace, not per individual project.

### Lab 7: Check compute-minute usage via the API
- **Goal:** Same data as Lab 6, but scriptable.
- **Steps:**
  1. `curl --header "PRIVATE-TOKEN: <your_pat>" "https://gitlab.com/api/v4/namespaces/<namespace_id>"`
  2. Look for usage-related fields in the response (field names shift between API versions — confirm against the current Namespaces/Usage Quotas API docs).
- **Expected result:** JSON includes namespace-level plan/usage info.
- **What this teaches:** Quota data is available for dashboards/alerts without screen-scraping the UI.

### Lab 8: Compare CI cost factor by making a job run on a public vs private project
- **Goal:** Directly observe that the default cost factor is the same regardless of visibility (correcting the old "public is nearly free" assumption).
- **Steps:**
  1. Create two throwaway projects: one Public, one Private, both under the same personal namespace.
  2. Add an identical `.gitlab-ci.yml` to each with one job that sleeps for a fixed short duration, e.g. `script: [sleep 30]`.
  3. Push to both, let the pipelines run on shared/instance runners.
  4. Compare compute-minute consumption for both in **Settings > Usage Quotas**.
- **Expected result:** Both projects consume roughly equal compute minutes for the same job duration (cost factor 1 for both) — unless one happens to be enrolled in the GitLab for Open Source program.
- **What this teaches:** Visibility alone (public vs private) no longer changes your compute-minute bill by default; the old "make it public to save CI minutes" advice is outdated.

### Lab 9: Hit the 5-user limit on a private namespace (read-only simulation)
- **Goal:** Understand the Free-tier private-namespace seat cap without needing 6 real users.
- **Steps:**
  1. Go to a private top-level group's **Manage > Members**.
  2. Note current member count against the documented 5-user Free-tier cap.
  3. Read **Settings > Usage Quotas > Seats** to see how GitLab surfaces remaining seats.
  4. (No need to actually exceed it — just identify where the warning banner would appear.)
- **Expected result:** You can locate where GitLab would warn/block before or upon hitting the cap.
- **What this teaches:** This is a common real-world "why is our repo suddenly read-only" incident — usually traced to inviting a 6th member to a private top-level Free group.

### Lab 10: Compare a public group's seat behavior against a private one
- **Goal:** Confirm the 5-user cap is visibility-specific, not tier-wide.
- **Steps:**
  1. Create a throwaway top-level group, set it Public.
  2. Add more than 5 members (using dummy/test accounts, or just reason through the Members page limits shown).
  3. Check **Usage Quotas > Seats** for that group vs the private one from Lab 9.
- **Expected result:** No 5-user read-only warning applies to the public group.
- **What this teaches:** The seat cap is tied specifically to private top-level namespaces on Free — public namespaces are exempt from it.

### Lab 11: Check which security scanners are available at your tier
- **Goal:** Separate "visibility" concerns from "tier" concerns for security features.
- **Steps:**
  1. Go to **Secure > Security configuration** on a Free-tier project.
  2. Note which scanners show **Configure** (available) vs a lock/upgrade icon (Premium/Ultimate-gated).
- **Expected result:** SAST/Secret Detection typically configurable; DAST/Container/Dependency scanning show tier-gating.
- **What this teaches:** Public/private visibility doesn't affect this at all — it's purely subscription tier.

### Lab 12: Audit visibility across all your projects via API
- **Goal:** Practice a realistic "compliance sweep" task.
- **Steps:**
  1. `curl --header "PRIVATE-TOKEN: <your_pat>" "https://gitlab.com/api/v4/projects?owned=true&per_page=100"`
  2. Pipe through `jq '.[] | {name, visibility}'` (or eyeball the JSON) to list every project's visibility in one shot.
- **Expected result:** A flat list of project name -> visibility pairs.
- **What this teaches:** This is exactly the kind of script a security/compliance review would run before an audit — much faster than clicking through Settings per project.

## Common Pitfalls
- Assuming public projects still get a large automatic CI-minutes discount — the default cost factor is 1 regardless of visibility now; only GitLab for Open Source program projects get the steep discount.
- Assuming "Internal" visibility is selectable on GitLab.com — it's self-managed/Dedicated only.
- Not noticing a private top-level namespace has silently gone read-only after crossing 5 members on Free tier.
- Confusing project visibility (who can view/clone) with tier (how much compute/which features you get) — they're independent.
- Treating a 404 on a private project as "project doesn't exist" instead of "you're not authorized to know it exists" — this is deliberate, not a bug.
- Relying on numeric pricing/quota figures from an old tutorial or blog post without re-checking gitlab.com/pricing — these change.

## Interview Questions & Answers
- **What are the three GitLab visibility levels and who can access each?**
  - Public: anyone, including anonymous users. Internal: any authenticated instance user (self-managed/Dedicated only). Private: explicit members only.
- **Is Internal visibility available on GitLab.com?**
  - Not for new projects/groups — it's restricted to self-managed and GitLab Dedicated instances.
- **What happens when a private top-level namespace exceeds the Free-tier user limit?**
  - It's placed in a read-only state (blocking new commits, LFS, package/registry pushes) until members are removed or the namespace upgrades to a paid tier; public namespaces aren't subject to this cap.
- **Do public projects get cheaper CI/CD minutes than private ones?**
  - Not by default anymore — the standard cost factor is 1 for both. Steep discounts only apply to projects enrolled in the GitLab for Open Source program.
- **What's the difference between "CI/CD minutes" and "compute minutes" in current GitLab terminology?**
  - Same concept, renamed — docs.gitlab.com now consistently uses "compute minutes" for the shared/instance-runner usage quota.
- **Does a self-hosted/project runner consume the shared compute-minutes quota?**
  - No — only GitLab-provided shared/instance runners are metered against the namespace's compute-minute quota.
- **What HTTP behavior distinguishes a private project from a nonexistent one for a non-member?**
  - Both return 404 — GitLab doesn't leak the existence of private projects to unauthorized users.
- **How would you check a project's visibility programmatically?**
  - `GET /api/v4/projects/:id` and read the `visibility` field, or list+filter via `GET /api/v4/projects` for a bulk audit.
- **Scenario: a public open-source project's maintainer complains their CI pipeline is burning through their compute-minute quota faster than expected. What would you check?**
  - Whether the project is actually enrolled in the GitLab for Open Source program (only then does the discounted cost factor apply); the runner types used per job (GPU/macOS runners cost far more per minute than small Linux runners); and whether jobs are unnecessarily long-running or duplicated across parallel/matrix jobs.
- **Scenario: a group admin says "our whole team suddenly can't push code." What's a likely visibility/tier-related cause?**
  - The group is a private top-level Free-tier namespace that just exceeded the 5-user limit and went read-only — check Usage Quotas > Seats.
- **Where do the current compute-minute quotas per tier come from, and why shouldn't you hardcode them in documentation?**
  - gitlab.com/pricing and the compute-minutes docs page; GitLab has changed these numbers before (e.g., cost-factor policy changes, quota changes across releases), so figures should be re-verified rather than assumed static.
- **Can a public group contain a private subgroup or project?**
  - Yes — a project/subgroup can be equal to or more restrictive than its parent, but not less restrictive (a private group cannot contain a public project).
