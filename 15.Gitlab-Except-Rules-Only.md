# Rules , Only and Except in Gitalb CI
Let’s go **step by step** and make it super clear how `rules`, `only`, and `except` work in GitLab CI/CD YAML files. These control **when a job runs**.

---

## **1️⃣ `only` and `except` (Old method)**

`only` and `except` are simpler but older keywords. They define **conditions based on branches, tags, or pipelines**.

### **Syntax and examples**

```yaml
stages:
  - build
  - deploy

build_job:
  stage: build
  script:
    - echo "Building the app"
  only:
    - main          # Run only on the 'main' branch
    - develop       # Also run on 'develop' branch
```

* ✅ Job runs **only** on `main` and `develop` branches.
* By default, **won’t run on other branches**.

```yaml
deploy_job:
  stage: deploy
  script:
    - echo "Deploying the app"
  except:
    - merge_requests  # Run on all branches except merge requests
    - tags            # Skip tags
```

* ✅ `except` excludes the job from specific branches or pipelines.

**Key Points**:

* `only` = **where to run**
* `except` = **where NOT to run**
* They can work with: `branches`, `tags`, `merge_requests`, `pipelines`.

---

## **2️⃣ `rules` (Modern and Flexible)**

`rules:` replaced `only/except` in GitLab 12+ because it’s **much more powerful**.
You can define **multiple conditions, variables, pipeline types**, and **custom expressions**.

### **Basic Example**

```yaml
build_job:
  stage: build
  script:
    - echo "Building..."
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'   # Run only on main
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'  # Or if MR
      when: manual  # Optional: trigger manually
```

* ✅ The job runs **automatically** on `main` branch or **manually** on merge requests.

---

### **Advanced Example**

```yaml
deploy_job:
  stage: deploy
  script:
    - echo "Deploying..."
  rules:
    - if: '$CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/'   # Run only for version tags like v1.2.3
      when: on_success
    - if: '$CI_COMMIT_BRANCH == "develop"'
      when: manual  # Manual deploy for develop branch
    - when: never   # Default: don’t run for other cases
```

✅ **Explanation**:

1. If the commit is a tag like `v1.2.3`, deploy automatically.
2. If on `develop`, deploy manually.
3. Otherwise, job **never runs**.

---

### **3️⃣ Key Differences**

| Feature           | only/except                  | rules                                                    |
| ----------------- | ---------------------------- | -------------------------------------------------------- |
| Flexibility       | Basic branch/tag conditions  | Branch, tag, MR, pipeline source, variables, expressions |
| Default action    | Run unless excluded (except) | Explicit: `when: never` if you want to skip              |
| Conditional logic | Limited                      | Multiple complex conditions allowed                      |
| Manual triggers   | No                           | Yes (`when: manual`)                                     |
| Recommended       | Legacy                       | Modern pipelines                                         |

---

### **4️⃣ Quick Summary / Cheat Sheet**

* Use **`only`**: “Run this job on these branches/tags/pipelines.”
* Use **`except`**: “Do NOT run this job on these branches/tags/pipelines.”
* Use **`rules`**: “I want full control with multiple conditions, variables, manual triggers, or default skip.”

---

## **6 `when` **

Let’s break down the **`when` keyword** in GitLab CI/CD with multiple examples. `when` controls **under what conditions a job is executed**.

---

## **1️⃣ Basic `when` Usage**

The `when` keyword can be used in **`rules`** or directly in a job. Its main values are:

| `when` value           | Meaning                                                          |
| ---------------------- | ---------------------------------------------------------------- |
| `on_success` (default) | Job runs **only if all previous jobs in earlier stages succeed** |
| `on_failure`           | Job runs **only if a previous job fails**                        |
| `always`               | Job runs **regardless of previous job status**                   |
| `manual`               | Job must be **triggered manually** from GitLab UI                |
| `delayed`              | Job runs **after a delay** (requires `start_in` attribute)       |
| `never`                | Job **will not run** (used to skip default execution)            |

---

## **2️⃣ Examples for Each `when`**

### **Example 1: on_success (default)**

```yaml
build_job:
  stage: build
  script:
    - echo "Building app"

test_job:
  stage: test
  script:
    - echo "Testing app"
  when: on_success   # Only runs if build_job succeeds
```

✅ If `build_job` fails, `test_job` **will not run**.

---

### **Example 2: on_failure**

```yaml
notify_failure:
  stage: deploy
  script:
    - echo "Build failed! Sending notification..."
  when: on_failure
```

* Runs **only if a previous job fails**.
* Useful for **alerts and cleanup tasks**.

---

### **Example 3: always**

```yaml
cleanup:
  stage: deploy
  script:
    - echo "Cleaning workspace..."
  when: always
```

* Runs **no matter what** (success or failure).
* Useful for **cleanup, logging, sending artifacts, notifications**.

---

### **Example 4: manual**

```yaml
deploy_job:
  stage: deploy
  script:
    - echo "Deploying to production"
  when: manual
```

* Job is **not triggered automatically**.
* A user must click **“Play”** in the GitLab UI.
* Can combine with `allow_failure: true` to avoid blocking pipelines.

---

### **Example 5: delayed**

```yaml
scheduled_job:
  stage: deploy
  script:
    - echo "Delayed job running..."
  when: delayed
  start_in: 10 minutes
```

* Runs automatically **after a specified delay**.
* Useful for **staged deployment or notifications**.

---

### **Example 6: Combining `when` with `rules`**

```yaml
deploy_job:
  stage: deploy
  script:
    - echo "Deploying app..."
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual       # Manual deploy on main branch
    - if: '$CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/'
      when: on_success   # Auto deploy for version tags
    - when: never        # Default: do not run
```

✅ Explanation:

* On `main` branch → Manual trigger
* On version tag → Automatic run if previous jobs succeed
* Otherwise → Job never runs

---

### **Example 7: Using `when` for failure notifications**

```yaml
build:
  stage: build
  script: make build

notify:
  stage: notify
  script: echo "Build failed!"
  when: on_failure
```

* Ensures **failure notification** only triggers if `build` fails.

---

### **8️⃣ Key Points to Remember**

* Default `when` is `on_success` — no need to specify if you want normal behavior.
* `manual` jobs **do not block pipeline** unless `allow_failure: false`.
* `always` jobs **always run**, great for cleanup.
* Combine `when` with `rules` for **complex conditional logic**.
* `delayed` requires `start_in` to specify delay.
