# 6. GitLab Manage & Plan — Members, Labels, Issues, Boards, Milestones, Wiki

## Quick Summary
- "Manage" and "Plan" are GitLab's project-management surface, separate from the "Code" (repository) and "Build" (CI/CD) surfaces.
- Members + roles control who can do what — this is the access-control backbone for everything else in the project.
- Labels are the tagging primitive used everywhere: issues, MRs, boards, and milestone filtering all key off labels.
- Issue Boards are just a Kanban view over issues filtered/grouped by label — no separate data model.
- Milestones group issues/MRs by time-box (sprint, release) and give burn-down/progress reporting.
- Wiki is a lightweight, git-backed docs space tied to the project — no external tool needed for runbooks.
- Interviewers care less about exact menu paths and more about whether you understand roles, workflow (issue -> board -> milestone), and how this maps to a real team's sprint cycle.

## Core Concepts

### Manage section
- **Activity** — reverse-chronological feed of commits, MRs, issue updates, comments for the project.
- **Members** — who has access and at what role.
  - Roles (lowest to highest): Guest, Planner, Reporter, Developer, Maintainer, Owner (plus Minimal Access at group level).
  - Guest: view/comment only, no code access on private projects.
  - Planner: manage issues, epics, milestones — no code/repo access (newer role, split out of Reporter-era workflows).
  - Reporter: view code, create issues, view CI/CD results — cannot push code.
  - Developer: push to non-protected branches, create MRs, run pipelines.
  - Maintainer: manage protected branches, CI/CD settings, project members, most settings.
  - Owner: full control including project deletion and visibility changes.
  - Members can be added directly, via a group, or invited by email (pending until accepted).
  - Access can also be time-limited ("Access expiration date").
- **Labels** — free-text or scoped tags (`bug`, `priority::high`) usable on issues and MRs.
  - Scoped labels (`key::value` syntax) enforce mutual exclusivity within the same key (an issue can't be both `priority::high` and `priority::low`).
  - Labels can be project-level or group-level (group labels are visible/usable across all projects in the group).
  - Labels drive board columns, filters, and saved searches.

### Plan section
- **Issues** — the atomic unit of planned work (bug, feature, task, chore).
  - Fields: title, description (markdown), assignee(s), labels, milestone, due date, weight, linked issues.
  - Issues can be created from the UI, via email, from a commit message (`Closes #12`), or via API.
  - Closing keywords in commit/MR descriptions (`Closes`, `Fixes`, `Resolves #12`) auto-close the issue on merge.
- **Issue Boards** — Kanban visualization of issues.
  - Columns = labels (or a "list" per label); default board has Open / To Do / Doing / Closed style flows depending on configuration.
  - Multiple boards per project are allowed (e.g., one per team, one per release).
  - Drag-and-drop between columns changes the underlying label on the issue.
- **Milestones** — time-boxed or version-boxed grouping of issues and MRs.
  - Project milestones vs group milestones (group milestone spans all projects in the group).
  - Has start date + due date, and a burndown/burn-up chart once issues are attached.
  - Not a hierarchy — an issue belongs to at most one milestone at a time.
- **Wiki** — Markdown/AsciiDoc/RDoc pages stored in their own git repo (`<project>.wiki.git`), clonable and editable outside the UI.
  - Supports page hierarchy (slug paths), history, and access control tied to the project.

### ⚠️ Deprecated / Changed
- The old flat "Guest → Reporter → Developer → Maintainer → Owner" 5-role model is no longer the complete picture — GitLab has since added **Planner** (issue/epic-focused, no code access) and **Minimal Access** (group-level, near-zero access) roles. Don't assume only 5 roles in an interview answer.
- Navigation labels ("Manage", "Plan") and their exact sub-item groupings have shifted across GitLab versions (older docs show slightly different left-nav groupings). Treat exact menu paths as approximate — the concepts (Members, Labels, Issues, Boards, Milestones, Wiki) are stable even when the sidebar is reorganized.

## Hands-On Labs

Running scenario: you're setting up a small "devops-app" project for a 3-person team (you as Owner, one Developer, one Reporter) and running one sprint end-to-end.

### Lab 1: Add a project member with a specific role
- **Goal:** Grant a teammate Developer access without giving them Maintainer rights.
- **Steps:**
  1. Project -> **Manage -> Members**.
  2. Click **Invite members**.
  3. Enter a username/email, set role = **Developer**, optionally set an expiration date.
  4. Click **Invite**.
- **Run it:** Repeat once more, this time setting role = **Reporter** for a second teammate.
- **Expected result:** Members list shows two new rows with the correct roles; the Reporter cannot push code (verify by trying `git push` as that user if you have a second account).
- **What this teaches:** Role-based access is per-member, not per-project-wide-default; least-privilege access starts here.

### Lab 2: Create scoped labels
- **Goal:** Build a `priority::` label set that's mutually exclusive.
- **Steps:**
  1. Project -> **Manage -> Labels -> New label**.
  2. Create `priority::high`, `priority::medium`, `priority::low` (pick distinct colors).
  3. Also create plain labels `bug` and `enhancement`.
- **Run it:** Open any issue and try applying both `priority::high` and `priority::low` at once.
- **Expected result:** GitLab automatically removes the previous `priority::*` label when you apply a new one from the same scope — confirming mutual exclusivity.
- **What this teaches:** Scoped labels (`key::value`) enforce single-select semantics, useful for priority/status fields without custom fields.

### Lab 3: File and triage an issue
- **Goal:** Create a realistic bug issue with full metadata.
- **Steps:**
  1. Project -> **Plan -> Issues -> New issue**.
  2. Title: `Fix Login API Timeout`.
  3. Description: repro steps + expected/actual behavior.
  4. Set assignee, labels (`bug`, `priority::high`), and leave milestone blank for now.
  5. Submit.
- **Run it:** Confirm the issue appears in the issue list and Activity feed.
- **Expected result:** Issue #N created; visible in **Manage -> Activity** immediately after creation.
- **What this teaches:** Issues are the unit of planned work; metadata (labels, assignee) is what makes filtering/boards useful later.

### Lab 4: Create a milestone and attach issues
- **Goal:** Time-box a sprint and track progress.
- **Steps:**
  1. Project -> **Plan -> Milestones -> New milestone**.
  2. Name: `Sprint 12`, set start date and due date (2 weeks out).
  3. Open 3-4 existing issues, set their **Milestone** field to `Sprint 12`.
- **Run it:** Return to the Milestone detail page.
- **Expected result:** Milestone page shows a progress bar (e.g., "0 of 4 closed — 0%") and a burndown chart once at least one issue closes.
- **What this teaches:** Milestones aggregate issues for reporting; progress % is derived automatically, not manually entered.

### Lab 5: Build an issue board filtered by label
- **Goal:** Get a Kanban view of Sprint 12 work.
- **Steps:**
  1. Project -> **Plan -> Issue boards -> Create board** (or use the default).
  2. Add lists for `To Do`, `Doing` (create/apply matching labels if needed).
  3. Filter the board by `milestone = Sprint 12`.
- **Run it:** Drag one issue card from `To Do` to `Doing`.
- **Expected result:** The issue's label changes automatically to match the new column; visible if you open the issue's label field.
- **What this teaches:** Boards are a view layer over labels — dragging a card is really just re-labeling the issue.

### Lab 6: Close an issue via commit message
- **Goal:** Auto-close an issue when the fix merges.
- **Steps:**
  1. Note an open issue's number, e.g. `#7`.
  2. On a feature branch, commit with message: `Fix login timeout, Closes #7`.
  3. Push and open a Merge Request into `main`.
  4. Merge the MR.
- **Run it:** Check the issue after merge.
- **Expected result:** Issue `#7` is automatically closed with a system note linking to the closing commit/MR.
- **What this teaches:** Closing keywords (`Closes`, `Fixes`, `Resolves`) wire commits/MRs directly into issue tracking — no manual bookkeeping.

### Lab 7: Create a group-level milestone (if you have a group)
- **Goal:** See the difference between project and group milestones.
- **Steps:**
  1. Create or use an existing GitLab group containing 2+ projects.
  2. Group -> **Plan -> Milestones -> New milestone** at the group level.
  3. Assign issues from two different projects in the group to it.
- **Run it:** Open the milestone report.
- **Expected result:** Progress aggregates issues across both projects in a single burndown.
- **What this teaches:** Group milestones span multiple repos — useful for cross-team release tracking, distinct from single-project milestones.

### Lab 8: Document a runbook in the Wiki
- **Goal:** Use Wiki as lightweight, versioned documentation.
- **Steps:**
  1. Project -> **Plan -> Wiki -> Create your first page**.
  2. Title: `Deployment Runbook`.
  3. Content: steps to deploy (markdown, can include a code block).
  4. Save.
  5. Clone the wiki repo separately: `git clone <project-url>.wiki.git`.
- **Run it:** Edit the page again from the UI, then `git pull` in your wiki clone.
- **Expected result:** The wiki is a real git repo — your local clone shows the new commit and updated content.
- **What this teaches:** Wiki content is git-backed, so it has full history and can be edited offline/via CI if needed.

### Lab 9: Use quick actions to manage an issue from a comment
- **Goal:** Speed up triage using GitLab quick actions.
- **Steps:**
  1. Open any issue.
  2. Add a comment containing:
     ```
     /label ~bug ~"priority::high"
     /assign @teammate
     /milestone %"Sprint 12"
     ```
  3. Submit the comment.
- **Run it:** Refresh the issue.
- **Expected result:** Labels, assignee, and milestone are all updated from the single comment — no separate form edits.
- **What this teaches:** Quick actions let you triage issues as fast as you can type, useful for bulk-processing a backlog.

### Lab 10: Filter and bulk-edit issues
- **Goal:** Simulate a sprint-planning pass over a backlog.
- **Steps:**
  1. Project -> **Plan -> Issues**.
  2. Filter by `label = bug` and `milestone = none`.
  3. Select all filtered issues (checkbox) -> **Edit issues** (bulk edit).
  4. Bulk-assign them to `Sprint 12` and add label `triaged`.
- **Run it:** Re-run the filter with `milestone = none`.
- **Expected result:** Previously-matching issues no longer appear (they now have a milestone); board/milestone views reflect the bulk change.
- **What this teaches:** Bulk edit is the practical tool for real backlog grooming, not one-by-one issue editing.

### Lab 11: Set up a second board for a different workflow
- **Goal:** Model a "Bugs only" triage board separate from the sprint board.
- **Steps:**
  1. **Plan -> Issue boards -> Create new board**, name it `Bug Triage`.
  2. Set the board's default filter to `label = bug`.
  3. Add lists per severity label (`priority::high`, `priority::medium`, `priority::low`).
- **Run it:** Switch between `Sprint 12` board and `Bug Triage` board using the board selector dropdown.
- **Expected result:** Each board shows a different slice of the same underlying issues — no duplication of data.
- **What this teaches:** Multiple boards are just multiple saved filters/views; issues remain the single source of truth.

## Common Pitfalls
- Assuming a Reporter can push code — they can't; only Developer+ can push to non-protected branches.
- Forgetting that scoped labels (`key::value`) auto-replace each other — useful, but surprising if you don't know the mechanic.
- Treating boards as a separate data store — deleting a board does not delete issues or labels.
- Not using closing keywords in commits/MRs, leading to manually-closed issues and lost traceability.
- Confusing project milestones with group milestones when reporting across multiple repos.
- Leaving Wiki as an afterthought instead of using it for runbooks that CI/CD steps or on-call docs can reference.

## Interview Questions & Answers
- **Q: What roles exist in a GitLab project and what can each do at a high level?**
  A: Guest (view/comment), Planner (plan issues/epics, no code), Reporter (view code + plan, no push), Developer (push non-protected branches, run pipelines), Maintainer (manage protected branches/settings/members), Owner (full control incl. delete). Group-level also has Minimal Access.
- **Q: What's the difference between a Label and a Milestone?**
  A: Label = arbitrary tag/category (many per issue, no time dimension). Milestone = time/version box (one per issue, has start/due date and progress reporting).
- **Q: How does an Issue Board relate to Labels?**
  A: A board is a filtered/grouped view of issues; each column typically maps to a label. Dragging a card between columns changes the issue's label — no separate board data model.
- **Q: How do you auto-close an issue when code is merged?**
  A: Use a closing keyword (`Closes`, `Fixes`, `Resolves #<issue-id>`) in a commit message or MR description; GitLab closes the issue automatically on merge to the default branch.
- **Q: What is a scoped label and why use one?**
  A: A label using `key::value` syntax (e.g. `priority::high`); GitLab enforces only one label per key on an issue, giving you exclusive-select fields (priority, status) without custom fields.
- **Q: Where does GitLab Wiki content actually live?**
  A: In a separate git repository (`<project>.wiki.git`) associated with the project — clonable, versioned, editable outside the UI.
- **Q: Project milestone vs group milestone — when would you use each?**
  A: Project milestone scopes to one repo/team; group milestone spans every project in a group, useful for cross-team releases tracked in one burndown.
- **Q: Scenario — a Reporter says they can't push a hotfix. What's happening and how do you fix it?**
  A: Reporter role has no push access by design; either temporarily elevate them to Developer, or have a Developer/Maintainer make the change — don't work around role restrictions with shared credentials.
- **Q: Scenario — your board shows an issue stuck in "To Do" even though someone says they're working on it. What's the likely cause?**
  A: They updated status verbally but never changed the issue's label/column (or changed a different label than the board's list is keyed on) — board state is driven purely by labels, not by intent.
- **Q: How would you give a contractor time-limited access to a private project?**
  A: Add them as a Member with an appropriate role (e.g., Developer) and set an **Access expiration date** — access auto-revokes on that date.
- **Q: What's the practical difference between filing an issue via UI vs via commit message vs via email?**
  A: All three create the same Issue object; commit-message creation ties the issue directly to a commit reference, email-in is useful for non-GitLab-native reporters (e.g., support inboxes wired to a project's issue email address).
