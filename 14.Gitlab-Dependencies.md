# 14. Artifact & Dependency Control: `dependencies:` vs `needs:`

## Quick Summary
- By default, a job automatically downloads **all artifacts from all jobs in all earlier stages** — no keyword required.
- `dependencies:` narrows that default: list the specific jobs whose artifacts you want; everything else is excluded.
- `needs:` is the modern keyword — it controls both **execution order** (DAG, jobs can start before their whole stage finishes) **and** artifact fetching (including from jobs in the *same* stage via `needs:artifacts`).
- Rule of thumb from current docs: don't combine `dependencies:` and `needs:` on the same job — pick one model.
- This file's focus is artifact/dependency **control**, not pipeline speed — see file 22 for `needs:`-driven parallelization and pipeline optimization.
- Interview-favorite mental model: stages are floors in a building; `dependencies:` decides which specific rooms on the floor below you're allowed to take packages from.

## Core Concepts

### Default behavior (no keyword)
- Without `dependencies:` or `needs:`, a job downloads artifacts from **every** job in **every earlier stage**.
- This is simple but can be wasteful (slow downloads, more storage/bandwidth) in pipelines with many artifact-producing jobs.

### `dependencies:` — artifact download control only
- Explicitly lists which earlier-stage jobs' artifacts to fetch; excludes everything not listed.
- Only affects **artifact downloading** — it does **not** change execution order; the job still waits for its entire stage to complete as normal.
- Jobs listed in `dependencies:` must be in an **earlier stage** — cannot reference a same-stage job.
- `dependencies: []` (empty array) explicitly downloads no artifacts at all.
- If a listed job produced no artifacts or was skipped, the current job still runs without erroring; if the artifacts existed but have since **expired**, the dependent job **fails**.

### `needs:` — DAG execution + artifact control (modern, recommended)
- Declares a direct dependency on specific jobs (by name), which:
  - Lets the job **start as soon as its named dependencies finish**, regardless of stage — this is what makes pipelines a DAG (directed acyclic graph) instead of strictly sequential stages.
  - Controls artifact fetching: by default a job with `needs:` downloads artifacts **from the jobs listed in needs** (same behavior intent as `dependencies:`, but works across and within stages).
- `needs: [job_a]` — fetch artifacts from `job_a`, run as soon as `job_a` completes (doesn't wait for the rest of `job_a`'s stage).
- `needs: [{ job: job_a, artifacts: false }]` — depend on `job_a` for ordering only, skip downloading its artifacts.
- `needs: [{ job: job_a, artifacts: true }]` — the default when artifacts aren't specified; explicit form for clarity.
- `needs:artifacts` is also how you fetch artifacts from a job in the **same stage** — `dependencies:` cannot do this at all, since it only looks at earlier stages.
- `needs:project` — cross-project artifact/job dependency (pull artifacts from a job in a different project's pipeline).
- Current docs explicitly advise: **do not combine `dependencies:` and `needs:` in the same job** — pick one consistently per job.

### `dependencies:` vs `needs:` — side-by-side
| Aspect | `dependencies:` | `needs:` |
| --- | --- | --- |
| Controls execution order | No — stage order still applies | Yes — enables out-of-stage-order (DAG) execution |
| Controls artifact download | Yes, from earlier-stage jobs only | Yes, from any listed job, including same-stage |
| Can reference same-stage job | No | Yes, via `needs:artifacts` |
| Cross-project | No | Yes, via `needs:project` |
| Recommended for new pipelines | Legacy-ish, still valid for pure artifact filtering in simple sequential pipelines | Yes — GitLab's recommended default for both ordering and artifact control |

### `⚠️ Deprecated / Changed`
- `dependencies:` is **not** deprecated, but it is increasingly a special-case tool: use it only when you want pure stage-sequential artifact filtering and have no interest in DAG-style speed-up. For anything needing same-stage artifact access or faster execution, `needs:` is the current recommendation.
- Older material undersold `needs:` as a minor "alternative" — current docs position `needs:` as the primary mechanism; `dependencies:` is the narrower, older tool.

## Hands-On Labs

### Lab 1: Baseline — default behavior with no keyword
- **Goal:** Confirm all earlier-stage artifacts are downloaded automatically with no keyword.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - test

build_job:
  stage: build
  script:
    - mkdir output
    - echo "app built" > output/result.txt
  artifacts:
    paths:
      - output/

test_job:
  stage: test
  script:
    - cat output/result.txt
```
- **Run it:** Push and check `test_job`'s log.
- **Expected result:** `app built` printed — artifacts flowed automatically, no `dependencies:`/`needs:` needed.
- **What this teaches:** The default (implicit) behavior you're about to override in later labs.

### Lab 2: `dependencies:` — narrow to one specific job
- **Goal:** Restrict a downstream job to only one of two earlier-stage artifact producers.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - test

build_job_a:
  stage: build
  script:
    - echo "Build A" > output_a.txt
  artifacts:
    paths:
      - output_a.txt

build_job_b:
  stage: build
  script:
    - echo "Build B" > output_b.txt
  artifacts:
    paths:
      - output_b.txt

test_job:
  stage: test
  dependencies:
    - build_job_a
  script:
    - cat output_a.txt
    - cat output_b.txt || echo "output_b.txt not available"
```
- **Run it:** Push and check `test_job`'s log.
- **Expected result:** `output_a.txt` content prints; `output_b.txt not available` prints for the second line.
- **What this teaches:** `dependencies:` opts out of the "download everything" default — only listed jobs' artifacts arrive.

### Lab 3: `dependencies: []` — download nothing
- **Goal:** Explicitly skip all artifact downloads for a job that doesn't need any.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - notify

build_job:
  stage: build
  script:
    - echo "built" > out.txt
  artifacts:
    paths:
      - out.txt

notify_job:
  stage: notify
  dependencies: []
  script:
    - echo "Sending notification, no artifacts needed"
    - ls out.txt || echo "out.txt correctly absent"
```
- **Run it:** Push and check `notify_job`'s log.
- **Expected result:** `out.txt correctly absent`.
- **What this teaches:** `dependencies: []` is the explicit way to say "this job needs zero artifacts," speeding up jobs that don't need any output from earlier stages.

### Lab 4: Parallel builds with selective `dependencies:` (frontend/backend)
- **Goal:** Two jobs build in parallel; a packaging job takes artifacts from only one.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - package

build_frontend:
  stage: build
  script:
    - echo "frontend" > frontend.txt
  artifacts:
    paths:
      - frontend.txt

build_backend:
  stage: build
  script:
    - echo "backend" > backend.txt
  artifacts:
    paths:
      - backend.txt

package_job:
  stage: package
  dependencies:
    - build_frontend
  script:
    - cat frontend.txt
    - cat backend.txt || echo "backend.txt not available"
```
- **Run it:** Push and check `package_job`'s log.
- **Expected result:** `build_frontend` and `build_backend` run in parallel (same stage); `package_job` runs after both finish, but only sees `frontend.txt`.
- **What this teaches:** `dependencies:` filters per-job even when multiple producers ran in parallel in the same earlier stage.

### Lab 5: Convert Lab 4 to `needs:` — same filtering, DAG semantics
- **Goal:** Achieve the same artifact filtering as Lab 4 but with `needs:`, and observe the ordering difference.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - package

build_frontend:
  stage: build
  script:
    - sleep 5
    - echo "frontend" > frontend.txt
  artifacts:
    paths:
      - frontend.txt

build_backend:
  stage: build
  script:
    - sleep 30
    - echo "backend" > backend.txt
  artifacts:
    paths:
      - backend.txt

package_job:
  stage: package
  needs:
    - build_frontend
  script:
    - cat frontend.txt
    - cat backend.txt || echo "backend.txt not available"
```
- **Run it:** Push and watch the pipeline graph (CI/CD > Pipelines > pipeline detail).
- **Expected result:** `package_job` starts as soon as `build_frontend` finishes — it does **not** wait for the slower `build_backend` (unlike Lab 4's `dependencies:`, where `package_job` waits for the whole `build` stage regardless).
- **What this teaches:** This is the key behavioral difference — `needs:` breaks strict stage-sequential waiting; `dependencies:` never does.

### Lab 6: `needs:artifacts` from a job in the SAME stage
- **Goal:** Do something `dependencies:` cannot do at all — fetch artifacts from a same-stage job.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build

generate_config:
  stage: build
  script:
    - echo "config=prod" > config.env
  artifacts:
    paths:
      - config.env

use_config:
  stage: build
  needs:
    - job: generate_config
      artifacts: true
  script:
    - cat config.env
```
- **Run it:** Push and check `use_config`'s log.
- **Expected result:** `config.env` content is available inside `use_config`, even though both jobs share the `build` stage.
- **What this teaches:** `dependencies:` is limited to earlier stages only; `needs:artifacts` is the only way to pull artifacts from a same-stage job.

### Lab 7: `needs:` for ordering only, without downloading artifacts
- **Goal:** Depend on a job completing first, without paying the cost of downloading its artifacts.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - verify

build_job:
  stage: build
  script:
    - echo "built" > out.txt
  artifacts:
    paths:
      - out.txt

verify_job:
  stage: verify
  needs:
    - job: build_job
      artifacts: false
  script:
    - echo "Just confirming build_job succeeded, no artifacts needed"
    - ls out.txt || echo "out.txt correctly absent"
```
- **Run it:** Push and check `verify_job`'s log.
- **Expected result:** `out.txt correctly absent` — ordering dependency honored, artifact skipped.
- **What this teaches:** `needs:` unbundles "wait for this job" from "download this job's artifacts" — two independent controls.

### Lab 8: Attempting to combine `dependencies:` and `needs:` (anti-pattern)
- **Goal:** See why current docs advise against mixing the two on one job.
- **`.gitlab-ci.yml`:** (do not do this — illustrative only)
```yaml
stages:
  - build
  - test

build_job:
  stage: build
  script:
    - echo "built" > out.txt
  artifacts:
    paths:
      - out.txt

confusing_job:
  stage: test
  needs:
    - build_job
  dependencies:
    - build_job
  script:
    - cat out.txt
```
- **Run it:** Push and check the pipeline for lint warnings, or just reason through it.
- **Expected result:** Works by coincidence here (both point at the same job), but is ambiguous/redundant and explicitly discouraged — pick one keyword.
- **What this teaches:** Mixing the two keywords adds no value and creates confusion about which one is actually governing behavior — always choose `needs:` for new pipelines unless you have a specific reason not to.

### Lab 9: `needs:` across stages for a multi-hop DAG
- **Goal:** Build a 3-stage DAG where a final job needs artifacts from a job two stages back, skipping the middle stage's wait.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - lint
  - deploy

build_job:
  stage: build
  script:
    - echo "built" > out.txt
  artifacts:
    paths:
      - out.txt

lint_job:
  stage: lint
  script:
    - sleep 20
    - echo "linting..."

deploy_job:
  stage: deploy
  needs:
    - build_job
  script:
    - cat out.txt
    - echo "Deploying without waiting on lint_job"
```
- **Run it:** Push and watch the pipeline graph.
- **Expected result:** `deploy_job` starts right after `build_job`, in parallel with `lint_job`, instead of waiting for the whole `lint` stage.
- **What this teaches:** `needs:` lets you skip entire intermediate stages for jobs that don't actually depend on them — impossible with `dependencies:`, which always respects full stage sequencing.

### Lab 10: Cross-project artifact dependency with `needs:project`
- **Goal:** Pull an artifact from a job in a *different* project's pipeline.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - use

use_upstream_artifact:
  stage: use
  needs:
    - project: group/upstream-project
      job: build_job
      ref: main
      artifacts: true
  script:
    - ls
```
- **Run it:** Push in the downstream project (requires the upstream project's pipeline to have run `build_job` on `main` with artifacts, and appropriate permissions/job-token allowlist per file 12).
- **Expected result:** Artifacts from `group/upstream-project`'s `build_job` are downloaded into this job.
- **What this teaches:** `needs:` extends dependency control beyond a single project's pipeline — something `dependencies:` cannot do at all.

### Lab 11: Expired artifact causes dependent job to fail
- **Goal:** Observe the failure mode when a referenced artifact has expired.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - test

build_job:
  stage: build
  script:
    - echo "built" > out.txt
  artifacts:
    paths:
      - out.txt
    expire_in: 30 seconds

test_job:
  stage: test
  dependencies:
    - build_job
  script:
    - cat out.txt
```
- **Run it:** Push, then manually retry only `test_job` (Pipelines > this pipeline > retry `test_job`) after waiting over 30 seconds.
- **Expected result:** Immediate run succeeds; the delayed retry of `test_job` fails because `build_job`'s artifact already expired.
- **What this teaches:** Unlike a "job produced no artifact" case (which doesn't error), a genuinely **expired** artifact that was expected causes the dependent job to fail — an important nuance for debugging flaky retries.

## Common Pitfalls
- Assuming `dependencies:` affects execution order — it never does; only `needs:` does.
- Trying to use `dependencies:` to pull artifacts from a same-stage job — impossible; only `needs:artifacts` supports that.
- Mixing `dependencies:` and `needs:` on the same job — current docs explicitly discourage this.
- Forgetting `dependencies: []` is valid and useful for jobs that need zero artifacts (faster job start).
- Not realizing an *expired* (vs simply absent) artifact causes a hard failure in the dependent job, while an absent one (job never produced artifacts) doesn't.
- Overusing `needs:` to reference dozens of jobs individually when a simpler stage-based flow would do — DAG complexity has a maintenance cost too.

## Interview Questions & Answers
- **Q: What's the default artifact-passing behavior if you specify neither `dependencies:` nor `needs:`?**
  A: The job automatically receives artifacts from all jobs in all earlier stages.
- **Q: What does `dependencies:` actually control?**
  A: Only which earlier-stage jobs' artifacts get downloaded — it has no effect on execution timing/order.
- **Q: What does `needs:` control that `dependencies:` cannot?**
  A: Execution order (DAG, out-of-stage-order start) and same-stage artifact fetching via `needs:artifacts`; also supports cross-project dependencies via `needs:project`.
- **Q: Can you fetch artifacts from a job in the same stage using `dependencies:`?**
  A: No — `dependencies:` only looks at earlier stages; use `needs:artifacts` instead.
- **Q: Should you combine `dependencies:` and `needs:` on one job?**
  A: No — current GitLab docs explicitly advise against combining them; pick one model per job.
- **Q: How do you make a job download zero artifacts?**
  A: `dependencies: []`, or `needs:` entries with `artifacts: false`.
- **Q: What happens if a job listed in `dependencies:` produced no artifacts at all?**
  A: The dependent job still runs fine, without error — it just won't have those files.
- **Q: What happens if a job's artifact existed but has since expired?**
  A: The dependent job fails — this is different from the "no artifacts produced" case.
- **Q: Scenario — a monorepo pipeline has `build-frontend`, `build-backend`, and `deploy` in sequential stages. `deploy` only needs frontend output but currently waits for backend too, and downloads both. How do you fix it?**
  A: Use `needs: [{ job: build-frontend, artifacts: true }]` on `deploy` — it will start as soon as `build-frontend` finishes (no longer waiting on `build-backend`) and only download frontend's artifacts. `dependencies:` alone would fix the artifact-filtering half but not the wait-time half.
  A: (dependencies-only variant) `dependencies: [build-frontend]` fixes which artifacts are downloaded, but `deploy` still waits for the entire `build` stage (including `build-backend`) to finish before starting — for real speed-up, use `needs:`.
- **Q: What's the "floors in a building" analogy for `dependencies:`?**
  A: By default you can take all packages from the floor below (all previous-stage artifacts); with `dependencies:` you only take packages from specific rooms (specific jobs) on that floor — anything unlisted stays behind.
- **Q: How would you pull an artifact from a job in a completely different GitLab project?**
  A: `needs: [{ project: group/other-project, job: job_name, ref: branch, artifacts: true }]` — requires appropriate access/job-token permissions.
