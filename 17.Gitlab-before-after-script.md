# 17. `before_script` and `after_script` in GitLab CI

## Quick Summary
- `before_script` — commands that run before `script`, concatenated into the same shell/execution context.
- `after_script` — commands that run after `script`, in a **separate, isolated shell context** with its own timeout.
- Both can be set globally (top-level or under `default:`) or per job.
- Job-level `before_script`/`after_script` **completely replaces** the global one — it does not merge.
- `after_script` runs even if `script` fails or the job is cancelled mid-`script` — but not for every failure type (e.g. not for a runner system failure).
- Real-world use: auth to a registry once globally, upload logs/notify on every job outcome via `after_script`.

## Core Concepts

### `before_script`
- Runs **before** the job's `script`, in the **same shell session** as `script` — variables exported, `cd`, aliases, etc. in `before_script` are visible to `script`.
- Typical uses: installing dependencies, exporting env vars, authenticating to a registry/package manager.
- Declared globally (applies as the default for every job) or per job (overrides the global one for that job only).

### `after_script`
- Runs **after** `script` finishes — success, failure, or most cancellations mid-run.
- Executes in a **new, separate shell context** — it does **not** see variables exported or `cd` changes made in `before_script`/`script`. Only predefined/`variables:`-block variables and files written to disk are visible.
- Has its own timeout, default 5 minutes, configurable via the `RUNNER_AFTER_SCRIPT_TIMEOUT` variable — a slow `after_script` can be silently cut off.
- Typical uses: uploading logs/artifacts regardless of outcome, sending a Slack/notification hook, cleaning up temp resources, tearing down a test container.

### Global vs job-level: replace, not merge
- Declared at the top level of `.gitlab-ci.yml` (or under `default:`), a `before_script`/`after_script` becomes the **default** for every job.
- If a job defines its **own** `before_script` or `after_script`, that job's version **completely replaces** the global one for that job — GitLab does not concatenate global + job-level.
  > "Job configuration and default configuration does not merge together. If the job has `before_script` defined, the job configuration takes precedence and the default configuration is not used." — GitLab CI/CD YAML reference
- To run both, you must **manually re-include** the global commands inside the job's own `before_script`/`after_script`.

### Execution order per job
1. `before_script` (global default, or job-level override)
2. `script`
3. `after_script` (global default, or job-level override) — runs regardless of step 1/2 outcome, with the caveats above.

### `after_script` failure-mode nuance
- Runs when: the job's `script` fails normally (`script_failure`), or the job is cancelled while `before_script`/`script` is still running.
- Does **not** reliably run for every failure type — e.g. a runner system failure, or the job hitting its overall timeout, can skip `after_script` entirely.
- Because `after_script` is a *separate shell*, a failure inside `after_script` itself does **not** change the job's overall pass/fail status.

### ⚠️ Deprecated / Changed
- Nothing here is deprecated — this is stable, long-standing GitLab CI behavior. The one nuance worth calling out (and missing from many tutorials, including the prior version of this file): `after_script`'s isolated shell context and separate timeout. ## Hands-On Labs

### Lab 1: Global `before_script` applies to all jobs
- **Goal:** See a global `before_script` run for every job automatically.
- **`.gitlab-ci.yml`:**
  ```yaml
  before_script:
    - echo "Starting job..."
    - export APP_ENV=dev
    - mkdir -p logs

  stages:
    - build
    - test

  build_job:
    stage: build
    script:
      - echo "Building the app..."
      - echo "Environment: $APP_ENV"

  test_job:
    stage: test
    script:
      - echo "Running tests..."
      - ls logs
  ```
- **Run it:** Push and watch both job logs.
- **Expected result:** Both `build_job` and `test_job` print `Starting job...`, and `$APP_ENV` is `dev` in both (proving `before_script` and `script` share a shell).
- **What this teaches:** Global `before_script` is the default for every job unless overridden.

### Lab 2: Job-level `before_script` replaces the global one
- **Goal:** Prove job-level override is a replacement, not an addition.
- **`.gitlab-ci.yml`:**
  ```yaml
  before_script:
    - echo "GLOBAL setup"

  build_job:
    stage: build
    before_script:
      - echo "Custom setup for build only"
    script:
      - echo "Building..."
  ```
- **Run it:** Push and inspect the `build_job` log.
- **Expected result:** Only `Custom setup for build only` appears — `GLOBAL setup` is never printed for this job.
- **What this teaches:** Job-level `before_script` fully replaces the global one.

### Lab 3: `after_script` runs even on failure
- **Goal:** Confirm `after_script` executes after a failing `script`.
- **`.gitlab-ci.yml`:**
  ```yaml
  test_job:
    stage: test
    script:
      - echo "Running tests..."
      - exit 1
    after_script:
      - echo "Tests finished, cleaning up..."
  ```
- **Run it:** Push and open the job log.
- **Expected result:** Job is marked **failed**, but `Tests finished, cleaning up...` still prints, after the `exit 1`.
- **What this teaches:** `after_script` is unconditional cleanup, independent of job outcome.

### Lab 4: `after_script` cannot see `script`'s exported variables
- **Goal:** Demonstrate the isolated shell context.
- **`.gitlab-ci.yml`:**
  ```yaml
  isolation_demo:
    stage: test
    script:
      - export BUILD_ID=12345
      - echo "In script, BUILD_ID=$BUILD_ID"
    after_script:
      - echo "In after_script, BUILD_ID=[$BUILD_ID]"
  ```
- **Run it:** Push and read the log.
- **Expected result:** `script` prints `BUILD_ID=12345`; `after_script` prints `BUILD_ID=[]` (empty) — proving it's a fresh shell.
- **What this teaches:** Don't rely on `export`ed variables surviving into `after_script`; write values to a file if `after_script` needs them.

### Lab 5: Manually merging global + job-level (the "include both" pattern)
- **Goal:** Run both global and job-specific setup/cleanup for one job.
- **`.gitlab-ci.yml`:**
  ```yaml
  before_script:
    - echo "Global setup"
  after_script:
    - echo "Global cleanup"

  test_job:
    stage: test
    before_script:
      - echo "Global setup"          # manually repeated
      - echo "Test-specific setup"
    script:
      - echo "Running tests..."
    after_script:
      - echo "Test-specific cleanup"
      - echo "Global cleanup"        # manually repeated
  ```
- **Run it:** Push and read `test_job`'s log.
- **Expected result:** Output order: `Global setup`, `Test-specific setup`, `Running tests...`, `Test-specific cleanup`, `Global cleanup`.
- **What this teaches:** There's no automatic merge — "both" only happens if you write both explicitly.

### Lab 6: Registry authentication — global `before_script`, per-job override
- **Goal:** A realistic pattern — authenticate to a container registry once globally, override for a job that needs a different registry.
- **`.gitlab-ci.yml`:**
  ```yaml
  before_script:
    - echo "$CI_REGISTRY_PASSWORD" | docker login -u "$CI_REGISTRY_USER" --password-stdin "$CI_REGISTRY"

  build_image:
    stage: build
    script:
      - docker build -t "$CI_REGISTRY_IMAGE:latest" .
      - docker push "$CI_REGISTRY_IMAGE:latest"

  push_to_dockerhub:
    stage: deploy
    before_script:
      - echo "$DOCKERHUB_PASSWORD" | docker login -u "$DOCKERHUB_USER" --password-stdin
    script:
      - docker tag "$CI_REGISTRY_IMAGE:latest" "myorg/app:latest"
      - docker push "myorg/app:latest"
  ```
- **Run it:** Push with `$CI_REGISTRY_PASSWORD`/`$DOCKERHUB_PASSWORD` set as masked CI/CD variables.
- **Expected result:** `build_image` logs into GitLab's registry via the global `before_script`; `push_to_dockerhub` skips that and logs into Docker Hub instead, via its own override.
- **What this teaches:** Overriding `before_script` per job to swap authentication targets without touching every other job.

### Lab 7: Always-upload-logs pattern with `after_script` + `artifacts: when: always`
- **Goal:** Guarantee logs are collected whether the job passes or fails.
- **`.gitlab-ci.yml`:**
  ```yaml
  run_integration_tests:
    stage: test
    script:
      - ./run-tests.sh > test-output.log 2>&1
    after_script:
      - echo "Test run finished with exit status unknown to after_script itself"
      - cp test-output.log after-script-copy.log || true
    artifacts:
      when: always
      paths:
        - test-output.log
      expire_in: 1 week
  ```
- **Run it:** Make `run-tests.sh` fail once, pass once.
- **Expected result:** `test-output.log` is attached as an artifact in both the passing and failing pipeline.
- **What this teaches:** `after_script` alone doesn't preserve files across job termination — pair it with `artifacts: when: always` (declared under the job, not `after_script`) for guaranteed log capture.

### Lab 8: Notification on completion regardless of outcome
- **Goal:** Send a notification whether the job succeeded or failed.
- **`.gitlab-ci.yml`:**
  ```yaml
  deploy_job:
    stage: deploy
    script:
      - ./deploy.sh
    after_script:
      - >
        curl -s -X POST "$SLACK_WEBHOOK_URL"
        -H 'Content-Type: application/json'
        -d "{\"text\": \"Pipeline $CI_PIPELINE_ID for $CI_PROJECT_NAME finished (job status not visible to after_script; check pipeline URL: $CI_PIPELINE_URL)\"}"
  ```
- **Run it:** Push with `$SLACK_WEBHOOK_URL` set, force `deploy.sh` to fail once.
- **Expected result:** The Slack message posts on both the successful and the failing run.
- **What this teaches:** `after_script` can't read the job's own final status directly (it doesn't know "pass" vs "fail" from inside itself) — link to `$CI_PIPELINE_URL`/use the GitLab API/webhooks if the notification needs the actual result.

### Lab 9: `after_script` timeout demonstration
- **Goal:** See `after_script`'s independent timeout in action.
- **`.gitlab-ci.yml`:**
  ```yaml
  variables:
    RUNNER_AFTER_SCRIPT_TIMEOUT: "10s"

  slow_cleanup:
    stage: test
    script:
      - echo "Main work done"
    after_script:
      - sleep 30
      - echo "You will not see this line"
  ```
- **Run it:** Push and watch the job log/timing.
- **Expected result:** The job log shows `after_script` getting cut off around 10 seconds instead of completing the full 30-second sleep; the final echo never prints.
- **What this teaches:** `after_script` has its own timeout (default 5 minutes), separate from the job's overall timeout — long cleanup work can get truncated.

### Lab 10: Default `before_script`/`after_script` via `default:` block
- **Goal:** Use the `default:` keyword (modern alternative to bare top-level `before_script:`) to set pipeline-wide defaults.
- **`.gitlab-ci.yml`:**
  ```yaml
  default:
    before_script:
      - echo "Default setup via default: block"
    after_script:
      - echo "Default cleanup via default: block"

  build_job:
    stage: build
    script:
      - echo "Building..."

  test_job:
    stage: test
    before_script:
      - echo "Job overrides default before_script"
    script:
      - echo "Testing..."
  ```
- **Run it:** Push and compare both job logs.
- **Expected result:** `build_job` runs the `default:` before/after scripts; `test_job` runs its own `before_script` (default is skipped) but still inherits the `default:` `after_script` since `test_job` doesn't override that one.
- **What this teaches:** `default:` is the current idiomatic place for pipeline-wide `before_script`/`after_script`, and override behavior applies per-keyword independently (overriding `before_script` doesn't affect inherited `after_script`).

## Common Pitfalls
- Assuming job-level `before_script`/`after_script` merges with the global one — it replaces it entirely.
- Trying to read a variable exported in `script` from inside `after_script` — different shell, won't be there; persist to a file instead.
- Writing a slow `after_script` (e.g. large log upload) without knowing about its separate, shorter default timeout.
- Relying on `after_script` for something that must always run even on runner-level failures (e.g. crashed runner) — it isn't guaranteed in every failure mode; use `artifacts: when: always` for critical file capture instead.
- Putting secrets-dependent login only in a job-level `before_script` override and forgetting other jobs still need the global login too.

## Interview Questions & Answers
- **Q: What's the execution order for a job with all three?**
  A: `before_script` → `script` → `after_script`.
- **Q: Does a job-level `before_script` merge with the global one?**
  A: No — it completely replaces it. GitLab does not concatenate job and default/global config for this keyword.
- **Q: Does `after_script` run if the job fails?**
  A: Yes, for normal script failures and mid-run cancellations. Not guaranteed for every failure class (e.g. runner system failures).
- **Q: Can `after_script` see variables exported in `script`?**
  A: No — `after_script` runs in a separate shell/context; only variables defined via the `variables:` keyword or files on disk carry over.
- **Q: How do you make both global and job-level setup run for one job?**
  A: Manually repeat the global commands inside the job's own `before_script`/`after_script` — there's no automatic merge.
- **Q: What's the default timeout for `after_script` and how do you change it?**
  A: 5 minutes by default; override with the `RUNNER_AFTER_SCRIPT_TIMEOUT` CI/CD variable.
- **Q: Where should you declare a pipeline-wide `before_script` today — top-level or `default:`?**
  A: Either works (top-level `before_script:` is implicitly folded into defaults), but `default:` is the more explicit, currently idiomatic location, and groups cleanly with other defaults like `default: image:`, `default: tags:`.
- **Q: Why might you deliberately override `after_script` to be empty (`after_script: []`) on one job?**
  A: To opt that specific job out of a global cleanup/notification step that doesn't apply to it, without deleting the global default for everyone else.
- **Q: Scenario — a job fails, and your team says "the cleanup step never ran." What are the two most likely causes?**
  A: (1) The job overrides `after_script` and forgot to include the cleanup command, since job-level replaces global; or (2) the failure was a runner-level/system failure or overall job timeout, which can skip `after_script` entirely.
- **Q: Scenario — `after_script` uploads a large log file and intermittently gets truncated mid-upload in CI, but works fine locally. What's the likely cause?**
  A: `after_script`'s separate, shorter default timeout (5 minutes) is being hit — either speed up the upload or raise `RUNNER_AFTER_SCRIPT_TIMEOUT`.
- **Q: Is `before_script` run in the same shell as `script`?**
  A: Yes — they're concatenated into a single shell session, so exports/`cd`/aliases in `before_script` carry into `script`.
- **Q: Give a realistic use case for global `before_script` and a realistic use case for `after_script`.**
  A: Global `before_script`: authenticate to a package registry/Docker registry once for every job. `after_script`: always upload logs or notify a Slack channel with the job outcome regardless of pass/fail.
