# 8. Intro to `.gitlab-ci.yml` — Structure and a Full Java -> Docker -> Kubernetes Pipeline

## Quick Summary
- `.gitlab-ci.yml`, in the repo root, is the single file that defines an entire GitLab CI/CD pipeline: what runs, in what order, on what runner.
- Pipelines are built from `stages` (ordered phases) and `jobs` (units of work assigned to a stage); jobs in the same stage run in parallel.
- `rules:` is the current, non-deprecated way to control whether/when a job runs — this file is the canonical home for the flagship advanced example in this series: a Java (Maven) app that builds, containerizes with Docker, and deploys to Kubernetes.
- `artifacts` pass files between stages/jobs; `variables` centralize reusable values; `image`/`services` control the job's execution environment (including Docker-in-Docker for building images).
- Kubernetes deploy credentials should use a narrowly-scoped Role/RoleBinding, never a `cluster-admin` ClusterRoleBinding, for a CI service account.
- This is the advanced flagship file in the series — see file 9 for a simpler, no-Docker beginner pipeline first if you're new to GitLab CI/CD.

## Core Concepts

### What `.gitlab-ci.yml` is
- The pipeline-as-code definition file, auto-detected by GitLab when present at the project root (path is configurable in Settings -> CI/CD -> General pipelines if needed).
- Written in YAML; validated via **CI/CD -> Pipelines -> Editor** (has a built-in linter) or `CI/CD -> Editor -> Lint`.

### Core structure
| Keyword | Purpose |
|---|---|
| `stages` | Ordered list of pipeline phases (e.g. build -> test -> package -> docker -> deploy). |
| `variables` | Global (or job-level) key/value pairs available as environment variables in jobs. |
| `default` | Shared job defaults (e.g. default `image`, `before_script`) to avoid repetition. |
| `<job_name>` | Any top-level key not reserved by GitLab becomes a job; must declare a `stage` (or uses `test` by default) and `script`. |
| `stage` | Which stage a job belongs to; jobs in the same stage run in parallel by default. |
| `script` | Shell commands the runner executes for the job — the only required job keyword besides an implicit stage. |
| `before_script` / `after_script` | Commands run before/after `script`, at job or global/default level. |
| `image` / `services` | Container image the job runs in; `services` attaches sidecar containers (e.g. `docker:dind` for building images). |
| `artifacts` | Files/directories preserved after a job and passed to later stages (and downloadable from the UI). |
| `rules` | Conditional logic controlling if/when a job is included in a pipeline, and with what attributes. |
| `environment` | Declares a deployment target (name + URL) for a job, powering GitLab's Environments/Deployments UI. |

### `rules:` — the modern trigger mechanism
- Replaces `only:`/`except:`, which are deprecated (still parse, but flagged for eventual removal — don't use them in new pipelines).
- Common forms:
  ```yaml
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
      when: manual
    - changes:
        - "src/**/*"
  ```
- Rules are evaluated top-to-bottom; the first matching rule decides the job's fate (`when: on_success` by default, or `never`, `manual`, `always`, `delayed`).
- If no rule matches, the job is not created in that pipeline at all (distinct from a job that runs but does nothing).

### ⚠️ Deprecated / Changed
- `only:`/`except:` (as seen in this file's earlier version, e.g. `only: [main]`) are deprecated — GitLab's docs explicitly say "use `rules` instead." They still work for backward compatibility but should not appear in new pipelines or tutorials.
- Granting a CI/CD service account `cluster-admin` via `ClusterRoleBinding` (common in copy-pasted tutorials) is an anti-pattern — a compromised or misconfigured pipeline gets full cluster control. Use a namespaced `Role` + `RoleBinding` scoped to only the verbs/resources the deploy job needs.
- Since Kubernetes 1.24, ServiceAccounts no longer get an auto-generated long-lived token Secret — you must create the token Secret manually (shown in Lab 9 below) if you need a static token for CI use (as opposed to short-lived tokens via `kubectl create token`).

## Hands-On Labs

### Lab 1: Anatomy of a minimal `.gitlab-ci.yml`
- **Goal:** Get the smallest possible pipeline running to see stages/jobs in action.
- **`.gitlab-ci.yml`:**
  ```yaml
  stages:
    - build

  hello_job:
    stage: build
    script:
      - echo "Hello from GitLab CI"
  ```
- **Run it:** Commit this file to a new branch, push, open the MR (or push to `main` directly if unprotected), then check **CI/CD -> Pipelines**.
- **Expected result:** One pipeline, one stage (`build`), one job (`hello_job`) that passes.
- **What this teaches:** The absolute minimum needed for GitLab to recognize and run a pipeline: `stages` + one job with `stage` + `script`.

### Lab 2: Add multiple stages
- **Goal:** See sequential stage execution.
- **`.gitlab-ci.yml`:**
  ```yaml
  stages:
    - build
    - test

  build_job:
    stage: build
    script:
      - echo "Building..."

  test_job:
    stage: test
    script:
      - echo "Testing..."
  ```
- **Run it:** Push and open the pipeline graph view.
- **Expected result:** `build_job` runs and completes before `test_job` starts — visualized left-to-right in the pipeline graph.
- **What this teaches:** Stages are sequential gates; a failed job in an earlier stage blocks later stages by default.

### Lab 3: Add a global variable
- **Goal:** Centralize a reusable value.
- **`.gitlab-ci.yml`:**
  ```yaml
  variables:
    APP_NAME: "java-deepak-webapp"

  stages:
    - build

  build_job:
    stage: build
    script:
      - echo "Building $APP_NAME"
  ```
- **Run it:** Check the job log/trace.
- **Expected result:** Log shows `Building java-deepak-webapp` — the variable was substituted.
- **What this teaches:** `variables:` at the top level is available to every job as an environment variable; job-level `variables:` can override it.

### Lab 4: Add artifacts to pass files between stages
- **Goal:** Produce a file in one job, consume it in the next.
- **`.gitlab-ci.yml`:**
  ```yaml
  stages:
    - build
    - test

  build_job:
    stage: build
    script:
      - mkdir out
      - echo "built" > out/result.txt
    artifacts:
      paths:
        - out/

  test_job:
    stage: test
    script:
      - cat out/result.txt
  ```
- **Run it:** Push and check `test_job`'s log.
- **Expected result:** `test_job` prints `built` — it received `out/` from `build_job` automatically.
- **What this teaches:** Artifacts are the mechanism for passing build outputs downstream; each job otherwise starts from a clean checkout.

### Lab 5: Add a `rules:` condition
- **Goal:** Make a job branch-conditional using the current, non-deprecated syntax.
- **`.gitlab-ci.yml`:**
  ```yaml
  stages:
    - deploy

  deploy_job:
    stage: deploy
    script:
      - echo "Deploying to production"
    rules:
      - if: '$CI_COMMIT_BRANCH == "main"'
  ```
- **Run it:** Push to a feature branch first, then to `main`.
- **Expected result:** On the feature branch, `deploy_job` does not appear in the pipeline at all; on `main`, it runs.
- **What this teaches:** `rules:if` decides whether the job is created in the pipeline, unlike a `script`-level `if` that would still create the job.

### Lab 6: Add a manual approval gate with `rules`
- **Goal:** Require a human click before a job runs.
- **`.gitlab-ci.yml`:**
  ```yaml
  deploy_prod:
    stage: deploy
    script:
      - echo "Deploying to production"
    rules:
      - if: '$CI_COMMIT_BRANCH == "main"'
        when: manual
  ```
- **Run it:** Push to `main`, open the pipeline.
- **Expected result:** `deploy_prod` sits in a "blocked/manual" state with a play button; pipeline doesn't finish until you click it (or it's skippable depending on `allow_failure`).
- **What this teaches:** `when: manual` combined with `rules:if` is the standard pattern for production deploy gates.

### Lab 7: Java build + test with Maven image
- **Goal:** Run a real Maven build instead of `echo`.
- **`.gitlab-ci.yml`:**
  ```yaml
  stages:
    - build
    - test

  build_job:
    stage: build
    image: maven:3.9.6-eclipse-temurin-17
    script:
      - mvn clean compile

  test_job:
    stage: test
    image: maven:3.9.6-eclipse-temurin-17
    script:
      - mvn test
  ```
- **Run it:** Push to a branch with a real `pom.xml` present.
- **Expected result:** Both jobs run inside the Maven image (not the runner's default image); build/test output appears in the job trace.
- **What this teaches:** `image:` swaps the job's container so you get the right toolchain without installing anything on the runner host.

### Lab 8: Package a JAR and keep it as an artifact
- **Goal:** Produce a deployable artifact.
- **`.gitlab-ci.yml`:**
  ```yaml
  package_job:
    stage: package
    image: maven:3.9.6-eclipse-temurin-17
    script:
      - mvn package -DskipTests
    artifacts:
      paths:
        - target/*.jar
      expire_in: 1 week
  ```
- **Run it:** Push, then open **Job -> Artifacts -> Browse** after it completes.
- **Expected result:** A downloadable `.jar` under `target/`; it auto-expires after a week.
- **What this teaches:** `expire_in` prevents artifact storage from growing unbounded — a common real-world gotcha if omitted.

### Lab 9: Full Java Maven -> Docker -> Kubernetes pipeline (flagship)
- **Goal:** Build the complete pipeline: compile, test, package, containerize, push to registry, deploy to Kubernetes with least-privilege RBAC.

**Directory structure:**
```
java-deepak-webapp/
├── .gitlab-ci.yml
├── Dockerfile
├── pom.xml
├── src/
└── k8s/
    ├── deployment.yaml
    ├── serviceaccount.yaml
    ├── role.yaml
    ├── rolebinding.yaml
    └── sa-token-secret.yaml
```

**`Dockerfile`:**
```Dockerfile
FROM openjdk:17-jdk-slim
WORKDIR /app
COPY target/java-deepak-webapp.jar app.jar
ENTRYPOINT ["java", "-jar", "app.jar"]
```

**`k8s/deployment.yaml`:**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: java-webapp
  namespace: devops
spec:
  replicas: 2
  selector:
    matchLabels:
      app: java-webapp
  template:
    metadata:
      labels:
        app: java-webapp
    spec:
      containers:
        - name: java-webapp
          image: registry.gitlab.com/deepak/java-deepak-webapp:latest
          ports:
            - containerPort: 8080
```

**One-time cluster setup — scoped RBAC (run by a cluster admin, once):**

⚠️ Don't grant `cluster-admin` to a CI service account. A pipeline (or an attacker who compromises it) with `cluster-admin` can read every secret and control every workload in the cluster. Instead, scope the service account to exactly what the deploy job needs — read/update `deployments` in one namespace.

**`k8s/serviceaccount.yaml`:**
```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: gitlab-deployer
  namespace: devops
```

**`k8s/role.yaml`:**
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: gitlab-deployer-role
  namespace: devops
rules:
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "watch", "update", "patch"]
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
```

**`k8s/rolebinding.yaml`:**
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: gitlab-deployer-binding
  namespace: devops
subjects:
  - kind: ServiceAccount
    name: gitlab-deployer
    namespace: devops
roleRef:
  kind: Role
  name: gitlab-deployer-role
  apiGroup: rbac.authorization.k8s.io
```

**`k8s/sa-token-secret.yaml`** (Kubernetes 1.24+ no longer auto-creates a token Secret, so create one explicitly):
```yaml
apiVersion: v1
kind: Secret
metadata:
  name: gitlab-deployer-token
  namespace: devops
  annotations:
    kubernetes.io/service-account.name: gitlab-deployer
type: kubernetes.io/service-account-token
```

**Apply and extract the token:**
```bash
kubectl apply -f k8s/serviceaccount.yaml -f k8s/role.yaml -f k8s/rolebinding.yaml -f k8s/sa-token-secret.yaml
kubectl -n devops get secret gitlab-deployer-token -o go-template='{{.data.token | base64decode}}'
```

**CI/CD variables** (Project -> Settings -> CI/CD -> Variables — mark secrets as Masked and Protected):

| Variable | Value | Type |
|---|---|---|
| `CI_REGISTRY_USER` | GitLab username or `$CI_REGISTRY_USER` (built-in for the project registry) | Predefined/Masked |
| `CI_REGISTRY_PASSWORD` | Personal/deploy access token | Masked |
| `K8S_NAMESPACE` | `devops` | Variable |
| `KUBE_TOKEN` | Token extracted above (from `gitlab-deployer` SA, not a cluster-admin identity) | Masked, Protected |
| `KUBE_SERVER` | Cluster API server URL | Variable |

**`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - test
  - package
  - docker
  - deploy

variables:
  IMAGE_TAG: "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"
  K8S_NAMESPACE: "devops"

default:
  before_script:
    - echo "Pipeline for $CI_PROJECT_NAME, branch $CI_COMMIT_REF_NAME"

build_job:
  stage: build
  image: maven:3.9.6-eclipse-temurin-17
  script:
    - mvn clean compile

test_job:
  stage: test
  image: maven:3.9.6-eclipse-temurin-17
  script:
    - mvn test

package_job:
  stage: package
  image: maven:3.9.6-eclipse-temurin-17
  script:
    - mvn package -DskipTests
  artifacts:
    paths:
      - target/*.jar
    expire_in: 1 week

docker_build:
  stage: docker
  image: docker:latest
  services:
    - docker:dind
  script:
    - docker login -u "$CI_REGISTRY_USER" -p "$CI_REGISTRY_PASSWORD" $CI_REGISTRY
    - docker build -t $IMAGE_TAG .
    - docker push $IMAGE_TAG
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'

deploy_to_k8s:
  stage: deploy
  image: bitnami/kubectl:latest
  script:
    - kubectl config set-cluster k8s --server="$KUBE_SERVER" --insecure-skip-tls-verify=true
    - kubectl config set-credentials gitlab-deployer --token="$KUBE_TOKEN"
    - kubectl config set-context k8s --cluster=k8s --user=gitlab-deployer --namespace=$K8S_NAMESPACE
    - kubectl config use-context k8s
    - kubectl -n $K8S_NAMESPACE set image deployment/java-webapp java-webapp=$IMAGE_TAG
    - kubectl -n $K8S_NAMESPACE rollout status deployment/java-webapp
  environment:
    name: production
    url: https://java.deepak-app.com
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```

- **Run it:**
  1. Commit and push all files: `git add . && git commit -m "Add Java/Docker/K8s pipeline" && git push origin main`.
  2. **CI/CD -> Pipelines**, watch stages run: `build -> test -> package -> docker -> deploy`.
  3. After success: `kubectl get pods -n devops` to confirm new pods with the updated image.
- **Expected result:** Docker image built and pushed to the GitLab Container Registry; Kubernetes `Deployment/java-webapp` rolled out with the new image, using a service account that can only touch `deployments`/`pods` in the `devops` namespace.
- **What this teaches:** How all previous labs compose into one realistic pipeline, and how to authenticate `kubectl` in CI without a kubeconfig file or over-broad cluster permissions.

### Lab 10: Restrict the Docker/deploy stages to protected branches only
- **Goal:** Prevent random feature branches from pushing images or deploying.
- **`.gitlab-ci.yml` (diff on `docker_build`/`deploy_to_k8s` from Lab 9):**
  ```yaml
  docker_build:
    rules:
      - if: '$CI_COMMIT_BRANCH == "main"'
        when: on_success
      - when: never
  ```
- **Run it:** Push the same pipeline definition to a feature branch.
- **Expected result:** `build`/`test`/`package` still run; `docker_build` and `deploy_to_k8s` are absent from the pipeline entirely on non-`main` branches.
- **What this teaches:** An explicit `when: never` fallback rule makes the "only run on main" intent unambiguous, versus relying purely on rule non-match.

### Lab 11: Add a merge-request pipeline variant
- **Goal:** Run build/test on every MR without deploying.
- **`.gitlab-ci.yml`:**
  ```yaml
  test_job:
    stage: test
    image: maven:3.9.6-eclipse-temurin-17
    script:
      - mvn test
    rules:
      - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
      - if: '$CI_COMMIT_BRANCH == "main"'
  ```
- **Run it:** Open an MR from a feature branch into `main`.
- **Expected result:** A merge-request pipeline runs `test_job` (visible on the MR widget), separate from the branch pipeline.
- **What this teaches:** `$CI_PIPELINE_SOURCE == "merge_request_event"` targets MR pipelines specifically — key for keeping CI feedback on the MR page itself.

## Common Pitfalls
- Still writing `only:`/`except:` in new pipelines — works today but is deprecated; use `rules:`.
- Copy-pasting a `cluster-admin` ClusterRoleBinding for a deploy service account "just to get it working."
- Forgetting `services: [docker:dind]` when building images inside a Docker-executor job — `docker build` fails with no daemon available.
- Not setting `expire_in` on artifacts, silently consuming storage quota over time.
- Assuming a job with no matching `rules` entry runs anyway — it doesn't; it's excluded from the pipeline.
- Hardcoding registry/cluster credentials directly in `.gitlab-ci.yml` instead of masked/protected CI/CD variables.
- Relying on an auto-created ServiceAccount token Secret on Kubernetes 1.24+ — it no longer exists by default and must be created manually or replaced with short-lived `kubectl create token`.

## Interview Questions & Answers
- **Q: What are the two mandatory pieces of a runnable GitLab CI job?**
  A: A `stage` (or default `test`) and a `script`. `stages:` at the top level plus at least one job block is the minimum viable `.gitlab-ci.yml`.
- **Q: Why use `rules:` instead of `only:`/`except:`?**
  A: `only`/`except` are deprecated by GitLab; `rules` is the actively supported, more expressive mechanism (`if`, `changes`, `exists`, `when`) and is what current docs/tutorials should use.
- **Q: How do jobs in the same stage relate to each other?**
  A: They run in parallel by default (subject to available runners); the pipeline only proceeds to the next stage once all jobs in the current stage finish (unless marked `allow_failure`).
- **Q: What's the difference between `artifacts` and `cache`?**
  A: Artifacts are pipeline outputs tied to a specific job run, passed to later stages and downloadable from the UI; cache is a reusable, best-effort speed optimization (e.g., dependency directories) shared across pipeline runs, not guaranteed to persist and not meant for passing build outputs.
- **Q: Why is `services: - docker:dind` needed for a Docker build job?**
  A: The job's own container doesn't have a Docker daemon; `docker:dind` runs Docker-in-Docker as a sidecar service the job's `docker` client connects to.
- **Q: Why is granting `cluster-admin` to a CI deploy service account a bad practice, and what's the fix?**
  A: It gives a pipeline (and anyone who compromises it) full cluster control, including reading unrelated secrets; fix is a namespaced `Role`/`RoleBinding` granting only the verbs/resources the deploy step actually needs (e.g., `update`/`patch` on `deployments` in one namespace).
- **Q: Scenario — your `deploy` job doesn't appear in the pipeline at all on a feature branch, no error shown. Why?**
  A: A `rules:` block evaluated to no match, so GitLab excluded the job from that pipeline entirely — this is expected behavior, not a failure, and is why an explicit `when: never` fallback is often added for clarity.
- **Q: Scenario — a Kubernetes deploy step that worked last year now fails to fetch a ServiceAccount token the old way. Why might that be?**
  A: Kubernetes 1.24+ stopped auto-creating a long-lived token Secret per ServiceAccount; you must create one explicitly (a Secret of type `kubernetes.io/service-account-token` with the SA annotation) or switch to short-lived tokens via `kubectl create token`.
- **Q: How would you make a deploy job require manual approval only on the production branch?**
  A: `rules: - if: '$CI_COMMIT_BRANCH == "main"' \n   when: manual` — combines a branch condition with a manual gate.
- **Q: What's the difference between a branch pipeline and a merge request pipeline?**
  A: Branch pipelines run on pushes to a branch ref; MR pipelines run specifically in the context of a merge request (`$CI_PIPELINE_SOURCE == "merge_request_event"`) and surface results directly on the MR widget — useful for gating merges on MR-specific checks.
- **Q: What does `environment:` in a job do?**
  A: Declares a named deployment target (and optional URL) for the job, which GitLab uses to populate the Environments/Deployments UI and enable features like environment-scoped variables and rollback.
