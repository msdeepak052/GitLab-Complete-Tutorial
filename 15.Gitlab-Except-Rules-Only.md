# Rules , Only and Except in Gitalb CI
Let’s go **step by step** and make it super clear how `rules`, `only`, and `except` work in GitLab CI/CD YAML files. These control **when a job runs**.

---

## **1️⃣ `only` and `except` (Old method)**

`only` and `except` are simpler but older keywords. They define **conditions based on branches, tags, or pipelines**.

### **Syntax and examples**

```yaml
stages:
  - build
  - deploy

build_job:
  stage: build
  script:
    - echo "Building the app"
  only:
    - main          # Run only on the 'main' branch
    - develop       # Also run on 'develop' branch
```

* ✅ Job runs **only** on `main` and `develop` branches.
* By default, **won’t run on other branches**.

```yaml
deploy_job:
  stage: deploy
  script:
    - echo "Deploying the app"
  except:
    - merge_requests  # Run on all branches except merge requests
    - tags            # Skip tags
```

* ✅ `except` excludes the job from specific branches or pipelines.

**Key Points**:

* `only` = **where to run**
* `except` = **where NOT to run**
* They can work with: `branches`, `tags`, `merge_requests`, `pipelines`.

---

## **2️⃣ `rules` (Modern and Flexible)**

`rules:` replaced `only/except` in GitLab 12+ because it’s **much more powerful**.
You can define **multiple conditions, variables, pipeline types**, and **custom expressions**.

### **Basic Example**

```yaml
build_job:
  stage: build
  script:
    - echo "Building..."
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'   # Run only on main
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'  # Or if MR
      when: manual  # Optional: trigger manually
```

* ✅ The job runs **automatically** on `main` branch or **manually** on merge requests.

---

### **Advanced Example**

```yaml
deploy_job:
  stage: deploy
  script:
    - echo "Deploying..."
  rules:
    - if: '$CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/'   # Run only for version tags like v1.2.3
      when: on_success
    - if: '$CI_COMMIT_BRANCH == "develop"'
      when: manual  # Manual deploy for develop branch
    - when: never   # Default: don’t run for other cases
```

✅ **Explanation**:

1. If the commit is a tag like `v1.2.3`, deploy automatically.
2. If on `develop`, deploy manually.
3. Otherwise, job **never runs**.

---

### **3️⃣ Key Differences**

| Feature           | only/except                  | rules                                                    |
| ----------------- | ---------------------------- | -------------------------------------------------------- |
| Flexibility       | Basic branch/tag conditions  | Branch, tag, MR, pipeline source, variables, expressions |
| Default action    | Run unless excluded (except) | Explicit: `when: never` if you want to skip              |
| Conditional logic | Limited                      | Multiple complex conditions allowed                      |
| Manual triggers   | No                           | Yes (`when: manual`)                                     |
| Recommended       | Legacy                       | Modern pipelines                                         |

---

### **4️⃣ Quick Summary / Cheat Sheet**

* Use **`only`**: “Run this job on these branches/tags/pipelines.”
* Use **`except`**: “Do NOT run this job on these branches/tags/pipelines.”
* Use **`rules`**: “I want full control with multiple conditions, variables, manual triggers, or default skip.”
