# Gitlab CI/CD Variables

Understanding **GitLab CI/CD Variables** is one of the most important parts of mastering pipelines because they control environment configuration, secrets, and dynamic behavior in builds.

Let’s break this down **clearly and practically** 👇

---

## 🧩 What Are GitLab CI/CD Variables?

**CI/CD variables** are key-value pairs that are **available to jobs and scripts** in your `.gitlab-ci.yml` file.

They are used to:

* Store **secrets** (e.g., tokens, passwords, API keys).
* Store **environment configurations** (like build environments or deployment URLs).
* Reuse **common values** across jobs.
* Make pipelines **dynamic** (behave differently depending on conditions).

---

## 🔹 1. **Predefined Variables**

GitLab automatically provides a large set of built-in variables.
They give details about:

* The **pipeline**
* The **repository**
* The **branch**
* The **runner**
* The **commit**

### 📘 Example

```yaml
stages:
  - info

show_predefined_vars:
  stage: info
  script: |
    echo "Project Name: $CI_PROJECT_NAME"
    echo "Branch Name: $CI_COMMIT_REF_NAME"
    echo "Commit SHA: $CI_COMMIT_SHA"
    echo "Pipeline ID: $CI_PIPELINE_ID"
    echo "GitLab Server: $CI_SERVER_URL"
```

### 🧠 Explanation

| Variable                 | Description                             |
| ------------------------ | --------------------------------------- |
| `$CI_PROJECT_NAME`       | Name of the GitLab project              |
| `$CI_COMMIT_REF_NAME`    | Current branch or tag name              |
| `$CI_COMMIT_SHA`         | Full commit hash                        |
| `$CI_PIPELINE_ID`        | Unique ID for the pipeline              |
| `$CI_SERVER_URL`         | GitLab server URL                       |
| `$CI_JOB_STAGE`          | Stage name the job belongs to           |
| `$CI_JOB_ID`             | Unique job ID                           |
| `$CI_RUNNER_DESCRIPTION` | Description of runner executing the job |

✅ **Use Case:** You can use these to label artifacts, generate reports, or dynamically tag Docker images like:

```bash
docker build -t myapp:$CI_COMMIT_SHORT_SHA .
```

## 🔹 2. **Custom Variables**

You define your own variables either:

* In the `.gitlab-ci.yml` file
* In the GitLab UI (under project or group settings)

### 📘 Example (Defined in YAML)

```yaml
variables:
  APP_ENV: "production"
  DEPLOY_DIR: "/opt/webapp"
  MAX_RETRIES: "3"

stages:
  - deploy

deploy_job:
  stage: deploy
  script:
    - echo "Deploying to $APP_ENV environment"
    - echo "Files will be placed in $DEPLOY_DIR"
    - echo "Retries allowed: $MAX_RETRIES"
```

✅ **Output Example:**

```
Deploying to production environment
Files will be placed in /opt/webapp
Retries allowed: 3
```

You can **override** these variables in:

* The **GitLab UI** under
  👉 *Settings → CI/CD → Variables*
* Or when **manually running a pipeline** (GitLab lets you input variables interactively)

---

## 🔹 3. **Group-Level Variables**

These are variables defined at the **group level** (applied to all projects inside a group).

### 📘 Example

Let’s say you have a GitLab Group:
`devops-projects/` containing:

* project-A
* project-B
* project-C

You can define variables like:

| Key            | Value        |
| -------------- | ------------ |
| AWS_ACCESS_KEY | AKIAxxxxxxxx |
| AWS_SECRET_KEY | yyyyyyyyyyy  |

📍 Add these under:
**Group → Settings → CI/CD → Variables**

Then, all your projects can access them directly in their `.gitlab-ci.yml`:

```yaml
deploy_aws:
  stage: deploy
  script:
    - echo "Deploying using AWS credentials..."
    - aws configure set aws_access_key_id $AWS_ACCESS_KEY
    - aws configure set aws_secret_access_key $AWS_SECRET_KEY
```

✅ **Use Case:**
Group-level variables are best for **shared credentials or tokens** used by multiple projects.

## 🔐 4. **Protected & Masked Variables**

GitLab lets you protect or mask sensitive variables:

| Setting       | Description                                                                                                      |
| ------------- | ---------------------------------------------------------------------------------------------------------------- |
| **Protected** | Variable is available only in protected branches/tags (like `main` or `release`).                                |
| **Masked**    | Variable value is hidden in job logs. GitLab allows only base64, alphanumeric, `_`, or `-` for masked variables. |

### 📘 Example

You can define:

```
Key: PROD_SECRET_KEY
Value: my-super-secret-key
```

* Mark it as **Protected**
* Mark it as **Masked**

Then in your job:

```yaml
deploy_secure:
  stage: deploy
  script:
    - echo "Deploying app..."
    - echo "Using secret key: $PROD_SECRET_KEY"
```

🧠 The secret will **not appear** in logs — GitLab masks it with `****`.

---

## 🔹 5. **Job-Level Variables**

You can also define variables inside **individual jobs** (overriding global ones):

```yaml
variables:
  ENV: "staging"

deploy_job:
  stage: deploy
  variables:
    ENV: "production"
  script:
    - echo "Deploying to $ENV"
```

✅ Output:
`Deploying to production`
(Job-level variable overrides global variable.)

---

## 🔹 6. **Using Variables in Scripts**

Inside scripts, you can:

* Access variables with `$VARIABLE_NAME`
* Or use interpolation in strings like `"${VARIABLE_NAME}"`

Example:

```yaml
script:
  - echo "Current branch: ${CI_COMMIT_REF_NAME}"
  - mkdir -p ${DEPLOY_DIR}/build
```
> The curly braces {} help clearly mark where the variable name ends — useful when appending text.

```bash
# Without braces
echo "$APP_NAMEv1"   # GitLab looks for a variable named APP_NAMEv1 ❌ (not found)

# With braces
echo "${APP_NAME}v1" # GitLab reads APP_NAME correctly ✅

```
---

## 🔹 7. **Dynamic Variables from Commands**

You can even define a variable based on a command using `export`:

```yaml
generate_dynamic_var:
  stage: build
  script:
    - export BUILD_VERSION=$(date +%Y%m%d%H%M)
    - echo "Build version is $BUILD_VERSION"
```

Or persist it using **artifacts** or the **CI_JOB_TOKEN** if needed across stages.

## ✅ Summary Table

| Type            | Defined Where     | Available To            | Example                              |
| --------------- | ----------------- | ----------------------- | ------------------------------------ |
| **Predefined**  | Auto (GitLab)     | All pipelines           | `$CI_PROJECT_NAME`, `$CI_COMMIT_SHA` |
| **Custom**      | YAML / Project UI | That project            | `APP_ENV=production`                 |
| **Group-level** | Group → CI/CD     | All projects in group   | `AWS_ACCESS_KEY`                     |
| **Protected**   | Project UI        | Only protected branches | `PROD_SECRET_KEY`                    |
| **Masked**      | Project UI        | Hidden in logs          | `API_TOKEN`                          |
| **Job-level**   | Inside job        | That job only           | `ENV=production`                     |

## 🧠 Practical Tip for DevOps Workflows

You can mix variables for secure and flexible setups:

```yaml
variables:
  ENVIRONMENT: "staging"
  APP_NAME: "myapp"

deploy_app:
  stage: deploy
  script:
    - echo "Deploying $APP_NAME to $ENVIRONMENT"
    - echo "Using AWS creds from group variables"
    - aws s3 cp ./build s3://$APP_NAME-$ENVIRONMENT --recursive
```
