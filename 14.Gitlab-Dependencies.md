# **Job dependencies in GitLab CI/CD** 

## **1️⃣ What are Dependencies in GitLab CI/CD?**

In GitLab CI/CD, a **job** is a set of instructions to perform a task. Sometimes jobs rely on the **output or artifacts of another job**. These are called **dependencies**.

There are two main ways to control job order and sharing:

1. **Stages** → High-level control (jobs in a stage run in parallel, next stage runs after current stage completes).
2. **Dependencies (job-level)** → Fine-grained control: a job explicitly depends on artifacts of specific previous jobs, even if they are in the same stage.

---

### **2️⃣ Using Stages for Ordering**

Simplest example:

```yaml
stages:
  - build
  - test
  - deploy

build_job:
  stage: build
  script:
    - echo "Building app..."
    - mkdir output
    - echo "app built" > output/result.txt
  artifacts:
    paths:
      - output/

test_job:
  stage: test
  script:
    - cat output/result.txt
```

✅ **Explanation**:

* `build_job` runs first because it’s in the `build` stage.
* `test_job` runs after `build_job` because it’s in the `test` stage.
* `artifacts` from `build_job` are automatically available to `test_job` (default behavior if stages are sequential).

---

### **3️⃣ Using `dependencies:` for Explicit Control**

Sometimes you want **specific jobs to receive artifacts** and ignore others.

```yaml
stages:
  - build
  - test

build_job_a:
  stage: build
  script:
    - echo "Build A" > output_a.txt
  artifacts:
    paths:
      - output_a.txt

build_job_b:
  stage: build
  script:
    - echo "Build B" > output_b.txt
  artifacts:
    paths:
      - output_b.txt

test_job:
  stage: test
  dependencies:
    - build_job_a
  script:
    - echo "Testing..."
    - cat output_a.txt
    - cat output_b.txt || echo "output_b.txt not available"
```

✅ **Explanation**:

* `test_job` **depends only on `build_job_a`**.
* `output_b.txt` from `build_job_b` will **not** be available in `test_job`.
* This reduces unnecessary artifact downloads and speeds up the pipeline.

---

### **4️⃣ Why Dependencies Are Useful**

* **Control artifact flow**: Only download what is needed.
* **Skip unrelated jobs**: If jobs are independent, they won’t block each other.
* **Complex pipelines**: For monorepos or multiple microservices, you might only need artifacts from certain jobs.

---

### **5️⃣ Parallel Jobs and Dependencies**

You can have multiple jobs in the same stage **run in parallel**, then a later job pick artifacts only from some of them.

```yaml
stages:
  - build
  - package

build_frontend:
  stage: build
  script:
    - echo "frontend" > frontend.txt
  artifacts:
    paths:
      - frontend.txt

build_backend:
  stage: build
  script:
    - echo "backend" > backend.txt
  artifacts:
    paths:
      - backend.txt

package_job:
  stage: package
  dependencies:
    - build_frontend
  script:
    - cat frontend.txt
    - cat backend.txt || echo "backend.txt not available"
```

* `build_frontend` and `build_backend` run **in parallel**.
* `package_job` runs **after both**, but only gets `frontend.txt` (because of `dependencies`).

---

### **6️⃣ Key Points**

| Concept         | Notes                                                                           |
| --------------- | ------------------------------------------------------------------------------- |
| `stages`        | Controls high-level order of job execution                                      |
| `needs:`        | Alternative for dependencies; allows jobs to start earlier if artifact is ready |
| `dependencies:` | Specifies exactly which artifacts to fetch from previous jobs                   |
| Artifacts       | Files shared between jobs                                                       |
| Parallel jobs   | Jobs in same stage run simultaneously; dependencies control what each consumes  |

---


> This is a subtle but important point about **GitLab CI/CD artifacts and the `dependencies:` keyword**. Let’s break it down carefully.

---

### **1️⃣ What happens by default without `dependencies:`**

If you **do not specify `dependencies:`**, GitLab automatically makes **artifacts from all jobs in previous stages available** to the current job.

For example:

```yaml
test_job:
  stage: test
  script:
    - cat output_a.txt
    - cat output_b.txt
```

* Both `output_a.txt` (from `build_job_a`) and `output_b.txt` (from `build_job_b`) are available.
* GitLab collects all artifacts from all jobs in **all previous stages** by default.

---

### **2️⃣ What `dependencies:` changes**

When you write:

```yaml
test_job:
  stage: test
  dependencies:
    - build_job_a
```

* You **override the default behavior**.
* GitLab now **only fetches artifacts from the jobs listed in `dependencies:`**, ignoring all others.
* So, even though `build_job_b` runs in the previous stage, its artifacts (`output_b.txt`) **will not be available** to `test_job`.

✅ That’s why your output shows:

```
output_b.txt not available
```

---

### **3️⃣ Why this behavior exists**

The reasoning is:

1. Pipelines can have **many jobs in previous stages**, producing lots of artifacts.
2. Automatically fetching all artifacts can be **slow** and consume **extra storage/bandwidth**.
3. `dependencies:` gives you **fine-grained control** — you decide exactly which artifacts a job needs.

---

### **4️⃣ Quick analogy**

Think of stages like **floors in a building**:

* Default: You can take **all packages from the floor below**.
* With `dependencies:`: You **only take packages from specific rooms** on the floor below.
* Anything you don’t list stays behind.

---

### **5️⃣ Solution if you want artifacts from both jobs**

Option 1: Remove `dependencies:`:

```yaml
test_job:
  stage: test
  script:
    - cat output_a.txt
    - cat output_b.txt
```

Option 2: Include both jobs in `dependencies:`:

```yaml
test_job:
  stage: test
  dependencies:
    - build_job_a
    - build_job_b
```
