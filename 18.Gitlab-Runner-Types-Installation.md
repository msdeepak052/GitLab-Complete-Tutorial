# 18. Installing and Running the GitLab Runner

## Quick Summary
- This file covers installing and operating the `gitlab-runner` binary/service itself — Linux, Windows, Docker container — plus health-checking it once installed.
- For *what* a runner is, shared vs. specific/group/project runners, and basic tag concepts, see file 10.
- For executor types (shell/docker/kubernetes/ssh/custom) and how `tags:` route jobs to runners, see file 19.
- GitLab has moved to **runner authentication tokens** (`glrt-` prefix) as the current registration method — the old fully-interactive `gitlab-runner register` prompt flow using a project **registration token** is legacy and being phased out.
- Once installed and registered, `gitlab-runner status` / `gitlab-runner verify` / `gitlab-runner list` are the go-to health-check commands.
- Docker-based runner install (`docker run ... gitlab/gitlab-runner:latest`) remains the current recommended way to run a runner as a container.

## Core Concepts

### What gets installed
- The `gitlab-runner` binary is a single executable that: registers itself with a GitLab instance, polls for jobs, and executes them via a configured **executor** (see file 19).
- Config lives in `/etc/gitlab-runner/config.toml` (Linux) or wherever `--config` points; each registered runner is one `[[runners]]` block in that file.
- Runner and executor are separate concepts: "installing the runner" gets you the binary/service; "registering" attaches it to a GitLab project/group/instance; the executor is chosen at registration/config time.

### Registration: current method vs legacy
- ⚠️ **Deprecated / Changed**: the classic flow — running `sudo gitlab-runner register`, pasting a project-level **registration token**, and answering interactive prompts one at a time (URL → token → description → tags → executor → image) — is the **legacy** method. GitLab has deprecated registration tokens; on GitLab.com they're disabled by default for new namespaces, and self-managed instances are pushed toward the new flow (registration-token removal was originally slated for GitLab 18.0, then walked back to remain available longer, but authentication tokens are the recommended path going forward and registration tokens are still on a deprecation track toward GitLab 20.0).
- **Current recommended flow** — runner authentication tokens:
  1. Create the runner **first**, in the GitLab UI or via the API (**Settings → CI/CD → Runners → New project runner**, or `POST /user/runners`), specifying its runner type (instance/group/project), executor, and tags up front.
  2. GitLab returns a **runner authentication token** (prefixed `glrt-`) — shown once.
  3. Register non-interactively on the machine that will run it:
     ```bash
     sudo gitlab-runner register \
       --url "https://gitlab.com" \
       --token "glrt-XXXXXXXXXXXXXXXXXXXX" \
       --non-interactive
     ```
  4. Executor/tags/description configured at creation time in the UI carry over automatically — no interactive prompts required.
- The interactive `gitlab-runner register` command **still works** and is fine for local learning/experiments, but treat the authentication-token + `--non-interactive` flow as the one to reach for in real projects and any automation (Terraform, Ansible, scripts).

### Runner lifecycle commands
| Command | Purpose |
|---|---|
| `gitlab-runner register` | Attach the binary to a GitLab instance/project/group (see above for current vs legacy method). |
| `gitlab-runner list` | List runners configured in the local `config.toml`. |
| `gitlab-runner verify` | Confirm each configured runner can still authenticate against GitLab (catches revoked/deleted tokens). |
| `gitlab-runner status` | Report whether the runner **service** is currently running on this host. |
| `gitlab-runner start` / `stop` / `restart` | Control the OS service (systemd on Linux, Windows service, etc.). |
| `gitlab-runner unregister` | Remove a runner's registration, both locally and from GitLab. |
| `gitlab-runner run` | Run in the foreground (useful for debugging; services normally run this under the hood). |

### Linux install (current)
- Debian/Ubuntu:
  ```bash
  curl -L "https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.deb.sh" | sudo bash
  sudo apt-get install gitlab-runner
  ```
- RHEL/CentOS/Fedora/Amazon Linux:
  ```bash
  curl -L "https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.rpm.sh" | sudo bash
  sudo yum install gitlab-runner   # or: sudo dnf install gitlab-runner
  ```
- Installing the package also installs and enables a `gitlab-runner` **systemd service** automatically; it starts once at least one runner is registered.

### Windows install
- ⚠️ **Deprecated / Changed**: the old S3 URL pattern (`gitlab-runner-downloads.s3.amazonaws.com`) has moved to the **dualstack** endpoint. Current official binaries are published under `https://s3.dualstack.us-east-1.amazonaws.com/gitlab-runner-downloads/latest/binaries/` — always confirm against the current docs.gitlab.com install page, since GitLab periodically reshuffles hosting.
- Steps:
  1. Create `C:\GitLab-Runner`, download `gitlab-runner-windows-amd64.exe` into it, rename to `gitlab-runner.exe`.
  2. Open an elevated CMD/PowerShell in that folder.
  3. Register (prefer the authentication-token + non-interactive flow described above):
     ```cmd
     gitlab-runner.exe register --url "https://gitlab.com" --token "glrt-XXXX" --non-interactive
     ```
  4. Install and start as a Windows service:
     ```cmd
     gitlab-runner.exe install
     gitlab-runner.exe start
     ```

### Docker-based runner
- Still the current recommended way to run a runner as a container:
  ```bash
  docker run -d --name gitlab-runner --restart always \
    -v /srv/gitlab-runner/config:/etc/gitlab-runner \
    -v /var/run/docker.sock:/var/run/docker.sock \
    gitlab/gitlab-runner:latest
  ```
- The `docker.sock` mount is only needed if this runner will itself launch sibling containers as its executor (Docker executor) — see file 19.
- Register **into** the running container (config persists to the mounted volume):
  ```bash
  docker exec -it gitlab-runner gitlab-runner register \
    --url "https://gitlab.com" \
    --token "glrt-XXXXXXXXXXXXXXXXXXXX" \
    --non-interactive \
    --executor "docker" \
    --docker-image "alpine:latest"
  ```
- ⚠️ Mounting the host's `docker.sock` into the runner container gives that runner (and therefore anyone who can push a `.gitlab-ci.yml` to a project it serves) effective root on the host — a real security tradeoff, not just a config detail.

### Health-checking an installed runner
- `sudo gitlab-runner status` → confirms the service process is alive on this host.
- `sudo gitlab-runner verify` → confirms GitLab still recognizes each configured runner's token (catches "runner shows offline in UI" issues caused by a revoked/deleted token).
- `sudo gitlab-runner list` → prints every runner defined in the local `config.toml` with its executor.
- GitLab UI: **Settings → CI/CD → Runners** shows last-contact time and an online/offline/stale indicator per runner — cross-check against local `status`/`verify` when debugging "job stuck in pending."
- Logs: `journalctl -u gitlab-runner -f` (systemd) or `docker logs -f gitlab-runner` (Docker install) for live troubleshooting.

## Hands-On Labs

### Lab 1: Install gitlab-runner on Ubuntu/Debian
- **Goal:** Get the binary and systemd service installed.
- **Steps:**
  ```bash
  curl -L "https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.deb.sh" | sudo bash
  sudo apt-get install gitlab-runner
  gitlab-runner --version
  ```
- **Run it:** Execute on a fresh Ubuntu VM/container.
- **Expected result:** `gitlab-runner --version` prints a version string; `systemctl status gitlab-runner` shows the service loaded (may be inactive until a runner is registered).
- **What this teaches:** The package-manager install path and that installation and registration are separate steps.

### Lab 2: Create a runner via GitLab UI and get an authentication token
- **Goal:** Use the current, non-legacy runner-creation flow.
- **Steps:**
  1. In a project: **Settings → CI/CD → Runners → New project runner**.
  2. Choose tags (e.g. `demo`) and an executor hint, click **Create runner**.
  3. Copy the generated command GitLab shows, which includes a `glrt-...` token.
- **Expected result:** A runner authentication token is displayed once; the runner appears in the Runners list as "never contacted."
- **What this teaches:** Registration now starts in the GitLab UI/API, not in the interactive CLI prompt.

### Lab 3: Non-interactive registration with the authentication token
- **Goal:** Register the runner from Lab 1 using the token from Lab 2, no prompts.
- **Steps:**
  ```bash
  sudo gitlab-runner register \
    --url "https://gitlab.com" \
    --token "glrt-XXXXXXXXXXXXXXXXXXXX" \
    --non-interactive \
    --executor "shell"
  ```
- **Run it:** Then run `sudo gitlab-runner list`.
- **Expected result:** Output lists the new runner with executor `shell`; the GitLab UI flips it to "online" within about a minute.
- **What this teaches:** The full modern registration path end-to-end, replacing the old prompt-by-prompt flow.

### Lab 4: (Legacy, for comparison) interactive registration with a registration token
- **Goal:** See the old flow so you can recognize it in existing infrastructure/scripts.
- **Steps:**
  ```bash
  sudo gitlab-runner register
  # Prompts: GitLab URL, registration token (Settings > CI/CD > Runners, if still enabled),
  # description, tags, executor, default image
  ```
- **Run it:** Only if your instance still has registration tokens enabled (GitLab.com disables this by default for new namespaces).
- **Expected result:** Same end state as Lab 3 (a working runner), but via prompts and a project-level registration token instead of a per-runner authentication token.
- **What this teaches:** Recognize the legacy flow in older tutorials/scripts and know it's superseded, not that it's necessarily broken today.

### Lab 5: Health-check with `status`, `verify`, `list`
- **Goal:** Confirm the runner from Lab 3 is genuinely healthy.
- **Steps:**
  ```bash
  sudo gitlab-runner status
  sudo gitlab-runner verify
  sudo gitlab-runner list
  ```
- **Expected result:** `status` → "Service is running"; `verify` → "is alive" for the registered runner; `list` → shows it with its executor and URL.
- **What this teaches:** The standard triage sequence before assuming "the runner is broken" when a job is stuck pending.

### Lab 6: Tail runner logs while a job runs
- **Goal:** Watch live job pickup and execution logs.
- **Steps:**
  ```bash
  sudo journalctl -u gitlab-runner -f
  ```
  In another terminal/browser, trigger any pipeline in the project this runner serves.
- **Expected result:** Log lines show the runner polling, picking up the job, and streaming execution output.
- **What this teaches:** Where to look when a job silently never starts (network/token issues surface here first).

### Lab 7: Run gitlab-runner as a Docker container
- **Goal:** Stand up a runner without installing anything on the host OS directly.
- **Steps:**
  ```bash
  docker run -d --name gitlab-runner --restart always \
    -v /srv/gitlab-runner/config:/etc/gitlab-runner \
    -v /var/run/docker.sock:/var/run/docker.sock \
    gitlab/gitlab-runner:latest

  docker exec -it gitlab-runner gitlab-runner register \
    --url "https://gitlab.com" \
    --token "glrt-XXXXXXXXXXXXXXXXXXXX" \
    --non-interactive \
    --executor "docker" \
    --docker-image "alpine:latest"
  ```
- **Run it:** Then `docker exec -it gitlab-runner gitlab-runner verify`.
- **Expected result:** Runner registers with executor `docker`, confirmed alive; `ls /srv/gitlab-runner/config` on the host shows the persisted `config.toml`.
- **What this teaches:** The container install pattern and why the config volume mount matters (registration survives container restarts).

### Lab 8: Install on Windows and run as a service
- **Goal:** Get a Windows box picking up jobs.
- **Steps:**
  1. Download `gitlab-runner-windows-amd64.exe` from the current dualstack S3 URL into `C:\GitLab-Runner\gitlab-runner.exe`.
  2. From an elevated prompt in that folder:
     ```cmd
     gitlab-runner.exe register --url "https://gitlab.com" --token "glrt-XXXX" --non-interactive --executor "shell"
     gitlab-runner.exe install
     gitlab-runner.exe start
     ```
- **Expected result:** `services.msc` shows a running "GitLab Runner" service; the runner appears online in the GitLab UI.
- **What this teaches:** Windows install parallels Linux (download → register → install-as-service → start), with the service step being an explicit extra command instead of automatic package-manager behavior.

### Lab 9: Unregister and re-register (rotate a compromised token)
- **Goal:** Practice safely rotating a runner's credentials.
- **Steps:**
  ```bash
  sudo gitlab-runner unregister --name <runner-description>
  # In GitLab UI: delete the old runner, create a new one, copy the new glrt- token
  sudo gitlab-runner register --url "https://gitlab.com" --token "glrt-NEWTOKEN" --non-interactive
  ```
- **Expected result:** Old runner disappears from the UI and stops accepting jobs; new registration picks up cleanly.
- **What this teaches:** Token rotation as an operational task, not just a one-time setup step.

### Lab 10: Diagnose an "offline" runner
- **Goal:** Practice the triage flow for a stuck/offline runner.
- **Steps:**
  1. Stop the local service: `sudo gitlab-runner stop`.
  2. Check GitLab UI — note the runner eventually shows "stale"/"offline" (may take a few minutes).
  3. Run `sudo gitlab-runner status` locally — observe it reports not running.
  4. `sudo gitlab-runner start`, then `sudo gitlab-runner verify`, confirm it flips back online.
- **Expected result:** You reproduce and resolve an offline runner using only the CLI commands from this file.
- **What this teaches:** Connecting the GitLab UI's online/offline signal to the actual local service state, and the fix (`start`, then `verify`).

### Lab 11: Multiple runners on one host
- **Goal:** Register two runners with different executors under one `gitlab-runner` install.
- **Steps:**
  ```bash
  sudo gitlab-runner register --url "https://gitlab.com" --token "glrt-TOKEN1" --non-interactive --executor "shell"
  sudo gitlab-runner register --url "https://gitlab.com" --token "glrt-TOKEN2" --non-interactive --executor "docker" --docker-image "alpine:latest"
  sudo gitlab-runner list
  ```
- **Expected result:** `list` shows two `[[runners]]` entries in one `config.toml`, one shell, one docker.
- **What this teaches:** One `gitlab-runner` service process can serve multiple registered runners/executors concurrently — you don't need a separate host per executor type.

## Common Pitfalls
- Following an old tutorial's fully-interactive `register` flow with a project registration token when the org has already disabled registration tokens — creation now must start in the UI/API.
- Forgetting to mount a persistent volume for `/etc/gitlab-runner` in the Docker install — losing the container loses all registrations.
- Mounting `docker.sock` without recognizing the host-root security implication.
- Confusing `gitlab-runner status` (is the local service alive) with the GitLab UI's online indicator (has GitLab heard from it recently) — they can disagree during network issues.
- Using a stale Windows binary URL from an old blog post instead of checking the current docs.gitlab.com download link.
- Registering a runner but never confirming its executor matches what the jobs targeting it expect (covered in depth in file 19).

## Interview Questions & Answers
- **Q: What's the difference between installing and registering a runner?**
  A: Installing gets the `gitlab-runner` binary/service on a machine; registering attaches that installed runner to a specific GitLab instance/project/group so it can pick up jobs.
- **Q: What is the current recommended runner registration method?**
  A: Create the runner in the GitLab UI/API first to get a runner authentication token (`glrt-` prefix), then run `gitlab-runner register --url ... --token ... --non-interactive` — not the old interactive prompt flow with a project registration token.
- **Q: Why is the old registration-token flow being phased out?**
  A: Registration tokens are project/instance-wide and less auditable/secure than per-runner authentication tokens; GitLab.com disables them by default for new namespaces and self-managed instances are pushed toward the authentication-token flow.
- **Q: How do you check if a runner process is alive on the host vs. whether GitLab recognizes it?**
  A: `gitlab-runner status` checks the local service; `gitlab-runner verify` checks GitLab's acceptance of the runner's token; the GitLab UI's online/offline badge reflects last-contact time.
- **Q: Where does runner configuration live on Linux?**
  A: `/etc/gitlab-runner/config.toml`, with one `[[runners]]` block per registered runner.
- **Q: Why mount `/var/run/docker.sock` into a Dockerized runner?**
  A: Needed only if that runner uses the Docker executor to launch sibling job containers on the host's Docker daemon — not needed for a shell-executor runner.
- **Q: How do you run more than one executor type from a single installed runner service?**
  A: Register multiple runners against the same `gitlab-runner` install — each registration adds a `[[runners]]` block, potentially with a different executor.
- **Q: What command would you run to rotate a runner's credentials?**
  A: `gitlab-runner unregister` the old one (and delete/revoke it in GitLab), create a new runner in the UI/API for a fresh `glrt-` token, then `gitlab-runner register` with that token.
- **Q: Scenario — a job has been "pending" for 20 minutes and no runner picks it up. What do you check first, at the runner-install level (not tags/executor)?**
  A: Whether the `gitlab-runner` service is actually running (`gitlab-runner status`), whether it still authenticates (`gitlab-runner verify`), and the runner logs (`journalctl -u gitlab-runner -f` or `docker logs`) for connectivity/token errors.
- **Q: Scenario — you inherit a Docker-based runner install with no `-v /srv/gitlab-runner/config:/etc/gitlab-runner` mount, and the container just got recreated during a host upgrade. What happened to the runner registration?**
  A: It's gone — config lived only inside the removed container's writable layer; the runner must be re-registered from scratch, this time with a persistent volume mount.
- **Q: Is the interactive `gitlab-runner register` command literally removed today?**
  A: No — it still works, but treat it as legacy; the authentication-token + `--non-interactive` flow is the current recommended path, especially for anything scripted/automated.
