# **Caching vs Artifacts in GitLab CI/CD**

## 🧩 1️⃣ **Caching in GitLab CI/CD**

### **What is caching?**

Caching is a way to **save files or directories between jobs or pipeline runs** so that you **don’t have to rebuild or download dependencies every time**.

* Cache is **intended for dependencies and intermediate files**.
* It is **shared between jobs** in the same branch (or across branches if configured).
* Cache is **not stored permanently** — GitLab can expire it.

### **When to use caching?**

* Saving **dependency packages** (like `node_modules`, `pip packages`, or Maven `.m2` repo).
* Speeding up **build times** by avoiding re-downloading files.

### **Key Points**

| Feature  | Caching                                      |
| -------- | -------------------------------------------- |
| Lifetime | Can expire, not permanent                    |
| Scope    | Usually branch-specific                      |
| Use case | Dependencies (npm, pip, Maven, etc.)         |
| Example  | `node_modules/`, `vendor/`, `.m2/repository` |

---

### **Example: Node.js Dependency Cache**

```yaml
stages:
  - build
  - test

variables:
  NODE_ENV: "production"

cache:
  key: ${CI_COMMIT_REF_SLUG}  # cache per branch
  paths:
    - node_modules/

install_dependencies:
  stage: build
  script:
    - echo "Installing dependencies..."
    - npm install

run_tests:
  stage: test
  script:
    - echo "Running tests..."
    - npm test
```

**Explanation:**

1. `cache` saves the `node_modules/` folder.
2. On the next pipeline run for the same branch, `npm install` will **reuse cached dependencies**, speeding up the job.
3. `key: ${CI_COMMIT_REF_SLUG}` ensures **separate cache per branch** (optional but useful).

---

### **Example: Maven Cache for Java**

```yaml
cache:
  key: ${CI_PROJECT_NAME}
  paths:
    - .m2/repository/

build_job:
  stage: build
  script:
    - mvn clean install
```

* `.m2/repository/` contains all downloaded Maven dependencies.
* By caching, **next builds skip downloading dependencies**, saving time.

---

## 🧩 2️⃣ **Artifacts in GitLab CI/CD**

### **What are artifacts?**

Artifacts are **job outputs that you want to keep after the job finishes**.

* Artifacts are **stored by GitLab** and can be **downloaded later**.
* Usually used for **build outputs, reports, coverage, binaries, or logs**.
* Artifacts are **job-specific**, not automatically shared between jobs (unless you define `dependencies`).

### **When to use artifacts?**

* Build outputs like `.jar`, `.war`, `.zip`, `.exe`, or Docker images.
* Test reports (JUnit, Cobertura, HTML).
* Logs for debugging pipelines.

### **Key Points**

| Feature  | Artifacts                             |
| -------- | ------------------------------------- |
| Lifetime | Defined per job (`expire_in`)         |
| Scope    | Stored in GitLab, can download via UI |
| Use case | Build outputs, test reports, logs     |
| Example  | `build/*.jar`, `reports/*.xml`        |

---

### **Example: Save Build Output**

```yaml
stages:
  - build
  - test

build_job:
  stage: build
  script:
    - echo "Building application..."
    - mkdir -p build
    - echo "Hello World" > build/app.txt
  artifacts:
    paths:
      - build/
    expire_in: 1 hour  # optional, deletes after 1 hour

test_job:
  stage: test
  dependencies:
    - build_job
  script:
    - echo "Testing application..."
    - cat build/app.txt
```

**Explanation:**

1. `build_job` creates a folder `build/` and saves `app.txt`.
2. `artifacts` stores `build/` and makes it **available to later jobs**.
3. `dependencies: - build_job` ensures `test_job` can access `build/` folder from the previous job.

---

### **Example: Saving Test Reports**

```yaml
test_job:
  stage: test
  script:
    - mkdir -p reports
    - echo "<testsuite></testsuite>" > reports/junit.xml
  artifacts:
    when: always
    paths:
      - reports/
    reports:
      junit: reports/junit.xml
    expire_in: 1 day
```

* `reports:` section lets GitLab **parse test results** and show them in the **pipeline UI**.
* `when: always` ensures reports are saved **even if the job fails**.

## 🧩 3️⃣ **Caching vs Artifacts: Key Differences**

| Feature    | Cache                                            | Artifacts                                              |
| ---------- | ------------------------------------------------ | ------------------------------------------------------ |
| Purpose    | Speed up jobs (dependencies, intermediate files) | Store job outputs (builds, reports, logs)              |
| Lifetime   | Temporary, can expire, reused                    | Temporary, can expire, downloadable                    |
| Visibility | Not visible in UI                                | Visible in UI, can download                            |
| Sharing    | Usually branch-specific                          | Job-specific, must declare `dependencies` for next job |
| Example    | `node_modules/`, `.m2/repository/`               | `build/*.jar`, `reports/*.xml`                         |

---

## 🧩 4️⃣ **Best Practices**

* Use **cache** for **dependencies** that are large and time-consuming to download.
* Use **artifacts** for **build outputs and test reports** that must be available for later jobs or for download.
* **Don’t use cache for artifacts** — cache may expire, artifacts are meant for storage and later retrieval.
* Use **branch-specific cache keys** to avoid conflicts between branches.
* Use `expire_in` for both artifacts and cache to control storage.

---

### 🔹 Example: Combined Cache + Artifacts

```yaml
stages:
  - build
  - test

cache:
  key: ${CI_COMMIT_REF_SLUG}
  paths:
    - node_modules/

build_job:
  stage: build
  script:
    - npm install
    - npm run build
  artifacts:
    paths:
      - dist/
    expire_in: 2 hours

test_job:
  stage: test
  dependencies:
    - build_job
  script:
    - echo "Testing build..."
    - ls dist/
```

✅ Explanation:

* `node_modules/` is **cached** for fast install.
* `dist/` folder (build output) is stored as **artifact** for test_job and downloadable.
