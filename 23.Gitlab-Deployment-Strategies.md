# 🚀 **1️⃣ What are Deployment Strategies?**

In GitLab CI/CD, *deployment strategies* define **when and how your app is deployed** to an environment.

They help you:

* Control when deployment happens (automatic or manual)
* Manage multiple environments (dev, staging, production)
* Preview changes before merging (review apps)

---

# 🧩 **2️⃣  Automatic Deployments**

### ✅ **Definition**

Automatic deployments happen **as soon as the pipeline reaches the deploy stage**, without human approval.

### ⚙️ **Example**

```yaml
stages:
  - build
  - deploy

build_job:
  stage: build
  script:
    - echo "Building app..."

deploy_auto:
  stage: deploy
  script:
    - echo "Deploying automatically to staging server..."
  environment:
    name: staging
    url: https://staging.example.com
  only:
    - develop
```

### 🧠 **How it works**

* When you push to the `develop` branch, this job runs automatically.
* GitLab marks it as a **deployment** to the `staging` environment.
* No human action is required.

### 📊 **Use case**

* CI pipelines for **staging/testing environments** where automatic updates are safe.
* Example: QA, UAT, or internal environments.

---

# 🧩 **3️⃣  Manual Deployments**

### ✅ **Definition**

Manual deployments **wait for human approval** before starting.

You trigger them from:

* The GitLab **UI**
* The **Environments page**
* Or the **pipeline view**

### ⚙️ **Example**

```yaml
stages:
  - build
  - deploy

build_job:
  stage: build
  script:
    - echo "Building app..."

deploy_prod:
  stage: deploy
  script:
    - echo "Deploying to production..."
  environment:
    name: production
    url: https://prod.example.com
  when: manual
  only:
    - main
```

### 🧠 **How it works**

* Pipeline runs until the `deploy_prod` job.
* It stops and waits for **you** to click “Play” in the GitLab UI.
* Once triggered, deployment happens.

### 📊 **Use case**

* For **production deployments** — where you want to validate changes first.
* Gives you control and avoids accidental production releases.

---

# 🧩 **4️⃣  Review Apps**

### ✅ **Definition**

Review apps automatically deploy a **temporary, isolated environment** for **each merge request (MR)** — letting reviewers test your feature *before merging*.
They’re great for teams using environments like **Kubernetes** or **Docker Compose**.

### ⚙️ **Example**

```yaml
stages:
  - build
  - review

build_job:
  stage: build
  script:
    - echo "Building app..."

review_app:
  stage: review
  script:
    - echo "Deploying review app for branch $CI_COMMIT_REF_NAME"
  environment:
    name: review/$CI_COMMIT_REF_NAME
    url: https://$CI_COMMIT_REF_SLUG.review.example.com
    on_stop: stop_review_app

stop_review_app:
  stage: review
  script:
    - echo "Stopping review app for branch $CI_COMMIT_REF_NAME"
  when: manual
  environment:
    name: review/$CI_COMMIT_REF_NAME
    action: stop
```

### 🧠 **How it works**

* When a developer opens a merge request:

  * A new environment (e.g., `review/feature-123`) is deployed automatically.
  * GitLab shows a link (`https://feature-123.review.example.com`) for live preview.
* After the MR is closed or merged, you can manually stop it to clean up.

### 📊 **Use case**

* **Preview branches** before merge.
* Ideal for **web apps** and **UI changes**.

# 📊 **5️⃣  Summary Table**

| Strategy Type   | Trigger Type         | Environment       | Typical Use Case              |
| --------------- | -------------------- | ----------------- | ----------------------------- |
| **Automatic**   | Auto-run on push     | Staging/UAT       | Frequent testing environments |
| **Manual**      | Requires human click | Production        | Controlled prod releases      |
| **Review Apps** | Per Merge Request    | Temporary Preview | Feature testing before merge  |

# 🧠 **6️⃣  Bonus Tip – Combining Strategies**

You can combine them for realistic pipelines 👇

```yaml
stages:
  - build
  - deploy

build_job:
  stage: build
  script: echo "Build app"

deploy_staging:
  stage: deploy
  script: echo "Deploy to staging"
  environment: staging
  only:
    - develop

deploy_production:
  stage: deploy
  script: echo "Deploy to production"
  environment: production
  when: manual
  only:
    - main
```

✅ Deploys automatically to staging when merging to `develop`
✅ Waits for approval for production when merging to `main`
