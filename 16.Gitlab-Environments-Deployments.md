# **Environments and Deployments in GitLab CI/CD** 

## **1️⃣ What are Environments in GitLab?**

* An **Environment** represents a **deployment target** — for example:

  * `development` → Dev server
  * `staging` → QA/staging server
  * `production` → Live server

* Environments help **track what version of your code is running where**, view deployment history, and roll back if needed.

* GitLab automatically tracks **deployments** to each environment.

---

## **2️⃣ Declaring an Environment in a Job**

You declare an environment using the **`environment:`** keyword in your job:

```yaml
stages:
  - build
  - deploy

build_job:
  stage: build
  script:
    - echo "Building the app..."

deploy_dev:
  stage: deploy
  script:
    - echo "Deploying to development server..."
  environment:
    name: development
    url: https://dev.example.com
```

✅ Explanation:

* `name` → Name of the environment (`development`)
* `url` → Optional; a link to your deployed environment
* GitLab will show **deployment info** under **Operations → Environments**.

---

## **3️⃣ Using Environments for Multiple Stages**

```yaml
deploy_staging:
  stage: deploy
  script:
    - echo "Deploying to staging server..."
  environment:
    name: staging
    url: https://staging.example.com
  only:
    - develop

deploy_prod:
  stage: deploy
  script:
    - echo "Deploying to production server..."
  environment:
    name: production
    url: https://www.example.com
  only:
    - main
```

* Jobs are triggered depending on the branch:

  * `develop` branch → deploy to `staging`
  * `main` branch → deploy to `production`

* Each deployment is **tracked separately** in GitLab.

---

## **4️⃣ Using `on_stop` to Stop/Destroy Environments**

Some environments are temporary (like review apps). You can define a **stop job**:

```yaml
review_app:
  stage: deploy
  script:
    - echo "Deploying review app..."
  environment:
    name: review/$CI_COMMIT_REF_NAME
    url: https://$CI_COMMIT_REF_NAME.review.example.com
    on_stop: stop_review_app

stop_review_app:
  stage: cleanup
  script:
    - echo "Stopping review app..."
  when: manual
  environment:
    name: review/$CI_COMMIT_REF_NAME
    action: stop
```

✅ Explanation:

* `on_stop` links the **deploy job** with a **stop job**.
* The stop job is **manual**, allowing developers to remove temporary environments.
* Useful for **review apps** for feature branches.

---

## **5️⃣ Deployment History & Tracking**

* GitLab automatically tracks:

  * Which commit was deployed
  * Who deployed it
  * Deployment time
* You can **roll back** to a previous deployment with a single click.

---

## **6️⃣ Example: Full Pipeline with Environments**

```yaml
stages:
  - build
  - test
  - deploy

build_job:
  stage: build
  script:
    - echo "Building app..."
  artifacts:
    paths:
      - app/

test_job:
  stage: test
  script:
    - echo "Running tests..."
    - ls app/

deploy_dev:
  stage: deploy
  script:
    - echo "Deploying to dev server..."
  environment:
    name: development
    url: https://dev.example.com
  only:
    - develop

deploy_prod:
  stage: deploy
  script:
    - echo "Deploying to production server..."
  environment:
    name: production
    url: https://www.example.com
  only:
    - main
```

**Flow**:

1. Build → artifacts generated
2. Test → runs tests using artifacts
3. Deploy → chooses environment based on branch

---

### **7️⃣ Key Points**

* `environment:` in jobs allows **tracking and visibility** of deployments.
* Use **different environments for dev, staging, production**.
* Use **`on_stop`** for temporary environments.
* Combine with **rules/only/except** to deploy only on specific branches/tags.
