# **GitLab Runners** 

Let’s go step-by-step and cover this fully — from **concept → types → configuration → real-world setup**.

---

## 🧭 1️⃣ What is a GitLab Runner?

A **GitLab Runner** is an **agent (a lightweight application)** that actually *executes your CI/CD jobs* defined in `.gitlab-ci.yml`.

Think of it like:

> 🧠 GitLab (CI/CD Orchestrator) = "What to do"
> 💪 Runner = "Who does it"

So when you push code and GitLab triggers a pipeline:

* GitLab schedules jobs (build, test, deploy)
* The **Runner** picks them up and executes commands like:

  ```bash
  mvn package
  docker build -t myimage .
  kubectl apply -f deployment.yaml
  ```

---

## ⚙️ 2️⃣ How GitLab Runners Work (Conceptually)

When a pipeline starts:

1. GitLab sends job instructions to the **Runner**.
2. The Runner:

   * Clones the repository
   * Executes the defined `script:` commands
   * Reports job status (success/failure) back to GitLab
3. The output/logs you see in GitLab UI come from that Runner.

---

## 🔸 3️⃣ Types of GitLab Runners

GitLab provides **two major types** of runners:

| Type                | Description                                                                  | Use Case                                                       |
| ------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------- |
| **Shared Runner**   | Provided by GitLab itself, available to all projects on that GitLab instance | Quick setup, no need to manage infrastructure                  |
| **Specific Runner** | Installed and managed by *you* (on your VM, EC2, or server)                  | Full control, security, custom tools (Docker, Terraform, etc.) |

---

### 🧩 A. Shared Runner

✅ **Features:**

* Already installed & managed by GitLab
* Works automatically — no setup required
* Executes on GitLab’s own infrastructure
* Uses Docker or shell environments

⚠️ **Limitations:**

* Limited compute power (especially for free plans)
* Cannot access private networks or internal resources
* Restricted customization

💡 **When to use:**

> For testing pipelines, learning CI/CD, or small open-source projects.

---

### 🧩 B. Specific Runner

✅ **Features:**

* Installed by you (e.g., on an EC2, RHEL, Ubuntu, or Windows machine)
* Can access your **private infra**, **Docker Daemon**, or **Kubernetes cluster**
* Fully customizable (install Maven, Terraform, AWS CLI, etc.)
* Can run on **Shell**, **Docker**, or **Kubernetes executors**

⚠️ **Requires setup and maintenance** by you.

💡 **When to use:**

> For enterprise projects, real deployments, and custom environments.

---

## 🧰 4️⃣ Runner Executors (Execution Modes)

When configuring a runner, you choose an **executor** — this defines *how* jobs are run.

| Executor           | Description                                   | Example Usage                          |
| ------------------ | --------------------------------------------- | -------------------------------------- |
| **Shell**          | Runs directly on the host machine             | Simple pipelines, fast testing         |
| **Docker**         | Runs each job in an isolated Docker container | Clean environment, best for app builds |
| **Docker Machine** | Auto-spins up & removes VMs dynamically       | Scalable runners for large workloads   |
| **Kubernetes**     | Runs jobs as K8s pods                         | Cloud-native GitLab pipelines          |
| **SSH**            | Executes jobs on remote hosts via SSH         | Deploying to on-prem servers           |

---

## 🧩 5️⃣ Shared vs Specific Runners — Quick Comparison

| Feature          | Shared Runner                 | Specific Runner                              |
| ---------------- | ----------------------------- | -------------------------------------------- |
| **Setup**        | Auto (by GitLab)              | Manual                                       |
| **Access**       | All projects                  | One project/group                            |
| **Custom tools** | ❌ Limited                     | ✅ You can install anything                   |
| **Security**     | Shared with others            | Fully isolated                               |
| **Performance**  | Limited resources             | Depends on your host                         |
| **Networking**   | Cannot reach private networks | Can connect to private infra (e.g., DB, K8s) |

## 🧭 6️⃣ How to Configure a GitLab Runner (Specific)

Let’s go step-by-step to set up your own **specific runner**.

### 🧱 Step 1: Install GitLab Runner

**On Linux (RHEL/Ubuntu):**

```bash
# Add GitLab Runner repository
curl -L https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.deb.sh | sudo bash

# Install runner
sudo apt-get install gitlab-runner -y
```

For RHEL:

```bash
sudo yum install gitlab-runner -y
```

---

### 🧩 Step 2: Register the Runner

Go to your GitLab project →
**Settings → CI/CD → Runners → Expand**

Click **“New project runner”** and copy the registration token.

Then run:

```bash
sudo gitlab-runner register
```

You’ll be prompted for:

```
Please enter the gitlab-ci coordinator URL (e.g. https://gitlab.com/):
> https://gitlab.com/

Please enter the registration token:
> <your-token>

Please enter the gitlab-ci description for this runner:
> Deepak-RHEL-Runner

Please enter the gitlab-ci tags for this runner (comma separated):
> deepak,java,devops

Please enter the executor:
> docker
```

If you use Docker executor:

```
Please enter the default Docker image (for example, ubuntu:latest):
> maven:3.9.6-eclipse-temurin-17
```

---

### 🧩 Step 3: Verify Runner Registration

List registered runners:

```bash
sudo gitlab-runner list
```

Output example:

```
Listing configured runners:
Deepak-RHEL-Runner (docker, maven:3.9.6-eclipse-temurin-17)
```

---

### 🧩 Step 4: Start the Runner Service

```bash
sudo gitlab-runner start
sudo systemctl enable gitlab-runner
```

---

### 🧩 Step 5: Verify in GitLab UI

Go to:

> **Settings → CI/CD → Runners → Project Runners**

✅ You’ll see your runner listed as **“Active”**.

Now your pipelines will run using **your own system**.

---

## 🧩 7️⃣ Tags and Job Matching

You can control **which jobs run on which runner** using **tags**.

For example:

```yaml
build_job:
  stage: build
  tags:
    - deepak
  script:
    - mvn package
```

This job will only run on a runner that has the tag `deepak`.

| Kubernetes deployment     | Specific Kubernetes Runner   |
| On-prem deployment        | Specific Shell or SSH Runner |

## 🧭 9️⃣ Troubleshooting Tips

| Problem                      | Solution                                                    |
| ---------------------------- | ----------------------------------------------------------- |
| Runner not visible in GitLab | Check token & URL during registration                       |
| Jobs stuck at “Pending”      | No active runner available for job tags                     |
| Permission denied            | Ensure `gitlab-runner` user has rights (esp. Docker socket) |
| Logs not updating            | Restart runner: `sudo gitlab-runner restart`                |
