# 25. GitLab CI/CD: Docker Build, Push & Deploy

## Quick Summary
- A CI pipeline can build a Docker image from a `Dockerfile`, push it to a registry (Docker Hub or GitLab's built-in Container Registry), then deploy it to a server.
- The standard build method is `docker:dind` (Docker-in-Docker) — a `docker` CLI image plus a `docker:dind` service giving the job its own Docker daemon.
- `docker:dind` requires the runner to run in **privileged mode**, a real security tradeoff; rootless alternatives (Kaniko, buildah) avoid that but trade off convenience/compatibility.
- GitLab's own Container Registry (`$CI_REGISTRY_IMAGE`) needs no separate account — auth uses CI-provided variables (`$CI_REGISTRY_USER`, `$CI_REGISTRY_PASSWORD`, `$CI_REGISTRY`).
- Tag images with `$CI_COMMIT_SHORT_SHA` (traceable, immutable) and `latest` (convenient, mutable) — push both.
- The build→push→deploy pipeline here is the foundation file 26 (multi-env) and file 27 (approval gates) build on for dev/staging/prod structuring.

## Core Concepts

### Docker-in-Docker (dind) — the standard approach
- `image: docker:latest` (or a pinned version) + `services: [docker:dind]` gives the job a Docker CLI talking to a nested, job-scoped Docker daemon.
- Requires the GitLab Runner's executor to allow **privileged** containers — this is the security tradeoff: a privileged container has near-full access to the host kernel, so a compromised job can potentially escape to the runner host.
- `DOCKER_TLS_CERTDIR` should be set (GitLab's dind images default to `/certs` since Docker 19.03) so the daemon connection is TLS-secured even within the job.

### Rootless / DinD-free alternatives
- **Kaniko**: builds images from a `Dockerfile` entirely in userspace, without a Docker daemon or privileged mode — runs well on Kubernetes executors where privileged containers are often disallowed by policy.
- **Buildah**: another daemonless, OCI-compliant builder; can run rootless.
- GitLab's own documentation presents dind, Docker socket binding, Kaniko, and buildah as **contextual tradeoffs** rather than declaring one universally correct — dind is the most compatible/simplest to set up; Kaniko/buildah avoid privileged mode at the cost of some Docker CLI compatibility (e.g. `docker run`/`docker-compose` inside the build itself won't work the same way).
- Socket binding (mounting the host's `/var/run/docker.sock`) is a third option that avoids privileged mode but shares the host's actual Docker daemon across jobs — a different (arguably worse, for multi-tenant runners) isolation tradeoff, not generally recommended for shared runners.

### Registry authentication
- Docker Hub: `docker login -u "$DOCKER_USERNAME" -p "$DOCKER_PASSWORD"` with variables set in Settings > CI/CD > Variables.
- GitLab Container Registry: `docker login -u "$CI_REGISTRY_USER" -p "$CI_REGISTRY_PASSWORD" $CI_REGISTRY` — these three variables are predefined by GitLab automatically, no manual setup needed, and images push to `$CI_REGISTRY_IMAGE` (resolves to `registry.gitlab.com/<namespace>/<project>`).

### Tagging strategy
- `$CI_COMMIT_SHORT_SHA` — immutable, traceable back to an exact commit; always push this.
- `latest` — convenient for "just run the newest," but mutable and not reproducible by itself; fine as a secondary tag, risky as the only one.
- Multi-tag push: build once, tag twice (`docker tag`), push both — do **not** rebuild per tag, that wastes time and can produce non-identical images if the build isn't perfectly reproducible.

## Hands-On Labs

### Lab 1: Basic Docker build (no push)
- **Goal:** Confirm the pipeline can build an image at all before adding registry credentials.
- **`Dockerfile`:**
```Dockerfile
FROM node:18-alpine
WORKDIR /app
COPY . .
RUN npm install
CMD ["npm", "start"]
```
- **`.gitlab-ci.yml`:**
```yaml
image: docker:latest

services:
  - docker:dind

variables:
  DOCKER_TLS_CERTDIR: "/certs"
  IMAGE_NAME: devops-app
  IMAGE_TAG: $CI_COMMIT_SHORT_SHA

stages:
  - build

build_image:
  stage: build
  script:
    - docker build -t $IMAGE_NAME:$IMAGE_TAG .
    - docker images
```
- **Run it:** Push to any branch.
- **Expected result:** Job log shows the image build steps and lists the built image under `docker images`.
- **What this teaches:** The minimal dind setup — CLI image + dind service + `DOCKER_TLS_CERTDIR` — before registry credentials enter the picture.

### Lab 2: Build & push to Docker Hub
- **Goal:** Push the built image to a real registry.
- **`.gitlab-ci.yml`:**
```yaml
image: docker:latest

services:
  - docker:dind

variables:
  DOCKER_TLS_CERTDIR: "/certs"
  IMAGE_NAME: deepakyadav/devops-app
  IMAGE_TAG: $CI_COMMIT_SHORT_SHA

stages:
  - build
  - push

before_script:
  - docker login -u "$DOCKER_USERNAME" -p "$DOCKER_PASSWORD"

build_image:
  stage: build
  script:
    - docker build -t $IMAGE_NAME:$IMAGE_TAG .

push_image:
  stage: push
  script:
    - docker push $IMAGE_NAME:$IMAGE_TAG
  needs: ["build_image"]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```
- **Run it:** Set `DOCKER_USERNAME`/`DOCKER_PASSWORD` as CI/CD variables, push to `main`.
- **Expected result:** Image appears at `hub.docker.com/r/deepakyadav/devops-app` tagged with the commit short SHA.
- **What this teaches:** Separating build and push into their own stage/jobs, with push gated to `main` via `rules:` (not `only:`).

### Lab 3: Push to GitLab's own Container Registry
- **Goal:** Use the registry built into every GitLab project — no external account needed.
- **`.gitlab-ci.yml`:**
```yaml
variables:
  IMAGE_TAG: $CI_COMMIT_SHORT_SHA

before_script:
  - docker login -u "$CI_REGISTRY_USER" -p "$CI_REGISTRY_PASSWORD" $CI_REGISTRY

push_image:
  stage: push
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$IMAGE_TAG .
    - docker push $CI_REGISTRY_IMAGE:$IMAGE_TAG
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```
- **Run it:** Push to `main` — no manual variable setup required, `$CI_REGISTRY*` variables are predefined.
- **Expected result:** Image visible under the project's Deploy > Container Registry page as `registry.gitlab.com/<namespace>/<project>:<sha>`.
- **What this teaches:** GitLab's Container Registry needs zero credential setup — it's often the fastest path for projects that don't already use Docker Hub.

### Lab 4: Multi-tag push (SHA + latest, one build)
- **Goal:** Push both an immutable and a convenience tag without rebuilding.
- **`.gitlab-ci.yml`:**
```yaml
build_and_push:
  stage: build
  script:
    - docker build -t $IMAGE_NAME:$CI_COMMIT_SHORT_SHA -t $IMAGE_NAME:latest .
    - docker push $IMAGE_NAME:$CI_COMMIT_SHORT_SHA
    - docker push $IMAGE_NAME:latest
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```
- **Run it:** Push to `main`, check the registry for both tags.
- **Expected result:** Both `<image>:<sha>` and `<image>:latest` point at the exact same image digest.
- **What this teaches:** `docker build -t a -t b` tags once during a single build — always prefer this over building twice, which risks the two tags diverging.

### Lab 5: BuildKit layer caching to speed up rebuilds
- **Goal:** Cut build time on repeated pipeline runs by reusing unchanged layers.
- **`.gitlab-ci.yml`:**
```yaml
variables:
  DOCKER_BUILDKIT: 1

build_image:
  stage: build
  script:
    - docker pull $IMAGE_NAME:latest || true
    - docker build --cache-from $IMAGE_NAME:latest -t $IMAGE_NAME:$CI_COMMIT_SHORT_SHA -t $IMAGE_NAME:latest .
    - docker push $IMAGE_NAME:$CI_COMMIT_SHORT_SHA
    - docker push $IMAGE_NAME:latest
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```
- **Run it:** Run the pipeline twice with only a small code change between runs.
- **Expected result:** Second run's `docker build` log shows `CACHED` for unaffected layers (e.g. `npm install` if `package.json` didn't change), finishing noticeably faster.
- **What this teaches:** `--cache-from` plus pulling the previous `latest` first gives cross-pipeline layer caching, since each dind service normally starts with an empty local cache.

### Lab 6: `rules:changes` to skip rebuilding when the Dockerfile/app didn't change
- **Goal:** Avoid rebuilding the image for commits that don't touch build-relevant files.
- **`.gitlab-ci.yml`:**
```yaml
build_image:
  stage: build
  script:
    - docker build -t $IMAGE_NAME:$CI_COMMIT_SHORT_SHA .
    - docker push $IMAGE_NAME:$CI_COMMIT_SHORT_SHA
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      changes:
        - Dockerfile
        - src/**
        - package.json
```
- **Run it:** Push a commit touching only `README.md`.
- **Expected result:** `build_image` doesn't run at all for that commit.
- **What this teaches:** Combining branch and path conditions in one `rules:` entry — both must match for the job to be created.

### Lab 7: Deploy the pushed image to EC2 via SSH
- **Goal:** Complete the pipeline — build, push, then run the new image on a server.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - push
  - deploy

deploy_to_ec2:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh
    - echo "$SSH_PRIVATE_KEY" > private_key.pem
    - chmod 600 private_key.pem
    - ssh-keyscan -H $EC2_HOST >> ~/.ssh/known_hosts 2>/dev/null || (mkdir -p ~/.ssh && ssh-keyscan -H $EC2_HOST >> ~/.ssh/known_hosts)
  script:
    - ssh -i private_key.pem $EC2_USER@$EC2_HOST "
        docker login -u $DOCKER_USERNAME -p $DOCKER_PASSWORD &&
        docker pull $IMAGE_NAME:latest &&
        docker stop devops-app || true &&
        docker rm devops-app || true &&
        docker run -d -p 80:80 --name devops-app $IMAGE_NAME:latest
      "
  needs: ["push_image"]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```
- **Run it:** Push to `main` with `EC2_HOST`/`EC2_USER`/`SSH_PRIVATE_KEY` set (see file 24 for the full SSH setup pattern).
- **Expected result:** EC2 instance pulls and runs the freshly pushed image, replacing any previous container.
- **What this teaches:** The registry is the handoff point between "CI builds/pushes" and "deploy job pulls/runs" — the deploy job never needs the source code, only registry credentials and the image tag.

### Lab 8: Post-deploy health check
- **Goal:** Fail the pipeline if the freshly deployed container isn't actually serving.
- **`.gitlab-ci.yml`:**
```yaml
deploy_to_ec2:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh curl
    - echo "$SSH_PRIVATE_KEY" > private_key.pem
    - chmod 600 private_key.pem
  script:
    - ssh -o StrictHostKeyChecking=no -i private_key.pem $EC2_USER@$EC2_HOST "docker pull $IMAGE_NAME:latest && docker stop devops-app || true && docker rm devops-app || true && docker run -d -p 80:80 --name devops-app $IMAGE_NAME:latest"
    - sleep 5
    - curl -f http://$EC2_HOST || (echo "App not healthy after deploy" && exit 1)
  needs: ["push_image"]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```
- **Run it:** Push a build whose container fails to start (e.g. bad `CMD`).
- **Expected result:** `curl -f` fails, job fails, pipeline clearly reports a broken deploy instead of appearing green.
- **What this teaches:** Same lesson as file 24 Lab 4 — a deploy job that doesn't verify the app actually responds only proves the *container started*, not that it *works*.

### Lab 9: Manual deploy trigger, decoupled from build/push
- **Goal:** Build and push automatically, but require a human click to actually deploy.
- **`.gitlab-ci.yml`:**
```yaml
push_image:
  stage: push
  script:
    - docker push $IMAGE_NAME:$CI_COMMIT_SHORT_SHA
    - docker push $IMAGE_NAME:latest
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'

deploy_to_ec2:
  stage: deploy
  script:
    - echo "Deploying $IMAGE_NAME:$CI_COMMIT_SHORT_SHA to EC2..."
  needs: ["push_image"]
  environment:
    name: production
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
```
- **Run it:** Push to `main`; `push_image` completes automatically; `deploy_to_ec2` waits for a Play click.
- **Expected result:** Every `main` commit gets an image pushed to the registry immediately, but nothing reaches the server until approved — the image is ready and waiting.
- **What this teaches:** Build/push and deploy don't have to happen at the same time — decoupling them means you can approve a deploy of an already-verified image without re-running the build.

### Lab 10: Rollback by redeploying a previous immutable tag
- **Goal:** Revert production to a known-good image without rebuilding anything.
- **`.gitlab-ci.yml`:**
```yaml
rollback_deploy:
  stage: deploy
  image: alpine:latest
  variables:
    ROLLBACK_TAG: ""
  before_script:
    - apk add --no-cache openssh
    - echo "$SSH_PRIVATE_KEY" > private_key.pem
    - chmod 600 private_key.pem
  script:
    - test -n "$ROLLBACK_TAG" || (echo "Set ROLLBACK_TAG to the SHA tag to roll back to" && exit 1)
    - ssh -o StrictHostKeyChecking=no -i private_key.pem $EC2_USER@$EC2_HOST "docker pull $IMAGE_NAME:$ROLLBACK_TAG && docker stop devops-app || true && docker rm devops-app || true && docker run -d -p 80:80 --name devops-app $IMAGE_NAME:$ROLLBACK_TAG"
  environment:
    name: production
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
```
- **Run it:** Trigger manually from CI/CD > Pipelines > Run pipeline, setting the `ROLLBACK_TAG` variable to a previous commit's short SHA.
- **Expected result:** Production runs the specified older image tag, pulled straight from the registry — no source checkout or rebuild involved.
- **What this teaches:** Because every commit's image is pushed under its own immutable SHA tag (Lab 2/4), rollback is just "pull and run a different tag" — this is exactly why immutable tags matter, not just `latest`.

### Lab 11: Kaniko build without Docker-in-Docker
- **Goal:** Build and push an image without a privileged dind service.
- **`.gitlab-ci.yml`:**
```yaml
build_with_kaniko:
  stage: build
  image:
    name: gcr.io/kaniko-project/executor:debug
    entrypoint: [""]
  script:
    - mkdir -p /kaniko/.docker
    - echo "{\"auths\":{\"$CI_REGISTRY\":{\"auth\":\"$(printf '%s:%s' "$CI_REGISTRY_USER" "$CI_REGISTRY_PASSWORD" | base64 | tr -d '\n')\"}}}" > /kaniko/.docker/config.json
    - /kaniko/executor --context "$CI_PROJECT_DIR" --dockerfile "$CI_PROJECT_DIR/Dockerfile" --destination "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```
- **Run it:** Push to `main` on a runner where privileged mode is disabled/disallowed.
- **Expected result:** Image builds and pushes successfully with no `docker:dind` service and no privileged executor requirement.
- **What this teaches:** Kaniko trades some Docker CLI convenience (no `docker` command available in the job) for running entirely without privileged containers — the go-to choice on Kubernetes executors or any runner where privileged mode is policy-disallowed.

## Common Pitfalls
- Running `docker:dind` on a shared/untrusted runner without understanding that privileged mode gives the job broad host access — fine on dedicated/trusted runners, a real risk on shared ones.
- Rebuilding the image once per tag instead of `docker build -t a -t b .` — wastes time and risks the tags not being byte-identical.
- Only ever pushing `latest` — makes rollback and auditing impossible since there's no way to address a specific past build.
- Forgetting `needs:` between build/push/deploy jobs, causing deploy to start (or wait) at the wrong time relative to the actual image being ready.
- Not setting `DOCKER_TLS_CERTDIR` with newer dind images — can cause the daemon connection to fail or silently run unencrypted depending on the image.
- Assuming Kaniko is a drop-in replacement for `docker build` in every job — it can build and push images, but general `docker run`/Compose workflows still need real Docker.

## Interview Questions & Answers
- **Q: What is Docker-in-Docker and why does it need privileged mode?**
  A: It runs a nested Docker daemon inside the CI job's container (via the `docker:dind` service) so the job can build/run images; the nested daemon needs kernel-level capabilities (namespaces, cgroups) that only a privileged container is granted.
- **Q: What are the alternatives to dind, and why would you choose them?**
  A: Kaniko and buildah build images without a Docker daemon or privileged mode — chosen when the runner/cluster policy disallows privileged containers (common on shared Kubernetes executors).
- **Q: How do you authenticate to GitLab's Container Registry in a job?**
  A: `docker login -u "$CI_REGISTRY_USER" -p "$CI_REGISTRY_PASSWORD" $CI_REGISTRY` — all three variables are predefined by GitLab, no manual setup.
- **Q: Why tag images with the commit SHA instead of only `latest`?**
  A: SHA tags are immutable and traceable to an exact commit, enabling reliable rollback and auditing; `latest` is mutable and doesn't identify what's actually running.
- **Q: How do you push two tags without doubling build time?**
  A: `docker build -t image:sha -t image:latest .` tags both from the same build; then push each tag separately.
- **Q: Scenario: you need to roll back production to yesterday's release right now — what do you do?**
  A: Redeploy the previous commit's immutable SHA-tagged image directly from the registry (`docker pull image:<old-sha> && docker run ...`) — no rebuild or checkout needed, assuming SHA tags were pushed.
- **Q: How would you speed up repeated Docker builds in CI?**
  A: `--cache-from` with a pulled previous `latest`/branch tag (BuildKit-aware caching), plus `rules:changes` to skip the build entirely when no build-relevant files changed.
- **Q: Scenario: your runner's Kubernetes executor rejects privileged containers — how do you still build Docker images?**
  A: Switch the build job to Kaniko (or buildah), which builds/pushes without needing a privileged dind service.
- **Q: What's the risk of mounting the host's Docker socket instead of using dind?**
  A: The job shares the host's actual Docker daemon with every other job/tenant on that runner — weaker isolation than dind's per-job nested daemon, generally avoided on shared runners.
- **Q: How do you decouple "image is ready" from "image is deployed"?**
  A: Push automatically on every `main` commit, but put the deploy job behind `when: manual` — the image sits ready in the registry until a human approves rolling it out.
