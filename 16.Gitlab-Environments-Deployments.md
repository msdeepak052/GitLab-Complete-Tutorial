# 16. Environments and Deployments in GitLab CI/CD

## Quick Summary
- An `environment:` is a named deployment target (e.g. `production`, `staging`, `review/feature-x`) that GitLab tracks deployments against.
- GitLab records every deployment to an environment: which commit, who triggered it, when, and lets you roll back from the UI.
- Dynamic environments (one per branch/MR) power review apps — a temporary environment per feature branch.
- `on_stop` + `action: stop` let you tear down temporary environments automatically or manually.
- `deployment_tier` classifies an environment (production/staging/testing/development/other) for dashboards, independent of its name.
- Protected environments gate *who* can deploy — separate concern from `environment:` itself.
- This is purely a tracking/visibility + gating mechanism — it does not deploy anything by itself; the `script:` still does the actual deploy work.

## Core Concepts

### Declaring an environment
- Add `environment:` under a job that performs a deploy:
  ```yaml
  deploy_dev:
    stage: deploy
    script:
      - ./deploy.sh dev
    environment:
      name: development
      url: https://dev.example.com
    rules:
      - if: $CI_COMMIT_BRANCH == "develop"
  ```
- `name` (required) — the environment identifier. Allowed: letters, digits, spaces, `-_/$` + CI/CD variables.
- `url` (optional) — shown as a clickable link on the MR widget and in **Operations → Environments**.
- Shorthand: `environment: production` is equivalent to `environment: { name: production }`.

### Environment scope and tracking
- Every job with `environment:` that succeeds creates a **deployment** record.
- GitLab UI (**Deploy → Environments**) shows deployment history, current commit deployed, and a one-click **Rollback** (re-runs the last successful deploy job for that environment).
- Environments are per-project; environment names can be reused across pipelines/branches to accumulate history for the same target.

### Dynamic environments (review apps)
- Use CI/CD variables in `name`/`url` to create one environment per branch or MR:
  ```yaml
  review_app:
    stage: deploy
    script:
      - ./deploy-review.sh
    environment:
      name: review/$CI_COMMIT_REF_SLUG
      url: https://$CI_COMMIT_REF_SLUG.review.example.com
      on_stop: stop_review_app
      auto_stop_in: 1 week
    rules:
      - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  ```
- `$CI_COMMIT_REF_SLUG` is DNS-safe (lowercased, `/` and invalid chars stripped) — prefer it over `$CI_COMMIT_REF_NAME` in URLs.
- Each branch/MR gets its own environment row (`review/my-feature`, `review/other-feature`, ...).

### Stopping environments — `on_stop`
- `on_stop: <job_name>` on the deploy job points to a **stop job** that tears the environment down.
- The stop job must:
  - Set `environment: name:` to the **same name** as the deploy job (so GitLab knows which environment it stops).
  - Set `environment: action: stop`.
  - Typically use `when: manual` so a human triggers teardown, or `rules:` to auto-stop (e.g. when the MR is merged/closed).
  ```yaml
  stop_review_app:
    stage: cleanup
    script:
      - ./teardown-review.sh
    when: manual
    environment:
      name: review/$CI_COMMIT_REF_SLUG
      action: stop
    rules:
      - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  ```
- ⚠️ Gotcha: the deploy job and its stop job must have **matching `rules:` (or legacy `only`/`except`)** — if their conditions diverge, GitLab may not be able to resolve which stop job to run when you click "Stop" in the UI.
- To trigger `on_stop` via the **Stop** button in the Environments UI, the deploy and stop jobs must also share the same `resource_group` (otherwise GitLab may not reliably associate them).

### Auto-stopping — `auto_stop_in`
- `auto_stop_in: <duration>` (e.g. `1 week`, `2 days`, `1 hour`) automatically stops an environment after that period of inactivity from creation — no manual click needed.
- Runs via a background worker that only executes **once per hour**, so actual stop time is "eventually within an hour" of the deadline, not exact.
- `action: prepare` or `action: access` jobs reset the `auto_stop_in` countdown (useful for "someone still viewing this review app" scenarios).
- Great default for review apps so stale feature-branch environments don't pile up forever if someone forgets to click Stop.

### `action:` values
| Value | Meaning |
|---|---|
| `deploy` (default) | Creates a deployment record, runs the deploy. |
| `stop` | Marks the job as the environment's teardown job. |
| `prepare` | Runs before a deploy without creating a deployment record (e.g. provisioning). Resets `auto_stop_in`. |
| `verify` | Verifies an environment without deploying. |
| `access` | Accesses an environment without deploying. Resets `auto_stop_in`. |

### `deployment_tier`
- GitLab guesses a tier from the environment **name** (e.g. anything starting with `prod` → production, `staging`/`stage` → staging, `review`/`test` → testing, `dev` → development).
- Override explicitly when the name doesn't match the convention:
  ```yaml
  environment:
    name: main-cluster
    deployment_tier: production
  ```
- Valid values: `production`, `staging`, `testing`, `development`, `other`.
- Drives grouping in dashboards like the CI/CD Analytics deployment frequency charts (DORA metrics) — a mis-tiered environment silently skews those numbers.

### Protected environments (basics)
- Configured under **Settings → CI/CD → Protected environments** (separate from `environment:` YAML).
- Restricts *who* (which users/groups/roles) can run deployment jobs targeting that environment name.
- Deploying to a protected environment typically requires at least Reporter-level access via an allow list, or Maintainer/Owner by default.
- Protected environments are **not auto-stopped** by cleanup jobs/`auto_stop_in` sweeps — intentional, to avoid accidentally tearing down production.
- Common pattern: protect `production`, require manual approval (`when: manual` + protected environment approvers) before the prod deploy job runs — see file 27 (approval gates) for the deeper multi-approver mechanics.

### `environment:` + `kubernetes` sub-key
- When deploying through the GitLab Kubernetes agent, `environment: kubernetes: namespace: <ns>` associates the environment with a specific cluster namespace for the Dashboard/Environments UI. Niche — only relevant if you use the GitLab agent for Kubernetes; most teams deploy with kubectl/helm in `script:` and skip this.

### ⚠️ Deprecated / Changed
- The old file's examples used `only: [develop]` / `only: [main]` as the trigger mechanism — `only`/`except` are legacy keywords. Use `rules:` (shown throughout this file) for all new pipelines; `only`/`except` still parse but receive no new features and are on GitLab's long-term deprecation track.
- Nothing about `environment:`, `on_stop`, `auto_stop_in`, or `deployment_tier` itself was factually wrong in the old version — this is a stable, mature part of the CI/CD YAML schema.

## Hands-On Labs

### Lab 1: Basic environment with URL
- **Goal:** Track a simple deploy to a named environment.
- **`.gitlab-ci.yml`:**
  ```yaml
  stages:
    - deploy

  deploy_dev:
    stage: deploy
    script:
      - echo "Deploying to dev server..."
    environment:
      name: development
      url: https://dev.example.com
  ```
- **Run it:** Push to any branch, let the pipeline run.
- **Expected result:** A `development` row appears under **Deploy → Environments** with a link to `https://dev.example.com`.
- **What this teaches:** Minimal `environment:` usage and where GitLab surfaces it in the UI.

### Lab 2: Branch-based environments with `rules:`
- **Goal:** Route deploys to `staging` or `production` based on branch, using `rules:` (not legacy `only:`).
- **`.gitlab-ci.yml`:**
  ```yaml
  deploy_staging:
    stage: deploy
    script:
      - echo "Deploying to staging..."
    environment:
      name: staging
      url: https://staging.example.com
    rules:
      - if: $CI_COMMIT_BRANCH == "develop"

  deploy_prod:
    stage: deploy
    script:
      - echo "Deploying to production..."
    environment:
      name: production
      url: https://www.example.com
    rules:
      - if: $CI_COMMIT_BRANCH == "main"
  ```
- **Run it:** Push to `develop`, then to `main`.
- **Expected result:** `develop` push creates/updates the `staging` environment only; `main` push creates/updates `production` only.
- **What this teaches:** `rules:` as the modern equivalent of `only: [develop]` / `only: [main]`.

### Lab 3: Dynamic review-app environment
- **Goal:** Create a distinct environment per branch.
- **`.gitlab-ci.yml`:**
  ```yaml
  review_app:
    stage: deploy
    script:
      - echo "Deploying review app for $CI_COMMIT_REF_SLUG"
    environment:
      name: review/$CI_COMMIT_REF_SLUG
      url: https://$CI_COMMIT_REF_SLUG.review.example.com
    rules:
      - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  ```
- **Run it:** Open an MR from a feature branch.
- **Expected result:** An environment named `review/<branch-slug>` appears; opening a second MR from a different branch creates a second, independent environment.
- **What this teaches:** Dynamic environment naming with `$CI_COMMIT_REF_SLUG`.

### Lab 4: `on_stop` — manual teardown
- **Goal:** Add a manual stop job paired to the review app.
- **`.gitlab-ci.yml`:**
  ```yaml
  review_app:
    stage: deploy
    script:
      - echo "Deploying review app..."
    environment:
      name: review/$CI_COMMIT_REF_SLUG
      url: https://$CI_COMMIT_REF_SLUG.review.example.com
      on_stop: stop_review_app
    rules:
      - if: $CI_PIPELINE_SOURCE == "merge_request_event"

  stop_review_app:
    stage: deploy
    script:
      - echo "Stopping review app..."
    when: manual
    environment:
      name: review/$CI_COMMIT_REF_SLUG
      action: stop
    rules:
      - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  ```
- **Run it:** Run the pipeline, then go to **Deploy → Environments → review/<branch>** and click **Stop**.
- **Expected result:** `stop_review_app` runs, and the environment's state flips to "stopped" in the UI.
- **What this teaches:** Pairing a deploy job with its teardown job via `on_stop` + `action: stop`, and why `rules:` must match between the two.

### Lab 5: `auto_stop_in` — automatic cleanup
- **Goal:** Let stale review apps self-destruct without manual intervention.
- **`.gitlab-ci.yml`:**
  ```yaml
  review_app:
    stage: deploy
    script:
      - echo "Deploying review app..."
    environment:
      name: review/$CI_COMMIT_REF_SLUG
      url: https://$CI_COMMIT_REF_SLUG.review.example.com
      on_stop: stop_review_app
      auto_stop_in: 1 day
    rules:
      - if: $CI_PIPELINE_SOURCE == "merge_request_event"

  stop_review_app:
    stage: deploy
    script:
      - echo "Stopping review app..."
    when: manual
    environment:
      name: review/$CI_COMMIT_REF_SLUG
      action: stop
    rules:
      - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  ```
- **Run it:** Deploy the review app, then wait (or inspect **Environments → Settings** for the scheduled stop time).
- **Expected result:** The environment auto-stops roughly 1 day after creation, without anyone clicking Stop — GitLab's hourly sweep picks it up.
- **What this teaches:** `auto_stop_in` as a safety net so review apps don't accumulate indefinitely.

### Lab 6: Full pipeline — build, test, deploy across environments
- **Goal:** Combine build/test/deploy stages with branch-routed environments.
- **`.gitlab-ci.yml`:**
  ```yaml
  stages:
    - build
    - test
    - deploy

  build_job:
    stage: build
    script:
      - echo "Building app..."
    artifacts:
      paths:
        - app/

  test_job:
    stage: test
    script:
      - echo "Running tests..."
      - ls app/

  deploy_dev:
    stage: deploy
    script:
      - echo "Deploying to dev..."
    environment:
      name: development
      url: https://dev.example.com
    rules:
      - if: $CI_COMMIT_BRANCH == "develop"

  deploy_prod:
    stage: deploy
    script:
      - echo "Deploying to production..."
    environment:
      name: production
      url: https://www.example.com
    rules:
      - if: $CI_COMMIT_BRANCH == "main"
  ```
- **Run it:** Push to `develop`, observe build → test → deploy_dev; push to `main`, observe deploy_prod.
- **Expected result:** Each branch only ever triggers its matching deploy job; the other is skipped.
- **What this teaches:** Environments composed with a normal multi-stage pipeline.

### Lab 7: `deployment_tier` override
- **Goal:** Force a non-standard environment name into the correct DORA tier.
- **`.gitlab-ci.yml`:**
  ```yaml
  deploy_main_cluster:
    stage: deploy
    script:
      - echo "Deploying to main-cluster..."
    environment:
      name: main-cluster
      deployment_tier: production
    rules:
      - if: $CI_COMMIT_BRANCH == "main"
  ```
- **Run it:** Run the pipeline, then check **Analyze → CI/CD Analytics → Deployment frequency**.
- **Expected result:** `main-cluster` is counted as a production deployment even though its name doesn't say "prod".
- **What this teaches:** `deployment_tier` decouples naming from DORA-metric classification.

### Lab 8: Rollback via the Environments UI
- **Goal:** Observe GitLab's built-in rollback.
- **Steps:**
  1. Deploy `v1` to `production` (any script that echoes a version).
  2. Change the script to "deploy v2", push, deploy again.
  3. Go to **Deploy → Environments → production**, open the deployment history, click **Rollback** on the `v1` entry.
- **Expected result:** GitLab re-runs the `v1` deploy job (creating a new pipeline/job that re-executes the old deploy), and the environment's "currently deployed" pointer moves back to `v1`.
- **What this teaches:** Rollback is really "re-run an old deploy job" — your `script:` must be idempotent/safe to re-run for this to work in practice.

### Lab 9: Protected environment gate
- **Goal:** Require explicit permission to deploy to `production`.
- **Steps:**
  1. **Settings → CI/CD → Protected environments** → protect `production`, allow only `Maintainers` to deploy.
  2. Keep the `deploy_prod` job from Lab 6, add `when: manual`.
  3. As a Developer-role user, try to click **Run** on `deploy_prod`.
- **Expected result:** The job is visible but cannot be triggered by a Developer; only a Maintainer (or whoever is on the allow list) can run it.
- **What this teaches:** `environment:` name is the join key between YAML and the protected-environment access-control list configured in the UI.

### Lab 10: Combine `needs:` fan-in with environment stop cleanup
- **Goal:** Auto-stop a review app when its MR is merged, without a manual click.
- **`.gitlab-ci.yml`:**
  ```yaml
  stop_review_app:
    stage: deploy
    script:
      - echo "Auto-stopping review app for merged MR..."
    environment:
      name: review/$CI_COMMIT_REF_SLUG
      action: stop
    rules:
      - if: $CI_PIPELINE_SOURCE == "push" && $CI_COMMIT_BRANCH == "main"
        when: on_success
  needs: []
  ```
- **Run it:** Merge the MR from Lab 3/4 into `main`.
- **Expected result:** The stop job fires automatically on the post-merge pipeline against `main`, stopping the now-stale review environment — no manual click needed.
- **What this teaches:** Auto-stop-on-merge as an alternative/complement to `auto_stop_in`, using `rules:` tied to the merge event rather than a timer.

## Common Pitfalls
- Forgetting `rules:` (or any trigger condition) on a deploy job — it then runs on every pipeline, including ones you didn't intend to deploy.
- Deploy and stop jobs with mismatched `rules:`/`only`/`except` — breaks the UI **Stop** button's ability to resolve the pairing.
- Using `$CI_COMMIT_REF_NAME` instead of `$CI_COMMIT_REF_SLUG` in URLs — branch names with `/` or uppercase letters produce invalid hostnames.
- Assuming `environment:` performs the deployment — it only *tracks* it; your `script:` still has to do the actual work.
- Forgetting `auto_stop_in` or a merge-triggered stop job — review-app environments (and their backing infra/cost) pile up forever.
- Relying on environment name alone for DORA tier classification when the name doesn't match convention — set `deployment_tier` explicitly.
- Expecting protected environments to also protect against `auto_stop_in`/cleanup sweeps — they're excluded from those by design, but that means production won't self-clean if you rename it into "review/..." by mistake.

## Interview Questions & Answers
- **Q: What does the `environment:` keyword actually do?**
  A: Registers a deployment record for the job against a named target; drives the Environments UI, deployment history, and rollback. It does not perform the deployment itself.
- **Q: How do dynamic environments work?**
  A: Use a CI/CD variable in `environment: name` (e.g. `review/$CI_COMMIT_REF_SLUG`) so each branch/MR gets its own environment instance instead of sharing one static name.
- **Q: What is `on_stop` for?**
  A: Points a deploy job to a separate job that tears the environment down; the stop job sets `environment: action: stop` with the same environment name.
- **Q: What happens if the deploy and stop jobs have different `rules:`?**
  A: GitLab may fail to correctly associate them for UI-triggered stops — keep their trigger conditions identical.
- **Q: What does `auto_stop_in` do and how precise is it?**
  A: Schedules automatic environment stop after a duration (e.g. `1 week`); actual execution happens via an hourly background sweep, so it's "within the hour," not exact-to-the-second.
- **Q: What is `deployment_tier` and why override it?**
  A: Classifies an environment into production/staging/testing/development/other for DORA metrics; override it when the environment's name doesn't match GitLab's name-based auto-detection heuristic.
- **Q: How does rollback work under the hood?**
  A: It re-runs the previously successful deploy job for that environment — there's no separate "rollback script"; write deploy scripts to be safely re-runnable.
- **Q: What's the difference between `environment:` and a protected environment?**
  A: `environment:` (YAML) creates/tracks the deployment target; protected environments (project settings) control *who* is authorized to run jobs deploying to a given environment name — two separate, complementary mechanisms.
- **Q: Scenario — your review apps for closed MRs are still running a week later, costing money. What's the fix?**
  A: Add `auto_stop_in` to the deploy job's `environment:` block, and/or add a `stop_review_app` job triggered by `rules:` on merge-to-main, so cleanup doesn't depend on a human clicking Stop.
- **Q: Scenario — you rename an environment from `prod-eu` to `frontend-cluster` and DORA deployment-frequency charts suddenly show zero production deploys. Why, and how do you fix it?**
  A: GitLab's tier auto-detection is name-based and no longer recognizes `frontend-cluster` as production; set `deployment_tier: production` explicitly on that job's `environment:` block.
- **Q: Can two jobs deploy to the same environment name from different branches?**
  A: Yes — deployment history simply accumulates against that environment name in chronological order; it's your `rules:` that should prevent unintended branches from deploying there.
- **Q: Why might a job with `environment: action: stop` fail to run automatically?**
  A: If it's `when: manual` it needs a human trigger (or the Stop button); if it relies on `on_stop` UI-triggering, mismatched `rules:`/`resource_group` between deploy and stop jobs can break the association.
