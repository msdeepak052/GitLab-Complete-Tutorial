# `before_script` and `after_script` in Gitlab CI

## **1️⃣ What is `before_script`?**

* `before_script` contains **commands that run before the main job script**.
* Useful for:

  * Installing dependencies
  * Setting environment variables
  * Logging in to registries

### **Global `before_script` Example**

```yaml
before_script:
  - echo "Starting job..."
  - export APP_ENV=dev
  - mkdir -p logs

stages:
  - build
  - test

build_job:
  stage: build
  script:
    - echo "Building the app..."
    - echo "Environment: $APP_ENV"

test_job:
  stage: test
  script:
    - echo "Running tests..."
```

✅ **Explanation**:

* The commands in `before_script` run **before every job**.
* Both `build_job` and `test_job` will execute `echo "Starting job..."` and create the `logs` directory.

---

### **Job-specific `before_script`**

You can **override** the global `before_script` for a specific job:

```yaml
build_job:
  stage: build
  before_script:
    - echo "Custom setup for build only"
  script:
    - echo "Building..."
```

* Here, `build_job` will run its **own before_script** instead of the global one.

---

## **2️⃣ What is `after_script`?**

* `after_script` contains **commands that run after the main job script**, **regardless of job success or failure**.
* Useful for:

  * Cleaning up resources
  * Collecting logs or artifacts
  * Sending notifications

### **Global `after_script` Example**

```yaml
after_script:
  - echo "Job finished!"
  - rm -rf temp_files

build_job:
  stage: build
  script:
    - echo "Building the app..."
```

✅ **Explanation**:

* After `build_job` runs, GitLab executes all commands in `after_script`.
* Even if the `script` fails, `after_script` still runs.

---

### **Job-specific `after_script`**

```yaml
test_job:
  stage: test
  script:
    - echo "Running tests..."
    - exit 1  # Simulate failure
  after_script:
    - echo "Tests finished, cleaning up..."  # Will still run
```

* The `after_script` **always runs**, even if the job fails (`exit 1`).

---

## **3️⃣ Combining `before_script` and `after_script`**

```yaml
before_script:
  - echo "Global setup"
after_script:
  - echo "Global cleanup"

stages:
  - build
  - test

build_job:
  stage: build
  script:
    - echo "Building app..."
    
test_job:
  stage: test
  before_script:
    - echo "Test-specific setup"
  script:
    - echo "Running tests..."
  after_script:
    - echo "Test-specific cleanup"
```

**Flow:**

| Job       | Commands Run                                                    |
| --------- | --------------------------------------------------------------- |
| build_job | Global before_script → script → Global after_script             |
| test_job  | Job-specific before_script → script → Job-specific after_script |

---

> Let’s go **deep into the mechanics** of how **global vs job-specific `before_script` and `after_script`** execute in GitLab CI/CD. I’ll explain **exactly why and when each runs**.

---


## **1️⃣ Global Scripts**

* `before_script` and `after_script` declared at the **top level** are **global**.
* **By default**, every job runs the global `before_script` **before its `script`** and the global `after_script` **after its `script`**, unless overridden by **job-specific scripts**.

---

## **2️⃣ Job-specific Scripts**

* If a job has its own `before_script` or `after_script`, it **overrides the global scripts**.
* That means:

  * The job **will not execute global `before_script`** if it has a **job-specific `before_script`**.
  * The job **will not execute global `after_script`** if it has a **job-specific `after_script`**.

✅ Important: It **does not merge** by default. Job-specific scripts **replace** global scripts.

---

## **3️⃣ Execution Flow for Each Job**

### **Job 1: `build_job`**

* No job-specific `before_script` or `after_script` → uses global scripts.
* Execution sequence:

1. **Global `before_script`**:

   ```bash
   echo "Global setup"
   ```
2. **Job `script`**:

   ```bash
   echo "Building app..."
   ```
3. **Global `after_script`**:

   ```bash
   echo "Global cleanup"
   ```

**Output**:

```
Global setup
Building app...
Global cleanup
```

---

### **Job 2: `test_job`**

* Has **job-specific `before_script` and `after_script`** → **global scripts are ignored**.
* Execution sequence:

1. **Job-specific `before_script`**:

   ```bash
   echo "Test-specific setup"
   ```
2. **Job `script`**:

   ```bash
   echo "Running tests..."
   ```
3. **Job-specific `after_script`**:

   ```bash
   echo "Test-specific cleanup"
   ```

**Output**:

```
Test-specific setup
Running tests...
Test-specific cleanup
```

---

## **4️⃣ Why This Happens**

1. **Global scripts** are meant as **default setup/cleanup** for all jobs.
2. **Job-specific scripts** exist to **customize behavior for that particular job**.
3. **Override logic**: GitLab assumes that if you provide a job-specific script, you **intend full control**, so it **does not automatically merge** with global scripts.
4. This allows jobs like `test_job` to have a completely different setup/cleanup without interfering with other jobs.

---

## **5️⃣ Optional: Merging Global and Job-Specific Scripts**

If you **want both global and job-specific scripts to run**, you have to explicitly include both:

```yaml
test_job:
  stage: test
  before_script:
    - echo "Global setup"          # Include global commands manually
    - echo "Test-specific setup"
  script:
    - echo "Running tests..."
  after_script:
    - echo "Test-specific cleanup"
    - echo "Global cleanup"        # Include global cleanup manually
```

* Now, `test_job` will run **both global and job-specific scripts**.

**Output**:

```
Global setup
Test-specific setup
Running tests...
Test-specific cleanup
Global cleanup
```

---

### **6️⃣ Key Takeaways**

| Aspect                    | Behavior                                                                    |
| ------------------------- | --------------------------------------------------------------------------- |
| Global `before_script`    | Runs for all jobs **without job-specific `before_script`**                  |
| Global `after_script`     | Runs for all jobs **without job-specific `after_script`**                   |
| Job-specific scripts      | **Override global scripts** completely (do not merge by default)            |
| Combining scripts         | Must **manually include global commands** in job-specific scripts if needed |
| Execution order           | `before_script` → `script` → `after_script`                                 |
| Guaranteed `after_script` | Runs even if job `script` fails (useful for cleanup/logs)                   |

---



### **4️⃣ Key Points**

* `before_script`: Runs **before the job script**, globally or job-specific.
* `after_script`: Runs **after the job script**, **even if the job fails**.
* Job-specific scripts **override global scripts**.
* Useful for **setup, cleanup, logging, and notifications**.
