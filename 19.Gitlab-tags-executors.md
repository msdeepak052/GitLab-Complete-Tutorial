## **1️⃣ Tags in GitLab CI/CD**

**Tags** are used to **control which runner picks up a job**.

* Each runner can have **tags assigned during registration**.
* Each job can specify **tags**, which means the job will **only run on runners with matching tags**.
* Tags allow you to **direct jobs to specific environments**, e.g., Linux, Docker, or Windows runners.

### **Example of Tags**

```yaml
stages:
  - build
  - test

build_job:
  stage: build
  script:
    - echo "Building on Linux runner"
  tags:
    - linux
    - docker

test_job:
  stage: test
  script:
    - echo "Testing on Windows runner"
  tags:
    - windows
```

✅ **Explanation**:

* `build_job` will only run on runners tagged **`linux` AND `docker`**.
* `test_job` will only run on runners tagged **`windows`**.

**Key point:** If no runner has matching tags, the job **stays pending** until a suitable runner is available.

## **2️⃣ GitLab Runner Executors**

Executors define **how the job is executed**. Common executor types:

| Executor                   | Description                                                         | Example / Use Case                             |
| -------------------------- | ------------------------------------------------------------------- | ---------------------------------------------- |
| **Shell**                  | Runs jobs directly on the host OS shell (bash, sh, cmd, PowerShell) | Simple Linux server or Windows server jobs     |
| **Docker**                 | Runs each job in a Docker container                                 | Isolated builds, reproducible environments     |
| **Docker Machine**         | Dynamically creates new Docker hosts for jobs                       | Scalable CI/CD pipelines                       |
| **Kubernetes**             | Runs jobs in Kubernetes pods                                        | Cloud-native pipelines, temporary pods per job |
| **SSH**                    | Runs job on remote server via SSH                                   | Legacy servers or remote deployment jobs       |
| **VirtualBox / Parallels** | Runs jobs in VM                                                     | Legacy setups, full VM environments            |

---

### **3️⃣ Examples for Executors**

#### **A. Shell Executor**

```bash
sudo gitlab-runner register
# Choose executor: shell
```

Job in `.gitlab-ci.yml`:

```yaml
build_shell:
  stage: build
  script:
    - echo "Running build on host shell"
```

* Executes **directly on the host OS**.
* No isolation — uses host environment.

---

#### **B. Docker Executor**

During registration:

```bash
sudo gitlab-runner register
# Choose executor: docker
# Enter default image: alpine:latest
```

Job:

```yaml
build_docker:
  stage: build
  script:
    - echo "Building inside Docker container"
  image: python:3.12
```

* Runs **inside a container** based on the specified image.
* Each job is **isolated**, easy to reproduce environments.

---

#### **C. Kubernetes Executor**

* Runner runs jobs inside **temporary Kubernetes pods**.
* Useful for **ephemeral CI/CD jobs in cloud environments**.

Example:

```yaml
build_k8s:
  stage: build
  script:
    - echo "Running in Kubernetes pod"
```

* Runner is configured with Kubernetes cluster.
* Each job spins up a **new pod**, runs script, and then deletes pod.

---

#### **D. SSH Executor**

* Runs jobs on a **remote server via SSH**.

```yaml
deploy_remote:
  stage: deploy
  script:
    - ssh user@remote-server "cd /app && git pull && systemctl restart app"
```

* Useful for **deploying to legacy servers** without Docker/Kubernetes.

---

### **4️⃣ How Tags and Executors Work Together**

1. **Runner registration**: Assign tags and choose executor.

   ```bash
   sudo gitlab-runner register
   # Tags: linux,docker
   # Executor: docker
   ```
2. **Job tags in YAML**: Job will only run on runners with matching tags.
3. **Executor determines environment**: How the job is executed — shell, container, pod, etc.

✅ Example Flow:

* Runner: tags = `linux,docker`, executor = docker
* Job: tags = `linux,docker` → picked up → runs in Docker container
* Job: tags = `windows` → **skipped**, waits for matching runner

---

### **5️⃣ Key Points**

* **Tags** → Match job to runner.
* **Executor** → Determines **how the job runs** (host shell, container, pod, etc.).
* You can have **multiple runners with different tags/executors** for different jobs.
* Tags + Executors → Gives **flexibility, isolation, and reproducibility**.
