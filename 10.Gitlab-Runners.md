# 10. GitLab Runners — Concepts, Scope, and Registration

## Quick Summary
- A GitLab Runner is the agent that actually executes the jobs defined in `.gitlab-ci.yml`; GitLab (the server) only schedules work, it never runs your `script:` commands itself.
- Runners come in three scopes: **instance** (all projects), **group** (a group + its subgroups), **project** (one or a few specific projects) — these replaced the older "shared" vs "specific" naming.
- Modern registration is **authentication-token based and non-interactive**: create the runner in the GitLab UI first (which issues a `glrt-` token), then run `gitlab-runner register` with that token — the old fully-interactive, registration-token prompt flow is deprecated and scheduled for removal.
- **Tags** match jobs to runners — a job with `tags: [docker]` only runs on a runner registered with the `docker` tag (or one that accepts untagged jobs, depending on config).
- Executor type (shell, Docker, Kubernetes, etc.) determines *how* a job runs, but the deep dive on executors lives in file 19 — this file only needs enough to register and use a runner.
- Installing the `gitlab-runner` binary on every OS is covered in file 18 — this file assumes it's already installed and focuses on concepts + registration + tags.

## Core Concepts

### What a runner does
- GitLab (server) schedules jobs; the **Runner** (agent) polls for and executes them.
- Per job: runner picks up the job -> checks out the repo -> runs `before_script`/`script`/`after_script` -> reports status/logs back to GitLab.
- Job logs visible in the GitLab UI are streamed from the runner in near-real-time.

### Runner scope: instance / group / project
| Scope | Old term | Availability | Typical use |
|---|---|---|---|
| Instance runner | "Shared runner" | Every project on the GitLab instance (e.g., all of gitlab.com) | Fast start, no infra to manage, general-purpose jobs |
| Group runner | (was under "specific") | All projects/subgroups in one group | Shared team infra without instance-wide exposure |
| Project runner | "Specific runner" | One or a small set of explicitly assigned projects | Dedicated hardware, private network access, custom tooling |

- Instance runners are managed by GitLab (on gitlab.com) or by the instance admin (self-managed); you don't install/maintain them yourself.
- Group and project runners are installed and maintained by the team — full control over OS, installed tools, network access (e.g., reaching a private Kubernetes cluster or internal DB).

### ⚠️ Deprecated / Changed
- **Terminology:** "Shared runner" and "specific runner" are legacy terms. Current GitLab docs and UI use **instance runners**, **group runners**, and **project runners**. Expect either term in the wild, but use the new one going forward.
- **Registration flow:** the fully-interactive `gitlab-runner register` prompt sequence (being asked one-by-one for URL, registration token, description, tags, executor) is the **legacy flow**, tied to **runner registration tokens**, which are deprecated and scheduled for removal in GitLab 20.0.
  - Current recommended flow: create the runner first in the GitLab UI (**Settings -> CI/CD -> Runners -> New instance/group/project runner**), which lets you set tags, "run untagged jobs," protection, and other config *at creation time* in the UI — then GitLab issues a **runner authentication token** (`glrt-...` prefix).
  - Registration itself becomes a single non-interactive command using that token:
    ```bash
    sudo gitlab-runner register \
      --non-interactive \
      --url "https://gitlab.com/" \
      --token "glrt-XXXXXXXXXXXXXXXXXXXX" \
      --executor "docker" \
      --docker-image "alpine:latest"
    ```
  - Tags/protection/run-untagged are no longer passed as `register` flags in the new flow — they're set on the runner record in the UI and travel with the authentication token.

### Tags
- A string label attached to a runner at creation/config time (e.g., `docker`, `java`, `deepak`).
- A job requests a runner via `tags:` in `.gitlab-ci.yml`; only runners with **all** listed tags (by default) are eligible to pick up that job.
- A runner can be configured to also accept **untagged jobs** (jobs with no `tags:` at all) — off by default for new project/group runners, must be explicitly enabled.
- Common real use: route Docker-build jobs only to runners with Docker socket access, or route deploy jobs only to a runner that can reach the private cluster network.

### Executors (brief — see file 19 for depth)
- The execution backend a runner uses: **Shell** (runs directly on host), **Docker** (isolated container per job), **Kubernetes** (job runs as a pod), among others.
- Chosen during runner registration (`--executor`) and configured further in `config.toml`.
- This file only needs you to know the executor exists and is chosen at registration time — job-level `image:`/`services:` interplay and per-executor tuning is file 19's scope.

### Installation (brief — see file 18 for depth)
- `gitlab-runner` binary installs via the official package repo/script for Linux, or via Homebrew/binary download for macOS/Windows.
- This file assumes the binary is already installed; file 18 covers OS-specific install steps.

## Hands-On Labs

### Lab 1: Confirm instance runners are available and see them used
- **Goal:** Verify a pipeline can run without any runner setup on your part.
- **Steps:**
  1. Push any `.gitlab-ci.yml` with a simple job (no `tags:`) to a gitlab.com project.
  2. **CI/CD -> Pipelines**, open the job.
- **Run it:** Check the job log header.
- **Expected result:** Log shows `Running with gitlab-runner ...` and a runner name/ID that you never registered yourself — an instance runner picked it up.
- **What this teaches:** Instance runners are on by default for gitlab.com projects; nothing to configure to get a working pipeline.

### Lab 2: Create a new project runner in the UI and capture its token
- **Goal:** Provision a runner record and get its authentication token, current-flow style.
- **Steps:**
  1. Project -> **Settings -> CI/CD -> Runners -> New project runner**.
  2. Select an OS (informational), optionally add tags (e.g., `deepak`), leave "Run untagged jobs" unchecked for now.
  3. Click **Create runner**.
  4. Copy the displayed registration command, and note the `glrt-...` authentication token embedded in it.
- **Run it:** Just capture the token/command — don't register yet.
- **Expected result:** A new runner row appears under **Project runners**, initially showing as not yet contacted/offline.
- **What this teaches:** In the current flow, the runner identity (tags, scope, protection) is defined in GitLab *before* any agent process exists — registration afterward just attaches an agent to that identity.

### Lab 3: Register the runner non-interactively
- **Goal:** Bring the runner online using the modern, scriptable registration command.
- **Steps:**
  ```bash
  sudo gitlab-runner register \
    --non-interactive \
    --url "https://gitlab.com/" \
    --token "glrt-XXXXXXXXXXXXXXXXXXXX" \
    --executor "docker" \
    --docker-image "alpine:latest" \
    --description "deepak-project-runner"
  ```
- **Run it:** Then verify locally: `sudo gitlab-runner list`.
- **Expected result:** Output shows the runner with the description you gave and the `docker` executor; back in GitLab, **Settings -> CI/CD -> Runners** now shows it as active/green.
- **What this teaches:** One non-interactive command replaces the old multi-prompt flow — scriptable and reproducible (e.g., in provisioning automation).

### Lab 4: Route a job to that runner using tags
- **Goal:** Prove tag-based job routing works.
- **`.gitlab-ci.yml`:**
  ```yaml
  build_job:
    stage: build
    tags:
      - deepak
    script:
      - mvn package
  ```
- **Run it:** Push to a branch and open the pipeline.
- **Expected result:** The job's log shows it ran on your registered runner (matching name/description), not an instance runner.
- **What this teaches:** `tags:` is the mechanism that pins specific jobs to specific runners — essential once you have more than one runner available.

### Lab 5: Watch a job stay "pending" due to a tag mismatch
- **Goal:** Deliberately reproduce the most common runner-related failure.
- **`.gitlab-ci.yml`:**
  ```yaml
  build_job:
    stage: build
    tags:
      - nonexistent-tag
    script:
      - echo "this will never run"
    timeout: 2m
  ```
- **Run it:** Push and watch the job status.
- **Expected result:** Job sits in **Pending** indefinitely (or until timeout) with a UI hint like "This job is stuck, because you don't have any active runners that can run this job."
- **What this teaches:** A tag with no matching runner is a silent-looking failure mode — recognizing this message quickly is a real troubleshooting skill.

### Lab 6: Enable "Run untagged jobs" and observe the effect
- **Goal:** Understand the untagged-job opt-in.
- **Steps:**
  1. **Settings -> CI/CD -> Runners**, edit your project runner.
  2. Enable **Run untagged jobs**, save.
  3. Push a job with no `tags:` key at all.
- **Run it:** Check which runner picks it up.
- **Expected result:** Your project runner now accepts the untagged job (previously it would have gone to an instance runner or stayed pending, depending on availability).
- **What this teaches:** Runners don't accept untagged jobs by default in the current UI-driven creation flow — it's an explicit opt-in, unlike some legacy defaults.

### Lab 7: Create a group runner and share it across two projects
- **Goal:** See group-scoped sharing in action (requires a group with 2+ projects).
- **Steps:**
  1. Group -> **Settings -> CI/CD -> Runners -> New group runner**.
  2. Register it the same non-interactive way as Lab 3.
  3. Add a tagged job to two different projects inside that group, both using the same tag.
- **Run it:** Trigger pipelines in both projects.
- **Expected result:** Both projects' jobs run on the same group runner — no per-project registration needed.
- **What this teaches:** Group runners avoid duplicating runner infrastructure per project when several projects share the same team/infra.

### Lab 8: Compare instance vs project runner behavior side by side
- **Goal:** See the scope difference directly in one pipeline.
- **`.gitlab-ci.yml`:**
  ```yaml
  stages:
    - build

  on_instance_runner:
    stage: build
    script:
      - echo "no tags - can land anywhere"

  on_project_runner:
    stage: build
    tags:
      - deepak
    script:
      - echo "must land on my tagged runner"
  ```
- **Run it:** Push and inspect both job logs' "Running with gitlab-runner" header.
- **Expected result:** `on_instance_runner` shows a GitLab-managed instance runner; `on_project_runner` shows your own registered runner.
- **What this teaches:** Tags are the only thing that changes routing here — scope (instance vs project) is a property of the runner, not something you declare per-job beyond tag matching.

### Lab 9: Pause and unpause a runner
- **Goal:** Practice taking a runner temporarily out of rotation (e.g., for maintenance) without deleting it.
- **Steps:**
  1. **Settings -> CI/CD -> Runners**, find your project runner.
  2. Toggle it to **Paused**.
  3. Push a job with a matching tag.
- **Run it:** Observe the job's status, then unpause and re-check.
- **Expected result:** While paused, the tagged job stays pending (paused runner won't pick up new jobs); after unpausing, a re-run/retry picks it up normally.
- **What this teaches:** Pausing is the safe way to take a runner offline for maintenance without losing its registration/config.

### Lab 10: Diagnose a stuck pipeline from scratch
- **Goal:** Practice the troubleshooting checklist for "my pipeline never starts."
- **Steps:**
  1. Intentionally misconfigure: register a runner with executor `docker` but request `tags: [shell-only]` in the job while the runner has tag `docker`.
  2. Push and observe the pending job.
  3. Work through: check job's required tags vs runner's configured tags (**Settings -> CI/CD -> Runners**); check runner status (active/paused, last contact time); check `sudo gitlab-runner verify` and `sudo systemctl status gitlab-runner` on the runner host.
- **Run it:** Fix the tag mismatch, confirm the job now runs.
- **Expected result:** Job transitions from Pending to Running once tags line up and the runner process is confirmed alive.
- **What this teaches:** A repeatable diagnostic order (tags -> runner status -> runner process health) resolves the majority of "stuck pipeline" incidents.

### Lab 11: Migrate a legacy registration-token runner to an authentication-token runner
- **Goal:** Practice the deprecation path teams are currently going through.
- **Steps:**
  1. If you have an old runner registered via the legacy interactive/registration-token flow, note its tags/executor config.
  2. Create a new project runner in the UI (Lab 2 steps) replicating the same tags.
  3. Register a fresh agent against the new `glrt-` token (Lab 3 steps), pointing at a new `config.toml` section or a new host/container.
  4. Once the new runner is confirmed active and picking up jobs, unregister/delete the old registration-token-based runner.
- **Run it:** Confirm pipelines keep running throughout, sourced from the new runner after cutover.
- **Expected result:** No pipeline downtime; old runner cleanly retired.
- **What this teaches:** This is the exact migration GitLab is pushing all users toward before registration tokens are removed in GitLab 20.0 — worth knowing hands-on, not just in theory.

## Common Pitfalls
- Following an old tutorial's fully-interactive `gitlab-runner register` prompts and registration token — works today but is deprecated and being removed in GitLab 20.0.
- Forgetting that new project/group runners don't accept untagged jobs by default — jobs with no `tags:` can end up pending if no instance runner is available and your runner isn't opted in.
- Mismatched tags (typo, or job tag not present on any runner) — the single most common "pipeline stuck at pending" cause.
- Confusing runner **scope** (instance/group/project — who can use it) with **executor** (shell/docker/kubernetes — how jobs run) — they're independent choices.
- Assuming a paused runner is the same as a deleted one — paused keeps config/registration intact, just stops picking up jobs.

## Interview Questions & Answers
- **Q: What's the difference between GitLab (the server) and a GitLab Runner?**
  A: GitLab schedules pipelines/jobs and stores results; the Runner is the separate agent process that actually executes `script:` commands and reports back.
- **Q: What are the three runner scopes and how do they differ?**
  A: Instance (all projects on the GitLab instance), group (all projects/subgroups in a group), project (one or a few explicitly assigned projects) — narrower scope means more dedicated/private infra, broader scope means less setup.
- **Q: How do tags control job scheduling?**
  A: A job's `tags:` list must be a subset of a runner's configured tags for that runner to be eligible; runners can additionally opt in to accept untagged jobs.
- **Q: What replaced the old interactive `gitlab-runner register` + registration token flow?**
  A: Creating the runner first in the GitLab UI (which sets tags/protection and issues a `glrt-` authentication token), then a single non-interactive `gitlab-runner register --non-interactive --url ... --token ...` command.
- **Q: Why were registration tokens deprecated?**
  A: They were project/group-wide shared secrets with broad, hard-to-audit scope; authentication tokens are tied to a single specific runner record created explicitly in the UI, giving tighter control and auditability.
- **Q: Scenario — a pipeline job has been "Pending" for 10 minutes. What do you check first?**
  A: Whether any runner (instance or your own) has all the tags the job requests, and whether your own runner (if applicable) is active/not paused and its process is actually running on the host.
- **Q: Scenario — you need a job to reach a private on-prem database that the internet can't reach. What runner setup do you need?**
  A: A project or group runner installed on infrastructure with network access to that database — instance runners (GitLab-hosted) cannot reach private networks.
- **Q: What does "Run untagged jobs" control, and what's its default for a newly created runner?**
  A: Whether the runner accepts jobs with no `tags:` at all; off by default for new project/group runners created via the current UI flow.
- **Q: Is choosing an executor (Docker, Shell, Kubernetes) a per-job decision or a per-runner decision?**
  A: Per-runner (chosen at registration/config time); a job's `image:`/`services:` then interacts with that executor but doesn't change which executor is used.
- **Q: How would you take a runner out of service for maintenance without losing its configuration?**
  A: Pause it in **Settings -> CI/CD -> Runners** rather than deleting/unregistering it — it stops accepting new jobs but keeps its tags/token/config intact.
