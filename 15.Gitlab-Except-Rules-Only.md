# 15. `only`/`except` (Legacy) vs `rules` (Modern) + `when` — Canonical Reference

## Quick Summary
- `only`/`except` are the original keywords for controlling job execution; per current GitLab docs they are **deprecated** — use `rules:` for all new pipelines.
- `rules:` is a strict superset in flexibility: supports variable expressions, file-change detection, file-existence checks, manual triggers, and per-condition `when:`/`variables:`.
- Default behavior differs: `only`/`except` run a job **unless excluded**; `rules:` runs a job **only if a rule explicitly matches** (implicit `when: never` otherwise).
- `when:` controls *if/how* a job executes once selected — same keyword works standalone on a job or nested inside a `rules:` entry.
- This file is the canonical only/except-vs-rules reference for this repo — file 11 (pipeline triggers) links back here instead of re-teaching the distinction.
- Realistic interview/take-home exercise: convert a legacy `only`/`except` job to its `rules:` equivalent — several labs below drill exactly that.

## Core Concepts

### `only`/`except` — legacy syntax
- `only:` — list of refs/keywords the job **is** allowed to run for (branches, tags, `merge_requests`, `schedules`, `pipelines`, `api`, `web`, etc.).
- `except:` — list of refs/keywords the job is **excluded** from.
- Default: without either, the job runs for (almost) everything; `only`/`except` narrow that default.
- Supports the special keywords `branches`, `tags`, `merge_requests`, `pipelines`, `schedules`, `api`, `web`, `triggers`, `pushes`, `external`, `chat`, among others — recognizable pipeline-source-style values, but far less composable than `rules:if` expressions.
- No support for arbitrary variable logic, manual-trigger gating per condition, or file-existence checks.

### `rules:` — modern syntax
- Ordered list of conditions; **first matching rule wins**, all later rules are ignored for that job.
- Each rule can combine: `if:` (variable expression), `changes:` (file-path glob match), `exists:` (file presence check), `when:`, `allow_failure:`, `variables:`.
- If **no** rule matches, the job is **not created** for that pipeline — this is the opposite default from `only`/`except`.
- `rules:` and `only`/`except` are mutually exclusive on a single job — if `rules:` is present, GitLab ignores any `only`/`except` on that job entirely.

### `only`/`except` current deprecation status
- Per current GitLab documentation: **"`only` and `except` are deprecated. To control when to add jobs to pipelines, use `rules` instead."**
- No fixed removal version is published — docs state they "could be scheduled for removal in a future major milestone," i.e. deprecated with an open-ended timeline, not yet removed.
- Practical guidance: still functional today, safe for reading legacy pipelines, but should not be used in new `.gitlab-ci.yml` files.

### `when:` — full value reference
| `when` value | Meaning |
| --- | --- |
| `on_success` (default) | Runs only if all jobs in earlier stages succeeded (or had `allow_failure: true`) |
| `on_failure` | Runs only if at least one job in an earlier stage failed |
| `always` | Runs regardless of earlier job status — common for cleanup/notifications |
| `manual` | Requires a user to click "Play" in the GitLab UI; combine with `allow_failure: true` to avoid blocking the pipeline while waiting |
| `delayed` | Runs automatically after a delay set by `start_in:` (e.g. `start_in: 10 minutes`) |
| `never` | Job is never created — typically used as the final fallback rule in a `rules:` list |
- `when:` can be set directly on a job (applies unconditionally) or nested inside a `rules:` entry (applies only if that rule's condition matches).
- A `rules:` entry with only `when:` and no `if`/`changes`/`exists` acts as an unconditional catch-all for whatever position it occupies in the list.

## Hands-On Labs

### Lab 1: Legacy `only` — restrict to specific branches
- **Goal:** See the original branch-restriction syntax.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build

build_job:
  stage: build
  script:
    - echo "Building the app"
  only:
    - main
    - develop
```
- **Run it:** Push to `main`, then to a `feature/x` branch.
- **Expected result:** Job runs on `main`; job absent on `feature/x`.
- **What this teaches:** `only:` default posture is "runs unless excluded from this list" — the baseline you're modernizing away from.

### Lab 2: Legacy `except` — exclude specific pipeline types
- **Goal:** See exclusion-based legacy syntax.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - deploy

deploy_job:
  stage: deploy
  script:
    - echo "Deploying the app"
  except:
    - merge_requests
    - tags
```
- **Run it:** Open a merge request, then push a tag.
- **Expected result:** Job does not run for either case; runs for a normal branch push.
- **What this teaches:** `except:` inverts the default — runs everywhere except the listed cases.

### Lab 3: Convert Lab 1 (`only`) to `rules:` — side by side
- **Goal:** Direct conversion exercise, branch restriction.
- **`.gitlab-ci.yml`** (legacy):
```yaml
build_job:
  stage: build
  script:
    - echo "Building"
  only:
    - main
    - develop
```
- **`.gitlab-ci.yml`** (modern equivalent):
```yaml
build_job:
  stage: build
  script:
    - echo "Building"
  rules:
    - if: '$CI_COMMIT_BRANCH == "main" || $CI_COMMIT_BRANCH == "develop"'
```
- **Run it:** Push the modern version to `main`, then to a `feature/x` branch.
- **Expected result:** Same behavior as Lab 1 — runs on `main`/`develop`, absent elsewhere.
- **What this teaches:** A short OR-expression in `rules:if` directly replaces a multi-item `only:` list.

### Lab 4: Convert Lab 2 (`except`) to `rules:` — side by side
- **Goal:** Direct conversion exercise, exclusion logic.
- **`.gitlab-ci.yml`** (legacy):
```yaml
deploy_job:
  stage: deploy
  script:
    - echo "Deploying"
  except:
    - merge_requests
    - tags
```
- **`.gitlab-ci.yml`** (modern equivalent):
```yaml
deploy_job:
  stage: deploy
  script:
    - echo "Deploying"
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
      when: never
    - if: '$CI_COMMIT_TAG'
      when: never
    - when: on_success
```
- **Run it:** Open an MR, push a tag, then push a plain branch commit.
- **Expected result:** Job absent for MR and tag pipelines; runs for the plain branch push.
- **What this teaches:** Converting `except:` requires inverting each excluded case into an explicit `when: never` rule, followed by a catch-all `on_success` — `rules:` makes the exclusion logic visible instead of implicit.

### Lab 5: `rules:if` with tag regex match
- **Goal:** Run a job automatically only for semantic-version-style tags.
- **`.gitlab-ci.yml`:**
```yaml
deploy_job:
  stage: deploy
  script:
    - echo "Deploying..."
  rules:
    - if: '$CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/'
      when: on_success
    - if: '$CI_COMMIT_BRANCH == "develop"'
      when: manual
    - when: never
```
- **Run it:** Push a tag `v1.2.3`, then push to `develop`, then push to an unrelated branch.
- **Expected result:** `v1.2.3` tag triggers an automatic run; `develop` shows a manual "Play" button; the unrelated branch shows no job at all.
- **What this teaches:** Regex matching (`=~`) inside `rules:if` has no legacy equivalent in `only`/`except` — a clear flexibility gap between the two.

### Lab 6: `when: on_success` (explicit default)
- **Goal:** Confirm `on_success` behavior even though it's the implicit default.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - test

build_job:
  stage: build
  script:
    - echo "Building app"

test_job:
  stage: test
  script:
    - echo "Testing app"
  when: on_success
```
- **Run it:** Push normally, then modify `build_job` to `exit 1` and push again.
- **Expected result:** `test_job` runs after a successful `build_job`; `test_job` is skipped (shown as "skipped") after a failed `build_job`.
- **What this teaches:** `on_success` is what you get for free — explicit here only for clarity.

### Lab 7: `when: on_failure` for failure notifications
- **Goal:** Trigger a job only when something upstream failed.
- **`.gitlab-ci.yml`:**
```yaml
build:
  stage: build
  script:
    - exit 1

notify_failure:
  stage: deploy
  script:
    - echo "Build failed! Sending notification..."
  when: on_failure
```
- **Run it:** Push (build is forced to fail for this lab).
- **Expected result:** `notify_failure` runs and prints its message; would be skipped if `build` had succeeded.
- **What this teaches:** `on_failure` is the standard pattern for alerting/cleanup-on-error jobs.

### Lab 8: `when: always` for guaranteed cleanup
- **Goal:** Run a job regardless of pipeline health.
- **`.gitlab-ci.yml`:**
```yaml
cleanup:
  stage: deploy
  script:
    - echo "Cleaning workspace..."
  when: always
```
- **Run it:** Push once with all jobs passing, once with an earlier job forced to fail.
- **Expected result:** `cleanup` runs in both cases.
- **What this teaches:** `always` is the only `when:` value indifferent to prior job outcomes.

### Lab 9: `when: manual` combined with `allow_failure: true`
- **Goal:** Add an optional manual job that doesn't block the pipeline while waiting to be clicked.
- **`.gitlab-ci.yml`:**
```yaml
deploy_job:
  stage: deploy
  script:
    - echo "Deploying to production"
  when: manual
  allow_failure: true
```
- **Run it:** Push and check the pipeline status before clicking "Play."
- **Expected result:** Pipeline shows overall success/green even though `deploy_job` is still pending manual action; clicking "Play" runs it on demand.
- **What this teaches:** `allow_failure: true` on a manual job prevents the whole pipeline from being blocked/held at "pending" waiting for a human.

### Lab 10: `when: delayed` with `start_in`
- **Goal:** Auto-run a job after a fixed delay.
- **`.gitlab-ci.yml`:**
```yaml
scheduled_job:
  stage: deploy
  script:
    - echo "Delayed job running..."
  when: delayed
  start_in: 10 minutes
```
- **Run it:** Push and watch the job in CI/CD > Pipelines — it should show a countdown before starting.
- **Expected result:** Job sits in a delayed/timer state for ~10 minutes, then executes automatically without a manual click.
- **What this teaches:** `delayed` is the automatic counterpart to `manual` — useful for staged rollouts (e.g. "deploy to region B 10 minutes after region A").

### Lab 11: Combining `rules:if` + `when:` for a full manual/auto/never matrix
- **Goal:** One job, three distinct behaviors depending on context.
- **`.gitlab-ci.yml`:**
```yaml
deploy_job:
  stage: deploy
  script:
    - echo "Deploying app..."
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
    - if: '$CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/'
      when: on_success
    - when: never
```
- **Run it:** Push to `main`, push a `v1.0.0` tag, push to an unrelated branch.
- **Expected result:** `main` push shows a manual Play button; tag push runs automatically; unrelated branch shows no job at all.
- **What this teaches:** `rules:` lets a single job encode multiple distinct trigger behaviors that would otherwise require several separate `only`/`except` jobs.

### Lab 12: Convert a mixed `only` + `except` job to a single `rules:if` expression
- **Goal:** Practice a realistic take-home-style conversion combining both legacy keywords into one job.
- **`.gitlab-ci.yml`** (legacy):
```yaml
build_job:
  stage: build
  script:
    - echo "build"
  only:
    - main
  except:
    - schedules
```
- **`.gitlab-ci.yml`** (modern equivalent):
```yaml
build_job:
  stage: build
  script:
    - echo "build"
  rules:
    - if: '$CI_COMMIT_BRANCH == "main" && $CI_PIPELINE_SOURCE != "schedule"'
```
- **Run it:** Push to `main` normally, then trigger a scheduled pipeline against `main`.
- **Expected result:** Normal push runs the job; scheduled pipeline does not.
- **What this teaches:** A combined `only`+`except` job collapses into a single boolean `if:` expression using `&&` — this is the pattern most take-home exercises test for.

## Common Pitfalls
- Mixing `rules:` and `only`/`except` on the same job — `rules:` silently wins and `only`/`except` is ignored entirely, which surprises anyone expecting both to apply.
- Forgetting `rules:`'s default is "skip unless matched" — porting an `only:` job to `rules:` without adding the equivalent `if:` makes the job never run.
- Placing a catch-all `when: on_success`/`when: always` rule too early in a `rules:` list — since first-match-wins, later more-specific rules never get evaluated.
- Using `delayed` without `start_in` — required and easy to forget.
- Treating `only`/`except` as "removed" — they're deprecated, not removed; legacy pipelines using them still run, just shouldn't be extended with more of the same.
- Assuming `when: manual` alone restricts a job to certain branches — it only affects trigger mechanism, not scope; must be paired with `if:` (or legacy `only:`) for branch targeting.

## Interview Questions & Answers
- **Q: Are `only`/`except` deprecated, and what does current GitLab documentation say?**
  A: Yes — current docs state "`only` and `except` are deprecated. To control when to add jobs to pipelines, use `rules` instead." No fixed removal version is published yet.
- **Q: What's the key default-behavior difference between `only`/`except` and `rules:`?**
  A: `only`/`except` run the job unless excluded (permissive default); `rules:` skip the job unless a rule explicitly matches (restrictive default, implicit `when: never`).
- **Q: Can you use both `only`/`except` and `rules:` on the same job?**
  A: They're mutually exclusive in effect — if `rules:` is present, GitLab ignores `only`/`except` on that job entirely.
- **Q: What are the valid `when:` values?**
  A: `on_success` (default), `on_failure`, `always`, `manual`, `delayed`, `never`.
- **Q: How do you prevent a manual job from blocking the rest of the pipeline while it waits to be clicked?**
  A: Set `allow_failure: true` alongside `when: manual`.
- **Q: What does `delayed` require to function?**
  A: A `start_in:` value specifying the delay (e.g. `start_in: 10 minutes`).
- **Q: How is rule order evaluated in a `rules:` list?**
  A: Top to bottom, first matching rule wins; remaining rules are not evaluated for that job.
- **Q: Scenario — you convert an `only: [main]` job to `rules:` but forget to add a condition; what happens?**
  A: With an empty/missing `rules:` list (or a rule that never matches), the job is never created for any pipeline — `rules:`'s restrictive default means "add the `if:`" is not optional the way it was implicitly true under `only:`.
- **Q: Scenario — a job that used to run on every push except merge requests now needs to also skip documentation-only changes. How would you extend the `rules:` version?**
  A: Add a `changes:`-based rule ahead of the catch-all: `- changes: ["*.md"] \n  when: never`, positioned before the final `on_success`/`never` fallback, alongside the existing `merge_request_event` exclusion rule.
- **Q: What's the modern equivalent of `except: [tags]`?**
  A: `rules: - if: '$CI_COMMIT_TAG' \n    when: never` followed by a fallback `when: on_success`.
- **Q: Why is `rules:` considered more powerful than `only`/`except`?**
  A: Supports arbitrary variable expressions (`if:`), file-change/-existence detection (`changes:`/`exists:`), per-condition `when:` and `allow_failure:`, and per-condition variable overrides — none of which `only`/`except` support.
- **Q: If neither `only`/`except` nor `rules:` is specified on a job, when does it run?**
  A: On every pipeline, subject only to the pipeline's own `workflow:rules` gating (see file 11) — the job itself has no restriction.
