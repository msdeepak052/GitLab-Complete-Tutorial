# **GitLab Branches**


## 🌿 What is a Branch in GitLab?

A **branch** in GitLab (and Git) is a **lightweight movable pointer** to a specific commit in your repository.
It allows developers to **work on new features, bug fixes, or experiments** independently without affecting the main (stable) codebase.

---

## 🧩 Why Branches Are Used

Branches help teams to:

* Develop **features** in isolation
* Fix **bugs** without breaking production
* Work on **multiple versions** of the code simultaneously
* Enable **code review** through Merge Requests
* Support **CI/CD pipelines** for testing before merging

---

## 🧱 Default Branch

When you create a GitLab project, GitLab automatically creates a **default branch** — usually called `main` (older projects may have `master`).

* The **default branch** represents the *production-ready* or *stable* version of your code.
* All new branches are usually created **from this branch**.

---

## ⚙️ Branch Types (by purpose)

| Branch Type           | Purpose                           | Example Name             | Typical Usage                        |
| --------------------- | --------------------------------- | ------------------------ | ------------------------------------ |
| **Main (default)**    | Stable production code            | `main` or `master`       | Used for deployment or releases      |
| **Feature branch**    | Develop a new feature             | `feature/add-login-page` | Add new modules/features             |
| **Bugfix branch**     | Fix bugs in the code              | `bugfix/fix-api-timeout` | Resolve specific bugs                |
| **Release branch**    | Prepare a new version for release | `release/v2.1`           | Stabilize and test before deployment |
| **Hotfix branch**     | Fix urgent production issues      | `hotfix/fix-db-crash`    | Quick fix on production code         |
| **Experiment branch** | Try new ideas                     | `experiment/new-theme`   | Test experimental features safely    |

---

## 🔧 How to Create and Manage Branches

### **Option 1: From GitLab Web UI**

**Steps:**

1. Go to your project → **Repository → Branches**.
2. Click **“New Branch”**.
3. Enter a branch name (e.g., `feature/user-login`).
4. Choose source branch (default is `main`).
5. Click **Create Branch**.

**Result:**
You’ll see your new branch listed under “Branches.”

---

### **Option 2: From Command Line (Git CLI)**

```bash
# Clone your GitLab repo
git clone https://gitlab.com/deepak/devops-app.git
cd devops-app

# Create a new branch
git checkout -b feature/add-login-page

# Make changes, then commit
git add .
git commit -m "Added login page feature"

# Push the branch to GitLab
git push origin feature/add-login-page
```

## 🔒 Protected Branches

### **What are Protected Branches?**

Protected branches prevent **unauthorized changes** to critical branches (like `main` or `release`).

**You can:**

* Restrict who can push or merge
* Require Merge Requests for changes
* Prevent force pushes

**Example:**

* Only **Maintainers** can push to `main`.
* All Developers must use **Merge Requests**.

**Path:**
👉 `Settings → Repository → Protected Branches`

## 🧭 Best Practices

✅ Use **clear branch names**:
`feature/login`, `bugfix/api-error`, `hotfix/ssl-fix`

✅ Always **create Merge Requests** before merging.
✅ Enable **branch protection** for main and release branches.
✅ Delete branches after merging to keep repo clean.
✅ Link branches with **issues** for better tracking (e.g., `#12` in commit messages).

> Let’s go step-by-step to **create and configure a `.gitlab-ci.yml`** file for your **Java application that builds, creates a Docker image, and deploys to Kubernetes**.

We’ll assume your app is a **Maven-based Java web app** similar to your `java-deepak-webapp` project.

---

## 🧭 Step-by-Step Guide — Creating `.gitlab-ci.yml` in GitLab Repo

---

### 🔹 **Step 1: Prerequisites**

Before creating the `.gitlab-ci.yml` file, make sure you have:

1. A **GitLab account** and repository (e.g., `https://gitlab.com/deepak/java-deepak-webapp`)
2. Your **application source code** pushed (including `pom.xml` and `Dockerfile`)
3. A **Kubernetes cluster** (like EKS/AKS/GKE)
4. A **Kubernetes Deployment YAML** (for your app)
5. GitLab **runners** (shared runners are fine)
6. GitLab **Container Registry** enabled for your project

---

### 🔹 **Step 2: Generate Kubernetes Access Token**

You need to give GitLab pipeline permission to deploy to your cluster.

Run these commands on your local machine (where `kubectl` is configured):

```bash
kubectl create serviceaccount gitlab-deployer -n devops
kubectl create clusterrolebinding gitlab-deployer-binding --clusterrole=cluster-admin --serviceaccount=devops:gitlab-deployer
kubectl -n devops get secret $(kubectl -n devops get sa gitlab-deployer -o jsonpath="{.secrets[0].name}") -o go-template="{{.data.token | base64decode}}"
```

Save the **output token** — this is your Kubernetes service account token.

---

### 🔹 **Step 3: Add CI/CD Variables in GitLab**

Go to your project →
**Settings → CI/CD → Variables → Expand**

Add the following variables (click **“Add Variable”** for each):

| Variable Name          | Value                                   | Type     |
| ---------------------- | --------------------------------------- | -------- |
| `CI_REGISTRY_USER`     | your GitLab username                    | Masked   |
| `CI_REGISTRY_PASSWORD` | your GitLab personal access token       | Masked   |
| `KUBE_CONTEXT`         | your Kubernetes context name (optional) | Variable |
| `KUBE_NAMESPACE`       | `devops`                                | Variable |
| `KUBECONFIG_DATA`      | Base64 of your kubeconfig file          | Masked   |

💡 To get Base64 of kubeconfig:

```bash
cat ~/.kube/config | base64 -w 0
```

---

### 🔹 **Step 4: Create `.gitlab-ci.yml` File**

In your **project root**, create a new file:

```bash
touch .gitlab-ci.yml
```

---

### 🔹 **Step 5: Add the Pipeline Configuration**

Paste the following content:

```yaml
stages:
  - build
  - test
  - package
  - docker
  - deploy

variables:
  IMAGE_TAG: "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"
  K8S_NAMESPACE: "devops"

before_script:
  - echo "Starting pipeline for $CI_PROJECT_NAME"
  - echo "Branch: $CI_COMMIT_REF_NAME"

build_job:
  stage: build
  image: maven:3.9.6-eclipse-temurin-17
  script:
    - mvn clean compile
  artifacts:
    paths:
      - target/

test_job:
  stage: test
  image: maven:3.9.6-eclipse-temurin-17
  script:
    - mvn test

package_job:
  stage: package
  image: maven:3.9.6-eclipse-temurin-17
  script:
    - mvn package -DskipTests
  artifacts:
    paths:
      - target/*.jar

docker_build:
  stage: docker
  image: docker:latest
  services:
    - docker:dind
  script:
    - echo "Logging into GitLab Registry..."
    - docker login -u "$CI_REGISTRY_USER" -p "$CI_REGISTRY_PASSWORD" $CI_REGISTRY
    - echo "Building Docker image..."
    - docker build -t $IMAGE_TAG .
    - echo "Pushing Docker image..."
    - docker push $IMAGE_TAG
  only:
    - main

deploy_to_k8s:
  stage: deploy
  image: bitnami/kubectl:latest
  script:
    - echo "$KUBECONFIG_DATA" | base64 -d > /tmp/config
    - export KUBECONFIG=/tmp/config
    - kubectl -n $K8S_NAMESPACE set image deployment/java-webapp java-webapp=$IMAGE_TAG
    - kubectl -n $K8S_NAMESPACE rollout status deployment/java-webapp
  only:
    - main
```

---

### 🔹 **Step 6: Commit and Push**

```bash
git add .gitlab-ci.yml
git commit -m "Added GitLab CI/CD pipeline"
git push origin main
```

---

### 🔹 **Step 7: Verify Pipeline Execution**

1. Go to your GitLab project
2. Navigate to **CI/CD → Pipelines**
3. You’ll see the pipeline stages:

   ```
   build → test → package → docker → deploy
   ```
4. Once it completes:

   * A Docker image is built and pushed to GitLab Registry
   * Kubernetes deployment is updated automatically

---

### 🔹 **Step 8: Verify Deployment in Kubernetes**

After successful deployment:

```bash
kubectl get pods -n devops
```

✅ You should see your updated Java app pods running with the new image tag.

---

### 🔹 **Optional Step 9: Secure Your Pipeline**

To make it more production-ready:

* Use **GitLab protected variables** for sensitive data
* Add **branch rules** to deploy only from `main` or `release/*`
* Enable **environment** tracking in `.gitlab-ci.yml` like:

  ```yaml
  environment:
    name: production
    url: https://java.deepak-app.com
  ```
