# 7. GitLab Branches — Branching Model, Naming, Protection, Merge Requests

## Quick Summary
- A branch is a lightweight, movable pointer to a commit — GitLab adds workflow (MRs, protection, approvals) on top of plain Git branching.
- The default branch (usually `main`) represents the stable/deployable state; almost everything else branches off it.
- Protected branches are the real access-control mechanism for "who can change production code" — separate from project member roles.
- Merge Requests (MRs) are GitLab's code-review + merge gate; direct pushes to protected branches are normally disabled.
- Merge conflicts, merge methods (merge commit / squash / fast-forward), and force-push rules are common interview topics because they trip people up in practice.
- CI/CD pipeline content (Docker/Kubernetes) does **not** belong in this file — see file 8 for the flagship build/deploy pipeline; this file is branching mechanics only.

## Core Concepts

### What a branch is
- A named, movable reference to a commit — creating a branch is O(1), it does not copy files.
- Branches let you isolate feature work, bug fixes, releases, and experiments from the stable line of history.

### Default branch
- Created automatically when the project is created (commonly `main`).
- Represents the production-ready/stable state; other branches are typically cut from it.
- Protected by default the moment it's created — no manual step required for baseline protection.

### Branch naming conventions (team convention, not enforced by Git itself)
| Type | Example | Typical use |
|---|---|---|
| Default | `main` | Stable/deployable code |
| Feature | `feature/add-login-page` | New functionality |
| Bugfix | `bugfix/fix-api-timeout` | Non-urgent bug fix |
| Hotfix | `hotfix/fix-db-crash` | Urgent production fix |
| Release | `release/v2.1` | Stabilization before a release |
| Experiment | `experiment/new-theme` | Throwaway spike/prototype |
- GitLab can enforce naming patterns via **push rules** (Premium/Ultimate) or **branch name regex** restrictions on protected branch rules.

### Creating/managing branches
- Web UI: **Repository -> Branches -> New branch**, pick a source branch, name it, create.
- CLI: `git checkout -b <branch>` locally, then `git push origin <branch>` to publish it to GitLab.
- Branches auto-delete-on-merge is an MR setting ("Delete source branch when merge request is accepted") — reduces stale branch clutter.

### Protected branches
- Purpose: prevent unauthorized direct pushes/force-pushes to critical branches (`main`, `release/*`).
- Configurable per rule:
  - **Allowed to merge** — who can merge into the branch (via MR).
  - **Allowed to push and merge** — who can push directly (bypassing MR) — usually restricted to Maintainer/no one.
  - **Allow force push** — off by default for protected branches; enabling it is a deliberate, risky choice.
  - **Require Code Owner approval** — gate merges behind CODEOWNERS sign-off (paid tiers).
  - Wildcards supported for patterns, e.g. `release/*`.
- Default branch is protected automatically on project creation; other branches (e.g. `release/*`) must be protected explicitly.

### Merge Requests (MRs)
- The review + integration mechanism: source branch -> target branch, with diff view, discussion threads, approvals, and CI pipeline status gating.
- Merge methods (set per-project in Settings -> Merge requests):
  - **Merge commit** — always creates a merge commit, preserves full branch history.
  - **Merge commit with semi-linear history** — requires the source branch to be up to date (rebased) before merging.
  - **Fast-forward merge** — no merge commit; requires a linear history, rebasing is the user's responsibility.
- **Squash and merge** — optional, condenses all source-branch commits into one commit on the target branch (independent of merge method).
- Merge conflicts must be resolved (via UI conflict editor for simple cases, or locally via `git merge`/`git rebase`) before GitLab allows the merge.

### Branch permissions
- Governed by two independent layers:
  1. **Project role** (Developer+ needed to push at all).
  2. **Protected branch rule** (who specifically can push/merge to *this* branch, which can be narrower than "all Developers").
- Force-pushing a protected branch requires it to be explicitly allowed in the branch rule, even for Maintainers/Owners.

### ⚠️ Deprecated / Changed
- The UI path for configuring protected branches has moved. Older docs/tutorials say `Settings -> Repository -> Protected Branches`. Current GitLab unifies this under `Settings -> Repository -> Branch rules`, where you pick a branch/pattern and configure protection, approvals, and other rules for it from one place.
- Don't assume "Maintainer can always force-push a protected branch" — force push on a protected branch is denied by default regardless of role unless explicitly allowed on that branch rule.

## Hands-On Labs

### Lab 1: Create a branch from the Web UI
- **Goal:** Create a feature branch without touching the CLI.
- **Steps:**
  1. Project -> **Repository -> Branches -> New branch**.
  2. Name: `feature/add-login-page`.
  3. Source: `main`.
  4. Click **Create branch**.
- **Run it:** Refresh the branches list.
- **Expected result:** `feature/add-login-page` appears, pointing at the same commit as `main`.
- **What this teaches:** Branch creation is instant and cheap — it's just a new pointer, not a copy.

### Lab 2: Create a branch and push from the CLI
- **Goal:** Do the same thing via Git commands.
- **`.gitlab-ci.yml` (if applicable) / Steps:**
  ```bash
  git clone https://gitlab.com/<you>/devops-app.git
  cd devops-app
  git checkout -b feature/user-login
  echo "<h1>Login</h1>" > login.html
  git add login.html
  git commit -m "Add login page skeleton"
  git push origin feature/user-login
  ```
- **Run it:** Check **Repository -> Branches** in GitLab after the push.
- **Expected result:** `feature/user-login` appears with your new commit; GitLab may show a banner offering to create an MR.
- **What this teaches:** `git push origin <branch>` publishes a local branch — GitLab has no concept of the branch until then.

### Lab 3: Open, review, and merge a Merge Request
- **Goal:** Run the full MR review-and-merge flow.
- **Steps:**
  1. **Merge requests -> New merge request**.
  2. Source: `feature/user-login`, Target: `main`.
  3. Add a description, assign a reviewer.
  4. Reviewer approves (or you approve yourself if solo).
  5. Click **Merge**, enable **Delete source branch**.
- **Run it:** Watch the MR page transition from Open to Merged.
- **Expected result:** `main` now contains the commit; `feature/user-login` is deleted automatically.
- **What this teaches:** MRs are the standard integration path — this is what protected branches force you into.

### Lab 4: Protect the default branch and verify direct push is blocked
- **Goal:** See protected-branch enforcement in action.
- **Steps:**
  1. **Settings -> Repository -> Branch rules -> Add branch rule**, target `main`.
  2. Set **Allowed to push and merge** = No one, **Allowed to merge** = Maintainers.
  3. Locally, try: `git checkout main && echo test >> README.md && git commit -am "direct push test" && git push origin main`.
- **Run it:** Observe the push result.
- **Expected result:** Push is rejected with a "protected branch" error from GitLab.
- **What this teaches:** Protected branch rules are enforced server-side, independent of local Git permissions.

### Lab 5: Create a wildcard-protected release branch pattern
- **Goal:** Protect all `release/*` branches with one rule.
- **Steps:**
  1. Create branch `release/v2.1` from `main`.
  2. **Settings -> Repository -> Branch rules -> Add branch rule**, pattern `release/*`.
  3. Set merge/push permissions same as `main`.
  4. Create a second branch `release/v2.2` and confirm it inherits the same protection without a new rule.
- **Run it:** Attempt a direct push to `release/v2.2`.
- **Expected result:** Push is blocked, same as `release/v2.1` — proving the wildcard rule applies retroactively to new matching branches.
- **What this teaches:** Wildcard patterns save you from having to protect every release branch individually.

### Lab 6: Resolve a merge conflict via the UI
- **Goal:** Practice conflict resolution without leaving the browser.
- **Steps:**
  1. On `main`, edit `README.md` line 1 and commit directly (if unprotected) or via a quick MR.
  2. On `feature/user-login` (not yet merged), edit the same line 1 differently and commit.
  3. Open an MR from `feature/user-login` into `main` — GitLab reports a conflict.
  4. Click **Resolve conflicts**, pick a resolution (or hand-edit), commit the resolution.
- **Run it:** Re-check the MR's mergeability status.
- **Expected result:** Conflict badge clears; **Merge** button becomes enabled.
- **What this teaches:** GitLab's inline conflict editor handles simple line-level conflicts without a local `git merge`.

### Lab 7: Resolve a merge conflict locally with rebase
- **Goal:** Practice the CLI equivalent for a conflict too complex for the UI editor.
- **`.gitlab-ci.yml` (if applicable) / Steps:**
  ```bash
  git checkout feature/user-login
  git fetch origin
  git rebase origin/main
  # resolve conflicts in the flagged files
  git add <resolved-files>
  git rebase --continue
  git push --force-with-lease origin feature/user-login
  ```
- **Run it:** Check the MR after the push.
- **Expected result:** MR now shows a linear, conflict-free diff against `main`; pipeline re-runs on the new commits.
- **What this teaches:** `--force-with-lease` (not plain `--force`) is the safe way to update a rebased branch you already pushed — it fails if someone else pushed in the meantime.

### Lab 8: Compare branches and diffs
- **Goal:** Inspect what changed between two branches before opening an MR.
- **Steps:**
  1. **Repository -> Compare**.
  2. Set source = `feature/user-login`, target = `main`.
  3. Review the file-by-file diff.
- **Run it:** Switch the compare direction (swap source/target).
- **Expected result:** Diff inverts — additions become deletions and vice versa, confirming compare is directional.
- **What this teaches:** The Compare view is useful for a pre-MR sanity check or for auditing what a release branch actually contains vs `main`.

### Lab 9: Delete a merged branch and confirm cleanup
- **Goal:** Practice repo hygiene.
- **Steps:**
  1. Merge an MR without checking "Delete source branch" first (leave the branch around).
  2. **Repository -> Branches -> Merged**, locate the stale branch.
  3. Click the delete icon next to it.
- **Run it (CLI alternative):**
  ```bash
  git push origin --delete feature/old-experiment
  git fetch --prune
  ```
- **Expected result:** Branch disappears from GitLab's branch list; `git branch -r` locally no longer lists it after `--prune`.
- **What this teaches:** Merged branches are safe to delete (history lives on via the merge commit) — leaving them around just adds noise.

### Lab 10: Configure a fast-forward-only merge method and observe the effect
- **Goal:** Understand how merge method choice changes repo history shape.
- **Steps:**
  1. **Settings -> Merge requests -> Merge method -> Fast-forward merge**.
  2. Create a feature branch, make 2 commits, open an MR into `main`.
  3. Before merging, deliberately let `main` diverge (merge a different MR first).
  4. Try to merge the original MR.
- **Run it:** Observe GitLab's response.
- **Expected result:** GitLab refuses the fast-forward merge and asks you to rebase the source branch onto the new `main` first — no merge commit is ever created.
- **What this teaches:** Fast-forward-only enforces linear history but pushes the rebase burden onto the contributor, unlike merge-commit mode which handles divergence automatically.

### Lab 11: Set required approvals before merge
- **Goal:** Add a review gate beyond "just protected branch push rules."
- **Steps:**
  1. **Settings -> Merge requests -> Merge request approvals -> Add approval rule**.
  2. Set **Approvals required** = 1, eligible approvers = Maintainers.
  3. Open an MR and try to merge it with zero approvals.
- **Run it:** Have an eligible approver approve, then retry merge.
- **Expected result:** Merge button is disabled/blocked until the approval count is met; becomes enabled immediately after approval.
- **What this teaches:** Branch protection controls *who can merge*; approval rules control *how many people must sign off* — they're independent, stackable controls.

## Common Pitfalls
- Confusing "protected branch" (server-side push/merge restriction) with "project role" (Developer/Maintainer/Owner) — they interact but are separate controls.
- Using `git push --force` on a shared branch instead of `--force-with-lease`, silently overwriting a teammate's commits.
- Forgetting that a new branch matching a wildcard protected pattern (`release/*`) is protected automatically — surprises people who expect to configure each one.
- Assuming fast-forward merge method behaves like merge-commit method when `main` has diverged — it will block the merge instead of auto-merging.
- Not deleting merged feature branches, leading to a branch list nobody trusts.
- Looking for "Protected Branches" in Settings and not finding it — it's now under **Branch rules**.

## Interview Questions & Answers
- **Q: What is a Git/GitLab branch, technically?**
  A: A lightweight, movable pointer to a specific commit — not a copy of the codebase.
- **Q: What's the difference between a protected branch and requiring MR approvals?**
  A: Protected branch controls *who can push/merge at all* (and force-push); approval rules control *how many reviewers* must sign off before an otherwise-permitted merge completes. Both can be active simultaneously.
- **Q: Explain the three GitLab merge methods.**
  A: Merge commit (always creates a merge commit, preserves full history), semi-linear/merge commit (requires source branch rebased first, then merge commit), fast-forward (no merge commit, requires linear history — blocks if diverged).
- **Q: When would you use `git rebase` vs `git merge` to integrate `main` into a feature branch?**
  A: Rebase for a clean, linear history on a not-yet-shared branch; merge when the branch is shared/already pushed and rewriting history would break collaborators.
- **Q: What does `--force-with-lease` do differently from `--force`?**
  A: It aborts the push if the remote branch has commits you haven't fetched (i.e., someone else pushed since your last fetch), preventing silent overwrites; plain `--force` overwrites unconditionally.
- **Q: Scenario — a Maintainer says they can't force-push to `main` even though they're a Maintainer. Why?**
  A: Protected branch rules block force-push by default regardless of role; someone must explicitly enable "Allow force push" on that branch's rule.
- **Q: Scenario — two people edited the same line in the same file on different branches. What are your options to resolve it?**
  A: Resolve inline via GitLab's MR conflict editor (simple cases), or fetch/rebase or merge locally, manually edit the conflicted region, then push the resolution.
- **Q: What happens to a branch's commits after it's merged and deleted?**
  A: They remain part of the repository's history via the merge commit (or squashed commit) on the target branch — deleting the branch ref does not delete the commits, though truly orphaned commits become subject to eventual garbage collection.
- **Q: How do wildcard protected branch patterns work, e.g. `release/*`?**
  A: One rule applies to every branch matching the pattern, including branches created after the rule was set up — no need to protect each release branch individually.
- **Q: What's a sensible branch naming convention for a team and why does it matter?**
  A: Prefix by intent (`feature/`, `bugfix/`, `hotfix/`, `release/`) — not enforced by Git itself, but keeps branch lists scannable and can be enforced via push rules/branch name regex in GitLab.
- **Q: Squash-and-merge — what does it do and when would you avoid it?**
  A: Condenses all commits on the source branch into a single commit on the target branch. Avoid it when you want to preserve granular commit history for bisecting/auditing individual changes.
