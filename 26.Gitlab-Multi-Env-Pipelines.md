# 26. Structuring Multi-Environment Pipelines (Dev → Staging → Prod)

## Quick Summary
- This file is about **structure**: how to organize one pipeline that promotes a release through dev → staging → prod, not about deployment strategy patterns (file 23) or approval-gate mechanics (file 27).
- The core principle is **build once, deploy many**: build a single artifact/image, then promote that *same* artifact through each environment — never rebuild per environment.
- Environment-scoped CI/CD variables let the same variable name (`API_URL`, `DB_HOST`, ...) resolve to a different value depending on which environment the job deploys to.
- `needs:` chains between environment-specific jobs (`deploy_staging: needs: [deploy_dev]`) control **promotion order**, not just speed — staging can't start until dev's job exists in the graph.
- Each environment should have its own infrastructure (separate EC2 hosts, separate DB, separate credentials) — sharing infra between environments defeats the purpose of having them.
- Interview framing: "how do you structure a pipeline for multiple environments?" and "what does build once, deploy many mean and why does it matter?" both live here.

## Core Concepts

### Build once, deploy many
- Build and tag the artifact/image **exactly once** per pipeline run (e.g. `$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA`), in the `build` stage.
- Every environment's deploy job references that same tag — dev, staging, and prod all end up running bit-for-bit the same image, just at different times with different config.
- Why it matters: rebuilding per environment risks subtle differences (dependency resolution at a different time, different base image digest) between what was tested in staging and what ships to prod — defeats the purpose of staging as a gate.
- "Different config per environment" is handled by environment-scoped variables (below) or runtime environment variables passed to `docker run`, not by rebuilding the image with different baked-in values.

### Environment-scoped variables
- GitLab CI/CD variables can be scoped to specific environments in Settings > CI/CD > Variables: the same variable **name** (e.g. `API_URL`) can have different **values** depending on `environment_scope`.
- Scope supports exact names (`production`) and wildcards (`review/*`, `staging/*`, `*` for all).
- A job only sees the value whose scope matches the `environment: name:` it declares — so `deploy_staging` and `deploy_prod` can both read `$API_URL` and get different results automatically, no `if/else` branching in the script.
- Caveat: don't rely on environment-scoped variables inside `rules:` or `include:` — those are evaluated before the environment context is fully resolved, so the value may not be what you expect at that stage.

### `needs:` chaining to control promotion order
- Beyond speed (file 22's angle), `needs:` between deploy jobs enforces **which environment must succeed before the next is even offered**.
- `deploy_staging: needs: [deploy_dev]` means staging's job doesn't appear as runnable until dev's job has completed — this is promotion-order control, distinct from approval (file 27 covers *who* is allowed to click the button; this is *what order* the buttons unlock in).
- Chaining `deploy_prod: needs: [deploy_staging]` (not `deploy_dev`) ensures prod can only be reached via a successful staging deploy — skipping straight from dev to prod isn't possible even manually.

### Environment tiers and naming
- GitLab infers a deployment tier from the environment name (`dev`/`review` → development, `staging`/`demo` → staging, `prod`/`live` → production, etc.) unless overridden with `deployment_tier:`.
- Consistent naming (`dev`, `staging`, `production`) keeps this automatic classification correct, which feeds the Environments dashboard and deployment frequency metrics.

### Separate infrastructure per environment
- Each environment should point at its own EC2 host(s)/cluster/database — never let staging and prod share a target server, or a "staging" deploy silently affects production.
- Structurally this means separate CI/CD variables per environment (`DEV_HOST`, `STAGING_HOST`, `PROD_HOST`), not a single `$HOST` toggled by branch logic.

## Hands-On Labs

### Lab 1: The base build-once pipeline skeleton
- **Goal:** Establish the single-build foundation everything else in this file promotes.
- **`.gitlab-ci.yml`:**
```yaml
image: docker:latest

services:
  - docker:dind

variables:
  DOCKER_TLS_CERTDIR: "/certs"
  IMAGE_NAME: deepakyadav/devops-app
  IMAGE_TAG: $CI_COMMIT_SHORT_SHA

stages:
  - build
  - push
  - deploy

build_image:
  stage: build
  script:
    - docker build -t $IMAGE_NAME:$IMAGE_TAG -t $IMAGE_NAME:latest .

push_image:
  stage: push
  script:
    - docker login -u "$DOCKER_USERNAME" -p "$DOCKER_PASSWORD"
    - docker push $IMAGE_NAME:$IMAGE_TAG
    - docker push $IMAGE_NAME:latest
  needs: ["build_image"]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```
- **Run it:** Push to `main`.
- **Expected result:** Exactly one build, tagged with the immutable SHA and `latest`, pushed once.
- **What this teaches:** This single tagged image is what every environment below will deploy — nothing downstream rebuilds it.

### Lab 2: Deploy to dev automatically (first promotion step)
- **Goal:** Wire up the first environment in the chain, deploying the Lab 1 image unchanged.
- **`.gitlab-ci.yml`:**
```yaml
deploy_dev:
  stage: deploy
  image: alpine:latest
  environment:
    name: dev
    url: http://$DEV_HOST
  before_script:
    - apk add --no-cache openssh
    - echo "$SSH_PRIVATE_KEY" > private_key.pem && chmod 600 private_key.pem
  script:
    - ssh -o StrictHostKeyChecking=no -i private_key.pem $DEV_USER@$DEV_HOST "docker pull $IMAGE_NAME:$IMAGE_TAG && docker stop devops-app || true && docker rm devops-app || true && docker run -d -p 80:80 --name devops-app $IMAGE_NAME:$IMAGE_TAG"
  needs: ["push_image"]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```
- **Run it:** Push to `main` with `DEV_HOST`/`DEV_USER` set.
- **Expected result:** Dev pulls and runs `$IMAGE_TAG` (the SHA tag) — not `latest` — making explicit exactly which build is running where.
- **What this teaches:** Deploying by the immutable SHA tag (not `latest`) is what makes "build once, deploy many" auditable — you can always tell which commit is live in which environment.

### Lab 3: Environment-scoped variables — same name, different value
- **Goal:** Let `deploy_dev` and `deploy_staging` both reference `$API_URL` and get environment-appropriate values automatically.
- **Setup (UI, not YAML):** Settings > CI/CD > Variables > Add variable `API_URL`, value `https://api-dev.example.com`, Environment scope `dev`. Add a second variable also named `API_URL`, value `https://api-staging.example.com`, Environment scope `staging`.
- **`.gitlab-ci.yml`:**
```yaml
deploy_dev:
  stage: deploy
  environment:
    name: dev
  script:
    - echo "Deploying with API_URL=$API_URL"
  needs: ["push_image"]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'

deploy_staging:
  stage: deploy
  environment:
    name: staging
  script:
    - echo "Deploying with API_URL=$API_URL"
  needs: ["deploy_dev"]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
```
- **Run it:** Push to `main`, run both jobs, compare their logs.
- **Expected result:** `deploy_dev`'s log prints the dev URL; `deploy_staging`'s log prints the staging URL — same `$API_URL` reference, different resolved value, with zero conditional logic in the script.
- **What this teaches:** Environment scoping moves per-environment config out of the pipeline script and into GitLab settings — the job doesn't need to know which environment it's in to pick the right value.

### Lab 4: `needs:` chaining to enforce promotion order
- **Goal:** Make staging unreachable until dev has actually succeeded, and prod unreachable until staging has.
- **`.gitlab-ci.yml`:**
```yaml
deploy_dev:
  stage: deploy
  environment:
    name: dev
  script:
    - echo "Deploy to dev"
  needs: ["push_image"]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'

deploy_staging:
  stage: deploy
  environment:
    name: staging
  script:
    - echo "Deploy to staging"
  needs: ["deploy_dev"]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual

deploy_prod:
  stage: deploy
  environment:
    name: production
  script:
    - echo "Deploy to production"
  needs: ["deploy_staging"]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
```
- **Run it:** Push to `main`; try clicking Play on `deploy_prod` before `deploy_staging` has run.
- **Expected result:** `deploy_prod` isn't runnable (blocked) until `deploy_staging` completes successfully, which itself waits on `deploy_dev`.
- **What this teaches:** `needs:` chaining is what makes "dev → staging → prod" an actual enforced order in the pipeline graph, not just a naming convention three unrelated jobs happen to follow.

### Lab 5: Full 3-environment pipeline (dev auto / staging manual / prod manual+protected)
- **Goal:** Assemble the complete running example this file centers on.
- **`.gitlab-ci.yml`:**
```yaml
image: docker:latest

services:
  - docker:dind

variables:
  DOCKER_TLS_CERTDIR: "/certs"
  IMAGE_NAME: deepakyadav/devops-app
  IMAGE_TAG: $CI_COMMIT_SHORT_SHA

stages:
  - build
  - push
  - deploy

build_image:
  stage: build
  script:
    - docker build -t $IMAGE_NAME:$IMAGE_TAG .

push_image:
  stage: push
  script:
    - docker login -u "$DOCKER_USERNAME" -p "$DOCKER_PASSWORD"
    - docker push $IMAGE_NAME:$IMAGE_TAG
  needs: ["build_image"]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'

.deploy_template:
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh
    - echo "$SSH_PRIVATE_KEY" > private_key.pem && chmod 600 private_key.pem

deploy_dev:
  extends: .deploy_template
  stage: deploy
  environment:
    name: dev
    url: http://$DEV_HOST
  script:
    - ssh -o StrictHostKeyChecking=no -i private_key.pem $DEV_USER@$DEV_HOST "docker pull $IMAGE_NAME:$IMAGE_TAG && docker stop devops-app || true && docker rm devops-app || true && docker run -d -p 80:80 --name devops-app $IMAGE_NAME:$IMAGE_TAG"
  needs: ["push_image"]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'

deploy_staging:
  extends: .deploy_template
  stage: deploy
  environment:
    name: staging
    url: http://$STAGING_HOST
  script:
    - ssh -o StrictHostKeyChecking=no -i private_key.pem $STAGING_USER@$STAGING_HOST "docker pull $IMAGE_NAME:$IMAGE_TAG && docker stop devops-app || true && docker rm devops-app || true && docker run -d -p 80:80 --name devops-app $IMAGE_NAME:$IMAGE_TAG"
  needs: ["deploy_dev"]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual

deploy_prod:
  extends: .deploy_template
  stage: deploy
  environment:
    name: production
    url: http://$PROD_HOST
  script:
    - ssh -o StrictHostKeyChecking=no -i private_key.pem $PROD_USER@$PROD_HOST "docker pull $IMAGE_NAME:$IMAGE_TAG && docker stop devops-app || true && docker rm devops-app || true && docker run -d -p 80:80 --name devops-app $IMAGE_NAME:$IMAGE_TAG"
  needs: ["deploy_staging"]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
```
- **Run it:** Set `DEV_HOST`/`STAGING_HOST`/`PROD_HOST` (+ matching `*_USER`), push to `main`. Protect the `production` environment in Settings > CI/CD > Protected environments (mechanics detailed in file 27).
- **Expected result:** `deploy_dev` runs automatically; `deploy_staging` waits for a click after dev succeeds; `deploy_prod` waits for a click after staging succeeds, and only users allowed on the protected `production` environment can trigger it.
- **What this teaches:** This is the canonical multi-environment structure the rest of this file's labs, and file 27's approval-gate labs, build on — note it uses `extends: .deploy_template` to avoid repeating the SSH setup three times (see file 22 for `extends:` mechanics).

### Lab 6: Separate infrastructure per environment (structural check)
- **Goal:** Make the "never share infra between environments" principle concrete and verifiable.
- **`.gitlab-ci.yml`:** Same as Lab 5, but add a guard job.
```yaml
verify_env_separation:
  stage: deploy
  script:
    - |
      if [ "$DEV_HOST" = "$STAGING_HOST" ] || [ "$STAGING_HOST" = "$PROD_HOST" ] || [ "$DEV_HOST" = "$PROD_HOST" ]; then
        echo "ERROR: two environments point at the same host!"
        exit 1
      fi
      echo "Environment hosts are all distinct — OK"
  needs: []
```
- **Run it:** Push with `DEV_HOST`/`STAGING_HOST`/`PROD_HOST` set to the same value (misconfiguration), then with distinct values.
- **Expected result:** First run fails the guard job with a clear error; second run passes.
- **What this teaches:** A cheap pipeline-level safety check that catches the single most damaging multi-env misconfiguration (accidentally pointing two environments at the same server) before any deploy job runs.

### Lab 7: Promote without rebuilding — retag/relabel only
- **Goal:** Make explicit that "promotion" to the next environment involves no new build step.
- **`.gitlab-ci.yml`:**
```yaml
promote_to_staging:
  stage: deploy
  image: docker:latest
  services:
    - docker:dind
  script:
    - docker login -u "$DOCKER_USERNAME" -p "$DOCKER_PASSWORD"
    - docker pull $IMAGE_NAME:$IMAGE_TAG
    - docker tag $IMAGE_NAME:$IMAGE_TAG $IMAGE_NAME:staging-verified
    - docker push $IMAGE_NAME:staging-verified
  needs: ["deploy_staging"]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
```
- **Run it:** Run after `deploy_staging` succeeds.
- **Expected result:** A new tag (`staging-verified`) is pushed pointing at the *same image digest* already tested in staging — `docker build` never runs again.
- **What this teaches:** "Promotion" can be as lightweight as a new tag on an existing, already-tested image — a useful pattern for marking exactly which build passed staging, without touching the build stage at all.

### Lab 8: Structuring per-environment jobs with `include:` (pointer)
- **Goal:** See how multi-environment structure scales past 3 environments without one giant file.
- **`.gitlab-ci.yml`:**
```yaml
include:
  - local: 'ci/deploy-dev.yml'
  - local: 'ci/deploy-staging.yml'
  - local: 'ci/deploy-prod.yml'
```
- **Run it / reference:** See file 21 for full `include:` mechanics and merge-order rules.
- **Expected result:** Same merged pipeline as Lab 5, split into one file per environment for readability as the environment count grows (e.g. adding `qa`, `perf`, regional prod splits).
- **What this teaches:** Structural scaling technique — don't re-derive `include:` mechanics here, just recognize when a multi-env pipeline has grown large enough to warrant splitting by environment.

### Lab 9: Rollback across environments using the same promoted tag
- **Goal:** Roll back any single environment to a previous known-good build without touching the others.
- **`.gitlab-ci.yml`:**
```yaml
rollback_staging:
  stage: deploy
  image: alpine:latest
  variables:
    ROLLBACK_TAG: ""
  before_script:
    - apk add --no-cache openssh
    - echo "$SSH_PRIVATE_KEY" > private_key.pem && chmod 600 private_key.pem
  script:
    - test -n "$ROLLBACK_TAG" || (echo "Set ROLLBACK_TAG" && exit 1)
    - ssh -o StrictHostKeyChecking=no -i private_key.pem $STAGING_USER@$STAGING_HOST "docker pull $IMAGE_NAME:$ROLLBACK_TAG && docker stop devops-app || true && docker rm devops-app || true && docker run -d -p 80:80 --name devops-app $IMAGE_NAME:$ROLLBACK_TAG"
  environment:
    name: staging
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
```
- **Run it:** Trigger manually with `ROLLBACK_TAG` set to an older commit's SHA.
- **Expected result:** Staging alone reverts to the specified build; dev and prod are untouched.
- **What this teaches:** Because every environment deploys by immutable SHA tag rather than `latest`, any single environment can be rolled back independently — a direct payoff of the build-once, deploy-by-SHA structure established in Lab 1/2.

### Lab 10: Deployment tier verification across environments
- **Goal:** Confirm GitLab classifies each environment into the expected tier for dashboard/reporting purposes.
- **`.gitlab-ci.yml`:**
```yaml
deploy_dev:
  stage: deploy
  environment:
    name: dev
    deployment_tier: development
  script:
    - echo "Deploying to dev"

deploy_staging:
  stage: deploy
  environment:
    name: staging
    deployment_tier: staging
  script:
    - echo "Deploying to staging"

deploy_prod:
  stage: deploy
  environment:
    name: production
    deployment_tier: production
  script:
    - echo "Deploying to production"
```
- **Run it:** Push, then check Operate > Environments — each environment should display its correct tier badge.
- **Expected result:** Dev/staging/prod show as development/staging/production tiers respectively, matching what naming alone would have inferred automatically.
- **What this teaches:** `deployment_tier:` is available for when your naming convention doesn't already match GitLab's auto-detection patterns (e.g. an environment literally named `blue` or `green` wouldn't auto-classify correctly).

## Common Pitfalls
- Rebuilding the image separately for each environment "just to be safe" — defeats build-once-deploy-many and risks staging/prod running genuinely different artifacts.
- Deploying by `latest` tag in every environment — makes it impossible to tell which commit is actually running where, and breaks single-environment rollback.
- Pointing two environments at the same server/database "temporarily" — this is the most common way a "staging" deploy accidentally breaks production.
- Using environment-scoped variables inside `rules:` conditions — the scoped value may not be resolved yet at that evaluation point; keep environment-scoped variables inside `script:`/`environment:` only.
- Skipping `needs:` chaining between deploy jobs — without it, a rushed engineer could click "deploy prod" before staging has even run.
- Letting the pipeline structure sprawl to one giant file as environment count grows instead of splitting via `include:` (file 21).

## Interview Questions & Answers
- **Q: What does "build once, deploy many" mean and why does it matter?**
  A: Build and tag the artifact/image exactly once per pipeline run, then deploy that identical artifact to every environment; it matters because it guarantees what was tested in staging is bit-for-bit what ships to production.
- **Q: How do you give different environments different config values without rebuilding?**
  A: Environment-scoped CI/CD variables — same variable name, different value per `environment_scope`, resolved automatically based on the job's `environment: name:`.
- **Q: How do you enforce that staging must succeed before prod can be deployed?**
  A: Chain `needs:` between the deploy jobs (`deploy_prod: needs: [deploy_staging]`) so the prod job isn't even reachable until staging's job has completed.
- **Q: What's the risk of tagging every environment's deploy with `latest`?**
  A: You lose the ability to tell which commit is running in which environment, and single-environment rollback becomes impossible without a separate tracking mechanism.
- **Q: Scenario: you need to add a 4th environment (e.g. `qa`) between dev and staging — what changes?**
  A: Add a `deploy_qa` job with its own environment-scoped variables and infra, insert it into the `needs:` chain (`deploy_staging: needs: [deploy_qa]`), and update `deploy_dev`'s consumer accordingly — no change to the build/push stages.
- **Q: Scenario: dev and staging accidentally point at the same EC2 host — what's the actual risk, not just "it's messy"?**
  A: A staging-only deploy (or a bad staging test) can take down what's supposed to be an isolated dev/staging boundary — worse, if staging's host is reused for prod by mistake, a "staging" click deploys straight to production traffic.
- **Q: Why avoid environment-scoped variables inside `rules:`?**
  A: `rules:` is evaluated at pipeline-creation time, potentially before the environment context needed to resolve a scoped variable is fully available — GitLab explicitly warns against relying on scoped variables there.
- **Q: What structural tool helps once you have many environments/services in one repo?**
  A: `include:` to split per-environment (or per-service) job definitions into separate files, keeping the top-level `.gitlab-ci.yml` a short manifest (file 21).
- **Q: Is `needs:` chaining the same thing as an approval gate?**
  A: No — `needs:` controls ordering (staging job isn't reachable until dev succeeds); approval gates (file 27) control *who* is allowed to click a reachable manual job, e.g. via protected environments.
- **Q: How do you roll back just one environment without affecting the others?**
  A: Redeploy that environment's job with an older immutable SHA tag as the target — since environments are deployed independently by SHA, no rebuild or other-environment change is required.
