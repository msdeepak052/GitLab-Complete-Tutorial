# 23. GitLab Deployment Strategy Patterns

## Quick Summary
- This file is about **deployment strategy patterns** — rolling, recreate, blue-green, canary — and **when** a deploy runs (automatic vs. manual), not the base pipeline skeleton itself.
- The underlying dev/staging/prod pipeline structure (build once, promote, environment scoping) is covered in file 26; approval-gate mechanics (protected environments, required approvers) are covered in file 27 — this file's labs focus purely on implementing each *strategy*.
- Review app mechanics (`environment:`, `on_stop`) are explained in full in file 16 — referenced briefly here, not re-derived.
- Recreate = simplest/fastest but causes downtime; rolling = gradual replacement, no full downtime; blue-green = instant, reversible cutover between two full environments; canary = partial rollout to catch problems before 100% exposure.
- `when: manual` is the core primitive for "requires a human to trigger" — combine with `rules:` to decide *which branch* even offers that manual button.
- Interview framing: "how would you reduce blast radius of a bad deploy?" maps directly to canary/blue-green; "how do you avoid downtime during deploy?" maps to rolling/blue-green vs. recreate.

## Core Concepts

### Strategy comparison

| Strategy | Downtime | Rollback speed | Infra cost | Complexity |
|---|---|---|---|---|
| Recreate | Yes (stop old, then start new) | Slow (redeploy old version) | Lowest (1 environment) | Lowest |
| Rolling | None/minimal (replace instances gradually) | Medium (roll back gradually) | Low-medium | Medium |
| Blue-green | None (instant traffic swap) | Instant (swap back) | High (2 full environments) | Medium-high |
| Canary | None (partial exposure) | Fast (stop rollout, revert canary) | Medium (extra capacity for canary slice) | Highest |

### Automatic vs. manual triggering
- Automatic: job has no `when: manual` — runs as soon as its `rules:` match and prior stage/`needs:` are satisfied. Typical for dev/staging.
- Manual: `when: manual` makes GitLab create the job in a "blocked/manual" state; a human must click Play in the UI, pipeline view, or Environments page. Typical for production.
- `rules:` and `when: manual` compose: `rules:` decides *if the job exists at all* for this ref; `when: manual` (as a rule-level or job-level attribute) decides whether it starts automatically or waits for a click once it exists.
- `allow_failure:` matters for manual jobs: default for a `when: manual` job is `allow_failure: true` in many contexts, meaning the pipeline can go "green" without that manual job ever running — set `allow_failure: false` if a deploy must actually happen for the pipeline to be considered fully successful (see file 27 for using this as a hard gate).

### Recreate strategy
- Stop the running version, then start the new one — simplest possible deploy, but there's a window with nothing serving traffic.
- Implemented as a single deploy job: `docker stop` / `docker rm` / `docker run` (or systemd restart) in sequence.

### Rolling strategy
- Replace instances/containers a few at a time, keeping some old-version capacity serving traffic throughout.
- On plain EC2/VM fleets, implemented as a loop over a host list with a health check between each; on Kubernetes, this is the default `Deployment` rollout behavior.

### Blue-green strategy
- Maintain two identical environments ("blue" = current live, "green" = new version); deploy to the idle one, verify it, then swap traffic (load balancer target group, DNS, or reverse-proxy symlink) to it.
- Old environment stays up as an instant rollback target — just swap traffic back.
- Costs double the standing infrastructure while both environments exist.

### Canary strategy
- Route a small percentage of traffic (or a small subset of instances) to the new version first; watch metrics/errors; then progressively increase the percentage until 100%, or abort and roll back if problems appear.
- GitLab's built-in "incremental rollout" pattern (historically part of Auto DevOps for Kubernetes) implements this as a sequence of jobs, each bumping `ROLLOUT_PERCENTAGE`, using `when: manual` or `when: delayed` between steps.
- On non-Kubernetes infra (e.g. plain EC2), canary is typically approximated by deploying to a subset of instances behind the same load balancer and monitoring before continuing.

## Hands-On Labs

### Lab 1: Automatic deploy on push (rules-based, not `only:`)
- **Goal:** Deploy to staging automatically whenever `develop` is updated, using `rules:` instead of the deprecated `only:`.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - deploy

build_job:
  stage: build
  script:
    - echo "Building app..."

deploy_auto:
  stage: deploy
  script:
    - echo "Deploying automatically to staging..."
  environment:
    name: staging
    url: https://staging.example.com
  rules:
    - if: '$CI_COMMIT_BRANCH == "develop"'
```
- **Run it:** Push to `develop`, then to a feature branch.
- **Expected result:** `deploy_auto` runs with no human interaction on `develop`; the job doesn't exist at all on other branches.
- **What this teaches:** `rules: if:` as the current, non-deprecated way to scope automatic deploys to a branch.

### Lab 2: Manual deploy gate for production
- **Goal:** Require a human click before deploying to production.
- **`.gitlab-ci.yml`:**
```yaml
deploy_prod:
  stage: deploy
  script:
    - echo "Deploying to production..."
  environment:
    name: production
    url: https://prod.example.com
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
```
- **Run it:** Push to `main`, open the pipeline, observe `deploy_prod` sitting in a blocked/manual state, then click Play.
- **Expected result:** Pipeline stage shows a "play" icon; nothing deploys until clicked; after clicking, deployment proceeds and is recorded against the `production` environment.
- **What this teaches:** Putting `when: manual` inside the matching `rules:` entry (rather than as a separate job attribute) so it's manual *only* on the branch where the rule matches.

### Lab 3: `when: on_success` vs `when: manual` on the same job, compared
- **Goal:** Directly observe the behavioral difference triggering identical deploy logic two ways.
- **`.gitlab-ci.yml`:**
```yaml
deploy_staging_auto:
  stage: deploy
  script:
    - echo "Deploying build $CI_COMMIT_SHORT_SHA"
  environment:
    name: staging
  rules:
    - if: '$CI_COMMIT_BRANCH == "develop"'
      when: on_success   # default; explicit here for comparison

deploy_staging_manual:
  stage: deploy
  script:
    - echo "Deploying build $CI_COMMIT_SHORT_SHA"
  environment:
    name: staging-manual-copy
  rules:
    - if: '$CI_COMMIT_BRANCH == "develop"'
      when: manual
```
- **Run it:** Push to `develop`, watch both jobs appear.
- **Expected result:** `deploy_staging_auto` starts and finishes without intervention; `deploy_staging_manual` sits waiting for a Play click even though its `rules:` condition matched identically.
- **What this teaches:** `rules: if:` decides *whether the job exists*; `when:` (default `on_success`) decides *whether it starts by itself* once it exists — two independent knobs.

### Lab 4: Recreate strategy (stop-then-start, with the downtime visible)
- **Goal:** Implement and observe the simplest deploy strategy's downtime window.
- **`.gitlab-ci.yml`:**
```yaml
deploy_recreate:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh curl
    - echo "$SSH_PRIVATE_KEY" > key.pem && chmod 600 key.pem
  script:
    - ssh -o StrictHostKeyChecking=no -i key.pem $EC2_USER@$EC2_HOST "docker stop devops-app || true"
    - ssh -o StrictHostKeyChecking=no -i key.pem $EC2_USER@$EC2_HOST "docker rm devops-app || true"
    - sleep 5   # simulate the visible downtime window
    - ssh -o StrictHostKeyChecking=no -i key.pem $EC2_USER@$EC2_HOST "docker run -d -p 80:80 --name devops-app $IMAGE_NAME:latest"
  environment:
    name: staging
  rules:
    - if: '$CI_COMMIT_BRANCH == "develop"'
```
- **Run it:** Push, and in a separate terminal `curl` the app's URL repeatedly during the deploy.
- **Expected result:** A few seconds of connection failures between "stop" and the new container coming up — the recreate strategy's defining tradeoff, made visible.
- **What this teaches:** Recreate is simple but has a real, measurable downtime window — the baseline every other strategy is trying to eliminate.

### Lab 5: Rolling deploy across multiple hosts
- **Goal:** Replace instances one at a time behind a shared load balancer, keeping capacity up throughout.
- **`.gitlab-ci.yml`:**
```yaml
deploy_rolling:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh curl
    - echo "$SSH_PRIVATE_KEY" > key.pem && chmod 600 key.pem
  script:
    - |
      for HOST in $HOST_1 $HOST_2 $HOST_3; do
        echo "Rolling deploy to $HOST"
        ssh -o StrictHostKeyChecking=no -i key.pem $EC2_USER@$HOST "docker pull $IMAGE_NAME:latest && docker stop devops-app || true && docker rm devops-app || true && docker run -d -p 80:80 --name devops-app $IMAGE_NAME:latest"
        sleep 5
        curl -f http://$HOST/health || (echo "Health check failed on $HOST, aborting rollout" && exit 1)
      done
  environment:
    name: production
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
```
- **Run it:** Set `HOST_1`/`HOST_2`/`HOST_3` as CI/CD variables pointing at 3 instances behind the same load balancer; trigger the manual job.
- **Expected result:** Each host is updated and health-checked in turn; the loop aborts on the first failing health check, leaving the remaining hosts on the old version instead of a fully broken fleet.
- **What this teaches:** Rolling deploys trade deploy speed for continuous capacity, and a per-host health check turns it into a self-limiting rollout.

### Lab 6: Blue-green deploy pair with a traffic swap
- **Goal:** Deploy to an idle "green" target and cut traffic over only after it's verified.
- **`.gitlab-ci.yml`:**
```yaml
deploy_green:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh curl
    - echo "$SSH_PRIVATE_KEY" > key.pem && chmod 600 key.pem
  script:
    - ssh -o StrictHostKeyChecking=no -i key.pem $EC2_USER@$GREEN_HOST "docker pull $IMAGE_NAME:latest && docker stop devops-app || true && docker rm devops-app || true && docker run -d -p 80:80 --name devops-app $IMAGE_NAME:latest"
    - curl -f http://$GREEN_HOST/health
  environment:
    name: production-green
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'

swap_to_green:
  stage: deploy
  script:
    - echo "Swapping load balancer target group from blue to green..."
    - aws elbv2 modify-listener --listener-arn $LISTENER_ARN --default-actions Type=forward,TargetGroupArn=$GREEN_TARGET_GROUP_ARN
  environment:
    name: production
  needs: ["deploy_green"]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
```
- **Run it:** Push to `main`; `deploy_green` runs and health-checks automatically; click Play on `swap_to_green` once satisfied.
- **Expected result:** The new version is fully live and verified on `green` *before* any real user traffic reaches it; the swap itself is a near-instant load-balancer config change.
- **What this teaches:** Splitting "deploy" from "cut traffic" into two jobs is what makes blue-green reversible and low-risk — rollback is just swapping the target group back.

### Lab 7: Instant rollback via re-swap
- **Goal:** Roll back a bad blue-green release in seconds.
- **`.gitlab-ci.yml`:**
```yaml
rollback_to_blue:
  stage: deploy
  script:
    - echo "Reverting load balancer to previous (blue) target group..."
    - aws elbv2 modify-listener --listener-arn $LISTENER_ARN --default-actions Type=forward,TargetGroupArn=$BLUE_TARGET_GROUP_ARN
  environment:
    name: production
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
```
- **Run it:** After Lab 6's swap, run this job from the pipeline (or re-run it from the Environments page).
- **Expected result:** Traffic reverts to the untouched "blue" instance, which never stopped running the previous version.
- **What this teaches:** Blue-green's real payoff — rollback is a config change, not a redeploy, because the old version was never torn down.

### Lab 8: Canary — partial rollout to a subset of instances
- **Goal:** Expose the new version to a small slice of traffic before a full rollout.
- **`.gitlab-ci.yml`:**
```yaml
deploy_canary:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh curl
    - echo "$SSH_PRIVATE_KEY" > key.pem && chmod 600 key.pem
  script:
    - echo "Deploying canary to 1 of 4 instances ($CANARY_HOST)"
    - ssh -o StrictHostKeyChecking=no -i key.pem $EC2_USER@$CANARY_HOST "docker pull $IMAGE_NAME:latest && docker stop devops-app || true && docker rm devops-app || true && docker run -d -p 80:80 --name devops-app $IMAGE_NAME:latest"
  environment:
    name: production-canary
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'

promote_canary_to_full:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh
    - echo "$SSH_PRIVATE_KEY" > key.pem && chmod 600 key.pem
  script:
    - |
      for HOST in $HOST_2 $HOST_3 $HOST_4; do
        ssh -o StrictHostKeyChecking=no -i key.pem $EC2_USER@$HOST "docker pull $IMAGE_NAME:latest && docker stop devops-app || true && docker rm devops-app || true && docker run -d -p 80:80 --name devops-app $IMAGE_NAME:latest"
      done
  environment:
    name: production
  needs: ["deploy_canary"]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
```
- **Run it:** Push to `main`; `deploy_canary` runs automatically against 1 of 4 instances; monitor error rates/logs on that instance; click Play on `promote_canary_to_full` to roll out to the remaining 3.
- **Expected result:** Only 25% of capacity runs the new version until a human confirms it's healthy, at which point the rest follow.
- **What this teaches:** Canary limits blast radius by exposing a minority of traffic first — the manual gate between canary and full rollout is what lets a human catch a bad release before it reaches everyone.

### Lab 9: Timed incremental rollout (percentage-based, GitLab's built-in pattern)
- **Goal:** Use GitLab's timed-rollout-job pattern to step through rollout percentages automatically, with delays.
- **`.gitlab-ci.yml`:**
```yaml
.canary_rollout:
  stage: deploy
  environment:
    name: production
  script:
    - echo "Rolling out to $ROLLOUT_PERCENTAGE% of capacity"

rollout 10%:
  extends: .canary_rollout
  when: delayed
  start_in: 1 minutes
  variables:
    ROLLOUT_PERCENTAGE: "10"
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'

rollout 50%:
  extends: .canary_rollout
  when: delayed
  start_in: 1 minutes
  variables:
    ROLLOUT_PERCENTAGE: "50"
  needs: ["rollout 10%"]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'

rollout 100%:
  extends: .canary_rollout
  variables:
    ROLLOUT_PERCENTAGE: "100"
  needs: ["rollout 50%"]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
```
- **Run it:** Push to `main`; watch `rollout 10%` fire automatically after a 1-minute delay, then `rollout 50%` after another delay, then `rollout 100%` waiting for a manual click.
- **Expected result:** A staged rollout timeline entirely expressed in `.gitlab-ci.yml`, with the final jump to 100% requiring explicit approval.
- **What this teaches:** `when: delayed` + `start_in:` automate the "wait and watch" part of canary between steps, while the last step stays a manual gate — combining automatic pacing with a human final check.

### Lab 11: Combining strategies in one realistic pipeline
- **Goal:** See automatic staging + manual, health-checked production deploy together.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - deploy

build_job:
  stage: build
  script:
    - echo "Build app"

deploy_staging:
  stage: deploy
  script:
    - echo "Deploy to staging"
  environment:
    name: staging
  rules:
    - if: '$CI_COMMIT_BRANCH == "develop"'

deploy_production:
  stage: deploy
  script:
    - echo "Deploy to production"
    - curl -f https://prod.example.com/health
  environment:
    name: production
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
```
- **Run it:** Push to `develop` (auto staging), then to `main` (manual prod with a post-deploy health check).
- **Expected result:** Staging updates on every `develop` push with zero clicks; production only updates when explicitly approved, and the job itself verifies health before finishing.
- **What this teaches:** Real pipelines combine automatic/manual triggering per-environment rather than picking one policy globally — the pattern file 26 builds on for full dev/staging/prod structure.

## Common Pitfalls
- Treating "recreate" as acceptable for production without measuring the downtime window it actually causes.
- Building blue-green without a real health check before the traffic swap — you've just automated deploying broken code to 100% of users faster.
- Canary rollouts with no monitoring step between stages — a canary you don't watch isn't providing any protection, it's just a slower recreate.
- Forgetting `allow_failure: false` on a `when: manual` deploy job that must actually run for the pipeline to be "done" — otherwise the pipeline can report success while production was never deployed (see file 27).
- Re-deriving `on_stop`/review-app mechanics from scratch in multiple files instead of treating file 16 as the source of truth.
- Using `only:`/`except:` for strategy branching instead of `rules:`, losing the ability to combine branch conditions with per-rule `when:`.

## Interview Questions & Answers
- **Q: What's the difference between rolling and blue-green deployment?**
  A: Rolling gradually replaces instances within one environment (no full duplicate infra, some old+new coexistence); blue-green keeps two complete environments and switches traffic atomically between them (higher infra cost, instant rollback).
- **Q: Why would you choose recreate despite the downtime?**
  A: Simplicity, and it's fine for internal/dev tools or apps that can tolerate a brief restart, and it's cheaper (only one running environment).
- **Q: How do you implement a manual production gate in GitLab CI?**
  A: `when: manual` on the deploy job's rule (or job level), typically combined with `environment:` + a protected environment for access control (file 27).
- **Q: What does `allow_failure` default to for manual jobs, and why does it matter for deployment strategies?**
  A: It commonly defaults to `true` for manual jobs in many rule contexts, meaning the overall pipeline can succeed without the deploy running — set `allow_failure: false` explicitly when a deploy must happen for the pipeline to be truly "done."
- **Q: How would you implement canary deployment without Kubernetes?**
  A: Deploy to a subset of instances behind the same load balancer/target group, monitor, then progressively deploy to the rest — same idea as GitLab's built-in timed incremental rollout jobs, just against EC2 hosts instead of pods.
- **Q: What makes blue-green rollback fast compared to rolling?**
  A: The previous version's environment was never torn down — rollback is a traffic/config swap, not a redeploy.
- **Q: Scenario: your canary deployment shows elevated error rates on the canary instance — what do you do in the pipeline?**
  A: Don't run the promote/full-rollout job (leave the manual gate un-clicked); redeploy the previous known-good image to the canary instance to fully revert that slice.
- **Q: Scenario: you need zero-downtime deploys but can't afford a second full production environment — what's your best option?**
  A: Rolling deploy across existing instances behind a load balancer, with a health check between each instance, rather than blue-green's full environment duplication.
- **Q: How do `rules:` and `when: manual` interact?**
  A: `rules:` decides whether the job exists in the pipeline at all for this ref; `when:` (which can be set per-rule) decides whether an existing job starts automatically or waits for a manual trigger.
- **Q: Are review apps a deployment strategy in the same sense as blue-green/canary?**
  A: Not really — they're an ephemeral, per-branch preview environment for pre-merge validation, not a production traffic-management technique, though they share the "separate environment" idea with blue-green.
