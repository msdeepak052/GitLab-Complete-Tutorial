# 27. GitLab Approval Gate Mechanics

## Quick Summary
- This file is about **mechanics**: how approval gates are actually implemented — protected environments, required approvers, hard-blocking manual jobs, delayed jobs, and MR approval rules. The base dev/staging/prod pipeline structure they attach to is covered in file 26; deployment strategy patterns are covered in file 23.
- Two genuinely different GitLab features both get called "approval gates" — **protected environment deployment approvals** (gates a specific environment, Premium/Ultimate) and **merge request approval rules** (gates merging code into a branch, available on more tiers) — this file covers both and is explicit about which is which.
- `when: manual` alone just adds a Play button — it does **not** restrict *who* can click it; that's what protected environments add.
- `allow_failure: false` on a manual job turns "optional click" into "pipeline cannot succeed until this runs" — the difference between a soft and a hard gate.
- `when: delayed` + `start_in:` adds a time-based gate (a cooling-off period) that doesn't require a human click at all, distinct from `when: manual`.
- Protected environment approval rules (multiple required approvers, self-approval blocking) are configured via Settings > CI/CD > Protected environments, not YAML — there's no pipeline keyword for "require 2 approvers."

## Core Concepts

### The gate types at a glance

| Gate type | What it restricts | Mechanism | Where configured |
|---|---|---|---|
| Manual trigger | Whether a job starts automatically | `when: manual` | `.gitlab-ci.yml` |
| Hard block | Whether the pipeline can succeed without the job running | `allow_failure: false` on a manual job | `.gitlab-ci.yml` |
| Who can deploy | Which users/groups can trigger jobs targeting an environment | Protected environment "Allowed to deploy" list | Settings > CI/CD > Protected environments |
| Required approvals | How many distinct people must approve before a protected deployment proceeds | Protected environment approval rules | Settings > CI/CD > Protected environments |
| Time-based gate | A minimum wait before a job can run | `when: delayed` + `start_in:` | `.gitlab-ci.yml` |
| Pre-merge gate | Whether code can be merged at all | Merge request approval rules | Settings > Merge requests (separate feature) |

### `when: manual` — necessary but not sufficient
- Makes the job wait for a UI click instead of starting automatically.
- By itself, **any** user with permission to run pipelines on that branch can click it — it is not an authorization control.
- Default `allow_failure` behavior for manual jobs commonly allows the pipeline to report success even if the manual job is never run — always set this explicitly for a real gate (below).

### `allow_failure: false` — the hard-block switch
- Without it, a `when: manual` job that's never clicked can let the pipeline finish "green," silently implying nothing more needs to happen.
- With `allow_failure: false`, the pipeline stays in a non-final ("blocked") state until the manual job runs (and passes) — this is what actually makes a manual job function as a real gate rather than an optional extra step.

### Protected environments — who can deploy
- Configured per-environment in Settings > CI/CD > Protected environments: pick the environment (exact name or a wildcard like `production/*`), then an "Allowed to deploy" list of users, roles, or groups.
- Any job whose `environment: name:` matches a protected environment can only actually run/deploy if the triggering user (or the job's authorization context) is on that allowed list — even if the job is otherwise fully configured to run.
- This is what turns `when: manual` from "anyone can click" into "only authorized people can click and have it succeed."

### Required approvers on a protected environment
- Premium/Ultimate feature: beyond restricting *who can deploy*, you can require a minimum number of **separate approvals** before a deployment to that environment proceeds, even from an authorized deployer.
- Configured as approval rules on the protected environment: choose approvers (users or groups) and a required approval count, which must be less than the total number of eligible approvers.
- By default the person who triggered the pipeline cannot approve their own deployment (self-approval blocked); an admin-level setting ("Allow pipeline triggerer to approve deployment") can override this if needed.
- A user can only grant one approval per deployment even if they belong to multiple eligible approver groups — approvals are per-person, not per-group-membership.
- Distinct from `when: manual`: the manual click starts the job; deployment approval rules gate whether the *deployment itself* is allowed to proceed once triggered — both can be layered together.

### `when: delayed` + `start_in:` — time-based gates
- Job is scheduled to start automatically after a wait (`start_in: 30 minutes`, `1 day`, etc.) instead of needing a click.
- Useful as a "cooling-off" gate — e.g. give the team 15 minutes to notice something's wrong before auto-promoting — or as the pacing mechanism in a staged/canary rollout (file 23, Lab 9).
- Can be cancelled manually before the timer elapses if something looks wrong, unlike a plain automatic job.

### Merge request approval rules — a different, earlier gate
- Gates **merging code**, not deploying it — configured in Settings > Merge requests > Merge request approvals (or via `.gitlab-ci.yml`-adjacent project settings, not pipeline YAML).
- Require N approvals from specified users/groups/code owners before the "Merge" button is enabled on an MR.
- Runs **before** any deploy pipeline even exists for that change — it's a pre-deploy gate in the sense that no deployable pipeline artifact reaches `main` without it, but it is a completely separate mechanism from protected-environment deployment approvals, which happen after the code is already merged and a pipeline is running.
- Common confusion: "approval gate" in casual conversation often means either of these — always clarify which one is meant.

## Hands-On Labs

### Lab 1: Basic manual gate (soft — reachable but skippable)
- **Goal:** Confirm the baseline: a manual job that the pipeline can succeed without.
- **`.gitlab-ci.yml`:**
```yaml
deploy_staging:
  stage: deploy
  script:
    - echo "Deploying to staging..."
  environment:
    name: staging
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
```
- **Run it:** Push to `main`, do **not** click Play, watch the pipeline finish.
- **Expected result:** Pipeline reports success even though `deploy_staging` never ran — a soft gate, easy to accidentally skip.
- **What this teaches:** `when: manual` alone doesn't force anything to happen — it's an optional step unless hardened (Lab 2).

### Lab 2: Hard-block gate with `allow_failure: false`
- **Goal:** Make the pipeline unable to report success until the deploy actually runs.
- **`.gitlab-ci.yml`:**
```yaml
deploy_staging:
  stage: deploy
  script:
    - echo "Deploying to staging..."
  environment:
    name: staging
  allow_failure: false
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
```
- **Run it:** Push to `main`, leave `deploy_staging` unclicked, check the pipeline's overall status.
- **Expected result:** Pipeline stays in a "blocked"/pending state (not green) until `deploy_staging` is run and passes.
- **What this teaches:** `allow_failure: false` is the difference between a real gate and an optional courtesy step — use it for any manual job that must genuinely happen.

### Lab 3: Protected environment setup — restrict who can deploy
- **Goal:** Ensure only specific users/roles can trigger jobs targeting `production`.
- **Steps (UI, not YAML):**
  1. Go to Settings > CI/CD > Protected environments.
  2. Select environment `production` (or a wildcard like `production/*` if using multiple prod-tier environments).
  3. Set "Allowed to deploy" to a specific role (e.g. Maintainer) or named group (e.g. "release-managers").
  4. Save.
- **`.gitlab-ci.yml`:** Reuse `deploy_prod` from file 26 Lab 5 unchanged — no YAML change needed, protection is enforced independently of the job definition.
- **Run it:** As a Developer-role user (below Maintainer), attempt to run `deploy_prod`; then as a Maintainer, run it.
- **Expected result:** The Developer sees the job but cannot successfully trigger it against the protected environment (blocked with a permissions message); the Maintainer can.
- **What this teaches:** Protected environments enforce authorization independently of the pipeline YAML — the same job definition behaves differently depending on who's clicking, which is exactly the point.

### Lab 4: Require multiple approvers on a protected environment
- **Goal:** Require 2 separate people to approve before a production deployment proceeds, even from an authorized deployer.
- **Steps (UI, not YAML):**
  1. Settings > CI/CD > Protected environments > `production` > Approval rules.
  2. Add an approval rule: approvers = group "release-managers" (must have at least 2 eligible members), required approvals = 2.
  3. Save.
- **Run it:** Trigger `deploy_prod` (from file 26's pipeline); observe the deployment enter a "waiting for approval" state; have two different eligible users each submit an approval (via the Environments page or API).
- **Expected result:** The deployment does not proceed after the manual job is clicked — it waits until 2 distinct approvals are recorded, then runs.
- **What this teaches:** This is the actual "N required approvers" mechanic — it's a property of the protected environment, not something expressible in `.gitlab-ci.yml`; the job's `when: manual` click and the environment's approval requirement are two separate, stacked checks.

### Lab 5: Self-approval is blocked by default
- **Goal:** Confirm the pipeline triggerer can't approve their own deployment.
- **Run it:** As the same user who pushed the commit (and thus triggered the pipeline), attempt to approve the `deploy_prod` deployment from Lab 4.
- **Expected result:** The approval option isn't available to that user for this deployment by default.
- **What this teaches:** Self-approval prevention is on by default for protected environment approvals; an admin can enable "Allow pipeline triggerer to approve deployment" if a team genuinely wants to allow it, but the safe default assumes a second pair of eyes.

### Lab 6: Approve a deployment via the API
- **Goal:** Approve a pending protected-environment deployment without using the UI — useful for automation or ChatOps-style approvals.
- **Run it:**
```bash
curl --request POST \
  --header "PRIVATE-TOKEN: $APPROVER_TOKEN" \
  "https://gitlab.example.com/api/v4/projects/$CI_PROJECT_ID/deployments/$DEPLOYMENT_ID/approval" \
  --data "status=approved&comment=Looks good, approving via API"
```
- **Expected result:** The deployment's approval count increments the same as a UI click would; once the required count is met, the deployment proceeds.
- **What this teaches:** Approval gates aren't UI-only — the same mechanism is reachable via API, which matters for building ChatOps bots or integrating external approval systems (e.g. a ServiceNow change ticket auto-approving via webhook).

### Lab 7: Delayed job as a time-based (non-human) gate
- **Goal:** Add a cooling-off window before a job runs, without requiring a click.
- **`.gitlab-ci.yml`:**
```yaml
promote_to_prod:
  stage: deploy
  script:
    - echo "Promoting to production after cooling-off period..."
  environment:
    name: production
  when: delayed
  start_in: 15 minutes
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```
- **Run it:** Push to `main`, watch the job sit in a "delayed" countdown state; optionally cancel it manually before the timer elapses.
- **Expected result:** Job auto-starts after 15 minutes unless someone intervenes — a gate based on elapsed time, not approval.
- **What this teaches:** `when: delayed` is a distinct gate type from `when: manual` — useful when you want a default "yes, unless someone objects" window rather than requiring an explicit "yes."

### Lab 8: Layering a manual click on top of a protected environment
- **Goal:** Combine both mechanics — an explicit click, restricted to authorized people, from file 26's base pipeline.
- **`.gitlab-ci.yml`:** (extends file 26 Lab 5's `deploy_prod` job)
```yaml
deploy_prod:
  extends: .deploy_template
  stage: deploy
  environment:
    name: production
    url: http://$PROD_HOST
  script:
    - ssh -o StrictHostKeyChecking=no -i private_key.pem $PROD_USER@$PROD_HOST "docker pull $IMAGE_NAME:$IMAGE_TAG && docker stop devops-app || true && docker rm devops-app || true && docker run -d -p 80:80 --name devops-app $IMAGE_NAME:$IMAGE_TAG"
  needs: ["deploy_staging"]
  allow_failure: false
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
```
- **Run it:** With `production` set up as a protected environment (Lab 3) requiring 2 approvals (Lab 4), push to `main` and go through the full flow: staging must pass first (`needs:`), then click Play (only works if authorized), then two people approve, then the job actually executes.
- **Expected result:** Four independent conditions all had to hold before code reached production: staging succeeded, an authorized user clicked Play, two distinct approvers signed off, and the pipeline couldn't have silently skipped it (`allow_failure: false`).
- **What this teaches:** Real production gates are usually a stack of these mechanisms, not any single one — `needs:` (order, file 26) + `when: manual` (explicit trigger) + protected environment (authorization + required approvals) + `allow_failure: false` (hard block).

### Lab 9: Merge request approval rules as a pre-deploy gate
- **Goal:** Ensure code can't even reach `main` (and thus can't reach the deploy pipeline) without review.
- **Steps (UI, not YAML):**
  1. Settings > Merge requests > Merge request approvals > Add approval rule.
  2. Set "Approvals required" to 2, approvers = a specific group (e.g. "senior-engineers").
  3. Save.
- **Run it:** Open an MR into `main` with 0 approvals; attempt to merge.
- **Expected result:** The Merge button stays disabled until 2 qualifying approvals are given — this happens entirely before any pipeline in this file's examples even runs.
- **What this teaches:** This is a genuinely different gate from everything else in this file — it protects the `main` branch itself, not a deployment. Both gates are often needed together (review before merge, approval before prod deploy), but they're configured in different settings pages and solve different problems.

### Lab 10: What an unauthorized deploy attempt looks like end-to-end
- **Goal:** See the full failure path when someone without access tries to bypass the gates.
- **Run it:** As a Developer-role user (not on the `production` allowed-to-deploy list), attempt to: (a) click Play on `deploy_prod`, and (b) call the deployment approval API directly with their token.
- **Expected result:** (a) The click is rejected or the job fails immediately with a permissions error; (b) the API call returns a 403/permission error — the API respects the same protected-environment rules as the UI.
- **What this teaches:** Protected environment rules are enforced server-side, consistently across UI and API — there's no "back door" through automation that bypasses the same authorization checks.

## Common Pitfalls
- Treating `when: manual` as an access control — it restricts *when*, not *who*; pair it with a protected environment for actual authorization.
- Leaving `allow_failure` at its default on a gate job — the pipeline can go green without the gate ever being exercised.
- Confusing merge request approval rules with protected-environment deployment approvals — they gate different things (merging vs. deploying) and are configured in different settings pages.
- Setting a required-approval count equal to or greater than the number of eligible approvers — deployments can never proceed.
- Assuming the pipeline triggerer can approve their own deployment — blocked by default; don't design a process around it without checking the "allow triggerer to approve" setting first.
- Forgetting that a user can only give one approval total per deployment, even if eligible via multiple approver groups — doesn't multiply toward the required count.
- Re-deriving the full dev/staging/prod pipeline skeleton in every approval-related doc instead of referencing the canonical version (file 26).

## Interview Questions & Answers
- **Q: Does `when: manual` restrict who can deploy?**
  A: No — it only makes the job wait for a click; anyone with pipeline-run permission on that branch can click it unless a protected environment also restricts who's allowed.
- **Q: How do you make a manual job a true hard gate instead of an optional step?**
  A: Set `allow_failure: false` — without it, the pipeline can report success even if the manual job never ran.
- **Q: How do you require 2 specific people to approve a production deployment?**
  A: Configure approval rules on the protected environment (Settings > CI/CD > Protected environments), setting required approvals and eligible approvers — there is no `.gitlab-ci.yml` keyword for this.
- **Q: What's the difference between protected-environment deployment approvals and merge request approval rules?**
  A: MR approval rules gate merging code into a branch (before any deploy pipeline exists for it); deployment approvals gate an already-triggered deployment to a specific protected environment. Different mechanisms, different settings pages, often used together.
- **Q: Can the person who pushed the commit approve their own production deployment?**
  A: Not by default — self-approval is blocked; an admin-level setting can override this if a team explicitly wants to allow it.
- **Q: What's `when: delayed` used for, and how does it differ from `when: manual`?**
  A: It auto-starts a job after a configured wait (`start_in:`) with no click required — a time-based "default yes" gate, versus `when: manual`'s "default no, requires a click."
- **Q: Scenario: your pipeline shows green but you later discover production was never actually updated — what's misconfigured?**
  A: The deploy job is almost certainly `when: manual` without `allow_failure: false` — the pipeline succeeded without the gate job ever running.
- **Q: Scenario: you need release approval to come from a ServiceNow change ticket instead of a person clicking in GitLab — is that possible?**
  A: Yes — approve the deployment via the GitLab API (`POST .../deployments/:id/approval`) from a webhook/integration triggered by the ticket's approval, rather than requiring a manual UI click.
- **Q: What GitLab tier is required for protected environment approval rules (multiple required approvers)?**
  A: Premium or Ultimate.
- **Q: How would you design gates for a pipeline where staging deploys automatically but prod needs both a manual click and two approvers?**
  A: `deploy_staging` with no `when: manual` (or `rules:` with default `on_success`); `deploy_prod` with `needs: [deploy_staging]`, `when: manual`, `allow_failure: false`, targeting a protected `production` environment configured with a 2-approver rule.
