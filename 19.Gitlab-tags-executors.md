# 19. Executor Types and Tag-Based Job Routing

## Quick Summary
- An **executor** is *how* a registered runner actually runs a job's `script:` — host shell, container, pod, remote SSH session, etc.
- **Tags** are *how a job picks which runner(s)* are eligible to run it — matching is exact string matching against tags set on the runner at creation/registration.
- This file assumes the runner is already installed and registered (file 18) and covers only executor mechanics and tag routing.
- Docker Machine is now in maintenance mode/deprecated — GitLab's current autoscaling story is the **Docker Autoscaler** + **Instance** executors, built on "fleeting" plugins.
- Choosing the right executor is mostly a tradeoff between isolation/reproducibility (Docker, Kubernetes) and simplicity/speed (Shell, SSH).
- A runner not accepting untagged jobs + a job with no tags = job stuck pending forever — one of the most common CI "why won't my job run" bugs.

## Core Concepts

### What an executor does
- Executors define the **execution environment** for `script:` — not the CI/CD logic, just where/how commands physically run.
- Set per runner (in `config.toml`'s `[[runners]]` block, or at creation time in the UI/API) — a single runner has exactly one executor.
- A job doesn't choose an executor directly; it lands on a runner (via tags) and inherits whatever executor that runner uses. `image:` in a job only makes sense for container-capable executors (Docker, Kubernetes).

### Executor types
| Executor | How it runs jobs | Isolation | Status | Typical use |
|---|---|---|---|---|
| **Shell** | Directly in a shell (bash/sh/pwsh/cmd) on the runner host | None — shares host OS state | Maintenance mode | Simple setups, trusted single-tenant hosts, fast startup |
| **Docker** | Each job in a fresh container from a specified `image:` | Per-job container isolation | Actively developed | Reproducible builds, most common choice for shared/team runners |
| **Docker Autoscaler** | Docker executor + dynamically provisioned/destroyed VM fleet via "fleeting" plugins (AWS/GCP/Azure) | Per-job container, autoscaled hosts | Actively developed | Elastic capacity, replaces Docker Machine |
| **Instance** | Runs the whole job directly on an autoscaled, ephemeral VM (via fleeting) | Full VM per job | Actively developed | Jobs needing more than container isolation, still elastic |
| **Kubernetes** | Each job in a pod in a configured cluster | Per-job pod isolation | Actively developed | Cloud-native pipelines, teams already running k8s |
| **SSH** | Commands sent to a remote host over SSH, executed there | Depends on remote host | Maintenance mode | Legacy/remote-deploy targets without Docker/k8s |
| **Custom** | You supply scripts implementing `prepare`/`run`/`cleanup` hooks — plug in any backend | Fully custom | Maintenance mode | Bespoke infra not covered by built-in executors |
| **VirtualBox / Parallels** | Job runs inside a VM snapshot | Full VM isolation | Maintenance mode | Legacy full-VM test matrices |
| **Docker Machine** | Old dynamic-host-provisioning mechanism for the Docker executor | Per-job container | ⚠️ Deprecated | Superseded — see below |

### ⚠️ Deprecated / Changed
- **Docker Machine** (`docker+machine` autoscaling) is in maintenance mode and deprecated — GitLab is not adding features to it and recommends migrating to the **Docker Autoscaler** or **Instance** executor, both built on the newer "fleeting" plugin architecture (supports AWS, GCP, Azure). If you inherit a runner fleet still using Docker Machine, treat it as a migration candidate, not a template for new setups.
- Shell, SSH, Custom, VirtualBox, and Parallels executors are all officially "maintenance mode" — they still work and receive security fixes, but no new capabilities. Prefer Docker/Docker Autoscaler/Kubernetes/Instance for anything new unless you have a specific legacy constraint (e.g. deploying to a host that genuinely has no Docker/k8s).

### Shell executor
- Runs job scripts as if you'd pasted them into a terminal on the runner host — no container, no isolation.
- Fast (no image pull, no pod scheduling) but jobs can leak state into each other (leftover files, installed packages) unless you clean up explicitly.
- `image:` in job YAML has no effect with this executor — ignored.

### Docker executor
- Registered with a default image; jobs can override with `image: <image>` per job/per pipeline.
- Each job gets a fresh container from that image — no cross-job contamination by default.
- Needs access to a Docker daemon (either the host's, or Docker-in-Docker for jobs that themselves build images — see file 25 for the DinD pattern).

### Kubernetes executor
- Runner is configured with cluster credentials; each job becomes a Pod, runs to completion, then the pod is deleted.
- Good for elastic, cloud-native fleets — pods scale with demand, no persistent VM to manage.
- Job-level `image:` maps to the pod's container image; resource requests/limits, node selectors, etc. are configurable via runner `config.toml` `[runners.kubernetes]`.

### SSH executor
- The runner itself doesn't execute the job locally — it SSHes into a configured remote host and runs commands there.
- Useful for deploying to a legacy server that isn't containerized and won't get a runner installed on it directly.
- Example deploy job (executor-agnostic YAML, but conceptually this is what an SSH-executor runner is doing under the hood; equally common written as an explicit `ssh` call from a Docker/Shell executor job):
  ```yaml
  deploy_remote:
    stage: deploy
    script:
      - ssh -o StrictHostKeyChecking=no "$DEPLOY_USER@$DEPLOY_HOST" "cd /app && git pull && systemctl restart app"
    environment:
      name: production
    rules:
      - if: $CI_COMMIT_BRANCH == "main"
  ```

### Custom executor
- You implement `prepare`, `run`, `cleanup` (and optional `config`) as scripts/binaries; GitLab Runner calls them at the right lifecycle points.
- Escape hatch for infrastructure with no built-in executor (e.g. a proprietary sandboxing system, LXC, a niche cloud).

### Tags — how job-to-runner matching works
- Tags are assigned to a runner at creation (UI/API) or in `config.toml`.
- A job's `tags:` list must be a **subset** of a runner's tags for that runner to be eligible — **all** listed job tags must be present on the runner (AND logic, not OR).
  ```yaml
  build_job:
    stage: build
    tags:
      - linux
      - docker
  ```
  This job only runs on a runner tagged with **both** `linux` and `docker` (it may have more tags too — extra runner tags don't disqualify it).
- If no runner currently matches, the job sits **pending** indefinitely — GitLab does not fall back to an unmatched runner.
- **"Run untagged jobs"** is a per-runner toggle (UI/API, default varies): if enabled, that runner will also pick up jobs with **no** `tags:` at all. A job with zero tags never matches a runner that has this toggle disabled.
- Tags are plain strings — no wildcards, no regex; `docker` and `Docker` are different tags (case-sensitive).

### Executor + tags working together
1. Runner is registered with tags (e.g. `linux, docker`) and an executor (e.g. `docker`).
2. A job declares `tags: [linux, docker]` → GitLab's scheduler filters to runners whose tag set is a superset → picks one → that runner's executor (docker) determines how the job actually runs.
3. A job declaring `tags: [windows]` finds no match among `linux/docker`-tagged runners → stays pending until a Windows-tagged runner exists.

## Hands-On Labs

### Lab 1: Route a job with a single matching tag
- **Goal:** See exact tag matching in action.
- **`.gitlab-ci.yml`:**
  ```yaml
  build_job:
    stage: build
    script:
      - echo "Building on tagged runner"
    tags:
      - demo
  ```
- **Run it:** Ensure at least one runner is registered with tag `demo` (file 18, Lab 3), push.
- **Expected result:** Job runs on that runner; job log's runner info confirms which one picked it up.
- **What this teaches:** Baseline tag-to-runner matching.

### Lab 2: Job with no matching runner stays pending
- **Goal:** Observe the "stuck pending" failure mode directly.
- **`.gitlab-ci.yml`:**
  ```yaml
  build_job:
    stage: build
    script:
      - echo "Needs a runner tagged 'gpu'"
    tags:
      - gpu
  ```
- **Run it:** Push without any `gpu`-tagged runner registered.
- **Expected result:** Job stays in **pending** state indefinitely; GitLab UI shows "This job is stuck because you don't have any active runners that can run this job."
- **What this teaches:** The most common real-world tag-routing failure and its exact UI message.

### Lab 3: Multiple required tags (AND logic)
- **Goal:** Confirm a job needs *all* listed tags present on one runner.
- **`.gitlab-ci.yml`:**
  ```yaml
  build_job:
    stage: build
    script:
      - echo "Needs linux AND docker"
    tags:
      - linux
      - docker
  ```
- **Run it:** Register one runner tagged only `linux`, another tagged `linux, docker`. Push.
- **Expected result:** Job only runs on the second runner.
- **What this teaches:** Tag matching is AND across the job's tag list, not OR.

### Lab 4: Enable "run untagged jobs" and observe the effect
- **Goal:** See how untagged jobs get scheduled.
- **Steps:**
  1. Runner Settings → toggle **Run untagged jobs** ON for one runner.
  2. Push a job with no `tags:` key at all.
- **Expected result:** The untagged job is picked up by that runner even though it declares zero tags; with the toggle OFF, the same job would stay pending (assuming no other untagged-eligible runner exists).
- **What this teaches:** Tags aren't the only gate — the runner-side "accept untagged" switch matters too.

### Lab 5: Shell executor — no isolation demo
- **Goal:** See state leak between jobs on a shell executor.
- **`.gitlab-ci.yml`:**
  ```yaml
  write_file:
    stage: build
    tags: [shell-demo]
    script:
      - echo "leftover data" > /tmp/leftover.txt

  read_file:
    stage: test
    tags: [shell-demo]
    script:
      - cat /tmp/leftover.txt
  ```
- **Run it:** Against a shell-executor runner tagged `shell-demo`.
- **Expected result:** `read_file` successfully reads the file `write_file` left behind — proving no isolation between jobs.
- **What this teaches:** Why shell executor requires discipline (explicit cleanup) that Docker/Kubernetes give you for free.

### Lab 6: Docker executor — per-job isolation
- **Goal:** Confirm the same scenario is isolated under Docker executor.
- **`.gitlab-ci.yml`:**
  ```yaml
  write_file:
    stage: build
    image: alpine:latest
    tags: [docker-demo]
    script:
      - echo "leftover data" > /tmp/leftover.txt

  read_file:
    stage: test
    image: alpine:latest
    tags: [docker-demo]
    script:
      - cat /tmp/leftover.txt || echo "File not found — fresh container confirmed"
  ```
- **Run it:** Against a Docker-executor runner tagged `docker-demo`.
- **Expected result:** `read_file` fails to find the file (unless using `artifacts`/cache to pass it) — each job got a fresh container.
- **What this teaches:** Docker executor's per-job isolation, and why cross-job data needs explicit `artifacts:`/`cache:`, not filesystem persistence.

### Lab 7: Override the Docker executor's default image per job
- **Goal:** Use a different language runtime per job on the same Docker-executor runner.
- **`.gitlab-ci.yml`:**
  ```yaml
  python_job:
    stage: test
    image: python:3.12
    tags: [docker-demo]
    script:
      - python --version

  node_job:
    stage: test
    image: node:20
    tags: [docker-demo]
    script:
      - node --version
  ```
- **Run it:** Push; both jobs use the same runner but different images.
- **Expected result:** Each job's log shows the correct language version, proving `image:` is job-scoped even on a shared runner.
- **What this teaches:** One Docker-executor runner can serve arbitrarily varied job environments via `image:`.

### Lab 8: SSH-style remote deploy job
- **Goal:** Deploy to a non-containerized remote host from a normal job.
- **`.gitlab-ci.yml`:**
  ```yaml
  deploy_remote:
    stage: deploy
    tags: [deploy-runner]
    script:
      - ssh -o StrictHostKeyChecking=no "$DEPLOY_USER@$DEPLOY_HOST" "cd /app && git pull && systemctl restart app"
    environment:
      name: production
    rules:
      - if: $CI_COMMIT_BRANCH == "main"
  ```
- **Run it:** With `$DEPLOY_USER`/`$DEPLOY_HOST` set and an SSH key available to the runner (via `SSH_PRIVATE_KEY` CI/CD variable loaded in `before_script`, or a runner-level SSH executor config).
- **Expected result:** Remote host pulls latest code and restarts the service; job log shows SSH output.
- **What this teaches:** Legacy-host deployment without Docker/Kubernetes on the target machine.

### Lab 9: Kubernetes executor job
- **Goal:** Run a job as an ephemeral pod.
- **`.gitlab-ci.yml`:**
  ```yaml
  build_k8s:
    stage: build
    image: alpine:latest
    tags: [k8s-demo]
    script:
      - echo "Running inside a Kubernetes pod"
      - hostname
  ```
- **Run it:** Against a runner registered with the Kubernetes executor, tagged `k8s-demo`.
- **Expected result:** `hostname` prints a pod name (random suffix); pod is visible briefly via `kubectl get pods -n <runner-namespace>` while the job runs, then disappears.
- **What this teaches:** Kubernetes executor's per-job pod lifecycle.

### Lab 10: Route different stages to different executors via tags
- **Goal:** Use tags to send build work to Docker and deploy work to SSH-capable runners, in one pipeline.
- **`.gitlab-ci.yml`:**
  ```yaml
  stages:
    - build
    - deploy

  build_job:
    stage: build
    image: node:20
    tags: [docker-demo]
    script:
      - npm install
      - npm run build
    artifacts:
      paths:
        - dist/

  deploy_job:
    stage: deploy
    tags: [deploy-runner]
    script:
      - scp -r dist/* "$DEPLOY_USER@$DEPLOY_HOST:/var/www/app/"
    environment:
      name: production
    rules:
      - if: $CI_COMMIT_BRANCH == "main"
  ```
- **Run it:** Push to `main` with both a `docker-demo`-tagged and a `deploy-runner`-tagged runner available.
- **Expected result:** `build_job` runs in a Docker container, produces `dist/` as an artifact; `deploy_job` runs on the SSH-capable runner and copies `dist/` to the remote host.
- **What this teaches:** Tags let a single pipeline deliberately mix executor types stage-by-stage, matching each job to the infrastructure it actually needs.

### Lab 11: Diagnose executor mismatch (`image:` on a shell runner)
- **Goal:** See what happens when YAML assumes the wrong executor.
- **`.gitlab-ci.yml`:**
  ```yaml
  misconfigured_job:
    stage: build
    image: alpine:latest
    tags: [shell-demo]
    script:
      - echo "This expects a container but shell-demo is a Shell executor"
  ```
- **Run it:** Against the shell-executor runner from Lab 5 (tagged `shell-demo`).
- **Expected result:** The job still runs, but directly on the host shell — `image:` is silently ignored, so if the script assumes Alpine-specific tools (e.g. `apk`), it fails with "command not found" instead of running in Alpine.
- **What this teaches:** `image:` only has meaning for container-capable executors; mismatched assumptions between job YAML and the actual runner executor are a common source of confusing failures.

## Common Pitfalls
- Assuming `image:` works on a Shell/SSH executor — it's silently ignored there.
- Treating tag matching as OR instead of AND — a job with `tags: [a, b]` needs a runner with both, not either.
- Forgetting "run untagged jobs" is a separate per-runner switch from tags themselves — an untagged job can still go pending.
- Copying Docker Machine autoscaling setup from an old blog post — it's deprecated; use Docker Autoscaler/Instance with fleeting plugins instead.
- Relying on filesystem persistence between jobs on a Docker/Kubernetes executor — each job is a fresh container/pod; use `artifacts:`/`cache:` instead.
- Mounting `docker.sock` (Docker executor on the host) without considering that any job on that runner effectively gets host-level Docker access.
- Case-sensitivity surprises — `Linux` and `linux` are different tags.

## Interview Questions & Answers
- **Q: What's the difference between an executor and a tag?**
  A: Executor = *how* a runner executes a job (shell/docker/kubernetes/ssh/custom); tag = *which runner* a job is allowed to run on. Tags route; executors execute.
- **Q: Is tag matching AND or OR across a job's `tags:` list?**
  A: AND — a runner must have every tag listed on the job (it may have additional tags beyond that).
- **Q: What happens to a job if no runner matches its tags?**
  A: It stays pending indefinitely; GitLab does not fall back to an unmatched runner.
- **Q: How do untagged jobs get scheduled?**
  A: Only by runners with "Run untagged jobs" enabled — a separate toggle from tag matching itself.
- **Q: When would you choose Kubernetes executor over Docker executor?**
  A: When you already operate a k8s cluster and want CI capacity to scale elastically as pods rather than managing a fixed or Docker-Machine-autoscaled VM fleet.
- **Q: What replaced Docker Machine for autoscaling?**
  A: The Docker Autoscaler and Instance executors, built on GitLab's "fleeting" plugin architecture (AWS/GCP/Azure); Docker Machine is deprecated/maintenance mode.
- **Q: Why might you still use the Shell executor today?**
  A: Simplicity and speed for trusted, low-volume, single-tenant hosts, or when the job genuinely needs direct host access that containers complicate.
- **Q: What is the SSH executor good for?**
  A: Running jobs on/deploying to a remote host that isn't containerized and won't have a runner installed directly on it.
- **Q: Scenario — your pipeline's `build_job` uses `image: node:20` but never seems to actually use Node 20, and commands sometimes fail as if on a totally different OS. What's the likely misconfiguration?**
  A: The job is landing on a Shell (or SSH) executor runner via tag match, where `image:` is silently ignored — check the runner's executor type, not just its tags.
- **Q: Scenario — you add `tags: [gpu]` to a job for a new ML training step and it never starts. What two things do you check?**
  A: (1) Does any registered runner actually carry the `gpu` tag, and (2) is that runner online/healthy (`gitlab-runner status`/`verify` from file 18) — a tag with zero matching runners looks identical in the UI to a tag matching an offline runner.
- **Q: Can one runner serve jobs requiring different container images?**
  A: Yes, if it's a Docker/Kubernetes executor — `image:` is set per job/pipeline, not fixed to the runner (the runner's registered image is just the default).
- **Q: What's the security concern with the Docker executor mounting the host's `docker.sock`?**
  A: It grants effective root/host-level control to whatever runs inside job containers on that runner — treat it as a privileged configuration, not a default.
