# **Private vs Public repositories** in GitLab

Here’s a detailed breakdown of **private vs public repositories** in GitLab, how visibility works, and what is allowed (or limited) in the **Free** vs **Enterprise / Paid** versions. If you like, I can also summarise in a table.

---

## Key Concepts: Visibility Levels in GitLab

GitLab allows projects (repos) and groups to have one of these visibility levels:

| Visibility                                                          | Who can see / clone / access etc                                                                                                                                                                         |
| ------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Public**                                                          | Anyone (including non-logged-in users) can see, clone, view the repository and repository’s web interface. ([docs.gitlab.com][1])                                                                        |
| **Private**                                                         | Only project/group members with explicit access can see or clone. Non-members can’t view anything. ([docs.gitlab.com][1])                                                                                |
| **Internal** *(Self-managed only, not for new GitLab.com projects)* | Any authenticated user on the instance can view/clone; but external users (if applicable) cannot. Existing projects/groups with “internal” visibility may still have that option. ([docs.gitlab.com][1]) |

---

## Differences between Public vs Private repos

Here are what differs when a repo is **public** vs **private**:

| Feature                                  | Public Repo                                          | Private Repo                                                                       |
| ---------------------------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Visibility to everyone / anonymous users | Yes                                                  | No                                                                                 |
| Clone via HTTP/HTTPS without login       | Yes                                                  | No (must be a member)                                                              |
| Viewing issues, wiki, readme etc in UI   | Yes                                                  | Only for members with permission                                                   |
| Access control                           | Less strict (many read-only features visible to all) | Strict – you must invite or be granted access                                      |
| Use cases                                | Open source projects; documentation; sharing broadly | Internal projects; proprietary or sensitive code; collaboration within closed team |

## Free vs Enterprise (Paid) Tiers: What’s different, especially for private/public repos

GitLab’s feature set depends on whether you are using **Free tier** (on GitLab.com or self-managed Community / Free) vs **Premium / Ultimate or other Paid / Enterprise tiers**.

Below are the important limitations / differences relevant to visibility, private/public repos, access, CI/CD etc.

---

### What Free tier allows (GitLab.com Free, or Free self-managed)

1. **Public and Private repos**
   You can create both public and private projects even on Free tier. ([docs.gitlab.com][1])

2. **CI/CD Minutes (Shared Runners)**
   There is a monthly quota of CI/CD minutes for shared runners. How many depends on tier. For Free:

   * **400 minutes/month** total with shared runners (for private projects). ([sels.tecnico.ulisboa.pt][2])
   * Public projects consume minutes at a *much lower effective rate*. For example, for namespaces created after a certain date, public jobs cost much less in “CI-minutes” accounting (e.g. a factor like 0.008). This means you can do a lot more builds on public repos vs private versus the same raw run time. ([sels.tecnico.ulisboa.pt][2])

3. **Number of users / collaborators for private repos on Free (GitLab.com SaaS)**

   * There is a **limit of 5 users** in top-level namespaces with private visibility on GitLab.com’s Free tier. If a group or project (namespace) is private and is top-level, and exceeds 5 users, it can become read-only for many actions until you upgrade. ([docs.gitlab.com][3])
   * Public namespaces / public groups are not subject to this user limit. ([about.gitlab.com][4])

4. **Feature limitations**
   Some advanced permissions, compliance, governance, security features are only available on higher (paid) tiers. E.g., restricting merge requests behind multiple approvals, custom roles, enterprise-level auditing etc. (These generally are not fully available in Free.) ([Reddit][5])

---

### What Paid / Enterprise tiers add

If you move to a Premium / Ultimate / Enterprise edition or the paid plan on GitLab.com / self-managed, you get:

* Much higher CI/CD minutes quotas (shared runners). For example Premium and Ultimate have larger quotas than Free. ([sels.tecnico.ulisboa.pt][2])
* More elaborate permission controls: more granular roles, ability to enforce approvals, protected branches etc.
* Additional features for security, compliance (e.g. audit logs, vulnerability scanning).
* Better support (SLAs etc).
* Possibly more storage, larger limits for artifacts / packages.
* For self-managed installations, more visibility control (internal visibility, group/project feature visibility etc) and admin controls.

---

## Some special and recent rules / caveats

* **Internal visibility**: On GitLab.com, the “Internal” visibility setting for new projects/groups is disabled. It’s used in **self-managed** instances. ([docs.gitlab.co.jp][6])
* **CI/CD minutes limits applied also for public projects now**: Historically public repos had more relaxed or unlimited CI minute usage, but GitLab has tightened this: public projects now also count toward quota in many cases. But because the “cost factor” is small, they use up far fewer minutes. ([about.gitlab.com][7])
* **Programs / Open Source / Education**: GitLab offers special programs (GitLab for Open Source, for Education, etc.) where some paid-tier or higher-feature benefits are made available free for qualifying public/open projects. ([about.gitlab.com][7])

---

## Summary: Differences & What’s Allowed

Putting it all together:

* On Free tier, you *can use private repos*, but with fewer CI minutes, fewer users (for private top-level groups), and less advanced features.
* Public repos are more “cheap” in terms of CI usage (public jobs use fewer “minutes” in quota), and public projects aren’t subject to the 5-user limit that private ones have in Free SaaS.
* On Enterprise / Paid, those limits are relaxed; you also get more control over visibility, permissions, compliance, support, etc.
