# 2. GitLab HTTPS Authentication (Windows & Linux)

## Quick Summary
- GitLab no longer accepts your account password for Git over HTTPS — you authenticate with a token instead.
- Personal Access Tokens (PATs) are the general-purpose token used as the "password" for HTTPS clone/push.
- Tokens carry scopes (permissions) and an expiration date — least-privilege and rotation are built in, not bolted on.
- A credential helper (OS-level cache/store) avoids re-entering the token on every `git` command.
- Different helpers trade off convenience vs security: memory cache (temporary) vs plaintext file (`store`) vs OS keychain (`manager` / `libsecret`).
- Interview framing: know why password auth was deprecated (tokens are scoped + revocable + expirable; passwords aren't) and how to diagnose "Authentication failed" errors.

## Core Concepts
- **Why tokens instead of passwords**
  - ⚠️ Deprecated / Changed: GitLab.com and modern self-managed GitLab reject account passwords for Git-over-HTTPS entirely — you must use a PAT (or Deploy Token / CI job token / OAuth token depending on context).
  - PATs are scoped (`read_repository`, `write_repository`, `api`, etc.) — request the minimum scope needed.
  - PATs have a mandatory expiration date; default UI suggests 365 days max (some instances can enable an extended limit via admin-controlled setting — verify on your instance, don't assume).
- **Token types you'll encounter (don't confuse them)**
  - Personal Access Token — tied to your user account, used interactively.
  - Deploy Token — tied to a project/group, no user account needed, good for CI/CD or servers pulling code.
  - CI/CD Job Token — automatically injected into pipeline jobs, scoped to that pipeline run.
  - Project/Group Access Token — like a PAT but owned by the project/group, not a person (useful for bots/service accounts).
- **Credential helpers**
  - `cache` — stores in memory only, for a configurable timeout (default 15 minutes); lost on reboot.
  - `store` — stores in plaintext in `~/.git-credentials`; convenient but not encrypted at rest.
  - `manager` (Git Credential Manager) — OS-backed secure storage; ships as default on Git for Windows, also available cross-platform (macOS solid, Linux support improving) — check what your Git install ships with using `git credential-manager --version`.
  - `libsecret` — Linux desktop keyring integration (GNOME Keyring/KWallet backends), needs manual build/install from Git's contrib scripts on many distros.
- **UI path for PATs (current)**
  - Avatar (top-right) > **Edit profile** > left sidebar **Access Tokens** (or directly `https://gitlab.com/-/user_settings/personal_access_tokens`).
  - Older docs/tutorials reference **User Profile > Preferences > Access Tokens** — sidebar labels have moved around release to release; if a menu item is missing, use the direct URL.

## Hands-On Labs

### Lab 1: Generate a PAT with minimal scope
- **Goal:** Create a token scoped only for read access.
- **Steps:**
  1. Go to `https://gitlab.com/-/user_settings/personal_access_tokens`.
  2. Name: `lab-read-only`; expiration: 7 days out.
  3. Check only `read_repository`.
  4. Click **Create personal access token** and copy it immediately (shown once).
- **Expected result:** Token string starting with `glpat-` is displayed once; it disappears on refresh.
- **What this teaches:** Tokens are shown exactly once — losing it means generating a new one, not "viewing" the old one again.

### Lab 2: Clone with the read-only PAT
- **Goal:** Confirm scoped auth works for read, and identify what fails without write scope.
- **Steps:**
  1. `git clone https://gitlab.com/<namespace>/<project>.git`
  2. When prompted: Username = your GitLab username; Password = the PAT from Lab 1.
  3. Make a local commit and try `git push origin main`.
- **Expected result:** Clone succeeds; push fails with a permissions/403 error because the token lacks `write_repository`.
- **What this teaches:** Scopes are enforced per-operation, not just per-token-existence.

### Lab 3: Generate a PAT with write scope and push successfully
- **Goal:** Complete the round trip.
- **Steps:**
  1. Create a second PAT named `lab-read-write` with `read_repository` + `write_repository`.
  2. Re-run `git push origin main` — when re-prompted, supply the new token.
- **Expected result:** Push succeeds.
- **What this teaches:** Multiple tokens can coexist; use narrowly-scoped ones per use case instead of one all-powerful token.

### Lab 4: Cache credentials temporarily (`cache`)
- **Goal:** Avoid retyping the token for a short working session.
- **Steps:**
  1. `git config --global credential.helper cache`
  2. `git config --global credential.helper 'cache --timeout=3600'` (1 hour instead of default 15 min)
  3. Run a `git pull` — enter credentials once.
  4. Run another `git pull` within the timeout window.
- **Expected result:** Second pull does not prompt for credentials.
- **What this teaches:** `cache` is memory-only and safe for shared/short-lived shells, but doesn't survive reboot.

### Lab 5: Store credentials permanently (`store`) and inspect the risk
- **Goal:** See exactly what "insecure plaintext storage" means.
- **Steps:**
  1. `git config --global credential.helper store`
  2. Run `git pull`, enter credentials once.
  3. `cat ~/.git-credentials`
- **Expected result:** You see your PAT in plaintext in that file.
- **What this teaches:** Why `store` is discouraged on shared/multi-user machines — anyone with file access reads your token.

### Lab 6: Use libsecret on Linux (OS keyring)
- **Goal:** Store the token encrypted via the desktop keyring instead of plaintext.
- **Steps:**
  1. `sudo apt install libsecret-1-0 libsecret-1-dev`
  2. `cd /usr/share/doc/git/contrib/credential/libsecret && sudo make`
  3. `git config --global credential.helper /usr/share/doc/git/contrib/credential/libsecret/git-credential-libsecret`
  4. `git pull` (enter credentials once), then check your GNOME Keyring / Seahorse app for a saved entry.
- **Expected result:** Token no longer appears in `~/.git-credentials`; subsequent pulls don't prompt.
- **What this teaches:** Desktop Linux has a secure-storage equivalent to Windows Credential Manager, but it's opt-in and requires a local build step.

### Lab 7: Use Git Credential Manager on Windows
- **Goal:** Use OS-backed secure storage on Windows.
- **Steps:**
  1. In Git Bash / PowerShell: `git config --global credential.helper manager`
  2. `git push origin main`, enter PAT when prompted.
  3. Open **Windows Credential Manager > Windows Credentials**, find an entry like `git:https://gitlab.com`.
- **Expected result:** Entry is visible and editable/removable from Credential Manager; no more prompts from Git.
- **What this teaches:** `manager` delegates storage to the OS keychain instead of a Git-managed file.

### Lab 8: Rotate a token (simulate expiry)
- **Goal:** Practice the token-expired recovery flow, since this happens in real teams regularly.
- **Steps:**
  1. Revoke the `lab-read-write` PAT from Lab 3 (**Access Tokens** page > **Revoke**).
  2. Try `git push` again using the old (now-revoked) cached credential.
  3. When it fails, clear the stale cached credential (Windows: delete the Credential Manager entry; Linux `store`: edit/delete the line in `~/.git-credentials`; `cache`: wait out the timeout or restart the shell).
  4. Generate a fresh PAT and push again.
- **Expected result:** First push fails with `Authentication failed`; after refreshing the stored credential, push succeeds.
- **What this teaches:** Credential helpers cache the token value, not a live session — a revoked token keeps failing until you clear the cached copy.

### Lab 9: Verify global Git config
- **Goal:** Confirm what's actually configured, for troubleshooting.
- **Steps:**
  1. `git config --global --list`
- **Expected result:** Output includes `user.name`, `user.email`, and `credential.helper` set to whatever you configured (`manager`, `cache`, `store`, or the libsecret path).
- **What this teaches:** This is the first command to run when debugging "keeps asking for my password" issues.

### Lab 10: Diagnose common HTTPS auth failures
- **Goal:** Practice reading the failure -> cause -> fix chain.
- **Steps:** For each row below, deliberately reproduce it (e.g., use an expired/revoked token, or a token missing `write_repository`) and confirm the error message you get matches:

| Issue | Cause | Fix |
| --- | --- | --- |
| `Authentication failed` | Using account password instead of a token, or token revoked/expired | Use a valid PAT as the password |
| Keeps asking for credentials every command | No credential helper configured | Set one: `cache`, `store`, `manager`, or `libsecret` |
| Push works but is read-only in effect / 403 on push | Token missing `write_repository` (or `api`) scope | Regenerate token with the correct scope |
| Token expired | Expiration date reached | Generate a new PAT — old one cannot be un-expired |
| Old credential still being offered after rotation | Cached/stored value is stale | Clear the OS keychain entry / `~/.git-credentials` line, re-auth |

- **Expected result:** You can map each symptom to its root cause without guessing.
- **What this teaches:** Most "GitLab auth is broken" tickets are one of these five things.

### Lab 11: Switch a remote from an old auth method to a fresh HTTPS + PAT setup
- **Goal:** Practice fixing a repo cloned long ago with stale auth.
- **Steps:**
  1. `git remote -v` to see the current URL.
  2. `git remote set-url origin https://gitlab.com/<namespace>/<project>.git`
  3. `git fetch` and supply a current PAT when prompted.
- **Expected result:** Fetch succeeds using the new token-based auth.
- **What this teaches:** Remote URLs don't carry credentials with them — re-pointing the URL is independent of re-authenticating.

## Common Pitfalls
- Typing your account password when prompted — GitLab rejects it outright for Git over HTTPS.
- Forgetting a token is shown only once and having to regenerate instead of "recover" it.
- Using `store` on a shared/multi-user machine, exposing the token in plaintext to anyone with file access.
- Assuming a revoked/expired token will silently stop being used — it keeps being offered from cache/store until you clear it manually.
- Requesting the broad `api` scope out of laziness when `read_repository`/`write_repository` would do.

## Interview Questions & Answers
- **Why can't you use your GitLab account password for `git clone` over HTTPS anymore?**
  - GitLab deprecated password auth for Git operations; a scoped, expiring, revocable Personal Access Token is required instead.
- **What's the difference between a Personal Access Token, a Deploy Token, and a CI Job Token?**
  - PAT: tied to a user, used interactively. Deploy Token: tied to a project/group, no user account, good for servers/CI pulling code. Job Token: auto-injected per pipeline run, scoped to that job.
- **What scopes does a PAT need to clone and push?**
  - `read_repository` for clone/fetch/pull; `write_repository` (or broader `api`) for push.
  - Least privilege: request the narrowest scope the task needs.
- **What's the risk of `git config credential.helper store`?**
  - Stores the token in plaintext in `~/.git-credentials`, readable by anyone with file access on that machine.
- **How would you make Git remember your credentials securely on Windows vs Linux?**
  - Windows: `credential.helper manager` (Git Credential Manager, backed by Windows Credential Manager).
  - Linux: `libsecret` helper backed by the desktop keyring (GNOME Keyring/KWallet), built from Git's contrib scripts.
- **What does `credential.helper cache --timeout=3600` do?**
  - Keeps the credential in memory (not on disk) for 3600 seconds, then forgets it, forcing re-auth.
- **Scenario: a teammate says Git keeps asking for their password on every single command. What's the likely cause?**
  - No credential helper is configured — check with `git config --global --list`; set `cache`, `store`, or `manager`/`libsecret` as appropriate for their OS.
- **Scenario: a teammate revoked their old PAT and generated a new one, but pushes still fail with the old error. Why?**
  - The old token is still cached/stored (Credential Manager entry, `~/.git-credentials` line, or in-memory cache) and Git keeps re-offering it; the stale entry must be cleared before the new token takes effect.
- **How do you verify what credential helper and Git identity are currently configured?**
  - `git config --global --list` — shows `user.name`, `user.email`, `credential.helper`, and any other global settings.
- **What HTTP status typically comes back when a token lacks the required scope?**
  - A 401/403-style authentication/authorization failure at push time, even though clone (read) may have worked fine.
- **Where in the UI do you create and manage PATs today?**
  - Avatar menu > Edit profile > Access Tokens (`/-/user_settings/personal_access_tokens`); older docs may reference a different sidebar path from prior UI versions.
