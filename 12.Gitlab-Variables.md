# 12. GitLab CI/CD Variables

## Quick Summary
- Variables are key-value pairs injected into job environments — used for secrets, config, and dynamic pipeline behavior.
- Sources range from GitLab-provided predefined variables to project/group/instance UI variables to inline YAML variables to runtime-provided ones (manual run, trigger, schedule).
- When the same variable name is defined at multiple levels, GitLab applies a documented precedence order — higher-precedence sources win.
- Protected variables only reach protected branches/tags; masked variables are hidden in job logs (with character/length restrictions).
- `CI_JOB_TOKEN` is itself a variable — it authenticates API calls from within a job and can be scope-limited to an allowlist of projects.
- The old `CI_JOB_JWT`/`CI_JOB_JWT_V2` predefined variables for OIDC-style auth are deprecated — `id_tokens:` is the current mechanism.

## Core Concepts

### Variable types and where they're defined
| Type | Defined where | Scope |
| --- | --- | --- |
| Predefined | Automatically by GitLab | Every job, read-only |
| Custom (YAML) | `variables:` in `.gitlab-ci.yml` (global or job-level) | Project (that pipeline) |
| Project | Settings > CI/CD > Variables | All jobs in that project |
| Group | Group > Settings > CI/CD > Variables | All projects in the group (and subgroups) |
| Instance | Admin Area > CI/CD | All projects on the instance (self-managed only) |
| Manual/trigger/schedule | Run pipeline UI, trigger API, or Schedules UI | That one pipeline run |

### Predefined variables (selection)
- `$CI_PROJECT_NAME`, `$CI_COMMIT_REF_NAME`, `$CI_COMMIT_SHA`, `$CI_COMMIT_SHORT_SHA`, `$CI_PIPELINE_ID`, `$CI_SERVER_URL`, `$CI_JOB_STAGE`, `$CI_JOB_ID`, `$CI_RUNNER_DESCRIPTION`.
- Common use: tagging Docker images, e.g. `docker build -t myapp:$CI_COMMIT_SHORT_SHA .`
- Read-only — cannot be overridden by user-defined variables of the same name.

### Precedence order (lowest to highest) — current docs
1. Predefined variables
2. Deployment variables (e.g. from a Kubernetes cluster integration)
3. Default/global `variables:` in `.gitlab-ci.yml`
4. Job-level `variables:` in `.gitlab-ci.yml`
5. Variables from dotenv artifact reports (`artifacts:reports:dotenv`)
6. Instance-level CI/CD variables (UI)
7. Group-level CI/CD variables (closer subgroup wins over parent group)
8. Project-level CI/CD variables (UI)
9. Variables set when triggering a pipeline manually, via schedule, via API, via trigger token, or in a downstream/multi-project pipeline
10. Scan execution policy variables
11. Pipeline execution policy variables (highest)
- Takeaway for interviews: the more "runtime-specific" and "manually asserted" a variable is, the higher it wins — a variable typed into "Run pipeline" beats one baked into `.gitlab-ci.yml`.
- ⚠️ This exact ordering has changed across GitLab versions — always sanity-check against current docs.gitlab.com rather than memorizing an old list verbatim.

### Protected and masked variables
- **Protected**: only exposed to pipelines running on protected branches or protected tags. Unprotected branches never see the value.
- **Masked**: value is replaced with `[MASKED]`/`****` in job logs. Requirements (current docs):
  - Minimum 8 characters.
  - Single line, no line breaks.
  - Restricted character set unless "masked and expandable" is checked (base64-safe style set: letters, digits, `_`, `-`, `+`, `.`, `~`, `=`, `:`, `@`).
  - Cannot share a name with an existing predefined or custom variable.
- Masking and protection are independent toggles — set both for real secrets.
- Masking is a **display-layer** protection only — it doesn't prevent a script from deliberately printing/exfiltrating the value; it's not encryption.

### `CI_JOB_TOKEN` scope
- Every job automatically gets a short-lived `CI_JOB_TOKEN` used to authenticate API/registry/package-registry calls as "the pipeline."
- By default, a job token can only access its **own** project's resources.
- To let project A's job token call project B's API (e.g. trigger a downstream pipeline, pull a package), project B must explicitly add project A to its **job token allowlist** (Settings > CI/CD > Job token permissions).
- Being on the allowlist does **not** grant extra permissions — the calling pipeline still needs the underlying user/role permissions.
- Interview angle: this is GitLab's main mechanism to prevent one project's pipeline from silently pivoting into another project using a leaked/implicit token.

### `id_tokens` (OIDC) — modern secretless auth
- `id_tokens:` issues a short-lived, per-job JSON Web Token signed by GitLab, scoped with an `aud:` (audience) claim for a specific external service (AWS, Vault, GCP, Azure, etc.).
- Used for secretless/OIDC authentication to cloud providers — no long-lived static credentials stored in CI/CD variables at all.
```yaml
job_with_id_tokens:
  id_tokens:
    AWS_ID_TOKEN:
      aud: https://aws.example.com
  script:
    - aws-auth-script.sh $AWS_ID_TOKEN
```

### Using variables in scripts
- Reference with `$VAR_NAME` or `${VAR_NAME}`.
- Prefer `${VAR_NAME}` when concatenating text immediately after the variable, e.g. `${APP_NAME}v1` vs the ambiguous `$APP_NAMEv1` (which GitLab/bash would try to resolve as a variable literally named `APP_NAMEv1`).

### Dynamic variables at runtime
- `export SOME_VAR=$(command)` inside `script:` makes the variable available for the rest of that job's script steps (same shell session).
- It does **not** automatically propagate to other jobs/stages — to pass a dynamically generated value to a later job, write it to a `.env` file and expose it via `artifacts:reports:dotenv`.

### `⚠️ Deprecated / Changed`
- `CI_JOB_JWT` and `CI_JOB_JWT_V2` (predefined variables that provided a JWT for OIDC-style third-party auth) are **deprecated** in favor of the `id_tokens:` keyword, which supports multiple tokens per job and an explicit `aud:` claim per token. Pipelines still referencing `$CI_JOB_JWT`/`$CI_JOB_JWT_V2` should migrate to `id_tokens:`.

## Hands-On Labs

### Lab 1: Print predefined variables
- **Goal:** See built-in variables in a job log.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - info

show_predefined_vars:
  stage: info
  script: |
    echo "Project Name: $CI_PROJECT_NAME"
    echo "Branch Name: $CI_COMMIT_REF_NAME"
    echo "Commit SHA: $CI_COMMIT_SHA"
    echo "Pipeline ID: $CI_PIPELINE_ID"
    echo "GitLab Server: $CI_SERVER_URL"
```
- **Run it:** Push to any branch, open the job log.
- **Expected result:** All five values printed, matching your project/branch/commit.
- **What this teaches:** Predefined variables need no declaration — they're always present.

### Lab 2: Custom YAML variables (global + override)
- **Goal:** Define project-specific config values directly in YAML.
- **`.gitlab-ci.yml`:**
```yaml
variables:
  APP_ENV: "production"
  DEPLOY_DIR: "/opt/webapp"
  MAX_RETRIES: "3"

stages:
  - deploy

deploy_job:
  stage: deploy
  script:
    - echo "Deploying to $APP_ENV environment"
    - echo "Files will be placed in $DEPLOY_DIR"
    - echo "Retries allowed: $MAX_RETRIES"
```
- **Run it:** Push and open the job log.
- **Expected result:** `Deploying to production environment`, `/opt/webapp`, `Retries allowed: 3`.
- **What this teaches:** Global `variables:` apply to every job unless a job overrides them.

### Lab 3: Job-level variable overrides global
- **Goal:** Prove job-level `variables:` beats global `variables:`.
- **`.gitlab-ci.yml`:**
```yaml
variables:
  ENV: "staging"

deploy_job:
  stage: deploy
  variables:
    ENV: "production"
  script:
    - echo "Deploying to $ENV"
```
- **Run it:** Push and check the log.
- **Expected result:** `Deploying to production` (not `staging`).
- **What this teaches:** Job-level `variables:` sits above global YAML variables in precedence.

### Lab 4: Project-level UI variable
- **Goal:** Store a value outside the YAML file (not committed to git).
- **Setup:** Settings > CI/CD > Variables > Add variable: key `GREETING`, value `Hello from UI`.
- **`.gitlab-ci.yml`:**
```yaml
show_ui_var:
  stage: info
  script:
    - echo "$GREETING"
```
- **Run it:** Push and check the log.
- **Expected result:** `Hello from UI`.
- **What this teaches:** UI-defined variables need no YAML declaration and keep values out of version control.

### Lab 5: Group-level variables for shared AWS credentials
- **Goal:** Share one set of credentials across multiple projects in a group.
- **Setup:** In a GitLab Group (e.g. `devops-projects/`) containing `project-A`, `project-B`, `project-C`, go to Group > Settings > CI/CD > Variables and add `AWS_ACCESS_KEY` / `AWS_SECRET_KEY` (mark masked).
- **`.gitlab-ci.yml`** (in any project inside the group):
```yaml
deploy_aws:
  stage: deploy
  script:
    - echo "Deploying using AWS credentials..."
    - aws configure set aws_access_key_id "$AWS_ACCESS_KEY"
    - aws configure set aws_secret_access_key "$AWS_SECRET_KEY"
```
- **Run it:** Push in any of the three projects.
- **Expected result:** Each project's pipeline can read the same group variable without redefining it.
- **What this teaches:** Group-level variables avoid duplicating shared secrets across every project.

### Lab 6: Protected + masked secret
- **Goal:** Restrict a secret to protected branches and hide it from logs.
- **Setup:** Settings > CI/CD > Variables > Add: key `PROD_SECRET_KEY`, value `my-super-secret-key12`, check **Protect variable** and **Mask variable**. Ensure `main` is a protected branch (Settings > Repository > Protected branches).
- **`.gitlab-ci.yml`:**
```yaml
deploy_secure:
  stage: deploy
  script:
    - echo "Deploying app..."
    - echo "Using secret key: $PROD_SECRET_KEY"
```
- **Run it:** Push to `main` (protected), then push the same file to a feature branch.
- **Expected result:** On `main`, log shows `Using secret key: [MASKED]`; on the feature branch, `$PROD_SECRET_KEY` is empty/undefined because it's not exposed there.
- **What this teaches:** Protected controls *where* a secret is available; masked controls *how* it's displayed — they're independent settings.

### Lab 7: Dynamic variable via `export` + `date`
- **Goal:** Generate a value at runtime and use it within the same job.
- **`.gitlab-ci.yml`:**
```yaml
generate_dynamic_var:
  stage: build
  script:
    - export BUILD_VERSION=$(date +%Y%m%d%H%M)
    - echo "Build version is $BUILD_VERSION"
```
- **Run it:** Push and check the log.
- **Expected result:** A timestamp-formatted version string, different on every run.
- **What this teaches:** `export` inside `script:` is scoped to that job's shell only — it will not appear in other jobs unless explicitly passed forward.

### Lab 8: Pass a dynamic variable to a later job via dotenv artifact
- **Goal:** Make a runtime-generated value available to a downstream job (fixing the limitation from Lab 7).
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - deploy

generate_version:
  stage: build
  script:
    - echo "BUILD_VERSION=$(date +%Y%m%d%H%M)" >> build.env
  artifacts:
    reports:
      dotenv: build.env

use_version:
  stage: deploy
  script:
    - echo "Deploying build $BUILD_VERSION"
```
- **Run it:** Push and check both job logs.
- **Expected result:** `use_version` prints the same `BUILD_VERSION` value `generate_version` computed.
- **What this teaches:** `artifacts:reports:dotenv` is the supported way to carry a runtime-generated variable across jobs/stages — plain `export` cannot cross job boundaries.

### Lab 9: Manually override a variable at pipeline run time
- **Goal:** Prove manually-supplied run-time variables outrank YAML-defined values.
- **`.gitlab-ci.yml`:**
```yaml
variables:
  APP_ENV: "production"

show_env:
  stage: info
  script:
    - echo "Environment: $APP_ENV"
```
- **Run it:** CI/CD > Pipelines > Run pipeline, add variable `APP_ENV` = `staging-override`, run.
- **Expected result:** Log prints `Environment: staging-override`, not `production`.
- **What this teaches:** Manually-supplied pipeline variables sit near the top of the precedence order, above `.gitlab-ci.yml`-defined variables.

### Lab 10: `id_tokens` for OIDC-style authentication (no static secret)
- **Goal:** See the modern secretless-auth pattern in a job definition (even without a live cloud target, inspect the token).
- **`.gitlab-ci.yml`:**
```yaml
oidc_demo:
  stage: deploy
  id_tokens:
    AWS_ID_TOKEN:
      aud: https://aws.example.com
  script:
    - echo "Token issued, length check only:"
    - echo -n "$AWS_ID_TOKEN" | wc -c
```
- **Run it:** Push and check the log.
- **Expected result:** A non-zero character count printed — confirms GitLab minted a short-lived signed JWT for this job with the specified audience.
- **What this teaches:** `id_tokens:` replaces the deprecated `$CI_JOB_JWT`/`$CI_JOB_JWT_V2` predefined variables; real usage exchanges this token with the cloud provider's STS/OIDC endpoint instead of storing static access keys.

### Lab 11: Restrict cross-project `CI_JOB_TOKEN` access
- **Goal:** Understand the job token allowlist by attempting a cross-project call.
- **Setup:** In Project B, add an API call from Project A's pipeline using `CI_JOB_TOKEN`, e.g. triggering Project B's pipeline via the trigger API with `-F token=$CI_JOB_TOKEN`. Before adding Project A to Project B's allowlist, the call is rejected (403); after adding Project A under Project B's Settings > CI/CD > Job token permissions, retry.
- **`.gitlab-ci.yml`** (in Project A):
```yaml
call_project_b:
  stage: deploy
  script:
    - >
      curl --request POST
      --form token="$CI_JOB_TOKEN"
      --form ref=main
      "https://gitlab.example.com/api/v4/projects/<PROJECT_B_ID>/trigger/pipeline"
```
- **Run it:** Push in Project A before and after updating Project B's allowlist.
- **Expected result:** 403/forbidden before the allowlist change; pipeline triggered successfully after.
- **What this teaches:** `CI_JOB_TOKEN` is project-scoped by default — cross-project use requires explicit opt-in from the target project.

## Common Pitfalls
- Committing real secrets into `variables:` in `.gitlab-ci.yml` — that file is version-controlled and visible to anyone with repo read access; use UI variables instead.
- Forgetting a variable is marked **Protected** and then wondering why it's empty on a feature-branch pipeline.
- Assuming `export FOO=bar` in one job's script is visible in a later job — it is not, without a dotenv artifact.
- Choosing a masked-variable value under 8 characters, or one containing characters outside the allowed set — GitLab will refuse to save it as masked.
- Forgetting that predefined variables are read-only — trying to redefine `$CI_COMMIT_SHA` yourself has no effect.
- Still referencing `$CI_JOB_JWT`/`$CI_JOB_JWT_V2` in scripts — migrate to `id_tokens:`.
- Assuming a job token automatically works across all your own projects — it needs the allowlist entry even between projects you own.

## Interview Questions & Answers
- **Q: What's the difference between a protected and a masked variable?**
  A: Protected controls *where* a variable is exposed (protected branches/tags only); masked controls *whether its value is hidden in job logs*. They're independent and often used together for secrets.
- **Q: What wins if the same variable is defined in both `.gitlab-ci.yml` and the project's UI settings?**
  A: Project-level UI variables outrank `.gitlab-ci.yml`-defined variables in the documented precedence order.
- **Q: How do you pass a dynamically computed value from one job to a later job?**
  A: Write it to a file (e.g. `KEY=value >> file.env`) and expose it via `artifacts:reports:dotenv`; plain shell `export` doesn't cross job boundaries.
- **Q: What are the requirements for a variable to be maskable?**
  A: At least 8 characters, single line, no name collision with an existing variable, and restricted to a base64-safe-ish character set unless "masked and expandable" is enabled.
- **Q: What is `CI_JOB_TOKEN` used for?**
  A: A short-lived, per-job token GitLab issues automatically to authenticate API/registry/package calls as that pipeline; scope-limited to the owning project unless the target project's allowlist permits others.
- **Q: What replaced `CI_JOB_JWT`/`CI_JOB_JWT_V2`?**
  A: The `id_tokens:` keyword — issues one or more scoped JWTs per job with an explicit `aud:` claim, used for OIDC/secretless auth to cloud providers.
- **Q: Where do group-level variables apply?**
  A: To every project inside that group (and its subgroups) — useful for shared credentials without duplicating them per project.
- **Q: What happens if you try to override a predefined variable like `CI_COMMIT_SHA`?**
  A: Nothing — predefined variables are read-only and cannot be overridden.
- **Q: Scenario — a masked variable you just added won't save, GitLab shows a validation error. What's likely wrong?**
  A: Value is shorter than 8 characters, contains a disallowed character (e.g. spaces, `$`, unescaped punctuation) for a non-expandable masked variable, or collides with an existing variable name.
- **Q: Scenario — a deploy job prints an empty value for a variable you know is set as Protected in project settings, but only on feature branches. Why?**
  A: Protected variables are withheld from pipelines running on non-protected branches/tags by design — the fix is either to protect that branch (if intended) or use a non-protected variable for feature-branch testing.
- **Q: What's the effect of `${VAR}v1` vs `$VARv1` in a script?**
  A: `${VAR}v1` correctly expands `VAR` then appends `v1`; `$VARv1` is parsed as a single variable name `VARv1`, which is usually undefined — braces disambiguate variable boundaries.
- **Q: Can you use CI/CD variables to conditionally control pipeline behavior?**
  A: Yes — combine with `rules:if` (see file 11) to gate jobs based on a variable's value, e.g. `rules: - if: '$RUN_EXTRA == "true"'`.
