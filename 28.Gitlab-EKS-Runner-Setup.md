# 28. Migrating GitLab Runner to Amazon EKS — Kubernetes Executor End-to-End Setup

## Quick Summary
- Goal: move CI job execution off a static shell/Docker/Docker-Machine runner onto GitLab Runner's **Kubernetes executor** running inside an **Amazon EKS** cluster.
- Deployment method is the **official GitLab Runner Helm chart**, not a manually-installed binary — this is GitLab's documented recommended path for Kubernetes.
- Each CI job becomes a **short-lived pod** (build container + helper container + optional service containers), not a job on a long-lived VM — this is the core mental-model shift.
- Node-level scaling is handled by the **cluster's own autoscaler** (Karpenter or Cluster Autoscaler), not by GitLab Runner itself — the Kubernetes executor has no built-in fleet autoscaler.
- AWS access from inside runner pods should use **IRSA (IAM Roles for Service Accounts)**, not long-lived AWS access keys stored as CI/CD variables.
- This migration is directly relevant because the old **Docker Machine executor is deprecated (GitLab 17.5) and scheduled for removal in GitLab 20.0 (~May 2027)** — teams still on Docker+Machine autoscaling on AWS EC2 need an exit path, and the Kubernetes executor on EKS is GitLab's recommended one.
- Common motivations besides the deprecation: faster job start times (no VM boot), no AMI/fleet patching, native integration with existing EKS-based infrastructure.

## Core Concepts

### Why migrate off shell / Docker Machine
- Docker Machine executor: **deprecated in GitLab 17.5**, scheduled for **removal in GitLab 20.0 (May 2027)** — Docker itself deprecated the underlying `docker-machine` tool, GitLab can no longer maintain it safely.
- Shell/Docker executors on static EC2 instances: no job isolation between builds on the same host (shell executor), manual patching, no scale-to-zero.
- Kubernetes executor on EKS: each job gets a fresh, isolated pod; scales with the cluster; GitLab's currently-recommended path for AWS-hosted, high-throughput CI.
- ⚠️ Deprecated / Changed: GitLab recommends the **GitLab Runner Autoscaler** (fleeting plugin for EC2/Azure/GCE) as the alternative *if you want to stay VM-based*; this tutorial covers the **Kubernetes executor on EKS** path specifically, which is the more common choice when a team already runs EKS.

### Deployment architecture
- `gitlab-runner` Helm release runs one or more **manager pods** inside the EKS cluster (in, e.g., a `gitlab-runner` namespace).
- The manager pod polls GitLab for jobs; for each job it creates a **new pod** via the Kubernetes API containing:
  - a **build container** (the `image:` from `.gitlab-ci.yml` or a Helm-configured default),
  - a **helper container** (clones the repo, manages artifacts/cache),
  - one **service container per `services:` entry** (e.g. `docker:dind`, `postgres`), reachable over `localhost` inside the pod.
- Pod is deleted after the job finishes — nothing persists on the pod's local disk between jobs, which is why remote caching (S3) matters.

### Runner registration — current method
- GitLab has moved to **runner authentication tokens** (`glrt-` prefix), created first via UI (**Settings > CI/CD > Runners > New instance/group/project runner**) or the API — NOT the older shared **registration token** flow.
- ⚠️ Deprecated / Changed: registration tokens and several legacy `register` arguments are deprecated and **scheduled for removal in GitLab 20.0** — always create the runner in the UI/API first and pass the resulting `glrt-...` token as `runnerToken` in Helm values.

### Required Helm values (minimum viable)
- `gitlabUrl` — full GitLab server URL (e.g. `https://gitlab.com/`).
- `runnerToken` — the `glrt-...` authentication token from the runner you created in the UI.
- `rbac.create: true` — lets the chart create the Role/RoleBinding/ServiceAccount the manager needs to create job pods.
- `concurrent` — max jobs the manager will run in parallel across the cluster (each spawns its own pod).
- `runners.config` — a raw **TOML** block (not YAML) injected into `config.toml`, this is where `[runners.kubernetes]` settings live (namespace, image, resource requests/limits, privileged mode, etc.).

### Kubernetes executor resource controls (per job)
- `cpu_request` / `cpu_limit`, `memory_request` / `memory_limit` — for the **build** container.
- `helper_cpu_request` / `helper_memory_request` (etc.) — for the **helper** container; GitLab recommends ≥250 MiB memory when caching is enabled.
- `service_cpu_request` / `service_memory_request` (etc.) — for **service** containers (`docker:dind`, databases, etc.).
- Per-job overrides via CI/CD variables: `KUBERNETES_CPU_REQUEST`, `KUBERNETES_MEMORY_LIMIT`, `KUBERNETES_HELPER_*`, `KUBERNETES_SERVICE_*` — capped by matching `*_overwrite_max_allowed` settings so a job can't request unbounded resources.
- Unset requests make it hard for the cluster autoscaler to bin-pack/scale correctly — always set at least `cpu_request`/`memory_request`.

### IRSA — AWS access without static credentials
- IRSA = binds a Kubernetes **ServiceAccount** to an AWS **IAM Role** via the cluster's OIDC provider; pods using that ServiceAccount get temporary AWS credentials injected automatically (`AWS_ROLE_ARN` + `AWS_WEB_IDENTITY_TOKEN_FILE` env vars).
- Setup is two steps: (1) `eksctl utils associate-iam-oidc-provider` once per cluster, (2) `eksctl create iamserviceaccount` per role/ServiceAccount pair.
- Helm chart wiring: `rbac.serviceAccountAnnotations: {eks.amazonaws.com/role-arn: <ROLE_ARN>}` plus `runners.serviceAccountName` pointing at that ServiceAccount.
- Typical uses on an EKS runner: S3 access for distributed cache, ECR pull/push for Docker builds, Secrets Manager/SSM for deploy credentials.
- ⚠️ Don't mix IRSA with node **instance-profile** permissions on the same workload — pick one model per pod to avoid confusing which credentials actually apply.

### Distributed caching (S3)
- Local pod disk cache is useless across jobs — pods are ephemeral and usually scheduled on different nodes each time.
- Configure `runners.cache` in Helm values with `s3ServerAddress`, `s3BucketName`, `s3BucketLocation`, and either `secretName` (referencing a Kubernetes Secret with S3 creds) or **IRSA** (no static keys needed if the ServiceAccount already has S3 permissions).
- Without this, every job re-downloads dependencies (`npm install`, `.m2/repository`, etc.) from scratch — a common source of "why did my pipeline get slower after migrating to Kubernetes?" complaints.

### Node-level autoscaling
- The Kubernetes executor itself does **not** scale EC2 nodes — that's the job of **Karpenter** or the **Cluster Autoscaler**, reacting to pending pods' resource requests.
- Known real-world gotcha (Karpenter): nodes can be marked `Ready` before the kubelet's certificate-signing request is approved, causing `tls: internal error` failures for the first pod scheduled — mitigated with a Karpenter `startupTaints` entry (e.g. `node.kubernetes.io/csr-pending`) removed only after CSR approval.
- Preferring **fewer, larger nodes** over many small ones reduces node churn and control-plane load during CI traffic spikes.

### ⚠️ Deprecated / Changed (summary)
- Docker Machine executor: deprecated GitLab 17.5, removal GitLab 20.0 (~May 2027) — the reason this migration exists.
- Runner registration tokens (shared secret + interactive `register`): deprecated, scheduled for removal GitLab 20.0 — use runner authentication tokens (`glrt-`) instead.
- `CI_JOB_JWT`/`CI_JOB_JWT_V2`: deprecated in favor of `id_tokens:` (relevant if your migrated pipelines also authenticate to AWS via OIDC from *inside* the job, separate from the runner's own IRSA identity — see file 12).

## Hands-On Labs (progressively builds a full migration)

### Lab 1: Prerequisites check
- **Goal:** Confirm tooling before touching the cluster.
- **Steps:**
  ```bash
  aws --version
  eksctl version
  kubectl version --client
  helm version
  aws eks update-kubeconfig --name <your-eks-cluster> --region <region>
  kubectl get nodes
  ```
- **Expected result:** All four CLIs report a version; `kubectl get nodes` lists your EKS worker nodes.
- **What this teaches:** The Kubernetes executor needs a working EKS cluster and locally-authenticated `kubectl`/`helm` before any GitLab-side steps.

### Lab 2: Create a namespace and a runner authentication token
- **Goal:** Prepare the cluster namespace and get a current-style `glrt-` token.
- **Steps:**
  1. `kubectl create namespace gitlab-runner`
  2. In GitLab: **Settings > CI/CD > Runners > New project runner** (or group/instance runner).
  3. Set tags, e.g. `eks`, `k8s-executor`; leave "Run untagged jobs" unchecked for now.
  4. Click **Create runner**, copy the `glrt-...` token shown (shown once).
- **Expected result:** A new runner listed as "Never contacted" in **Settings > CI/CD > Runners**, and a `glrt-...` token in hand.
- **What this teaches:** Modern GitLab issues a per-runner authentication token up front — you no longer register against a shared project/group registration token.

### Lab 3: Minimal Helm install of the Kubernetes executor
- **Goal:** Get a runner picking up jobs with the smallest possible config.
- **`values-minimal.yaml`:**
  ```yaml
  gitlabUrl: https://gitlab.com/
  runnerToken: "glrt-REPLACE_ME"
  concurrent: 5
  rbac:
    create: true
  runners:
    config: |
      [[runners]]
        [runners.kubernetes]
          namespace = "gitlab-runner"
          image = "alpine:3.20"
  ```
- **Run it:**
  ```bash
  helm repo add gitlab https://charts.gitlab.io
  helm repo update
  helm install gitlab-runner gitlab/gitlab-runner \
    --namespace gitlab-runner -f values-minimal.yaml
  kubectl get pods -n gitlab-runner
  ```
- **Expected result:** A `gitlab-runner-*` manager pod is `Running`; the runner shows as green/online in the GitLab UI.
- **What this teaches:** The chart only strictly needs `gitlabUrl`, `runnerToken`, and `rbac.create: true` to come online — everything else is tuning.

### Lab 4: Run a job and watch the ephemeral job pod
- **Goal:** See the per-job pod lifecycle firsthand.
- **`.gitlab-ci.yml`:**
  ```yaml
  test_on_eks:
    tags: [eks]
    script:
      - echo "Running on Kubernetes executor"
      - hostname
      - sleep 20
  ```
- **Run it:** Push, then immediately run `kubectl get pods -n gitlab-runner -w`.
- **Expected result:** A new `runner-<id>-project-<id>-concurrent-<n>` pod appears, goes `Running`, then disappears once the job finishes.
- **What this teaches:** Confirms the "one pod per job, then it's gone" model — nothing written to that pod's local disk survives to the next job.

### Lab 5: Set resource requests/limits for build, helper, and service containers
- **Goal:** Give the cluster autoscaler something to bin-pack against, and stop noisy-neighbor jobs.
- **`values.yaml` addition:**
  ```yaml
  runners:
    config: |
      [[runners]]
        [runners.kubernetes]
          namespace = "gitlab-runner"
          cpu_request = "250m"
          cpu_limit = "1"
          memory_request = "256Mi"
          memory_limit = "1Gi"
          helper_cpu_request = "100m"
          helper_memory_request = "250Mi"
          service_cpu_request = "250m"
          service_memory_request = "256Mi"
  ```
- **Run it:** `helm upgrade gitlab-runner gitlab/gitlab-runner -n gitlab-runner -f values.yaml`, then re-run Lab 4's job and `kubectl describe pod <job-pod> -n gitlab-runner`.
- **Expected result:** The pod spec shows the requests/limits you set on each container.
- **What this teaches:** Without explicit requests, the scheduler/autoscaler has no signal to size nodes correctly — this is the #1 cause of "runner pods stuck Pending forever."

### Lab 6: Enable Docker builds inside the Kubernetes executor (privileged + dind service)
- **Goal:** Run `docker build` from within a job pod.
- **`.gitlab-ci.yml`:**
  ```yaml
  build_image:
    tags: [eks]
    image: docker:27
    services:
      - docker:27-dind
    variables:
      DOCKER_TLS_CERTDIR: "/certs"
    script:
      - docker build -t myapp:$CI_COMMIT_SHORT_SHA .
  ```
- **`values.yaml` addition:**
  ```yaml
  runners:
    config: |
      [[runners]]
        [runners.kubernetes]
          privileged = true
  ```
- **Run it:** `helm upgrade ...` then push.
- **Expected result:** `docker build` succeeds inside the pod's dind service container.
- **What this teaches:** `privileged: true` is required for Docker-in-Docker on the Kubernetes executor — a real security tradeoff (see Common Pitfalls) worth weighing against Kaniko for image builds without a privileged pod.

### Lab 7: Set up IRSA for S3 access via eksctl
- **Goal:** Give runner job pods AWS credentials without static keys.
- **Steps:**
  ```bash
  eksctl utils associate-iam-oidc-provider --cluster <your-eks-cluster> --approve

  eksctl create iamserviceaccount \
    --cluster <your-eks-cluster> \
    --name gitlab-runner \
    --namespace gitlab-runner \
    --attach-policy-arn arn:aws:iam::aws:policy/AmazonS3FullAccess \
    --approve
  ```
- **Run it:** `kubectl get sa gitlab-runner -n gitlab-runner -o yaml`
- **Expected result:** The ServiceAccount YAML shows an `eks.amazonaws.com/role-arn` annotation pointing at a new IAM role `eksctl-...`.
- **What this teaches:** `eksctl create iamserviceaccount` does the OIDC trust-policy wiring for you — no hand-written IAM JSON needed for the common case.

### Lab 8: Wire the Helm chart to use the IRSA service account + configure S3 cache
- **Goal:** Point the runner at the IRSA-bound ServiceAccount and enable a shared S3 cache.
- **`values.yaml` addition:**
  ```yaml
  rbac:
    create: true
    serviceAccountAnnotations:
      eks.amazonaws.com/role-arn: "arn:aws:iam::<ACCOUNT_ID>:role/eksctl-<cluster>-addon-iamserviceaccount-..."
  runners:
    serviceAccountName: gitlab-runner
    cache:
      Type: s3
      Path: "runner-cache"
      Shared: true
      s3ServerAddress: s3.amazonaws.com
      s3BucketName: my-gitlab-runner-cache-bucket
      s3BucketLocation: <region>
  ```
- **Run it:** `helm upgrade gitlab-runner gitlab/gitlab-runner -n gitlab-runner -f values.yaml`, then run a job with a `cache:` block twice in a row.
- **Expected result:** Second run's cache-restore step shows a cache hit downloaded from S3 (check job log for "Downloading cache" vs "Creating cache").
- **What this teaches:** Because job pods are ephemeral, remote (S3) cache — not local disk — is what makes `cache:` actually useful on the Kubernetes executor.

### Lab 9: Migrate cutover — run old and new runners side by side, then switch traffic
- **Goal:** Move real pipeline traffic from the legacy shell/Docker Machine runner to the new EKS runner without a hard cutover.
- **Steps:**
  1. Tag the new EKS runner `eks` (already done above); leave the legacy runner's existing tag (e.g. `legacy-vm`) untouched.
  2. In a handful of low-risk projects, change `tags: [legacy-vm]` to `tags: [eks]` in `.gitlab-ci.yml` and merge.
  3. Watch those pipelines for a few days; compare job duration and failure rate against the legacy runner's history.
  4. Roll the tag change out project-by-project (or via a shared CI template if you use `include:`, see file 21) until nothing targets `legacy-vm`.
- **Run it:** `kubectl top pods -n gitlab-runner` and GitLab's **Runners** admin page to watch load shift.
- **Expected result:** Job volume on the legacy runner drops to zero over the rollout; the EKS runner's job count climbs.
- **What this teaches:** Tag-based routing lets you migrate incrementally and roll back a single project instantly by reverting its tag, instead of a risky big-bang cutover.

### Lab 10: Decommission the legacy runner
- **Goal:** Finish the migration by retiring the old runner.
- **Steps:**
  1. Confirm zero jobs have run on the legacy runner in the last N days (**Runners** admin page, "Last contact"/job history).
  2. Pause it first (**Runners > (legacy runner) > Pause**) rather than deleting immediately — pausing stops new jobs but keeps history/config visible.
  3. After a safe observation window, delete the runner registration and decommission/terminate the underlying EC2 instance or Docker Machine fleet.
- **Expected result:** Only the EKS-based runner remains active; legacy VM/instance costs stop accruing.
- **What this teaches:** Pause-before-delete gives you a fast rollback switch during migration; deleting is the point of no return.

### Lab 11: Autoscale the underlying EKS nodes with Karpenter (avoid the TLS-bootstrap race)
- **Goal:** Let node count follow CI load instead of running a fixed-size node group.
- **`NodePool` (Karpenter) excerpt:**
  ```yaml
  apiVersion: karpenter.sh/v1
  kind: NodePool
  metadata:
    name: gitlab-runners
  spec:
    template:
      spec:
        startupTaints:
          - key: node.kubernetes.io/csr-pending
            effect: NoSchedule
        requirements:
          - key: karpenter.sh/capacity-type
            operator: In
            values: ["on-demand"]
    limits:
      cpu: "1000"
  ```
- **Run it:** Fire a burst of 20+ parallel jobs (e.g. a `parallel: 20` job from file 20) and watch `kubectl get nodes -w`.
- **Expected result:** New nodes appear as pending pods accumulate, and job pods only get scheduled onto a node once its `csr-pending` startup taint is removed (i.e., after kubelet's certificate is approved).
- **What this teaches:** A documented real-world failure mode is nodes marked `Ready` before their kubelet TLS bootstrap finishes, causing random `tls: internal error` job failures — a `startupTaints` entry closes that race instead of just retrying jobs.

### Lab 12: Upgrade and roll back the runner deployment safely
- **Goal:** Practice changing runner config without an outage, and reversing a bad change.
- **Run it:**
  ```bash
  helm upgrade gitlab-runner gitlab/gitlab-runner -n gitlab-runner -f values.yaml
  helm history gitlab-runner -n gitlab-runner
  helm rollback gitlab-runner <PREVIOUS_REVISION> -n gitlab-runner
  ```
- **Expected result:** `helm history` lists each prior revision; `helm rollback` restores the manager pod to the previous config within seconds.
- **What this teaches:** Because the manager deployment is just a Helm release, config changes (resource limits, image, cache backend) are versioned and reversible the same way any other Helm-managed workload is.

## Common Pitfalls
- Forgetting `rbac.create: true` — the manager pod can authenticate to GitLab fine but can't create job pods, jobs sit stuck.
- Using the deprecated shared **registration token** instead of a per-runner `glrt-` authentication token — works today but is on the deprecation path (removal targeted GitLab 20.0).
- No `cpu_request`/`memory_request` set — cluster/Karpenter autoscaler can't size nodes correctly, leading to over-provisioned or perpetually-`Pending` job pods.
- No S3 (or equivalent) cache configured — every job re-downloads dependencies since pod-local disk never survives between jobs, silently erasing the speed benefit of migrating.
- `privileged: true` used for Docker-in-Docker builds without evaluating Kaniko/buildah as a rootless alternative — a real security tradeoff, not just a checkbox.
- Mixing IRSA role permissions with node **instance-profile** permissions on the same workload — pick one model, mixing makes it unclear which credentials actually apply to a given AWS call.
- Migrating all projects to the new runner in one shot instead of tag-based incremental rollout — removes your fast rollback path.
- Ignoring the Karpenter/EKS TLS-bootstrap race (nodes `Ready` before kubelet CSR approval) — shows up as intermittent, hard-to-reproduce `tls: internal error` job failures under autoscaling load.
- Deleting the legacy runner immediately instead of pausing it first — removes the instant-rollback option during the observation window.

## Interview Questions & Answers
- **Q: Why would a team migrate GitLab Runner from Docker Machine to the Kubernetes executor on EKS?**
  A: Docker Machine executor is deprecated (GitLab 17.5) with removal targeted for GitLab 20.0; Kubernetes executor gives per-job pod isolation, faster job start (no VM boot), and scales via the cluster's own autoscaler.
- **Q: What are the three container types inside a single Kubernetes-executor job pod?**
  A: Build container (runs `script:`), helper container (clones repo, handles cache/artifacts), and one service container per `services:` entry.
- **Q: How does the Kubernetes executor scale out — does GitLab Runner itself provision EC2 nodes?**
  A: No — GitLab Runner only creates pods; actual node provisioning/scaling is done by the cluster's own autoscaler (Karpenter or Cluster Autoscaler), reacting to pending pods' resource requests.
- **Q: What is IRSA and why prefer it over CI/CD variables holding AWS access keys?**
  A: IAM Roles for Service Accounts binds a Kubernetes ServiceAccount to an AWS IAM role via the cluster's OIDC provider, giving pods short-lived, automatically-rotated credentials instead of long-lived static keys stored as secrets.
- **Q: Scenario — after migrating to the Kubernetes executor, pipelines got slower, not faster. What's the likely cause?**
  A: Almost certainly no remote (S3) cache configured — job pods are ephemeral, so without `runners.cache` pointed at S3, every job re-downloads dependencies from scratch every time.
- **Q: Scenario — job pods stay `Pending` indefinitely after migrating to EKS. What would you check first?**
  A: Whether `rbac.create: true` is set (manager needs permission to create pods), whether `cpu_request`/`memory_request` are set so the autoscaler can size nodes, and whether the cluster autoscaler/Karpenter is actually configured to add nodes for this workload.
- **Q: Why is `privileged: true` needed for Docker-in-Docker builds on the Kubernetes executor, and what's the alternative?**
  A: `docker:dind` needs privileged mode to run its own Docker daemon inside the pod; Kaniko or buildah can build images without a privileged container, trading some convenience for a smaller security footprint.
- **Q: How do you migrate pipelines from an old runner to a new EKS-based runner with a rollback path?**
  A: Tag-based incremental rollout — give the new runner a distinct tag, switch `tags:` project by project, monitor, and revert a single project's tag instantly if something breaks, rather than a big-bang cutover.
- **Q: What real-world failure mode has been reported with Karpenter-autoscaled EKS nodes running GitLab Runner job pods, and how is it mitigated?**
  A: Nodes get marked `Ready` before the kubelet's certificate-signing request is approved, causing `tls: internal error` job failures on pods scheduled too early; mitigated with a Karpenter `startupTaints` entry removed only after CSR approval.
- **Q: What GitLab Runner registration method is current, and what's deprecated?**
  A: Current: create the runner in the UI/API first, get a `glrt-...` authentication token, pass it as `runnerToken`. Deprecated (removal targeted GitLab 20.0): the shared project/group registration-token + interactive `register` flow.
- **Q: How would you safely change the runner's resource limits in production?**
  A: Edit `values.yaml`, `helm upgrade` the release, verify via `kubectl describe pod`/a test job, and keep `helm history` handy so `helm rollback` can undo it in seconds if something's wrong.
