# 9. Get Started with `.gitlab-ci.yml` — Beginner Pipeline (No Docker)

## Quick Summary
- This is the "hello world" of GitLab CI/CD: build -> test -> deploy, using plain shell commands, no Docker/Java/Kubernetes required.
- Goal is to see a real pipeline execute end-to-end on GitLab's shared runners before adding any complexity.
- Uses `artifacts` to pass a file from the build job to the test job — the same mechanism real pipelines use for compiled binaries, JARs, or build reports.
- Uses `rules:` (not the deprecated `only:`) to restrict the deploy job to the default branch.
- Once this pattern clicks, everything in the advanced flagship pipeline (file 8) is the same shape with more steps and real tools swapped in for `echo`.

## Core Concepts
- **Where GitLab looks for the pipeline file:** root of the repo, filename `.gitlab-ci.yml` (dot-prefixed, exact name; configurable path in Settings -> CI/CD -> General pipelines but root is the default and by far the most common).
- **`stages:`** declares the ordered phases; jobs are assigned to a stage with `stage:`.
- **Jobs run on shared runners by default** — no runner setup needed to follow this file; see file 10 for what a runner actually is.
- **`artifacts:`** — files a job produces that should survive into later stages and be downloadable from the job page.
- **`script:`** — plain shell commands; any command available in the job's base image runs here (default image is a minimal Linux environment provided by the runner unless overridden with `image:`).
- **`rules:`** is the current, non-deprecated way to gate a job to specific branches/conditions (see file 8's Core Concepts for the fuller reference — `only:`/`except:` are deprecated).
- **Pipeline visibility:** every push that includes/changes `.gitlab-ci.yml` (or any push once it exists) triggers a pipeline visible under **CI/CD -> Pipelines**; each job's live/completed output is under **Job -> trace/log**.

### ⚠️ Deprecated / Changed
- The original version of this walkthrough used `only: - main` on the deploy job. `only:`/`except:` are deprecated — this file now uses `rules: - if: '$CI_COMMIT_BRANCH == "main"'` throughout.

## Hands-On Labs

### Lab 1: Build -> test -> deploy with a shell script (foundational)
- **Goal:** Get a complete, working pipeline running with zero external dependencies.
- **Steps:**
  1. **New project -> Create blank project**, name it `gitlab-simple-ci`.
  2. Add `hello.sh`:
     ```bash
     #!/bin/bash
     echo "Hello, GitLab CI/CD is running successfully!"
     ```
     Make it executable locally if you cloned it: `chmod +x hello.sh`.
  3. Add `.gitlab-ci.yml` at the repo root:
     ```yaml
     stages:
       - build
       - test
       - deploy

     build_job:
       stage: build
       script:
         - echo "Building the project..."
         - mkdir build
         - echo "Build completed successfully!" > build/build_output.txt
       artifacts:
         paths:
           - build/

     test_job:
       stage: test
       script:
         - echo "Running tests..."
         - if [ -f build/build_output.txt ]; then echo "Test passed"; else echo "Test failed" && exit 1; fi

     deploy_job:
       stage: deploy
       script:
         - echo "Deploying application..."
         - echo "Deployed successfully by GitLab CI/CD!"
       rules:
         - if: '$CI_COMMIT_BRANCH == "main"'
     ```
- **Run it:** Commit and push (`git add . && git commit -m "Add simple GitLab CI pipeline" && git push origin main`), then **CI/CD -> Pipelines**.
- **Expected result:** Pipeline graph shows `build -> test -> deploy`, all green; `deploy_job` only appears because the push was to `main`.
- **What this teaches:** The minimum realistic pipeline shape — artifacts flowing between stages, and a branch-gated deploy — without any tooling overhead.

### Lab 2: Inspect job logs and artifacts
- **Goal:** Learn where pipeline output and produced files actually live.
- **Steps:**
  1. Open the pipeline from Lab 1.
  2. Click `build_job` -> view the job trace.
  3. Click **Browse** (or download) under the job's Artifacts panel.
- **Run it:** Confirm `build/build_output.txt` is present and contains "Build completed successfully!".
- **Expected result:** Log shows each `script:` line and its output in order; artifact browser shows the `build/` directory.
- **What this teaches:** The job trace is the primary debugging tool; artifacts are inspectable independent of re-running the job.

### Lab 3: Make the test job actually fail
- **Goal:** See pipeline failure behavior, not just the happy path.
- **`.gitlab-ci.yml` (change to `build_job`):**
  ```yaml
  build_job:
    stage: build
    script:
      - echo "Building the project..."
      - mkdir build
      # Intentionally skip creating build_output.txt
  ```
- **Run it:** Push and watch the pipeline.
- **Expected result:** `test_job` fails (`exit 1` from the missing-file check); pipeline status is red; `deploy_job` does not run because the stage before it failed.
- **What this teaches:** A failed job blocks later stages by default — this is what "quality gate" means in a pipeline.

### Lab 4: Add a `variables:` block
- **Goal:** Avoid repeating a literal string across jobs.
- **`.gitlab-ci.yml`:**
  ```yaml
  variables:
    GREETING: "Hello from CI"

  build_job:
    stage: build
    script:
      - echo "$GREETING"
      - mkdir build
      - echo "Build completed successfully!" > build/build_output.txt
    artifacts:
      paths:
        - build/
  ```
- **Run it:** Check `build_job`'s log.
- **Expected result:** Log prints `Hello from CI` — the variable substituted into the shell command.
- **What this teaches:** Global `variables:` are available as environment variables in every job's `script:`.

### Lab 5: Run on every branch, not just `main`
- **Goal:** Understand rule scoping by testing on a feature branch.
- **Steps:**
  1. `git checkout -b feature/try-ci`.
  2. Push the same `.gitlab-ci.yml` from Lab 1 unchanged.
- **Run it:** Push and check **CI/CD -> Pipelines** for the feature branch.
- **Expected result:** `build_job` and `test_job` run normally; `deploy_job` is absent from the pipeline (rule didn't match `main`).
- **What this teaches:** `rules:` decides per-pipeline whether a job is even created — confirms the deploy gate actually works, not just that it looks right in the YAML.

### Lab 6: Add a second, independent job in the same stage
- **Goal:** See parallel execution within a stage.
- **`.gitlab-ci.yml` (add alongside `test_job`):**
  ```yaml
  lint_job:
    stage: test
    script:
      - echo "Pretending to lint hello.sh..."
      - bash -n hello.sh && echo "Syntax OK"
  ```
- **Run it:** Push and open the pipeline graph.
- **Expected result:** `test_job` and `lint_job` both appear in the `test` stage and run concurrently (subject to available runners).
- **What this teaches:** Stage is a synchronization point, not a queue — everything in one stage can run at once.

### Lab 7: Use `when: manual` for the deploy job
- **Goal:** Require a human click before "deploying."
- **`.gitlab-ci.yml` (change to `deploy_job`):**
  ```yaml
  deploy_job:
    stage: deploy
    script:
      - echo "Deploying application..."
    rules:
      - if: '$CI_COMMIT_BRANCH == "main"'
        when: manual
  ```
- **Run it:** Push to `main`, open the pipeline.
- **Expected result:** `deploy_job` sits with a play button instead of auto-running; pipeline only completes fully once you trigger it manually.
- **What this teaches:** The exact mechanism used for real production deploy gates — same pattern scales to the advanced pipeline in file 8.

### Lab 8: Set artifact expiry
- **Goal:** Avoid accumulating storage from every pipeline run.
- **`.gitlab-ci.yml` (change to `build_job`):**
  ```yaml
  build_job:
    stage: build
    script:
      - mkdir build
      - echo "Build completed successfully!" > build/build_output.txt
    artifacts:
      paths:
        - build/
      expire_in: 3 days
  ```
- **Run it:** Push, then check the Artifacts panel on the job page.
- **Expected result:** Panel shows an expiration date/countdown for the artifact.
- **What this teaches:** `expire_in` is a real cost/hygiene control, not just cosmetic — worth setting on every artifact-producing job.

### Lab 9: Add a Python "app" and a real test command
- **Goal:** Replace toy `echo` commands with something closer to a real app, still no Docker.
- **Steps:**
  1. Add `app.py`:
     ```python
     def add(a, b):
         return a + b

     if __name__ == "__main__":
         print(add(2, 3))
     ```
  2. Add `test_app.py`:
     ```python
     from app import add

     def test_add():
         assert add(2, 3) == 5
     ```
  3. `.gitlab-ci.yml`:
     ```yaml
     stages:
       - build
       - test

     build_job:
       stage: build
       image: python:3.12-slim
       script:
         - python app.py

     test_job:
       stage: test
       image: python:3.12-slim
       script:
         - pip install pytest
         - pytest -v
     ```
- **Run it:** Push and check both job logs.
- **Expected result:** `build_job` prints `5`; `test_job` shows pytest output with 1 passed.
- **What this teaches:** Swapping `image:` is how a pipeline gets a real language toolchain — the pipeline shape (stages/jobs/artifacts/rules) doesn't change.

### Lab 10: Cache dependencies instead of reinstalling every run
- **Goal:** Speed up the Python pipeline from Lab 9 using `cache:` (distinct from `artifacts:`).
- **`.gitlab-ci.yml`:**
  ```yaml
  test_job:
    stage: test
    image: python:3.12-slim
    cache:
      key: pip-cache
      paths:
        - .cache/pip
    variables:
      PIP_CACHE_DIR: "$CI_PROJECT_DIR/.cache/pip"
    script:
      - pip install pytest
      - pytest -v
  ```
- **Run it:** Push twice in a row and compare the `pip install` step timing in each run's log.
- **Expected result:** Second run's `pip install` is noticeably faster (cache hit), though not guaranteed instant — cache is best-effort, not a hard guarantee.
- **What this teaches:** `cache:` speeds up repeated dependency installs across pipeline runs; unlike `artifacts:`, it isn't meant for passing required build outputs downstream and isn't downloadable from the UI.

### Lab 11: Point the deploy job at an `environment`
- **Goal:** Get this beginner pipeline to show up in GitLab's Environments view.
- **`.gitlab-ci.yml` (change to `deploy_job`):**
  ```yaml
  deploy_job:
    stage: deploy
    script:
      - echo "Deploying application..."
    environment:
      name: staging
    rules:
      - if: '$CI_COMMIT_BRANCH == "main"'
  ```
- **Run it:** Push to `main`, then check **Operate -> Environments** (or **Deployments -> Environments**).
- **Expected result:** A `staging` environment appears with a deployment record linked to this pipeline/job.
- **What this teaches:** `environment:` is a one-line addition that turns a plain deploy job into something GitLab tracks as an actual deployment, laying groundwork for the multi-environment and approval-gate patterns covered later in this series.

## Common Pitfalls
- Forgetting the leading dot in `.gitlab-ci.yml` — GitLab won't detect a pipeline file named `gitlab-ci.yml`.
- Expecting `deploy_job` to run on a feature branch — the `rules:` gate is working as intended if it doesn't.
- Confusing `artifacts:` (guaranteed, downloadable, passed between stages) with `cache:` (best-effort speed optimization, not for required build outputs).
- Not checking the job trace before assuming "the pipeline is broken" — most beginner failures are visible in the first few log lines.
- Writing `only: [main]` because an old tutorial/example used it — use `rules:` instead.

## Interview Questions & Answers
- **Q: What's the simplest possible working `.gitlab-ci.yml`?**
  A: A `stages:` list plus one job with a `stage:` and `script:` — no `image`, `artifacts`, or `rules` are strictly required.
- **Q: How does GitLab know to run a pipeline at all?**
  A: It detects `.gitlab-ci.yml` at the repo root (or the configured custom path) on any push/event matching the project's pipeline triggers.
- **Q: What happens if a job in an earlier stage fails?**
  A: By default, later stages don't run — the pipeline stops and is marked failed, unless the failing job has `allow_failure: true`.
- **Q: Why use `artifacts:` here instead of just relying on the git checkout in the next job?**
  A: Each job starts from a fresh checkout of the repo; artifacts are the only supported way to carry files a previous job generated (not committed to git) into a later job.
- **Q: What's the difference between `cache:` and `artifacts:`?**
  A: Cache speeds up repeated work (e.g., dependency installs) across pipeline runs and is best-effort/not guaranteed; artifacts are guaranteed outputs of a specific job run, passed to later stages and downloadable from the UI.
- **Q: How do you restrict a job to only run on the default branch using current syntax?**
  A: `rules: - if: '$CI_COMMIT_BRANCH == "main"'` (not the deprecated `only: - main`).
- **Q: Scenario — you pushed to a feature branch and the deploy job never appears in the pipeline, no error. What's going on?**
  A: Expected behavior — the `rules:` condition didn't match, so GitLab excluded the job from that pipeline entirely rather than running and skipping it.
- **Q: Scenario — a beginner asks why their pipeline "does nothing" after adding `.gitlab-ci.yml`. What do you check first?**
  A: Filename/path exactly `.gitlab-ci.yml` at repo root, valid YAML (use the CI/CD -> Editor -> Lint tool), and that a runner is available (shared runners are on by default for gitlab.com projects).
- **Q: What does `when: manual` do and where would you use it in a beginner pipeline like this one?**
  A: Turns a job into a manually-triggered gate instead of automatic; commonly used on the deploy stage so a human confirms before anything ships.
- **Q: How would you extend this beginner pipeline toward the advanced Docker/Kubernetes one in file 8?**
  A: Swap `image:` to a real toolchain image (Maven, Python, Node), add `services: [docker:dind]` plus a `docker` stage once containerizing, and replace the `deploy_job` echo commands with real `kubectl`/cloud CLI calls guarded by `rules:` and `environment:` — the stage/job/artifact/rules skeleton stays identical.
