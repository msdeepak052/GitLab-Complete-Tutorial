# **Job dependencies in GitLab CI/CD** 

## **1️⃣ What are Dependencies in GitLab CI/CD?**

In GitLab CI/CD, a **job** is a set of instructions to perform a task. Sometimes jobs rely on the **output or artifacts of another job**. These are called **dependencies**.

There are two main ways to control job order and sharing:

1. **Stages** → High-level control (jobs in a stage run in parallel, next stage runs after current stage completes).
2. **Dependencies (job-level)** → Fine-grained control: a job explicitly depends on artifacts of specific previous jobs, even if they are in the same stage.

---

### **2️⃣ Using Stages for Ordering**

Simplest example:

```yaml
stages:
  - build
  - test
  - deploy

build_job:
  stage: build
  script:
    - echo "Building app..."
    - mkdir output
    - echo "app built" > output/result.txt
  artifacts:
    paths:
      - output/

test_job:
  stage: test
  script:
    - cat output/result.txt
```

✅ **Explanation**:

* `build_job` runs first because it’s in the `build` stage.
* `test_job` runs after `build_job` because it’s in the `test` stage.
* `artifacts` from `build_job` are automatically available to `test_job` (default behavior if stages are sequential).

---

### **3️⃣ Using `dependencies:` for Explicit Control**

Sometimes you want **specific jobs to receive artifacts** and ignore others.

```yaml
stages:
  - build
  - test

build_job_a:
  stage: build
  script:
    - echo "Build A" > output_a.txt
  artifacts:
    paths:
      - output_a.txt

build_job_b:
  stage: build
  script:
    - echo "Build B" > output_b.txt
  artifacts:
    paths:
      - output_b.txt

test_job:
  stage: test
  dependencies:
    - build_job_a
  script:
    - echo "Testing..."
    - cat output_a.txt
    - cat output_b.txt || echo "output_b.txt not available"
```

✅ **Explanation**:

* `test_job` **depends only on `build_job_a`**.
* `output_b.txt` from `build_job_b` will **not** be available in `test_job`.
* This reduces unnecessary artifact downloads and speeds up the pipeline.

---

### **4️⃣ Why Dependencies Are Useful**

* **Control artifact flow**: Only download what is needed.
* **Skip unrelated jobs**: If jobs are independent, they won’t block each other.
* **Complex pipelines**: For monorepos or multiple microservices, you might only need artifacts from certain jobs.

---

### **5️⃣ Parallel Jobs and Dependencies**

You can have multiple jobs in the same stage **run in parallel**, then a later job pick artifacts only from some of them.

```yaml
stages:
  - build
  - package

build_frontend:
  stage: build
  script:
    - echo "frontend" > frontend.txt
  artifacts:
    paths:
      - frontend.txt

build_backend:
  stage: build
  script:
    - echo "backend" > backend.txt
  artifacts:
    paths:
      - backend.txt

package_job:
  stage: package
  dependencies:
    - build_frontend
  script:
    - cat frontend.txt
    - cat backend.txt || echo "backend.txt not available"
```

* `build_frontend` and `build_backend` run **in parallel**.
* `package_job` runs **after both**, but only gets `frontend.txt` (because of `dependencies`).

---

### **6️⃣ Key Points**

| Concept         | Notes                                                                           |
| --------------- | ------------------------------------------------------------------------------- |
| `stages`        | Controls high-level order of job execution                                      |
| `needs:`        | Alternative for dependencies; allows jobs to start earlier if artifact is ready |
| `dependencies:` | Specifies exactly which artifacts to fetch from previous jobs                   |
| Artifacts       | Files shared between jobs                                                       |
| Parallel jobs   | Jobs in same stage run simultaneously; dependencies control what each consumes  |
