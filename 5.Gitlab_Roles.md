# Gitlab Roles

Let’s go step by step to clearly understand **GitLab roles**, their **types**, **permissions**, and **how to configure them with examples** — for both **projects** and **groups**.

---

## 🧠 1. What are GitLab Roles?

GitLab roles determine **what actions a user can perform** on a **project** or **group** — such as pushing code, managing issues, configuring CI/CD, or changing settings.

You assign roles when:

* Adding a member to a project or group
* Managing access to repositories, issues, merge requests, pipelines, etc.

---

## 🔑 2. Types of Roles in GitLab

GitLab defines **five default roles** for **both groups and projects**:

| Role                              | Description                                                                      | Common Use Case                                                             |
| --------------------------------- | -------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| **Guest**                         | Read-only access to issues, merge requests, and pipelines (no code access).      | For external stakeholders who need visibility but shouldn’t modify code.    |
| **Reporter**                      | Can view and download the repository, and view pipelines.                        | For QA, testers, or auditors who need to inspect code and pipeline results. |
| **Developer**                     | Full code access — can push, create branches, merge requests, and run CI/CD.     | Regular developers who actively contribute to code.                         |
| **Maintainer**                    | Can configure project settings, protected branches, runners, and manage members. | Leads or DevOps engineers managing configurations and team access.          |
| **Owner** *(only at group level)* | Full administrative rights including deleting the group or changing visibility.  | Organization or project admin.                                              |

> 🧩 **Note:** There’s **no Owner role at the project level**, only at **group level**.

## 🧩 4. How to Configure Roles — Step-by-Step (UI Method)

Let’s see how to assign or change roles for a user.

### Example: Adding a Developer to a Project

#### Step 1: Open your Project

* Go to **GitLab > Projects > Your Project**.

#### Step 2: Go to Members

* In the left sidebar, click **Project Information → Members**
  (In older UI: **Settings → Members**).

#### Step 3: Invite a Member

* Click **“Invite members”** button.

#### Step 4: Enter Details

* Type the **username**, **email**, or **group name** of the user.
* Under **Select a role**, choose one of:

  * Guest
  * Reporter
  * Developer
  * Maintainer

#### Step 5: Set Expiration (optional)

* You can set an **access expiry date** (useful for contractors).

#### Step 6: Click **Invite**

* The user will receive an email or see access in their GitLab dashboard.

✅ Example result:
You added *Deepak Yadav* as a **Developer** — he can now push code and create merge requests.

## 💻 5. Configure Roles via CLI / API

You can also configure roles using **GitLab’s REST API**.

### Example: Add a user to a project as Developer

```bash
curl --request POST "https://gitlab.com/api/v4/projects/<project_id>/members" \
     --header "PRIVATE-TOKEN: <your_access_token>" \
     --data "user_id=<user_id>&access_level=30"
```

**Access Level Codes:**

| Level | Role                 |
| ----- | -------------------- |
| 10    | Guest                |
| 20    | Reporter             |
| 30    | Developer            |
| 40    | Maintainer           |
| 50    | Owner *(group only)* |

Example:

```bash
--data "user_id=12345&access_level=30"
```

→ Adds the user as **Developer**.

## 🧱 6. Assign Roles at Group Level

You can manage permissions for multiple projects by adding members at the **Group** level.
All members of the group will automatically inherit access to **subprojects**.

### Steps:

1. Go to **Group → Manage → Members**
2. Click **Invite Members**
3. Choose role (Guest → Owner)
4. Click **Invite**

✅ Example:
If you add *Alice* as a **Maintainer** at group level, she will be Maintainer for all subprojects in that group.

## 🚀 8. Bonus: Custom Roles (Premium/Ultimate Feature)

In **GitLab Premium and Ultimate (Enterprise)** editions, you can define **Custom Roles**.

✅ You can:

* Create a role like “Release Manager”
* Define fine-grained permissions (e.g., allow tag creation but not member management)
* Assign it to specific users or groups

🧭 Example YAML (Custom Role Definition):

```yaml
custom_roles:
  release_manager:
    description: "Can manage releases and deployments only"
    permissions:
      - read_code
      - manage_releases
      - manage_pipelines
```

> Custom roles are **not available in Free tier**.
