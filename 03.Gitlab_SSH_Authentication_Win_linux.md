# 3. GitLab SSH Authentication (Windows & Linux)

## Quick Summary
- SSH auth uses a key pair instead of a password/token: a private key stays on your machine, a public key is registered in GitLab.
- Once set up, `git@gitlab.com` clone/push URLs never prompt for credentials interactively.
- `ed25519` is the currently recommended key type (smaller, faster, more secure than RSA); RSA is still supported but should be at least 4096 bits.
- `ssh-agent` holds your decrypted private key in memory so you're not re-entering a passphrase on every operation.
- Multiple accounts (e.g., personal + work GitLab) are handled with host aliases in `~/.ssh/config`, not multiple GitLab logins.
- Same setup mechanics on Windows (via Git Bash) and Linux — the difference is mainly file paths and how the agent is started.

## Core Concepts
- **How it works**
  - You generate a public/private key pair locally; the public key is uploaded to GitLab, the private key never leaves your machine.
  - Git over SSH authenticates by proving you hold the private key matching a public key GitLab has on file — no password/token exchanged per operation.
- **Key type guidance**
  - `ed25519` — recommended default: smaller keys, faster signing, strong security margins.
  - `rsa` — supported fallback for old systems that lack ed25519 support; use at least 4096 bits (`-b 4096`).
  - ⚠️ Deprecated / Changed: DSA keys are deprecated and should not be used; security concerns that apply to DSA also apply to ECDSA — prefer ed25519 or RSA-4096.
- **ssh-agent**
  - A background process that caches your decrypted private key (protected by your passphrase) so you don't retype the passphrase per Git command.
  - Must be started per shell session unless your OS/desktop environment auto-starts one (many Linux desktops and modern Git for Windows do).
- **Where SSH keys live in GitLab**
  - Current UI path: avatar (top-right) > **Edit profile** > left sidebar **SSH Keys** (or directly `https://gitlab.com/-/user_settings/ssh_keys`).
  - Each key gets a title (label it by device, e.g. `Windows-Laptop`, `linux-work-desktop`) and an optional expiration date — GitLab emails a warning 7 days before expiry and on the expiry date itself.
- **Multiple keys / multiple accounts**
  - GitLab supports adding many public keys to one account (e.g., one per device) — you don't need "primary" vs "backup" keys.
  - For multiple *GitLab accounts* (e.g., personal vs employer), use SSH config host aliases pointing different alias hostnames at different `IdentityFile`s — the alias, not the account, determines which key is offered.
- **Verifying which key is actually used**
  - `ssh -T git@gitlab.com` confirms auth works and prints your username.
  - `ssh -vT git@gitlab.com` (verbose) shows exactly which key file was offered — critical when multiple keys exist.

## Hands-On Labs

### Lab 1: Generate an ed25519 key pair
- **Goal:** Create the recommended modern key type.
- **Steps:**
  1. Open Git Bash (Windows) or a terminal (Linux).
  2. `ssh-keygen -t ed25519 -C "your_email@example.com"`
  3. Press Enter to accept the default path (`~/.ssh/id_ed25519`).
  4. Set a passphrase when prompted (recommended, not optional in practice).
- **Expected result:** `~/.ssh/id_ed25519` (private) and `~/.ssh/id_ed25519.pub` (public) exist.
- **What this teaches:** Key generation is identical on Windows Git Bash and Linux — same command, same file layout.

### Lab 2: Fall back to RSA-4096 if ed25519 isn't supported
- **Goal:** Handle old systems/servers that lack ed25519 support.
- **Steps:**
  1. `ssh-keygen -t rsa -b 4096 -C "your_email@example.com"`
  2. Accept default path (`~/.ssh/id_rsa`) or a custom name if you already have a default key.
- **Expected result:** `~/.ssh/id_rsa` and `~/.ssh/id_rsa.pub` created, 4096-bit.
- **What this teaches:** RSA remains valid but requires an explicit larger bit size — the old 2048-bit default is considered weak.

### Lab 3: Start ssh-agent and load the key
- **Goal:** Avoid re-entering your passphrase every Git operation.
- **Steps:**
  1. `eval "$(ssh-agent -s)"`
  2. `ssh-add ~/.ssh/id_ed25519` (or `~/.ssh/id_rsa` if you used RSA)
  3. `ssh-add -l` to confirm it's loaded.
- **Expected result:** Agent prints a PID; `ssh-add -l` lists your key's fingerprint.
- **What this teaches:** The agent is a separate cache layer from the key files themselves — restarting your terminal usually means re-running this.

### Lab 4: Add the public key to GitLab
- **Goal:** Register your key so GitLab will accept it.
- **Steps:**
  1. `cat ~/.ssh/id_ed25519.pub` and copy the full output.
  2. Go to `https://gitlab.com/-/user_settings/ssh_keys`.
  3. Paste the key, set title `lab-key-<your-device>`, optionally set an expiration date.
  4. Click **Add key**.
- **Expected result:** Key appears in the list with a fingerprint and "no expiration" or your chosen date.
- **What this teaches:** GitLab stores only the public half — losing the private key means the registered public key becomes useless (generate a new pair, don't try to "recover" it).

### Lab 5: Test the connection
- **Goal:** Confirm end-to-end SSH auth works before trying a real clone.
- **Steps:**
  1. `ssh -T git@gitlab.com`
  2. If prompted "Are you sure you want to continue connecting?", type `yes` (first-time host key trust).
- **Expected result:** `Welcome to GitLab, @<your-username>!`
- **What this teaches:** This is the fastest smoke test for SSH auth issues — no repo needed.

### Lab 6: Clone and push using the SSH URL
- **Goal:** Confirm the full clone/push loop works passwordless.
- **Steps:**
  1. `git clone git@gitlab.com:<namespace>/<project>.git`
  2. Make a commit, `git push origin main`.
- **Expected result:** No credential prompt at any point.
- **What this teaches:** SSH URLs (`git@gitlab.com:...`) are distinct from HTTPS URLs and use the key pair, not a PAT.

### Lab 7: Convert an existing HTTPS clone to SSH
- **Goal:** Fix a repo you originally cloned over HTTPS.
- **Steps:**
  1. `git remote -v` (confirm it currently shows an `https://` URL).
  2. `git remote set-url origin git@gitlab.com:<namespace>/<project>.git`
  3. `git remote -v` again to confirm, then `git fetch` to prove it works.
- **Expected result:** Remote now uses the SSH URL and fetch succeeds without a token prompt.
- **What this teaches:** Auth method is a property of the remote URL scheme, not a one-time repo setting — switchable anytime.

### Lab 8: Confirm which key is actually being offered (verbose debug)
- **Goal:** Learn the diagnostic command for "wrong key" problems.
- **Steps:**
  1. `ssh -vT git@gitlab.com`
  2. Scan the output for a line like `Offering public key: /home/<user>/.ssh/id_ed25519`.
- **Expected result:** The offered key path matches the one you registered in Lab 4.
- **What this teaches:** When multiple keys exist, SSH doesn't always offer the one you expect — verbose mode shows the real negotiation.

### Lab 9: Configure multiple SSH identities with host aliases
- **Goal:** Support two GitLab accounts (e.g., personal + work) from one machine, cleanly.
- **Steps:**
  1. Generate a second key pair: `ssh-keygen -t ed25519 -C "work_email@example.com" -f ~/.ssh/id_gitlab_work`
  2. Add its public key to your work GitLab account.
  3. Edit `~/.ssh/config` (create if missing):
     ```
     Host gitlab.com
       HostName gitlab.com
       User git
       IdentityFile ~/.ssh/id_ed25519

     Host gitlab-work
       HostName gitlab.com
       User git
       IdentityFile ~/.ssh/id_gitlab_work
     ```
  4. Clone using the alias instead of `gitlab.com`: `git clone gitlab-work:<namespace>/<project>.git`
- **Expected result:** The `gitlab-work` clone authenticates as your work identity; plain `gitlab.com` clones still use your personal key.
- **What this teaches:** The Host alias — not account switching in the browser — is what routes Git to the right key; this is the standard pattern for multi-account setups (also works identically for mixing GitLab + GitHub keys).

### Lab 10: Set and observe key expiration behavior
- **Goal:** Understand GitLab's key-expiry notifications, since expired keys are a recurring real-world support issue.
- **Steps:**
  1. Add a throwaway key (Labs 1+4 pattern) with an expiration date set to a few days out.
  2. Note the key's status on the SSH Keys settings page.
  3. (Optional, if you want to see it fire) wait for the 7-day-before-expiry email, or just note where GitLab documents this behavior.
- **Expected result:** You understand that GitLab sends a warning email 7 days before expiry and again on the expiry date, but does not silently rotate the key for you.
- **What this teaches:** Expired keys aren't auto-removed from working locally per se, but GitLab will start rejecting auth attempts using them once expired — plan rotation ahead of time for CI/service accounts.

### Lab 11: Troubleshoot common SSH failures
- **Goal:** Practice mapping symptoms to fixes.
- **Steps:** Reproduce at least one of these (e.g., temporarily remove the key from `ssh-agent` with `ssh-add -D`, or point `IdentityFile` at a nonexistent path) and confirm the resulting error matches:

| Issue | Reason | Fix |
| --- | --- | --- |
| `Permission denied (publickey)` | Wrong key or key not added to GitLab | Add the correct public key to `/-/user_settings/ssh_keys` |
| SSH key not offered | `ssh-agent` not running or key not loaded | `eval "$(ssh-agent -s)"` then `ssh-add ~/.ssh/id_ed25519` |
| Old HTTPS remote still set | Repo cloned before switching to SSH | `git remote set-url origin git@gitlab.com:...` |
| Firewall blocks port 22 | Corporate network restriction | Use HTTPS + PAT instead, or GitLab's SSH-over-443 workaround if enabled on the instance |
| Wrong identity used with multiple keys | No host alias configured | Add a `Host` block per identity in `~/.ssh/config` |

- **Expected result:** You can diagnose each symptom without trial-and-error.
- **What this teaches:** SSH auth failures are almost always one of: key not registered, agent not loaded, wrong remote scheme, network block, or identity ambiguity.

## Common Pitfalls
- Generating a new key pair every time instead of reusing/adding to `ssh-agent` — leads to a pile of unused keys in GitLab settings.
- Forgetting `ssh-agent` doesn't persist across terminal restarts on most setups — `ssh-add` again after reopening a shell.
- Using the same single key across multiple unrelated GitLab accounts without host aliases, then wondering why the wrong identity is used.
- Leaving keys with no expiration date on shared/former-employee machines — treat SSH keys like credentials that need offboarding.
- Confusing "SSH key added to GitLab" with "SSH key loaded in agent" — both are required for auth to succeed.

## Interview Questions & Answers
- **How does SSH authentication differ from PAT-based HTTPS authentication?**
  - SSH uses a public/private key pair verified via cryptographic challenge; HTTPS+PAT sends a bearer token as the password on each request. SSH avoids re-sending a secret over the wire per operation.
- **Why is ed25519 preferred over RSA today?**
  - Smaller key size, faster signing/verification, strong security margins; RSA remains supported but needs at least 4096 bits to be considered comparably secure.
- **What does `ssh-agent` do, and why is it needed?**
  - Caches your decrypted private key in memory for the session so you don't retype your passphrase on every SSH-based Git operation.
- **How do you support two different GitLab accounts (e.g., personal and work) on one machine?**
  - Generate separate key pairs, register each public key on its respective account, and define `Host` aliases in `~/.ssh/config` mapping each alias to its own `IdentityFile`; clone using the alias hostname.
- **What command shows exactly which SSH key was offered during authentication?**
  - `ssh -vT git@gitlab.com` (verbose test) — look for the "Offering public key" line.
- **Scenario: a teammate gets `Permission denied (publickey)` when pushing. What do you check first?**
  - Whether their public key is actually registered in GitLab settings, whether `ssh-agent` is running with the key loaded (`ssh-add -l`), and whether the remote URL uses the SSH form (`git@gitlab.com:...`) not HTTPS.
- **Scenario: your corporate network blocks outbound port 22. How do you still use SSH-style auth, or what's the workaround?**
  - Fall back to HTTPS + PAT, or use GitLab's SSH-over-HTTPS-port (443) workaround if the instance has it enabled; otherwise SSH simply won't traverse the blocked port.
- **What happens when an SSH key's expiration date passes?**
  - GitLab sends a warning 7 days prior and on the day of expiry; once expired, authentication attempts using that key are rejected and it needs to be replaced/renewed with a fresh key.
- **Are DSA keys still acceptable to use with GitLab?**
  - No — DSA is deprecated; the same security concerns extend to ECDSA. Use ed25519 or RSA-4096+.
- **What's the difference between where the private key and public key live?**
  - Private key stays on the local machine (never uploaded); only the public key is pasted into GitLab's SSH Keys settings.
- **How do you verify SSH auth is working without cloning a full repo?**
  - `ssh -T git@gitlab.com` — a lightweight connectivity/identity check that just prints a welcome message.
