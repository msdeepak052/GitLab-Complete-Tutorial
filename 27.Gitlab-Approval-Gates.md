# CI/CD pipelines with approval gates

## 🚦 **1. What Are Approval Gates?**

**Approval gates** (also called *manual approvals* or *quality gates*) are checkpoints in your CI/CD pipeline that require **human review or approval** before moving to the next stage — especially for **production** or **sensitive environments**.

They ensure:

* Code meets quality & security standards.
* Deployments are **reviewed, tested, and authorized** before release.
* Compliance and audit requirements are met.

---

## 🧩 **2. Types of Approval Gates in GitLab**

| Type                                  | Description                                                   | Example Use                           |
| ------------------------------------- | ------------------------------------------------------------- | ------------------------------------- |
| **Manual Jobs (`when: manual`)**      | Requires a human to click “Play” in GitLab UI before job runs | Approve deployment to staging or prod |
| **Protected Environments**            | Restrict who can deploy to a specific environment             | Only team leads can deploy to prod    |
| **Merge Request Approvals**           | Require approval before code merges into main                 | Code review before pipeline triggers  |
| **External Approval APIs (optional)** | Integrate with ServiceNow, Jira, etc. for change approvals    | Enterprise-grade release management   |

---

## ⚙️ **3. GitLab CI/CD with Approval Gates Example**

Here’s a **complete `.gitlab-ci.yml`** for multi-stage deployment with approvals 👇

```yaml
image: docker:latest

services:
  - docker:dind

variables:
  IMAGE_NAME: deepakyadav/devops-app
  IMAGE_TAG: $CI_COMMIT_SHORT_SHA
  DOCKER_BUILDKIT: 1

stages:
  - build
  - push
  - deploy

# 🔹 Build Stage
build_image:
  stage: build
  script:
    - echo "Building Docker image..."
    - docker build -t $IMAGE_NAME:$IMAGE_TAG .
    - docker tag $IMAGE_NAME:$IMAGE_TAG $IMAGE_NAME:latest
  artifacts:
    paths:
      - Dockerfile
    expire_in: 1 hour

# 🔹 Push Stage
push_image:
  stage: push
  script:
    - docker login -u "$DOCKER_USERNAME" -p "$DOCKER_PASSWORD"
    - docker push $IMAGE_NAME:$IMAGE_TAG
    - docker push $IMAGE_NAME:latest
  needs: ["build_image"]
  only:
    - main

# 🔹 Deploy to Dev (Automatic)
deploy_dev:
  stage: deploy
  environment:
    name: dev
    url: http://$DEV_HOST
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh
    - echo "$SSH_PRIVATE_KEY" > private_key.pem
    - chmod 600 private_key.pem
  script:
    - echo "Deploying to DEV..."
    - ssh -o StrictHostKeyChecking=no -i private_key.pem $DEV_USER@$DEV_HOST "
        docker login -u $DOCKER_USERNAME -p $DOCKER_PASSWORD &&
        docker pull $IMAGE_NAME:latest &&
        docker stop devops-app || true &&
        docker rm devops-app || true &&
        docker run -d -p 80:80 --name devops-app $IMAGE_NAME:latest
      "
  needs: ["push_image"]
  only:
    - main

# 🔹 Deploy to Staging (Manual Approval Gate)
deploy_staging:
  stage: deploy
  environment:
    name: staging
    url: http://$STAGING_HOST
  when: manual
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh
    - echo "$SSH_PRIVATE_KEY" > private_key.pem
    - chmod 600 private_key.pem
  script:
    - echo "Deploying to STAGING..."
    - ssh -o StrictHostKeyChecking=no -i private_key.pem $STAGING_USER@$STAGING_HOST "
        docker login -u $DOCKER_USERNAME -p $DOCKER_PASSWORD &&
        docker pull $IMAGE_NAME:latest &&
        docker stop devops-app || true &&
        docker rm devops-app || true &&
        docker run -d -p 80:80 --name devops-app $IMAGE_NAME:latest
      "
  needs: ["deploy_dev"]

# 🔹 Deploy to Production (Manual + Protected Environment)
deploy_prod:
  stage: deploy
  environment:
    name: production
    url: http://$PROD_HOST
  when: manual
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh
    - echo "$SSH_PRIVATE_KEY" > private_key.pem
    - chmod 600 private_key.pem
  script:
    - echo "Deploying to PRODUCTION..."
    - ssh -o StrictHostKeyChecking=no -i private_key.pem $PROD_USER@$PROD_HOST "
        docker login -u $DOCKER_USERNAME -p $DOCKER_PASSWORD &&
        docker pull $IMAGE_NAME:latest &&
        docker stop devops-app || true &&
        docker rm devops-app || true &&
        docker run -d -p 80:80 --name devops-app $IMAGE_NAME:latest
      "
  needs: ["deploy_staging"]
```

## 🧠 **4. How This Pipeline Works**

| Stage                 | Behavior                                                        |
| --------------------- | --------------------------------------------------------------- |
| **Build & Push**      | Automatically builds and pushes image to Docker Hub.            |
| **Deploy to Dev**     | Runs automatically — no approval required.                      |
| **Deploy to Staging** | Waits for manual approval.                                      |
| **Deploy to Prod**    | Waits for manual approval and only authorized users can run it. |

---

## 🔐 **5. Protected Environment Setup (Prod)**

In GitLab UI:

1. Go to **Deployments → Environments → production**
2. Click **Protect**
3. Grant deploy access only to specific users or roles (e.g., Team Lead)

This ensures **only authorized people can approve Prod deployments.**

---

## 🧾 **6. Optional — Add “Approval Steps” via Merge Requests**

Before deployment even starts, you can enforce:

* Code review approvals
* Security scan gates (SAST, DAST)
* Merge approvals (min 2 approvers)

Example (in project settings → Merge Request Approvals):

> Require 2 approvals before merge to `main`.

This acts as a **pre-deployment gate**.

---

## ✅ **7. Real-World Flow**

```
Developer → Merge Request (Code Review Gate)
             ↓
Build → Push → Deploy to Dev (auto)
             ↓
Staging Approval (QA Lead clicks “Play”)
             ↓
Prod Approval (Release Manager clicks “Play”)
```
