# 11. Pipeline Triggers: `rules`, `workflow`, and `when`

## Quick Summary
- Controls **whether a pipeline runs at all** (`workflow:`) and **whether an individual job runs** (`rules:`) once it does.
- Without any `rules`/`only`/`except`, a job runs on every push and every pipeline source by default.
- `rules:` is the current, recommended way to control job execution — it replaces the legacy `only:`/`except:` keywords (deprecated; full comparison lives in file 15).
- `workflow:rules` runs once per pipeline, before any job is created — used to block duplicate pipelines (e.g. branch pipeline + MR pipeline for the same commit).
- Common real-world triggers: push to a branch, merge request event, schedule, manual click, tag, specific file changes.
- Interview-critical: knowing the difference between "pipeline doesn't run" (`workflow:rules`) and "job is skipped but pipeline still runs" (job `rules:` with `when: never`).

## Core Concepts

### Pipeline creation vs job selection
- Two separate layers of control:
  - `workflow:rules` — decides if the **pipeline** is created at all.
  - job-level `rules:` — decides which **jobs** are added to a pipeline that already exists.
- If `workflow:rules` evaluates to no match, the pipeline never appears in CI/CD > Pipelines, no minutes are consumed.
- If a job's `rules:` evaluates to no match, the pipeline still runs, that one job just doesn't appear.

### `rules:` syntax (job-level)
- Evaluated top to bottom — **first matching rule wins**, remaining rules are ignored.
- Available clauses per rule:
  - `if:` — CI/CD variable expression (single quotes recommended).
  - `changes:` — list of file paths/globs; true if any match was modified (paths relative to repo root).
  - `exists:` — true if the given file(s) exist in the repository.
  - `when:` — `on_success` (default), `on_failure`, `always`, `manual`, `delayed`, `never`.
  - `allow_failure:` — job can fail without failing the pipeline.
  - `variables:` — set/override variables only when that rule matches.
- If **no** rule matches, the job is **not** added to the pipeline (implicit `when: never`) — opposite default behavior from `only`/`except`, where jobs ran unless excluded.
- Best practice: end a `rules:` list with an explicit `- when: never` (or an explicit final match) so behavior is unambiguous to future readers.

### `workflow:rules` syntax (pipeline-level)
- Lives at the top level of `.gitlab-ci.yml`, not inside a job.
- Supports only a subset of clauses: `if`, `changes`, `exists`, `variables`, and `when` restricted to `always` or `never` (no `manual`/`delayed`/`on_failure` at this level).
- `start_in`, `allow_failure`, `needs` are **not** valid inside `workflow:rules`.
- `workflow:rules:variables` sets pipeline-wide default variables when a rule matches — these override globally defined `variables:` but are themselves overridden by job-level `variables:`.
- `workflow:name` sets a custom, interpolated pipeline name (e.g. `workflow: { name: "Pipeline for $CI_COMMIT_REF_NAME" }`) — shown in the Pipelines list UI.
- Classic use case: avoid **duplicate pipelines** for the same commit (one branch pipeline + one MR pipeline) by blocking the branch pipeline when an open MR exists for that branch. GitLab ships this as the built-in `Workflows/MergeRequest-Pipelines` template.

### Key predefined variables used in rules
- `$CI_PIPELINE_SOURCE` — `push`, `merge_request_event`, `schedule`, `web` (manual "Run pipeline" button), `trigger`, `api`, `pipeline` (from a parent pipeline), etc.
- `$CI_COMMIT_BRANCH` — set only on branch pipelines (empty on MR/tag pipelines).
- `$CI_COMMIT_TAG` — set only when the pipeline runs for a tag.
- `$CI_MERGE_REQUEST_IID` — set only inside merge request pipelines.

### `⚠️ Deprecated / Changed`
- `only:`/`except:` are **deprecated** per current GitLab docs ("could be scheduled for removal in a future major milestone" — no fixed removal version yet, but new pipelines should not use them). See file 15 for the full legacy-vs-modern breakdown.
- Older tutorials show `changes:` as a bare list under `rules:` (`rules: - changes: [...]`) — this still works, but always pair it with a `when:` (or a fallback rule) or you may get surprising "job silently skipped" behavior since an unmatched `changes:` rule is just skipped, not an error.

## Hands-On Labs

### Lab 1: Default trigger — run on every push
- **Goal:** Confirm the zero-config default: no `rules`, no `only` = runs on every push to every branch.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build

build_every_push:
  stage: build
  script:
    - echo "Runs on every push, any branch, no rules needed."
```
- **Run it:** Commit and push this file to any branch.
- **Expected result:** Pipeline appears immediately in CI/CD > Pipelines with `build_every_push` running.
- **What this teaches:** The implicit default behavior you're overriding with `rules:`.

### Lab 2: Restrict a job to a single branch with `rules:if`
- **Goal:** Convert the legacy `only: [main]` pattern to `rules:`.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build

build_main_only:
  stage: build
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
  script:
    - echo "Runs only on main branch."
```
- **Run it:** Push to `main`, then push the same file to a feature branch.
- **Expected result:** Job appears in the pipeline for `main`; job is absent (not even listed) in the feature-branch pipeline.
- **What this teaches:** Unmatched `rules:` means "job not created," not "job skipped/greyed out."

### Lab 3: Run only on merge requests
- **Goal:** Trigger a job only when a merge request pipeline runs.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - test

test_on_merge_request:
  stage: test
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
  script:
    - echo "Validating merge request changes..."
```
- **Run it:** Open a merge request from a feature branch into `main`.
- **Expected result:** Job runs inside the MR's pipeline (visible on the MR "Pipelines" tab); it does not run on a plain branch push.
- **What this teaches:** `merge_request_event` is the value to test for MR-only jobs — more explicit than the legacy `only: [merge_requests]`.

### Lab 4: Trigger only when specific files change
- **Goal:** Skip a build unless files under `src/` or `app/` changed.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build

build_on_code_change:
  stage: build
  rules:
    - changes:
        - src/**/*
        - app/**/*
  script:
    - echo "Code files changed, running build..."
```
- **Run it:** Push a commit that only touches `README.md`, then push another that edits a file inside `src/`.
- **Expected result:** Job is absent from the README-only pipeline; present and runs in the `src/` pipeline.
- **What this teaches:** `changes:` compares against the target branch (MR) or previous commit (branch push) to decide relevance.

### Lab 5: Skip a job when only docs changed (ordered rules)
- **Goal:** Demonstrate first-match-wins ordering with an explicit skip.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - test

skip_on_docs_change:
  stage: test
  rules:
    - changes:
        - "*.md"
      when: never
    - when: on_success
  script:
    - echo "Docs-only commits skip this job; everything else runs it."
```
- **Run it:** Push a commit changing only `*.md` files, then push a commit changing a `.yml` or code file.
- **Expected result:** Job absent for the docs-only push; present for the other push.
- **What this teaches:** Rules are evaluated top-down — the `.md`-only `when: never` rule must come before the catch-all `on_success` rule or it would never be reached.

### Lab 6: Manual trigger job
- **Goal:** Require a human click before a job runs, restricted to `main`.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - deploy

manual_deploy:
  stage: deploy
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
  script:
    - echo "Deploying manually..."
```
- **Run it:** Push to `main`, open the pipeline, click the "Play" icon next to `manual_deploy`.
- **Expected result:** Job sits in a blocked/manual state until clicked; then runs and completes.
- **What this teaches:** Combining `if:` with `when: manual` restricts *both* the branch *and* requires a click — different from a bare `when: manual` on the job (which would still require a branch check separately, or run on every branch).

### Lab 7: Scheduled pipeline job
- **Goal:** Run a job only when triggered by GitLab's pipeline scheduler.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - scheduled

scheduled_cleanup:
  stage: scheduled
  rules:
    - if: '$CI_PIPELINE_SOURCE == "schedule"'
  script:
    - echo "Running nightly cleanup..."
```
- **Run it:** Go to CI/CD > Schedules > New schedule, set an interval (e.g. every day), target a branch, save, then click "Run now" to test immediately instead of waiting.
- **Expected result:** Job runs in the scheduled pipeline; it does not appear in ordinary push pipelines.
- **What this teaches:** `$CI_PIPELINE_SOURCE == "schedule"` is the modern replacement for legacy `only: [schedules]`.

### Lab 8: Variable-conditional job (manual pipeline variable)
- **Goal:** Run a job only when a variable is explicitly set when starting the pipeline.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - conditional

conditional_job:
  stage: conditional
  rules:
    - if: '$RUN_EXTRA == "true"'
      when: always
    - when: never
  script:
    - echo "Conditional variable-based job executed."
```
- **Run it:** Go to CI/CD > Pipelines > Run pipeline, add variable `RUN_EXTRA` = `true`, run. Then run again without the variable.
- **Expected result:** Job present and runs on the first run; absent on the second.
- **What this teaches:** Manually-supplied pipeline variables can gate optional jobs — useful for "run extra checks" or "run full test suite" toggles.

### Lab 9: `workflow:rules` to block duplicate pipelines
- **Goal:** Prevent a redundant branch pipeline from running when the same commit already has an MR pipeline.
- **`.gitlab-ci.yml`:**
```yaml
workflow:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_COMMIT_BRANCH == "main"'
    - when: never

stages:
  - build

build_job:
  stage: build
  script:
    - echo "Build runs only inside pipelines allowed by workflow:rules."
```
- **Run it:** Open an MR from a feature branch, watch the MR pipeline run. Push directly to the feature branch (not via MR) and check CI/CD > Pipelines.
- **Expected result:** MR pipeline runs; a plain push to the feature branch (no open MR context matched) produces no pipeline at all.
- **What this teaches:** `workflow:rules` operates before pipeline creation — this is the difference between "no pipeline" and "pipeline with skipped jobs."

### Lab 10: Named pipelines with `workflow:name` and rule variables
- **Goal:** Give pipelines a readable custom name and set a pipeline-wide default variable conditionally.
- **`.gitlab-ci.yml`:**
```yaml
workflow:
  name: 'Pipeline: $CI_COMMIT_REF_NAME ($CI_PIPELINE_SOURCE)'
  rules:
    - if: '$CI_PIPELINE_SOURCE == "schedule"'
      variables:
        DEPLOY_ENV: "nightly"
    - when: always
      variables:
        DEPLOY_ENV: "manual-run"

stages:
  - info

show_env:
  stage: info
  script:
    - echo "Deploying as $DEPLOY_ENV"
```
- **Run it:** Trigger via a normal push, then via CI/CD > Schedules > Run now.
- **Expected result:** Pipelines list shows the custom name per pipeline; job log shows `DEPLOY_ENV` value differing between the two trigger types.
- **What this teaches:** `workflow:rules:variables` sets pipeline-wide defaults per trigger context — useful for labeling deploy environments by trigger source.

### Lab 11: Convert a legacy `only`/`except` job to `rules`
- **Goal:** Practice the realistic "modernize this job" exercise.
- **`.gitlab-ci.yml`:** (before, legacy)
```yaml
legacy_job:
  stage: build
  script:
    - echo "legacy"
  only:
    - main
  except:
    - schedules
```
- **`.gitlab-ci.yml`:** (after, modern equivalent)
```yaml
modern_job:
  stage: build
  rules:
    - if: '$CI_COMMIT_BRANCH == "main" && $CI_PIPELINE_SOURCE != "schedule"'
  script:
    - echo "modern"
```
- **Run it:** Push to `main` normally, then trigger a scheduled pipeline targeting `main`.
- **Expected result:** `modern_job` runs on the normal push, is absent on the scheduled pipeline.
- **What this teaches:** A single `rules:if` boolean expression often replaces a whole `only`/`except` block — see file 15 for more conversion patterns.

## How to Test Each Scenario — Cheat Reference
| Scenario | How to trigger it |
| --- | --- |
| Every push | Push any commit to any branch |
| Branch-restricted | Push to the named branch (e.g. `main`) |
| Merge request | Open/update an MR from a feature branch |
| File change | Edit a file under the watched path |
| Docs-only skip | Commit only `.md` files |
| Manual | Click "Play" in CI/CD > Pipelines |
| Scheduled | CI/CD > Schedules > New schedule > Run now |
| Variable-conditional | CI/CD > Pipelines > Run pipeline > add variable |
| workflow:rules dedupe | Compare MR pipeline vs plain branch push |

## Common Pitfalls
- Forgetting the trailing `- when: never` in a `rules:` list — an unmatched job silently disappears instead of erroring, which is confusing to debug.
- Mixing `only`/`except` and `rules` on the same job — GitLab ignores `only`/`except` entirely once `rules` is present; don't mix them.
- Using `changes:` on a branch pipeline expecting it to diff against `main` — for a plain push it diffs against the previous commit on that ref, not the target branch (that behavior applies to MR pipelines).
- Forgetting `workflow:rules` operates on the whole pipeline — a `when: manual` there is invalid; only `always`/`never` are allowed at that level.
- Believing `rules: - when: manual` alone restricts a job to a branch — it doesn't; it only changes *when* the job runs, not *where*. Pair it with an `if:`.
- Quoting inconsistently in `if:` expressions — always wrap the whole expression in single quotes and use `==`/`!=`/`=~` correctly; unquoted expressions are a common YAML parse error.

## Interview Questions & Answers
- **Q: What's the difference between `workflow:rules` and job-level `rules:`?**
  A: `workflow:rules` decides if the pipeline is created at all (pipeline-level gate); job-level `rules:` decides which jobs are added to a pipeline that's already running.
- **Q: What happens if none of a job's `rules:` match?**
  A: The job is not added to the pipeline at all — implicit `when: never`, opposite of legacy `only`/`except` defaults.
- **Q: How do you avoid duplicate pipelines for the same commit (branch + MR)?**
  A: Use `workflow:rules` (often via the built-in `Workflows/MergeRequest-Pipelines` template) to only allow MR pipelines and direct pushes to specific branches like `main`/default.
- **Q: How do you make a job run only for merge requests?**
  A: `rules: - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'`.
- **Q: How do you make a job run only when specific files change?**
  A: `rules: - changes: [path/glob, ...]`, optionally combined with `when:`.
- **Q: Are `only`/`except` still usable?**
  A: Yes, but deprecated per current docs — GitLab states they "could be scheduled for removal in a future major milestone," no fixed date yet; new pipelines should use `rules:`.
- **Q: What predefined variable tells you what triggered the pipeline?**
  A: `$CI_PIPELINE_SOURCE` (values: `push`, `merge_request_event`, `schedule`, `web`, `trigger`, `api`, `pipeline`, etc.).
- **Q: How do you require a manual click but only on the default branch?**
  A: `rules: - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH' \n   when: manual`.
- **Q: Scenario — a job runs on every push when it should only run on merge requests. What's likely wrong?**
  A: The job has no `rules:`/`only:` restriction at all (defaults to every push), or it has a `rules:if` that's too broad / missing the `merge_request_event` check, or `rules` and `only` are mixed and `rules` unintentionally overrides the intended `only`.
- **Q: Scenario — a `changes:`-based rule isn't triggering the job even though the relevant file was clearly edited. What would you check?**
  A: Confirm exact glob path (case/typo), confirm whether this is a branch push (diffs vs previous commit) or MR pipeline (diffs vs target branch) since the comparison base differs, and confirm the rule isn't preceded by an earlier matching rule that already decided the job's fate (first-match-wins).
- **Q: Can `workflow:rules` use `when: manual`?**
  A: No — only `always` or `never` are valid `when` values at the workflow level.
- **Q: What's the modern equivalent of legacy `only: [schedules]`?**
  A: `rules: - if: '$CI_PIPELINE_SOURCE == "schedule"'`.
