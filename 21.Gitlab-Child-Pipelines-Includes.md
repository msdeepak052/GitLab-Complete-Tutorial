# 21. Child Pipelines, Multi-Project Pipelines & Includes

## Quick Summary
- `trigger:` creates a **downstream pipeline** (parent-child, or multi-project) — a genuinely separate pipeline with its own jobs/stages/status.
- `include:` pulls YAML fragments into the **current** pipeline — no new pipeline is created, just more jobs merged into the same one.
- Child pipelines modularize large monorepos/microservices; `include:` modularizes a single large `.gitlab-ci.yml` file.
- `strategy: depend` (or `mirror`) makes the parent pipeline wait on / reflect the child's outcome instead of finishing immediately.
- Multi-project pipelines (`trigger: project:`) trigger a pipeline in a **different** GitLab project — used for cross-repo/cross-team pipelines.
- CI/CD Components (`include: component:`) are the current recommended way to package and version reusable pipeline logic, superseding plain `include: project:` templates for shareable, versioned building blocks.
- Both features are essential interview topics: "how do you avoid a 2000-line `.gitlab-ci.yml`?" and "how do you fan out a monorepo pipeline?" both point here.

## Core Concepts

### Child pipelines (`trigger:`)
- Declared on a job using `trigger:`, not `script:`.
- Two forms:
  - `trigger: include: <file>` — parent-child pipeline, same project, same ref/SHA.
  - `trigger: project: <group/project>` — multi-project pipeline, different project.
- Parent-child max nesting depth: 2 levels (a child cannot trigger another child pipeline that triggers another — GitLab enforces a limit).
- Multi-project pipelines have **no nesting limit** since each is an independent pipeline linked by trigger relationships.
- `strategy:`
  - Omitted (default): trigger job succeeds as soon as the downstream pipeline is *created*; parent does not wait.
  - `strategy: depend`: trigger job's status waits for the downstream pipeline to finish, but doesn't necessarily mirror it exactly.
  - `strategy: mirror`: trigger job's status always equals the downstream pipeline's current status.
- Passing variables downstream:
  - Static: `variables:` block on the trigger job.
  - Dynamic: `rules:` with `variables:` overrides per condition (see Lab 3).
  - Dotenv artifacts from an earlier job can also be forwarded.
- Child pipeline jobs are billed/run like any other pipeline — separate pipeline ID, separate view in the UI, separate retry/cancel controls.

### `include:`
- Merges external YAML into the current pipeline at parse time — the result is still **one pipeline**.
- Types:
  - `include: local:` — file in the same repo.
  - `include: remote:` — file at a public HTTPS URL (no auth headers).
  - `include: project:` — file from another GitLab project, requires `file:` and optionally `ref:` (defaults to that project's default branch).
  - `include: template:` — GitLab-maintained templates (e.g. `Jobs/SAST.gitlab-ci.yml`).
  - `include: component:` — CI/CD Components (see below).
- Can mix multiple `include:` entries — GitLab merges all of them plus the local file into one config before running.
- If the same job name is defined in more than one included file, the last one merged wins (later `include:` entries and the local file override earlier ones).

### CI/CD Components (`include: component:`)
- Newer, higher-level abstraction over `include: project:` templates.
- A component is a self-contained, **versioned**, parameterized pipeline unit published to a project (ideally the project's CI/CD Catalog entry).
- Syntax: `include: - component: $CI_SERVER_FQDN/group/project/component-name@version`, with `inputs:` for parameters (typed, validated, unlike raw variable substitution in templates).
- Preferred over plain `include: project:` template files when you want: input validation, semantic versioning (`@1.0`, `@~latest`, `@main`), and discoverability via the CI/CD Catalog.
- `include: project:` templates still work and are fine for simple, in-org sharing where you don't need versioned inputs.

### ⚠️ Deprecated / Changed
- `only:`/`except:` are officially deprecated in favor of `rules:` — any branch-based trigger logic for child pipelines should use `rules:` as shown throughout this file.
- CI/CD Components did not exist when `include: project:` was the only cross-project sharing mechanism — for **new** reusable pipeline logic, prefer components; keep `include: project:` for existing simple template files.

### `trigger:` vs `include:` at a glance

| Aspect | `trigger:` (child/multi-project) | `include:` |
|---|---|---|
| Result | New, separate pipeline | Same pipeline, more jobs |
| Status | Own pipeline status, optionally linked via `strategy:` | No separate status |
| Scope | Same or different project | Same pipeline config only |
| Use case | Microservices, monorepo fan-out, cross-team triggers | Splitting one large YAML file, reusable job templates |
| Nesting | Max depth 2 (parent→child), unlimited for multi-project | N/A (just YAML merging) |

## Hands-On Labs

### Lab 1: Basic parent-child pipeline
- **Goal:** Trigger a child pipeline from a parent and see them as two separate pipeline runs.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - deploy

build_job:
  stage: build
  script:
    - echo "Building main project..."

trigger_child_pipeline:
  stage: deploy
  trigger:
    include: child-pipeline.yml
```
- **`child-pipeline.yml`:**
```yaml
stages:
  - test
  - deploy

test_job:
  stage: test
  script:
    - echo "Running tests in child pipeline..."

deploy_job:
  stage: deploy
  script:
    - echo "Deploying from child pipeline..."
```
- **Run it:** Commit both files, push, open CI/CD > Pipelines. Click into the parent pipeline, then click the downstream pipeline icon on `trigger_child_pipeline`.
- **Expected result:** Parent pipeline shows 2 stages; `trigger_child_pipeline` succeeds as soon as the child pipeline is *created* (not when it finishes) since no `strategy:` is set.
- **What this teaches:** The default (non-blocking) trigger behavior — parent doesn't wait for child.

### Lab 2: Make the parent wait with `strategy: depend`
- **Goal:** See the parent pipeline block on the child's real outcome.
- **`.gitlab-ci.yml`:**
```yaml
trigger_child_pipeline:
  stage: deploy
  trigger:
    include: child-pipeline.yml
    strategy: depend
```
- **Run it:** Add a deliberately failing job to `child-pipeline.yml` (`script: [\"exit 1\"]`), push, watch the parent pipeline.
- **Expected result:** `trigger_child_pipeline` stays "running" until the child pipeline finishes, then goes **failed** because the child failed. Without `strategy: depend` it would have shown "passed" immediately.
- **What this teaches:** `strategy: depend` is what you need whenever downstream failures must block/fail the parent.

### Lab 3: Dynamic, branch-based child pipeline variables
- **Goal:** Deploy to different environments from the same child pipeline file, chosen by the branch that triggered the parent.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - deploy

deploy_to_env:
  stage: deploy
  trigger:
    include: child-pipeline.yml
    strategy: depend
  rules:
    - if: '$CI_COMMIT_BRANCH == "develop"'
      variables:
        ENVIRONMENT: "staging"
    - if: '$CI_COMMIT_BRANCH == "main"'
      variables:
        ENVIRONMENT: "production"
```
- **`child-pipeline.yml`:**
```yaml
deploy_job:
  stage: deploy
  script:
    - echo "Deploying to $ENVIRONMENT"
```
- **Run it:** Push to `develop`, then to `main`, compare the `$ENVIRONMENT` value printed in each child pipeline's job log.
- **Expected result:** `develop` push prints "Deploying to staging"; `main` push prints "Deploying to production" — one reusable child file, two behaviors.
- **What this teaches:** Combining `rules:` + per-rule `variables:` to parameterize a single child pipeline by branch.

### Lab 4: Multiple local includes (splitting one pipeline into files)
- **Goal:** Break a monolithic `.gitlab-ci.yml` into per-stage files without creating a separate pipeline.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - test
  - deploy

include:
  - local: 'ci-templates/build.yml'
  - local: 'ci-templates/test.yml'
  - local: 'ci-templates/deploy.yml'
```
- **`ci-templates/build.yml` / `test.yml` / `deploy.yml`:** one job each, e.g.
```yaml
build_job:
  stage: build
  script:
    - echo "Building the project..."
```
- **Run it:** Push, open the pipeline — check the "CI lint" view (CI/CD > Editor > Lint) to see the fully merged config.
- **Expected result:** Single pipeline with 3 jobs, one per included file — no downstream pipeline is created.
- **What this teaches:** `include:` is pure YAML composition, not pipeline forking.

### Lab 5: Multi-project pipeline trigger (`trigger: project:`)
- **Goal:** Trigger a pipeline in a *different* GitLab project from this one.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - deploy

trigger_downstream_project:
  stage: deploy
  trigger:
    project: 'my-group/shared-infra-project'
    branch: main
    strategy: depend
```
- **Run it:** Requires an existing second project (`my-group/shared-infra-project`) with its own `.gitlab-ci.yml`, and a user/token with at least Developer access to trigger it. Push to this project and watch the pipeline.
- **Expected result:** A brand-new pipeline appears under `my-group/shared-infra-project`'s own Pipelines list, linked back to the triggering pipeline via the downstream-pipeline icon.
- **What this teaches:** Multi-project pipelines are how one repo's pipeline can kick off a pipeline in a completely separate repo/project — the basis for cross-team release orchestration.

### Lab 6: Reusable template from another project (`include: project:`)
- **Goal:** Pull a shared job template from a separate "shared-ci-templates" project into this pipeline (no new pipeline created, unlike Lab 5).
- **`.gitlab-ci.yml`:**
```yaml
include:
  - project: 'group/shared-ci-templates'
    file: '/templates/build.yml'
    ref: main

stages:
  - build

build_job:
  extends: .shared_build
  stage: build
```
- **`group/shared-ci-templates` repo, `/templates/build.yml`:**
```yaml
.shared_build:
  image: node:20
  script:
    - npm ci
    - npm run build
```
- **Run it:** Requires the CI/CD token or the triggering user to have at least read access to `group/shared-ci-templates`. Push and check the Lint view to confirm `.shared_build` merged in.
- **Expected result:** `build_job` runs `npm ci && npm run build` even though that logic lives in a different project's repo.
- **What this teaches:** `include: project:` vs `trigger: project:` — both cross project boundaries, but one merges YAML into your pipeline, the other spawns an independent pipeline elsewhere.

### Lab 7: CI/CD Component with typed inputs
- **Goal:** Use a versioned, parameterized CI/CD Component instead of a raw template include.
- **`.gitlab-ci.yml`:**
```yaml
include:
  - component: gitlab.com/my-group/ci-components/node-build@1.2.0
    inputs:
      node_version: "20"
      run_lint: true

stages:
  - build
```
- **Run it:** Requires a published component project (`my-group/ci-components/node-build`) with a `template.yml` defining `spec: inputs:`. Push and confirm the merged job appears with `node_version` substituted.
- **Expected result:** Pipeline includes the component's job(s), with `$[[ inputs.node_version ]]` resolved to `20` inside the component's script.
- **What this teaches:** Components add input validation and versioning (`@1.2.0`) on top of what a plain template `include:` gives you — the modern way to publish reusable pipeline building blocks.

### Lab 8: Child pipeline generated dynamically (dynamic child pipelines)
- **Goal:** Generate the child pipeline's YAML at runtime instead of committing a static file.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - generate
  - trigger

generate_config:
  stage: generate
  script:
    - echo "deploy_job:\n  script:\n    - echo Deploying $CI_COMMIT_SHORT_SHA" > generated-config.yml
  artifacts:
    paths:
      - generated-config.yml

trigger_dynamic_child:
  stage: trigger
  trigger:
    include:
      - artifact: generated-config.yml
        job: generate_config
    strategy: depend
```
- **Run it:** Push, inspect the generated child pipeline's single job log.
- **Expected result:** Child pipeline runs a job whose script was written at pipeline runtime by `generate_config`, not committed to the repo.
- **What this teaches:** Dynamic child pipelines — useful for matrix-of-microservices monorepos where the set of jobs depends on what changed.

### Lab 9: Fan-out monorepo pipeline (one child per service)
- **Goal:** Trigger one child pipeline per microservice folder, each with `rules:changes` so only changed services run.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - deploy

trigger_service_a:
  stage: deploy
  trigger:
    include: services/service-a/.gitlab-ci.yml
    strategy: depend
  rules:
    - changes:
        - services/service-a/**

trigger_service_b:
  stage: deploy
  trigger:
    include: services/service-b/.gitlab-ci.yml
    strategy: depend
  rules:
    - changes:
        - services/service-b/**
```
- **Run it:** Change a file only under `services/service-a/`, push, observe the pipeline.
- **Expected result:** Only `trigger_service_a` runs and creates a downstream pipeline; `trigger_service_b` is skipped.
- **What this teaches:** Combining `trigger:` with `rules:changes` gives cheap, scoped monorepo fan-out — no wasted downstream pipelines for untouched services.

### Lab 10: Merged job override across two includes
- **Goal:** Observe GitLab's "last include wins" merge rule when two included files define the same job name.
- **`.gitlab-ci.yml`:**
```yaml
include:
  - local: 'ci-templates/base-deploy.yml'
  - local: 'ci-templates/override-deploy.yml'
```
- **`ci-templates/base-deploy.yml`:**
```yaml
deploy_job:
  script:
    - echo "base deploy"
```
- **`ci-templates/override-deploy.yml`:**
```yaml
deploy_job:
  script:
    - echo "override deploy"
```
- **Run it:** Push, open the job log for `deploy_job`.
- **Expected result:** Log prints "override deploy" — the later `include:` entry wins entirely (script is replaced, not merged).
- **What this teaches:** Include-merge order matters; put the most specific/override file last.

### Lab 11: Parent-child nesting limit
- **Goal:** Confirm the 2-level nesting limit for parent-child pipelines.
- **`.gitlab-ci.yml`:** parent triggers `child-a.yml`; `child-a.yml` itself has a `trigger: include: child-b.yml` job.
- **Run it:** Push and watch the pipeline graph.
- **Expected result:** Parent → child-a works fine; child-a → child-b (a third level) fails validation with a nesting-depth error.
- **What this teaches:** Parent-child pipelines are capped at 2 levels deep — deeper fan-out needs multi-project pipelines instead (which have no such cap).

## Common Pitfalls
- Forgetting `strategy: depend` (or `mirror`) and assuming the parent "waits" for the child — by default it doesn't.
- Confusing `trigger: project:` (new pipeline, different project) with `include: project:` (same pipeline, borrowed YAML) — they solve different problems.
- Relying on parent-child nesting beyond 2 levels — GitLab will reject it; restructure as multi-project or dynamic fan-out.
- Two included files defining the same job name and being surprised the last one silently wins instead of merging.
- Using `include: remote:` against a URL that requires auth headers — remote includes only support plain HTTPS GET, no credentials.
- Forgetting that variables set with `rules: ... variables:` on the trigger job only apply if that specific rule matches — a catch-all `else` rule is easy to forget.
- Not giving the CI/CD token/user access to the target project when using cross-project `include: project:` or `trigger: project:` — pipeline fails with a permissions error.

## Interview Questions & Answers
- **Q: What's the core difference between `trigger:` and `include:`?**
  A: `trigger:` creates a new, independent pipeline (possibly in another project); `include:` merges YAML into the current pipeline — no new pipeline.
- **Q: How do you make a parent pipeline fail if its child pipeline fails?**
  A: Set `strategy: depend` (or `strategy: mirror` for exact status mirroring) on the trigger job.
- **Q: What's the max nesting depth for parent-child pipelines?**
  A: 2 levels. Multi-project pipelines have no such limit since each is independent.
- **Q: When would you use `trigger: project:` instead of `trigger: include:`?**
  A: When the pipeline you want to kick off lives in a different GitLab project/repo, e.g. triggering a shared deploy pipeline from multiple app repos.
- **Q: What happens if two `include:` files define a job with the same name?**
  A: The last one included wins completely — GitLab does not merge the two job definitions, it overrides.
- **Q: What are CI/CD Components and how do they relate to `include: project:`?**
  A: Components are versioned, input-validated, catalog-discoverable packages of pipeline config (`include: component:`) — the modern, preferred evolution of plain `include: project:` template sharing.
- **Q: Can you pass variables into a child pipeline dynamically based on branch?**
  A: Yes — use `rules:` with per-condition `variables:` blocks on the trigger job.
- **Q: Scenario: you have a monorepo with 10 microservices and want CI to only build the ones that changed. How would you structure it?**
  A: One `trigger:` job per service, each gated with `rules: changes: [service/path/**]`, each pointing at that service's own child pipeline file — only touched services spawn downstream pipelines.
- **Q: Scenario: a child pipeline needs config that doesn't exist as a file in the repo — how do you supply it?**
  A: Use a dynamic child pipeline: generate the YAML as a job artifact, then trigger with `include: - artifact: generated.yml, job: generate_job`.
- **Q: Does `include:` support authenticated remote URLs?**
  A: No — `include: remote:` only supports plain public HTTPS; for private cross-project files use `include: project:` instead.
- **Q: Is `only:`/`except:` still relevant to child pipeline job triggering?**
  A: No — both are deprecated; use `rules:` for any conditional triggering of `trigger:` jobs.
