# 24. GitLab CI/CD Deployment to AWS EC2 (SSH/SCP)

## Quick Summary
- Classic "no Kubernetes, no fancy tooling" deploy: GitLab Runner SSHes into an EC2 box and copies/restarts the app.
- Core mechanics: store the SSH private key as a protected/masked CI/CD variable, write it to a file at job time, `scp` the code over, `ssh` in to restart the service.
- The private key never lives in the repo — it's injected at runtime from GitLab CI/CD variables.
- `StrictHostKeyChecking no` is a common shortcut that disables host-key verification — it works, but it's a real (if often accepted) security weakness; a pinned `known_hosts` via `ssh-keyscan` is the safer alternative.
- This pattern generalizes: swap `scp` + `systemctl restart` for `pm2 reload`, Docker commands, or a symlink swap, and you get process-manager deploys, container deploys, or blue-green — all built on the same SSH foundation.
- Interview framing: "how do you deploy without Kubernetes/a PaaS?" and "how do you handle SSH keys securely in CI?" both live here.

## Core Concepts

### The building blocks
- **CI/CD variables** (Settings > CI/CD > Variables): `EC2_HOST`, `EC2_USER`, `SSH_PRIVATE_KEY` — mark `SSH_PRIVATE_KEY` **protected** and **masked** (masking a multi-line PEM key isn't supported by GitLab's masking, so protect it and restrict which branches/environments can access it instead).
- **Runtime key setup**: `echo "$SSH_PRIVATE_KEY" > ~/.ssh/id_rsa && chmod 600 ~/.ssh/id_rsa` — `chmod 600` is mandatory, `ssh` refuses keys with looser permissions.
- **Transfer**: `scp -r ./ $EC2_USER@$EC2_HOST:/path/` for files, or a Docker/registry pull for container-based variants (file 25).
- **Restart**: `ssh $EC2_USER@$EC2_HOST "sudo systemctl restart myapp"` or process-manager equivalent (`pm2 reload`).

### Host-key verification: the tradeoff
- SSH normally refuses to connect to a host it hasn't seen before (or whose key changed) — this stops on-path attacks, but in CI, a fresh runner/container has an empty `known_hosts` every time, so the first connection always prompts.
- `StrictHostKeyChecking no` (or `-o UserKnownHostsFile=/dev/null`) skips that prompt entirely — convenient, but it also means a spoofed host would be accepted silently. Realistic and extremely common in tutorials/small teams, but a real weakness worth knowing about and flagging explicitly.
- The safer pattern: run `ssh-keyscan $EC2_HOST >> ~/.ssh/known_hosts` **once, from a trusted context**, and commit that known-hosts entry (or store it as a CI/CD variable) so the CI job pins the expected key instead of accepting anything.

### Rollback-friendly layout
- Deploying straight into `/var/www/myapp` and overwriting in place makes rollback painful (you've destroyed the previous version).
- Versioned release directories (`/var/www/releases/<sha>/`) plus a `current` symlink pointed at the active release is the standard pattern — rollback becomes "point the symlink at the previous release directory," not a redeploy.

## Hands-On Labs

### Lab 1: Prepare the EC2 instance and GitLab variables
- **Goal:** One-time setup so later labs have somewhere to deploy to.
- **Steps (not YAML):**
  1. On EC2: `sudo yum install git -y` (or `apt install git`), `mkdir -p /var/www/myapp`.
  2. In GitLab: Settings > CI/CD > Variables, add `EC2_HOST` (public IP), `EC2_USER` (e.g. `ec2-user`), `SSH_PRIVATE_KEY` (full contents of the `.pem` file) — mark `SSH_PRIVATE_KEY` **Protected**.
- **Run it:** No pipeline yet — just confirm the three variables exist and are correctly scoped.
- **Expected result:** Variables visible (values masked/hidden) under Settings > CI/CD > Variables.
- **What this teaches:** Secrets belong in CI/CD variables, never committed to the repo — the foundation every later lab depends on.

### Lab 2: Basic SCP deploy (with the `StrictHostKeyChecking no` tradeoff)
- **Goal:** Get the simplest possible working deploy, understanding what it trades away.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - deploy

deploy_to_ec2:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh
    - mkdir -p ~/.ssh
    - echo "$SSH_PRIVATE_KEY" > ~/.ssh/id_rsa
    - chmod 600 ~/.ssh/id_rsa
    # ⚠️ Disables host-key verification entirely — convenient but accepts any host silently.
    - echo -e "Host *\n\tStrictHostKeyChecking no\n" > ~/.ssh/config
  script:
    - echo "Deploying to EC2..."
    - scp -r ./ $EC2_USER@$EC2_HOST:/var/www/myapp/
    - ssh $EC2_USER@$EC2_HOST "sudo systemctl restart myapp || echo 'No service to restart'"
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```
- **Run it:** Push to `main`.
- **Expected result:** Files land in `/var/www/myapp` on EC2; service restarts.
- **What this teaches:** ⚠️ `StrictHostKeyChecking no` is realistic and common, but it means the job would silently connect to an attacker-controlled host presenting the same IP (e.g. via DNS/ARP spoofing) without any warning — acceptable for a learning lab or low-risk internal tool, not for anything sensitive without compensating controls.

### Lab 3: Safer alternative — pin the host key with `ssh-keyscan`
- **Goal:** Get the same deploy without disabling host-key verification.
- **`.gitlab-ci.yml`:**
```yaml
deploy_to_ec2_safe:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh
    - mkdir -p ~/.ssh
    - echo "$SSH_PRIVATE_KEY" > ~/.ssh/id_rsa
    - chmod 600 ~/.ssh/id_rsa
    # Pin the real host key instead of disabling verification.
    - ssh-keyscan -H $EC2_HOST >> ~/.ssh/known_hosts
  script:
    - scp -r ./ $EC2_USER@$EC2_HOST:/var/www/myapp/
    - ssh $EC2_USER@$EC2_HOST "sudo systemctl restart myapp"
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```
- **Run it:** Push to `main`; optionally test the failure mode by pre-populating `~/.ssh/known_hosts` with a deliberately wrong key and confirming `ssh` refuses to connect.
- **Expected result:** Deploy succeeds identically to Lab 2, but the job explicitly trusts only the key `ssh-keyscan` fetched for `$EC2_HOST` at job time.
- **What this teaches:** `ssh-keyscan` (run fresh each job, or better, its output stored once as a CI/CD variable and appended to `known_hosts`) gets you host-key pinning without the manual step of a persistent runner cache — closes the gap `StrictHostKeyChecking no` leaves open, for a few extra lines.

### Lab 4: Add a post-deploy health check
- **Goal:** Fail the pipeline (not just log a warning) if the app doesn't come back up healthy.
- **`.gitlab-ci.yml`:**
```yaml
deploy_with_healthcheck:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh curl
    - mkdir -p ~/.ssh
    - echo "$SSH_PRIVATE_KEY" > ~/.ssh/id_rsa
    - chmod 600 ~/.ssh/id_rsa
    - ssh-keyscan -H $EC2_HOST >> ~/.ssh/known_hosts
  script:
    - scp -r ./ $EC2_USER@$EC2_HOST:/var/www/myapp/
    - ssh $EC2_USER@$EC2_HOST "sudo systemctl restart myapp"
    - sleep 5
    - curl -f http://$EC2_HOST/health
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```
- **Run it:** Push with a healthy app, then push with an app that returns a 500 on `/health`.
- **Expected result:** First run: pipeline succeeds. Second run: `curl -f` exits non-zero, job (and pipeline) fails, immediately visible instead of silently leaving a broken deploy.
- **What this teaches:** A deploy job without a health check only proves the *copy* succeeded, not that the *app* works — `curl -f` turns that gap into a hard pipeline failure.

### Lab 5: Rollback on failed health check
- **Goal:** Automatically revert to the previous version if the new one fails its health check.
- **`.gitlab-ci.yml`:**
```yaml
deploy_with_rollback:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh curl
    - mkdir -p ~/.ssh
    - echo "$SSH_PRIVATE_KEY" > ~/.ssh/id_rsa
    - chmod 600 ~/.ssh/id_rsa
    - ssh-keyscan -H $EC2_HOST >> ~/.ssh/known_hosts
  script:
    - ssh $EC2_USER@$EC2_HOST "cp -r /var/www/myapp /var/www/myapp.backup"
    - scp -r ./ $EC2_USER@$EC2_HOST:/var/www/myapp/
    - ssh $EC2_USER@$EC2_HOST "sudo systemctl restart myapp"
    - sleep 5
    - |
      if ! curl -f http://$EC2_HOST/health; then
        echo "Health check failed — rolling back"
        ssh $EC2_USER@$EC2_HOST "rm -rf /var/www/myapp && mv /var/www/myapp.backup /var/www/myapp && sudo systemctl restart myapp"
        exit 1
      fi
    - ssh $EC2_USER@$EC2_HOST "rm -rf /var/www/myapp.backup"
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```
- **Run it:** Push a broken build (failing `/health`).
- **Expected result:** New code is deployed, health check fails, the previous version is restored from the backup, service is restarted on the old version, and the pipeline still reports failure (so the team knows) — but users end up back on working code.
- **What this teaches:** "Deploy" and "stay deployed" are different guarantees — an automated rollback path turns a bad release into a noisy-but-safe non-event instead of an outage.

### Lab 6: Versioned releases + symlink for instant rollback
- **Goal:** Keep every deployed version on disk so rollback is a symlink change, not a file copy.
- **`.gitlab-ci.yml`:**
```yaml
deploy_versioned:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh
    - mkdir -p ~/.ssh
    - echo "$SSH_PRIVATE_KEY" > ~/.ssh/id_rsa
    - chmod 600 ~/.ssh/id_rsa
    - ssh-keyscan -H $EC2_HOST >> ~/.ssh/known_hosts
  script:
    - ssh $EC2_USER@$EC2_HOST "mkdir -p /var/www/releases/$CI_COMMIT_SHORT_SHA"
    - scp -r ./ $EC2_USER@$EC2_HOST:/var/www/releases/$CI_COMMIT_SHORT_SHA/
    - ssh $EC2_USER@$EC2_HOST "ln -sfn /var/www/releases/$CI_COMMIT_SHORT_SHA /var/www/myapp-current && sudo systemctl restart myapp"
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```
- **Run it:** Push twice with different commits; note two directories under `/var/www/releases/` on EC2.
- **Expected result:** `/var/www/myapp-current` points at the latest release; the previous commit's full release directory still exists untouched.
- **What this teaches:** Rollback to any previous commit becomes `ln -sfn /var/www/releases/<old-sha> /var/www/myapp-current` — no redeploy, no rebuild, just re-pointing a symlink (this is the same idea used later for blue-green in Lab 9).

### Lab 7: Node.js deploy with pm2 process management
- **Goal:** Deploy a Node app and reload it with pm2 instead of a generic systemd restart.
- **`.gitlab-ci.yml`:**
```yaml
deploy_node_pm2:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh
    - mkdir -p ~/.ssh
    - echo "$SSH_PRIVATE_KEY" > ~/.ssh/id_rsa
    - chmod 600 ~/.ssh/id_rsa
    - ssh-keyscan -H $EC2_HOST >> ~/.ssh/known_hosts
  script:
    - scp -r ./ $EC2_USER@$EC2_HOST:/var/www/myapp/
    - ssh $EC2_USER@$EC2_HOST "cd /var/www/myapp && npm install --production && pm2 reload app.js --update-env || pm2 start app.js --name myapp"
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```
- **Run it:** Push to `main` with a Node app + `app.js` entrypoint on the EC2 box.
- **Expected result:** `pm2 reload` performs a near-zero-downtime restart of an already-running process; `pm2 start` handles the first-ever deploy.
- **What this teaches:** `pm2 reload` (vs `restart`) keeps the old process serving until the new one is ready — a lighter-weight rolling-style restart for single-instance Node apps.

### Lab 8: systemd-managed deploy with `daemon-reload`
- **Goal:** Deploy an app managed as a proper systemd service, picking up unit file changes too.
- **`.gitlab-ci.yml`:**
```yaml
deploy_systemd:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh
    - mkdir -p ~/.ssh
    - echo "$SSH_PRIVATE_KEY" > ~/.ssh/id_rsa
    - chmod 600 ~/.ssh/id_rsa
    - ssh-keyscan -H $EC2_HOST >> ~/.ssh/known_hosts
  script:
    - scp -r ./ $EC2_USER@$EC2_HOST:/var/www/myapp/
    - scp ./myapp.service $EC2_USER@$EC2_HOST:/tmp/myapp.service
    - ssh $EC2_USER@$EC2_HOST "sudo mv /tmp/myapp.service /etc/systemd/system/myapp.service && sudo systemctl daemon-reload && sudo systemctl restart myapp && sudo systemctl status myapp --no-pager"
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```
- **Run it:** Push with a `myapp.service` unit file in the repo.
- **Expected result:** Unit file is updated and reloaded before restart; `systemctl status` in the log confirms the service came up.
- **What this teaches:** Real systemd deploys need `daemon-reload` whenever the unit file itself changes, not just the app code — easy to forget and a common source of "my config change didn't take effect" bugs.

### Lab 9: Blue-green via symlink swap between two directories
- **Goal:** Maintain two full app directories and cut over between them.
- **`.gitlab-ci.yml`:**
```yaml
deploy_blue_green:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh curl
    - mkdir -p ~/.ssh
    - echo "$SSH_PRIVATE_KEY" > ~/.ssh/id_rsa
    - chmod 600 ~/.ssh/id_rsa
    - ssh-keyscan -H $EC2_HOST >> ~/.ssh/known_hosts
  script:
    - |
      TARGET=$(ssh $EC2_USER@$EC2_HOST "readlink /var/www/myapp-current" | grep -q app_v1 && echo app_v2 || echo app_v1)
      echo "Deploying to idle slot: $TARGET"
      scp -r ./ $EC2_USER@$EC2_HOST:/var/www/$TARGET/
      ssh $EC2_USER@$EC2_HOST "cd /var/www/$TARGET && sudo systemctl restart myapp-$TARGET"
      sleep 5
      ssh $EC2_USER@$EC2_HOST "curl -f http://localhost:8081/health" || (echo "New slot failed health check, not swapping" && exit 1)
      ssh $EC2_USER@$EC2_HOST "ln -sfn /var/www/$TARGET /var/www/myapp-current"
  environment:
    name: production
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
```
- **Run it:** First run deploys to `app_v2` (since `app_v1` is presumed current) and swaps; second run deploys to `app_v1` and swaps back — alternating slots each release.
- **Expected result:** The idle directory is always the deploy target; the symlink only moves after the new slot passes its health check, so a bad deploy never gets traffic.
- **What this teaches:** This is file 23's blue-green pattern applied purely with `ssh`/filesystem primitives — no load balancer required, useful when you're on a single EC2 box running two ports/services behind a local reverse proxy.

### Lab 10: Manual approval gate before EC2 production deploy
- **Goal:** Require a human click for production, automatic for everything else.
- **`.gitlab-ci.yml`:**
```yaml
deploy_ec2_prod:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh
    - mkdir -p ~/.ssh
    - echo "$SSH_PRIVATE_KEY" > ~/.ssh/id_rsa
    - chmod 600 ~/.ssh/id_rsa
    - ssh-keyscan -H $EC2_HOST >> ~/.ssh/known_hosts
  script:
    - scp -r ./ $EC2_USER@$EC2_HOST:/var/www/myapp/
    - ssh $EC2_USER@$EC2_HOST "sudo systemctl restart myapp"
  environment:
    name: production
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
      allow_failure: false
```
- **Run it:** Push to `main`, confirm the job waits for a Play click; click it.
- **Expected result:** Pipeline stays at "waiting for manual action" until clicked; `allow_failure: false` means the overall pipeline can't be considered fully successful while this job is un-run or fails.
- **What this teaches:** The minimal manual-gate pattern for EC2 deploys — full approval-gate mechanics (protected environments, multiple approvers) are covered in file 27, which builds on exactly this job shape.

## Common Pitfalls
- Forgetting `chmod 600` on the private key file — SSH refuses to use a key that's group/world-readable.
- Using `StrictHostKeyChecking no` without realizing what it disables — fine for a lab/internal tool, a real gap for anything sensitive; prefer `ssh-keyscan` pinning (Lab 3).
- Deploying by overwriting the same directory every time — makes rollback require a full redeploy instead of a symlink flip.
- Health-checking immediately with no `sleep`/retry — the app may not have finished starting yet, causing false-positive failures.
- Restarting with `systemctl restart` after changing the unit file itself without `daemon-reload` first — the old unit definition silently stays in effect.
- Storing `SSH_PRIVATE_KEY` unprotected — anyone who can run a pipeline on any branch can exfiltrate it; mark it Protected and restrict protected branches/environments accordingly.
- Not cleaning up backup/old release directories (Lab 5/6) — disk fills up over time without a retention policy.

## Interview Questions & Answers
- **Q: How do you get an SSH private key into a GitLab CI job without committing it to the repo?**
  A: Store it as a Protected CI/CD variable, then write it to a file (`echo "$SSH_PRIVATE_KEY" > ~/.ssh/id_rsa`) and `chmod 600` it at job runtime.
- **Q: What does `StrictHostKeyChecking no` actually disable, and what's the safer alternative?**
  A: It skips verifying the remote host's SSH key against `known_hosts`, accepting any host silently; the safer alternative is pinning the real key via `ssh-keyscan $HOST >> ~/.ssh/known_hosts` (ideally scanned once from a trusted context, not blindly trusted every job).
- **Q: How would you make an EC2 deploy zero-downtime without Kubernetes?**
  A: Either a rolling deploy across multiple instances behind a load balancer with health checks between each, or a blue-green symlink/port swap on a single box, gated on a health check before cutover.
- **Q: How do you roll back a bad EC2 deploy quickly?**
  A: Versioned release directories with a `current` symlink — rollback is `ln -sfn` to the previous release directory plus a service restart, no redeploy needed.
- **Q: Why `pm2 reload` instead of `pm2 restart`?**
  A: `reload` keeps the old process serving connections until the new one is ready (near-zero-downtime); `restart` tears down first, causing a brief gap.
- **Q: What CI/CD variable settings matter most for a deploy key?**
  A: Mark it Protected (only exposed on protected branches/tags) at minimum; GitLab's masking doesn't support multi-line values like PEM keys, so protection is the main control.
- **Q: Scenario: your deploy job succeeds but the app is actually down — what's missing?**
  A: A post-deploy health check (`curl -f .../health`) — a successful `scp`/`ssh` only proves the copy/restart commands ran, not that the app is serving correctly.
- **Q: Scenario: you need to deploy the same app to dev, staging, and prod EC2 instances with different hosts/keys — how do you avoid duplicating the whole job three times?**
  A: Parameterize via per-environment CI/CD variables (`DEV_HOST`, `STAGING_HOST`, `PROD_HOST`, etc., possibly environment-scoped) and reuse one job body via `extends:` or a child pipeline — see file 26 for the full multi-environment structure.
- **Q: What's the risk of restarting a systemd service after editing its unit file without `daemon-reload`?**
  A: systemd keeps using the previously loaded unit definition — the restart applies your app code changes but silently ignores the unit file change until `daemon-reload` runs.
- **Q: Why keep a `.backup` or versioned copy before overwriting the deploy directory?**
  A: It's what makes an automatic rollback-on-failed-health-check possible — without a preserved previous version, "rollback" would require rebuilding and redeploying the old commit from scratch.
