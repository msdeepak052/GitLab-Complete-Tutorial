# 13. Caching vs Artifacts in GitLab CI/CD

## Quick Summary
- Cache and artifacts both persist files between jobs, but solve different problems and are frequently confused in interviews.
- Cache = speed optimization for dependencies (e.g. `node_modules/`, `.m2/repository/`); best-effort, shared across pipelines, not guaranteed to exist.
- Artifacts = pipeline output that must reliably pass to later jobs/stages, visible and downloadable in the GitLab UI, has an explicit expiry.
- Cache is restored *before* `script:` runs and saved *after*; artifacts are uploaded after the job finishes and downloaded automatically by dependent jobs.
- `cache:key` strategies (`key`, `key:files`, `key:prefix`) control cache invalidation; `cache:policy` controls pull/push behavior for performance tuning.
- Never rely on cache for correctness — a cache miss must never break a build, only slow it down; artifacts are the correctness-guaranteeing mechanism.

## Core Concepts

### Cache
- Purpose: avoid re-downloading/re-building the same dependencies on every pipeline run.
- Scope: shared best-effort, typically keyed per branch (`$CI_COMMIT_REF_SLUG`) or per project; not guaranteed available (runner-dependent storage, can be evicted).
- Restored at the **start** of a job, saved at the **end** — happens automatically if `cache:` is declared, no explicit "download" step needed.
- Typical contents: `node_modules/`, `vendor/`, `.m2/repository/`, `~/.cache/pip`.

### `cache:key` strategies
| Strategy | Behavior |
| --- | --- |
| `cache: key: <string or var>` | Static or variable-based key, e.g. `${CI_COMMIT_REF_SLUG}` for one cache per branch |
| `cache: key: files: [path]` | Key derived from the content hash of the listed file(s) (e.g. `package-lock.json`) — cache automatically invalidates when the file changes |
| `cache: key: prefix: <string>` | Combined with `key:files` to add a readable prefix in front of the content hash |
| `fallback_keys` | Up to 5 additional keys tried in order if the primary key misses — lets a job partially reuse an older cache instead of starting cold |
| `cache: policy: pull` | Only restore cache, never save (use on jobs that consume but don't change dependencies, saves time) |
| `cache: policy: push` | Only save cache, never restore |
| `cache: policy: pull-push` | Default — both restore and save |
| `cache: paths` | List of directories/files to cache |

### Artifacts
- Purpose: reliably move a job's output (build results, reports, binaries) forward to later stages, and expose it for download from the pipeline/job UI.
- Default expiry: current GitLab default is **30 days** unless `expire_in:` is set explicitly.
- Downloaded automatically into dependent jobs based on stage order (see file 14 for `dependencies:`/`needs:` fine control).
- Special report types (`artifacts:reports:junit`, `dotenv`, `coverage_report`, etc.) get parsed and surfaced natively in the GitLab UI (test results tab, MR widget, etc.).
- `artifacts:when: always` — keep artifacts even if the job fails (useful for logs/test reports that explain the failure).

### Cache vs Artifacts — comparison table
| Feature | Cache | Artifacts |
| --- | --- | --- |
| Purpose | Speed up jobs by reusing dependencies | Persist and pass job output |
| Guarantee | Best-effort, may be empty/missing | Guaranteed present until expiry, passed reliably to dependent jobs |
| Visible in UI | No | Yes, downloadable |
| Default lifetime | Until evicted/replaced (no fixed schedule) | 30 days by default, configurable via `expire_in` |
| Typical contents | `node_modules/`, `.m2/repository/`, package manager caches | `dist/`, `build/`, test reports, binaries |
| Passing between jobs | Same cache key, works across pipelines too | Controlled via stage order + `dependencies:`/`needs:` within one pipeline |

### `⚠️ Deprecated / Changed`
- Older material sometimes implies cache is "reliably shared" between arbitrary jobs — current docs are explicit that cache is best-effort and must never be relied on for correctness; only artifacts guarantee delivery.
- `key:files_commits` variant also exists (keys off the latest commit touching specific files) — a lesser-known alternative to `key:files`' content-hash approach.

## Hands-On Labs

### Lab 1: Basic branch-scoped dependency cache (Node.js)
- **Goal:** Cache `node_modules/` per branch to speed up repeat `npm install`.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - test

variables:
  NODE_ENV: "production"

cache:
  key: ${CI_COMMIT_REF_SLUG}
  paths:
    - node_modules/

install_dependencies:
  stage: build
  script:
    - echo "Installing dependencies..."
    - npm install

run_tests:
  stage: test
  script:
    - echo "Running tests..."
    - npm test
```
- **Run it:** Push twice to the same branch (second push should be noticeably faster on install).
- **Expected result:** First run: `Downloading cache...` shows nothing restored. Second run: `Restoring cache...` shows the cache hit, `npm install` completes faster.
- **What this teaches:** Cache restore/save is automatic once declared — no explicit steps in `script:`.

### Lab 2: Maven cache for Java builds
- **Goal:** Cache the local `.m2` repository to avoid re-downloading Maven dependencies.
- **`.gitlab-ci.yml`:**
```yaml
cache:
  key: ${CI_PROJECT_NAME}
  paths:
    - .m2/repository/

build_job:
  stage: build
  script:
    - mvn clean install
```
- **Run it:** Push twice.
- **Expected result:** Second run's Maven output shows far fewer "Downloading..." lines.
- **What this teaches:** Same cache mechanism applies across language ecosystems — only the cached path changes.

### Lab 3: Content-hash cache key with `key:files`
- **Goal:** Auto-invalidate cache only when the lockfile actually changes, not on every branch.
- **`.gitlab-ci.yml`:**
```yaml
cache:
  key:
    files:
      - package-lock.json
    prefix: npm-cache
  paths:
    - node_modules/

install_dependencies:
  stage: build
  script:
    - npm install
```
- **Run it:** Push, then push again without touching `package-lock.json`, then edit `package-lock.json` and push again.
- **Expected result:** Same cache key (and hit) for the first two pushes; a new cache key (miss, fresh install, new cache saved) after the lockfile changes.
- **What this teaches:** `key:files` ties cache lifetime to dependency-definition content rather than branch name — safer than a branch-based key when multiple branches share the same dependencies.

### Lab 4: `fallback_keys` for partial cache reuse
- **Goal:** Avoid a fully cold cache when the primary key misses (e.g. brand-new feature branch).
- **`.gitlab-ci.yml`:**
```yaml
cache:
  key: ${CI_COMMIT_REF_SLUG}
  fallback_keys:
    - main-cache
  paths:
    - node_modules/
  policy: pull-push

install_dependencies:
  stage: build
  script:
    - npm install
```
- **Run it:** Push to a brand-new branch that has never had its own cache.
- **Expected result:** Job log shows the branch-specific key missing, then falling back to `main-cache` (if it exists) instead of installing fully cold.
- **What this teaches:** `fallback_keys` reduces cold-cache pain for new branches by borrowing a nearby cache.

### Lab 5: `cache:policy: pull` for read-only consumer jobs
- **Goal:** Speed up a job that uses the cache but never changes dependencies, by skipping the (slow) re-upload.
- **`.gitlab-ci.yml`:**
```yaml
cache:
  key: ${CI_COMMIT_REF_SLUG}
  paths:
    - node_modules/
  policy: pull

run_lint:
  stage: test
  script:
    - npx eslint .
```
- **Run it:** Push after a build job has already populated the cache.
- **Expected result:** Job log shows cache restored, but no "Saving cache..." step at the end.
- **What this teaches:** `policy: pull` is a performance tweak for jobs that consume, but don't modify, cached content.

### Lab 6: Save build output as an artifact
- **Goal:** Produce a build output directory and make it downloadable/passable to later jobs.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - test

build_job:
  stage: build
  script:
    - echo "Building application..."
    - mkdir -p build
    - echo "Hello World" > build/app.txt
  artifacts:
    paths:
      - build/
    expire_in: 1 hour

test_job:
  stage: test
  script:
    - echo "Testing application..."
    - cat build/app.txt
```
- **Run it:** Push and open both job logs; also check the job's "Browse" artifacts link in the UI.
- **Expected result:** `test_job` prints `Hello World` — `build/` was auto-downloaded because `test_job` is in a later stage with no `dependencies:`/`needs:` restriction. Artifact is downloadable from the UI until it expires in 1 hour.
- **What this teaches:** Artifacts pass automatically to later-stage jobs by default; cache does not do this reliably across pipelines the same way.

### Lab 7: JUnit test report artifact, kept even on failure
- **Goal:** Ensure test reports survive a failing job and get parsed into the UI.
- **`.gitlab-ci.yml`:**
```yaml
test_job:
  stage: test
  script:
    - mkdir -p reports
    - echo "<testsuite></testsuite>" > reports/junit.xml
  artifacts:
    when: always
    paths:
      - reports/
    reports:
      junit: reports/junit.xml
    expire_in: 1 day
```
- **Run it:** Push (optionally modify the script to `exit 1` after generating the report to simulate failure).
- **Expected result:** Report is uploaded and parsed into the pipeline's "Tests" tab even if the job fails, because `when: always` overrides the default (artifacts only on success).
- **What this teaches:** `artifacts:when: always` is essential for diagnostics — a report that only saves on success is useless for debugging failures.

### Lab 8: Combined cache + artifacts in one pipeline
- **Goal:** Use cache for dependencies and artifacts for build output in the same job.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - test

cache:
  key: ${CI_COMMIT_REF_SLUG}
  paths:
    - node_modules/

build_job:
  stage: build
  script:
    - npm install
    - npm run build
  artifacts:
    paths:
      - dist/
    expire_in: 2 hours

test_job:
  stage: test
  script:
    - echo "Testing build..."
    - ls dist/
```
- **Run it:** Push twice to the same branch.
- **Expected result:** Second run's `npm install` is faster (cache hit); `test_job` always sees `dist/` regardless of cache state (artifact, not cache).
- **What this teaches:** Cache and artifacts are complementary, not interchangeable — dependencies go in cache, deliverable output goes in artifacts.

### Lab 9: Trace the execution — cache restore, install, build, artifact save, cache save
- **Goal:** Walk the exact order of operations for a single job, stage by stage, to internalize the mechanism.
- **`.gitlab-ci.yml`:** (same as Lab 8)
- **Run it:** Push, then open the `build_job` log and read top to bottom.
- **Expected result and reading order:**
  1. Runner starts a fresh environment — `node_modules/` absent unless restored.
  2. GitLab attempts cache restore keyed by `${CI_COMMIT_REF_SLUG}` — first run on a branch: nothing restored; later runs: `node_modules/` appears before `npm install` executes.
  3. `npm install` runs — installs missing packages only if cache was restored.
  4. `npm run build` runs — produces `dist/`.
  5. Artifacts step: `dist/` is uploaded and registered against this job — available to `test_job` next stage.
  6. Cache save step: `node_modules/` is saved back under the branch's cache key for the *next* pipeline run.
  7. `test_job` starts in the next stage: artifacts from `build_job` are downloaded automatically (no `dependencies:` needed here — see file 14 for restricting this); `dist/` is present, script runs `ls dist/`.
- **What this teaches:** Cache and artifacts have distinct save/restore lifecycles even inside a single job — cache persists forward to *future pipelines* on the same key, while artifacts persist forward to *later jobs in this same pipeline*.

### Lab 10: Prove cache is best-effort — clear it and confirm the build still works
- **Goal:** Confirm cache absence never breaks correctness, only speed.
- **`.gitlab-ci.yml`:** (same as Lab 1)
- **Run it:** Go to CI/CD > Pipelines > Clear runner caches (or bump the cache key, e.g. temporarily rename it), then push.
- **Expected result:** Pipeline still succeeds; `npm install` just takes longer because it has to download everything fresh.
- **What this teaches:** This is the core interview distinction — cache loss degrades performance, artifact loss (before expiry) would break the pipeline.

### Lab 11: Multiple cache paths with per-job override
- **Goal:** Use a global cache definition but let one job cache an additional path.
- **`.gitlab-ci.yml`:**
```yaml
cache:
  key: ${CI_COMMIT_REF_SLUG}
  paths:
    - node_modules/

build_job:
  stage: build
  cache:
    key: ${CI_COMMIT_REF_SLUG}
    paths:
      - node_modules/
      - .npm-cache/
  script:
    - npm ci --cache .npm-cache
    - npm run build
```
- **Run it:** Push and inspect the cache save step in the log.
- **Expected result:** Log shows both `node_modules/` and `.npm-cache/` being saved for this job, while other jobs only cache `node_modules/`.
- **What this teaches:** Job-level `cache:` overrides (not merges with) the global `cache:` block for that job — declare everything that job needs explicitly.

## Common Pitfalls
- Using cache to pass build output to the next stage instead of artifacts — cache is best-effort and not guaranteed present, so a dependent job can silently break.
- Forgetting `artifacts:expire_in` — old artifacts pile up and consume storage quota (default is 30 days, not forever).
- Using a single global cache key across all branches — causes cross-branch cache pollution/races; prefer `${CI_COMMIT_REF_SLUG}` or `key:files`.
- Not setting `artifacts:when: always` on diagnostic output (logs, reports) — they vanish exactly when you need them most, on failure.
- Assuming cache is instantly available to parallel jobs in the *same* pipeline run — cache is only guaranteed after being saved at the end of a job; parallel jobs in the same stage don't share an in-flight cache with each other.
- Caching `dist/`/build output "just in case" — bloats the cache without benefit; that's what artifacts are for.

## Interview Questions & Answers
- **Q: What's the core difference between cache and artifacts?**
  A: Cache speeds up jobs by reusing dependencies across pipeline runs (best-effort, not guaranteed); artifacts reliably persist a job's output within a pipeline and are downloadable via the UI, with an explicit expiry.
- **Q: If the cache is empty/missing, does the pipeline fail?**
  A: No — cache misses only slow the job down (fresh install); this is the defining trait of cache vs artifacts.
- **Q: How do you scope a cache per branch?**
  A: `cache: key: ${CI_COMMIT_REF_SLUG}`.
- **Q: How do you make a cache automatically invalidate when dependencies change?**
  A: `cache: key: files: [package-lock.json]` (or equivalent lockfile) — key is derived from the file's content hash.
- **Q: What does `cache:policy: pull` do and when would you use it?**
  A: Only restores cache, never saves it — use on jobs that consume dependencies but don't modify them, to skip the unnecessary upload step.
- **Q: What's the default artifact expiry if `expire_in` isn't set?**
  A: 30 days (current GitLab default).
- **Q: How do you keep artifacts even when the job fails?**
  A: `artifacts: when: always`.
- **Q: What are `fallback_keys` used for?**
  A: Up to five secondary cache keys tried in order when the primary key misses — lets a job reuse a related cache (e.g. from `main`) instead of a fully cold cache.
- **Q: Scenario — a job's test report only shows up in the pipeline UI when tests pass, but you need it on failure too. What's wrong?**
  A: `artifacts:when` defaults to `on_success`; set `when: always` so the report uploads regardless of exit status.
- **Q: Scenario — two branches keep overwriting each other's caches and builds get inconsistent. What's the fix?**
  A: The cache key isn't branch-scoped (e.g. a static key or project-only key); switch to `${CI_COMMIT_REF_SLUG}` or a content-hash key via `key:files`.
- **Q: Can artifacts from one job be restricted so only specific downstream jobs receive them?**
  A: Yes, via `dependencies:` or `needs:` on the downstream job — see file 14.
- **Q: Is cache shared across different projects?**
  A: No — cache (and artifacts) are scoped to the project; sharing across projects requires other mechanisms (e.g. package registry, downstream pipelines).
