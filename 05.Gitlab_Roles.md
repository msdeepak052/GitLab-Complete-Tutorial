# 5. GitLab Roles & Permissions

## Quick Summary
- Roles control what a member can do on a project or group — view, push, merge, manage CI/CD, manage members, delete.
- GitLab now has more than the classic "five roles" — Planner (between Guest and Reporter) and Security Manager have been added in recent releases.
- Owner is no longer strictly "group-level only" — it's assignable at the project level too (notably for personal-namespace projects, and generally as the top project role).
- Roles map to numeric access levels via the API (Guest=10, Planner=15, Reporter=20, Security Manager=25, Developer=30, Maintainer=40, Owner=50) — memorize these for API work.
- Custom roles let you grant fine-grained permission sets beyond the defaults, but they're configured via the UI or GraphQL/REST API — there is no YAML file in a repo that defines them.
- Custom roles require Ultimate tier.
- Group-level role assignment cascades to all projects/subgroups underneath — assign at the group when managing many projects at once.

## Core Concepts
- **Role hierarchy (lowest to highest, current)**
  - No access (0) — explicitly no access, used to override inherited access.
  - Minimal Access (5) — Premium/Ultimate only; sees limited group info, no project access.
  - Guest (10) — view/comment on issues and epics; cannot see repository code.
  - Planner (15) — plan-focused: manage issues, epics, milestones, iterations; no code access.
  - Reporter (20) — view code, download repo, view pipelines/reports; cannot push.
  - Security Manager (25) — view/manage security vulnerabilities, compliance configs, audit events (introduced as beta in recent 18.x releases — verify GA status on the docs page).
  - Developer (30) — push to unprotected branches, open MRs, run CI/CD pipelines.
  - Maintainer (40) — manage protected branches, CI/CD settings, runners, most project members; cannot delete the project.
  - Owner (50) — full control including deletion, visibility changes, transferring the project/group.
  - Admin (60) — instance-level administrator, not a project/group role per se.
  - ⚠️ Deprecated / Changed: the "classic five roles" (Guest/Reporter/Developer/Maintainer/Owner) framing is outdated — current GitLab has at least Planner and Security Manager as additional predefined roles, with access levels reshuffled to leave numeric gaps (15, 25) for them.
- **Owner at project level**
  - ⚠️ Deprecated / Changed: older material states "no Owner role at project level, only group level." Current docs describe Owner as available for both group Owners and project Owners — most visibly for projects in personal namespaces (the personal-namespace owner is the project Owner by default), and generally as the top assignable project role today. Don't assert Owner is group-only without checking the current permissions page.
- **Group vs project role assignment**
  - Adding a member at the group level grants that role on every project/subgroup beneath it (inherited access).
  - Adding a member directly on a project only affects that project.
  - The effective permission for a user on a project is the highest of any inherited (group) and direct (project) role.
- **Numeric access levels (used by the REST/GraphQL Members API)**

| Level | Role |
| --- | --- |
| 0 | No access |
| 5 | Minimal Access (Premium/Ultimate) |
| 10 | Guest |
| 15 | Planner |
| 20 | Reporter |
| 25 | Security Manager |
| 30 | Developer |
| 40 | Maintainer |
| 50 | Owner |
| 60 | Admin (instance-level) |

- **Custom roles (current mechanism — not YAML)**
  - ⚠️ Deprecated / Changed: there is no `custom_roles:` YAML block in any GitLab config file. Custom roles are built by picking a **base role** and enabling a set of individual permission booleans (e.g. `read_code`, `admin_merge_request`, `admin_vulnerability`), configured through:
    - **UI:** group (GitLab.com) or Admin area (self-managed) > **Settings > Roles and permissions > New role** — choose base role, name, description, and toggle individual permissions.
    - **API:** GraphQL mutations `memberRoleCreate` (member/custom roles) and `memberRoleAdminCreate` (custom admin roles); there's also REST API support for member roles on newer versions — check the current custom roles API docs for the exact endpoint your instance version supports.
  - Requires **Ultimate** tier (not Premium — verify this hasn't changed on your version, tier gating for custom roles has shifted before).
  - Practical limits: a capped number of custom roles per instance (check current docs for the exact cap, it has changed release to release), and you cannot use certain roles (e.g. Auditor) as a base.
- **Access expiration**
  - Member access (any role) can have an optional expiration date set at invite time — useful for contractors/temporary access; GitLab auto-revokes at expiry.

## Hands-On Labs

### Lab 1: Read the current role/permission matrix for your own project
- **Goal:** Confirm what each role can actually do, rather than trusting memorized tables (they change).
- **Steps:**
  1. Go to any project you own > **Manage > Members**.
  2. Note your own role (should be Owner if you created it).
  3. Open `docs.gitlab.com/user/permissions/` in another tab and cross-reference the "Project members permissions" table for Developer vs Maintainer.
- **Expected result:** You can name at least 3 things a Maintainer can do that a Developer cannot.
- **What this teaches:** The permission matrix is large and detailed — worth checking the live docs before asserting a specific permission boundary in an interview or a real access-control decision.

### Lab 2: Invite a member as Developer via the UI
- **Goal:** Practice the standard onboarding flow.
- **Steps:**
  1. Project > **Manage > Members > Invite members**.
  2. Enter a username/email, select role **Developer**.
  3. Optionally set an access expiration date.
  4. Click **Invite**.
- **Expected result:** New member appears in the Members list with role "Developer."
- **What this teaches:** This is the everyday task behind "add a teammate to the repo."

### Lab 3: Confirm a Guest cannot see code, but a Planner can plan without seeing code
- **Goal:** Distinguish two easily-confused low-tier roles.
- **Steps:**
  1. Invite a second test account as **Guest**; log in as that account (or use an incognito session with a test user) and confirm the repository file browser is inaccessible.
  2. Change that member's role to **Planner**; confirm they can create/edit issues and epics but still cannot browse repository code.
- **Expected result:** Guest: no code, limited issue visibility. Planner: full issue/epic/milestone management, still no code access.
- **What this teaches:** Planner exists specifically to give project-management-only staff (PMs, scrum masters) a role without the "view code" side effect that Reporter carries.

### Lab 4: Push code as Developer, then attempt a Maintainer-only action
- **Goal:** Feel the Developer/Maintainer boundary directly.
- **Steps:**
  1. As a Developer-role test account, push a commit to an unprotected branch — should succeed.
  2. Attempt to edit **Settings > Repository > Protected branches** — should be inaccessible/greyed out.
  3. Attempt to add a new member — should be inaccessible.
- **Expected result:** Push succeeds; settings/member-management actions are blocked.
- **What this teaches:** Developer = code contribution; Maintainer = code contribution + project configuration + member management.

### Lab 5: Add a member via the REST API with a specific access level
- **Goal:** Automate onboarding instead of clicking through the UI.
- **Steps:**
  1. `curl --request POST "https://gitlab.com/api/v4/projects/<project_id>/members" --header "PRIVATE-TOKEN: <your_access_token>" --data "user_id=<user_id>&access_level=30"`
  2. Check **Manage > Members** to confirm the user was added as Developer (level 30).
- **Expected result:** API response returns the new member object; UI reflects the addition.
- **What this teaches:** `access_level=30` == Developer — this numeric mapping is exactly what real onboarding automation/Terraform providers use under the hood.

### Lab 6: Change an existing member's role via the API
- **Goal:** Practice role changes, not just initial grants.
- **Steps:**
  1. `curl --request PUT "https://gitlab.com/api/v4/projects/<project_id>/members/<user_id>" --header "PRIVATE-TOKEN: <your_access_token>" --data "access_level=40"`
  2. Confirm the member now shows as Maintainer.
- **Expected result:** Role updates from 30 (Developer) to 40 (Maintainer) without removing/re-inviting the member.
- **What this teaches:** Promotions/demotions are a PUT on the existing membership, not a delete+recreate.

### Lab 7: Assign a role at the group level and confirm inheritance
- **Goal:** See cascading permissions in action.
- **Steps:**
  1. Create (or use) a group containing 2+ projects.
  2. **Group > Manage > Members > Invite members**, add a test account as **Maintainer**.
  3. Check that account's effective role on each project under the group (**Project > Manage > Members** — inherited members show a "group" badge/source).
- **Expected result:** The test account shows as Maintainer on every project in the group, without being added individually to each.
- **What this teaches:** Group-level role assignment is the efficient way to manage access across many projects — avoids per-project drift.

### Lab 8: Set an access expiration date for a temporary contractor
- **Goal:** Practice time-boxed access, a common real-world compliance requirement.
- **Steps:**
  1. Invite a test member as Developer with an **Access expiration date** set a few days out.
  2. Check **Manage > Members** — note the expiration column.
- **Expected result:** Member shows an expiration date; GitLab will auto-revoke access on that date.
- **What this teaches:** Time-boxed access removes the "forgot to remove the contractor" risk.

### Lab 9: Create a custom role via the UI (Ultimate tier or trial)
- **Goal:** See the real custom-role mechanism, not a fabricated YAML block.
- **Steps:**
  1. Go to a group's **Settings > Roles and permissions** (or **Admin > Roles and permissions** on self-managed) — requires Ultimate license/trial.
  2. Click **New role**, choose base role **Developer**, name it `Release Manager`.
  3. Toggle on specific permissions relevant to releases (e.g., permissions related to tags/releases) while leaving member-management permissions off.
  4. Save and assign it to a test member instead of a default role.
- **Expected result:** The member's role shows as the custom role name, with exactly the toggled permission set — not the full Developer/Maintainer bundle.
- **What this teaches:** Custom roles are base-role-plus-boolean-toggles built in the UI/API, confirming there's no YAML config file involved.

### Lab 10: Create a custom role via the GraphQL API
- **Goal:** See the automatable path for custom roles.
- **Steps:**
  1. Open **GraphQL explorer**: `https://gitlab.com/-/graphql-explorer`.
  2. Build a `memberRoleCreate` mutation supplying `namespacePath`, `baseAccessLevel`, `name`, and the specific permission booleans (e.g., `readCode: true`).
  3. Run the mutation and inspect the returned custom role `id`.
- **Expected result:** A new custom role is created and visible in **Settings > Roles and permissions**, matching what Lab 9 does manually.
- **What this teaches:** Custom role provisioning can be scripted/IaC'd via GraphQL — useful to know since teams sometimes assume (incorrectly) it's a repo config file.

### Lab 11: Build a real-world role assignment plan
- **Goal:** Apply everything above to a realistic team.
- **Steps:** For a hypothetical 5-person team, decide and justify a role for each, then actually configure it (using test/dummy accounts) in a sandbox group:

| Team Member | Role | Why |
| --- | --- | --- |
| DevOps engineer | Maintainer | Configures runners, CI/CD variables, protected branches |
| Backend developer | Developer | Pushes code, opens MRs |
| QA engineer | Reporter | Views pipelines/test reports, no push |
| Product manager | Planner | Manages issues/epics/milestones, no code access needed |
| CTO / admin | Owner (group) | Full control, billing, visibility, member management |

- **Expected result:** Each test account's actual UI-visible permissions match the intended role.
- **What this teaches:** Role selection should map to job function, not default everyone to Maintainer/Owner out of convenience — least privilege applies to internal teams too.

### Lab 12: Audit all members and roles across a group via API
- **Goal:** Practice a compliance-style access review.
- **Steps:**
  1. `curl --header "PRIVATE-TOKEN: <your_pat>" "https://gitlab.com/api/v4/groups/<group_id>/members/all"`
  2. Review `access_level` per member across the whole group (including inherited members).
- **Expected result:** A full member+role listing, useful for spotting over-privileged accounts.
- **What this teaches:** `/members/all` (vs `/members`) includes inherited group members — the distinction matters for a complete audit.

## Common Pitfalls
- Assuming the "five classic roles" are the complete list — Planner and Security Manager exist now, with numeric gaps (15, 25) left for them.
- Assuming Owner is strictly group-only — it's assignable at the project level too in current GitLab.
- Trying to define custom roles in a YAML file in the repo — they don't work that way; it's UI or GraphQL/REST API, base role plus permission toggles.
- Forgetting group-level role assignments cascade — adding someone as Maintainer on a group makes them Maintainer on every project underneath, which can over-grant access unintentionally.
- Confusing Reporter (can view code) with Planner (cannot view code, plan-only) — easy to mix up since both sit below Developer.
- Assuming custom roles are available on Premium — they require Ultimate.

## Interview Questions & Answers
- **What are GitLab's default roles today, in order?**
  - No access, Minimal Access, Guest, Planner, Reporter, Security Manager, Developer, Maintainer, Owner (plus instance Admin) — more than the "classic five" people often quote.
- **What numeric access level does the Members API use for Developer? Maintainer? Owner?**
  - Developer = 30, Maintainer = 40, Owner = 50 (also: Guest = 10, Planner = 15, Reporter = 20, Security Manager = 25, Minimal Access = 5).
- **Is Owner available at the project level, or only group level?**
  - Both — current GitLab assigns Owner at the project level too (notably the default for personal-namespace projects), not exclusively at group level as older material claimed.
- **What's the difference between Reporter and Planner?**
  - Reporter can view/download repository code and pipelines but not push; Planner manages issues/epics/milestones but has no code access at all — aimed at PM-only staff.
- **How do you grant access that automatically expires?**
  - Set an access expiration date when inviting/editing a member — GitLab auto-revokes access on that date.
- **How are custom roles actually configured in GitLab?**
  - Via the UI (group or Admin area > Settings > Roles and permissions > New role) or the GraphQL API (`memberRoleCreate` / `memberRoleAdminCreate`) — a base role plus individually toggled permission booleans. There is no YAML file for this.
- **What tier is required for custom roles?**
  - Ultimate.
- **If a user is added as Maintainer at the group level and Developer directly on one project inside it, what's their effective role on that project?**
  - The highest of the two — Maintainer (inherited group access and direct project access are combined by taking the maximum).
- **Scenario: a teammate can't push to `main`. What roles/settings would you check?**
  - Their role (must be Developer+ to push at all), whether `main` is a protected branch requiring Maintainer+ or specific allowed roles to push/merge, and whether they're getting access via an inherited group role that's lower than expected.
- **Scenario: you need to give a contractor Developer access for exactly 30 days with no manual follow-up to revoke it. How?**
  - Invite them as Developer and set the access expiration date 30 days out; GitLab automatically revokes access at that date.
- **What's the difference between `/members` and `/members/all` in the Members API?**
  - `/members` returns only directly-added members of that project/group; `/members/all` also includes members who have access via group inheritance.
- **Why might a real access audit use the API instead of the UI?**
  - To pull a complete, scriptable, cross-project/group listing of members and access levels for compliance review, rather than manually clicking through each project's Members page.
