## 🧭 1. Manage Section — Repository and Team Management

### 📘 **Introduction**

The **Manage** section in GitLab focuses on maintaining the **smooth operation and organization** of your project.
It provides tools to:

* Track repository activities
* Manage team access and permissions
* Categorize and organize project components

---

### 🔹 **1. Activity**

**Purpose:** View everything happening in your repository in chronological order.

**Includes:**

* Recent commits
* Merge requests
* Issue updates

**Example:**
If a developer pushes a new feature branch, merges a request, or comments on an issue — it appears in the **Activity Feed**.

**Path:**
👉 Project → **Manage → Activity**

---

### 🔹 **2. Members**

**Purpose:** Control who can access your project and what they can do.

**Features:**

* Add or remove team members
* Assign **roles** (Guest, Reporter, Developer, Maintainer, Owner)
* Manage **permissions**

**Example:**
If Deepak creates a GitLab project and adds teammates:

* Rahul → **Developer** (can push code, create merge requests)
* Sneha → **Reporter** (can only view issues and reports)
* Deepak → **Owner** (full access)

**Path:**
👉 Project → **Manage → Members**

---

### 🔹 **3. Labels**

**Purpose:** Categorize and tag issues or merge requests for easy tracking.

**Functionality:**

* Acts as **tags** (like `bug`, `enhancement`, `urgent`)
* Helps **filter** and **sort** work items
* Improves project workflow and reporting

**Example:**
Label all critical bugs as `priority::high` and filter by that label during your sprint review.

**Path:**
👉 Project → **Manage → Labels**

---

## 📅 2. Plan Section — Planning and Tracking Work

### 📘 **Introduction**

The **Plan** section is used for **project planning, task tracking, and documentation**.
It includes:

* **Issues**
* **Issue Boards**
* **Milestones**
* **Wiki**

---

### 🔹 **1. Issues**

**Purpose:** Track individual tasks, bugs, or feature requests.

**Usage:**

* Create issues to report bugs or request features
* Assign issues to team members
* Add labels and due dates

**Example:**

* Issue Title: *“Fix Login API Timeout”*
* Assignee: Rahul
* Labels: `backend`, `bug`
* Milestone: *Sprint 12*

**Path:**
👉 Project → **Plan → Issues**

---

### 🔹 **2. Issue Boards**

**Purpose:** Visual task management tool (like Trello or Jira board).

**Functionality:**

* Represents issues as **cards** on a board
* Supports **Kanban workflow**: “To Do” → “Doing” → “Done”
* Allows filtering by labels or milestones

**Example:**
A “Sprint 12” board may show:

* “To Do”: Feature A, Bug B
* “Doing”: Feature C
* “Done”: Bug D

**Path:**
👉 Project → **Plan → Issue Boards**

---

### 🔹 **3. Milestones**

**Purpose:** Group related issues or merge requests for a particular phase or sprint.

**Features:**

* Define **due dates**
* Track **progress** visually
* Generate milestone **reports**

**Example:**
Milestone: *Sprint 12*
Includes:

* 10 issues (7 closed, 3 open)
* Due: Oct 15, 2025
* Progress: 70% completed

**Path:**
👉 Project → **Plan → Milestones**

---

### 🔹 **4. Wiki**

**Purpose:** A built-in documentation space for project knowledge.

**Usage:**

* Store guidelines, architecture, and setup docs
* Allow collaborative editing
* Maintain long-term project reference material

**Example:**
Wiki Pages:

* “Setup Instructions”
* “Deployment Steps”
* “API Documentation”

**Path:**
👉 Project → **Plan → Wiki**

---

## 🧩 Putting It All Together — Example Scenario

Let’s take a **DevOps Project Example**:

1. **Manage → Members:**

   * Deepak adds his team (Developers, Testers, Maintainers).

2. **Plan → Issues:**

   * Team creates issues: “Integrate Jenkins CI”, “Deploy app to EKS”.

3. **Plan → Issue Board:**

   * Issues are organized into Kanban columns for sprint tracking.

4. **Plan → Milestones:**

   * Milestone “October Release” groups related issues.

5. **Plan → Wiki:**

   * Team documents CI/CD pipeline steps and architecture diagrams.

6. **Manage → Activity:**

   * Deepak tracks all commits and merge requests made by the team.
