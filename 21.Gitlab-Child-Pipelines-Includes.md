## **1️⃣ What is a Child Pipeline?**

* A **child pipeline** is a **pipeline triggered by a parent pipeline**.
* Useful for **modularizing CI/CD**, separating logic, or reusing pipelines across projects.
* Allows **splitting a large `.gitlab-ci.yml` into smaller pipelines** for easier management.

**Key points:**

* Parent pipeline triggers child pipeline using `trigger:`.
* Child pipeline can live in the **same project** or **another project**.
* Useful for **microservices, multiple environments, or large monorepo setups**.

---

### **Example: Simple Child Pipeline**

**Parent pipeline (`.gitlab-ci.yml`):**

```yaml
stages:
  - build
  - deploy

build_job:
  stage: build
  script:
    - echo "Building main project..."

trigger_child_pipeline:
  stage: deploy
  trigger:
    include: child-pipeline.yml
    strategy: depend  # Wait for child pipeline success before marking parent as success
```

**Child pipeline (`child-pipeline.yml`):**

```yaml
stages:
  - test
  - deploy

test_job:
  stage: test
  script:
    - echo "Running tests in child pipeline..."

deploy_job:
  stage: deploy
  script:
    - echo "Deploying from child pipeline..."
```

✅ **Explanation:**

1. `build_job` runs in parent pipeline.
2. `trigger_child_pipeline` triggers the child pipeline defined in `child-pipeline.yml`.
3. Parent pipeline **waits for child pipeline** to finish (`strategy: depend`) and reports overall status.

## **2️⃣ What is `include`?**

* The `include:` keyword is used to **split `.gitlab-ci.yml` into multiple files** for better maintainability.
* Can include **local files, remote URLs, templates, or project files**.

### **Syntax:**

```yaml
include:
  - local: 'path/to/file.yml'       # file within same repo
  - remote: 'https://example.com/file.yml'  # external URL
  - project: 'group/project'        # file from another GitLab project
    file: '/templates/template.yml'
```

---

### **Example: Using Include**

**`.gitlab-ci.yml` (parent/main file):**

```yaml
stages:
  - build
  - test
  - deploy

include:
  - local: 'ci-templates/build.yml'
  - local: 'ci-templates/test.yml'
  - local: 'ci-templates/deploy.yml'
```

**`ci-templates/build.yml`:**

```yaml
build_job:
  stage: build
  script:
    - echo "Building the project..."
```

**`ci-templates/test.yml`:**

```yaml
test_job:
  stage: test
  script:
    - echo "Running tests..."
```

**`ci-templates/deploy.yml`:**

```yaml
deploy_job:
  stage: deploy
  script:
    - echo "Deploying the project..."
```

✅ **Explanation:**

* The parent pipeline **combines all included files** and executes jobs as a single pipeline.
* Makes **YAML modular, reusable, and clean**.

---

## **3️⃣ Key Differences Between `trigger` and `include`**

| Feature            | Child Pipeline (`trigger`)                                             | Include (`include`)                                              |
| ------------------ | ---------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Purpose            | Trigger **separate pipeline**                                          | Include **YAML definitions** into main pipeline                  |
| Execution          | Runs as **independent pipeline** (can be in same or different project) | Runs as **part of main pipeline**                                |
| Use Case           | Large pipelines, microservices, conditional pipelines                  | Split large `.gitlab-ci.yml` into modular files, reuse templates |
| Status propagation | `strategy: depend` can make parent wait for child                      | Jobs become part of parent pipeline; no separate pipeline status |

---

### **4️⃣ Advanced Child Pipeline Example**

* Suppose you want **dynamic child pipelines for different environments**:

```yaml
stages:
  - deploy

deploy_to_env:
  stage: deploy
  trigger:
    include: child-pipeline.yml
    strategy: depend
  rules:
    - if: '$CI_COMMIT_BRANCH == "develop"'
      variables:
        ENVIRONMENT: "staging"
    - if: '$CI_COMMIT_BRANCH == "main"'
      variables:
        ENVIRONMENT: "production"
```

* Child pipeline reads `$ENVIRONMENT` and deploys accordingly.
* Allows **dynamic, branch-based deployments** using a **single reusable child pipeline**.

---

### **5️⃣ Key Takeaways**

1. **Child pipelines (`trigger`)** → separate pipeline, modular execution, can wait for completion (`strategy: depend`).
2. **Include (`include`)** → YAML modularization, no separate pipeline; jobs are merged into parent.
3. Both make **large CI/CD pipelines maintainable and reusable**.
4. Child pipelines are ideal for **microservices, conditional deployments, or monorepo setups**.
5. Include is ideal for **splitting your YAML into smaller, reusable templates**.
