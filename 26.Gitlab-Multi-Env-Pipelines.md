👉 **Multi-environment pipelines (Dev → Staging → Prod)**.

Let’s break this down **step by step with an example** that mirrors what real companies do.

---

## 🧩 1. What Are Multi-Environment Pipelines?

They let you **deploy the same app to multiple environments**, usually in order:

| Environment       | Purpose                                      |
| ----------------- | -------------------------------------------- |
| **Dev**           | For developers to test new code frequently.  |
| **Staging (UAT)** | For pre-production validation or QA testing. |
| **Prod**          | Live environment serving real users.         |

Each environment has its **own servers or configuration** — but uses **the same build artifact** (Docker image, WAR file, etc.) to ensure consistency.

---

## ⚙️ 2. GitLab Features That Help

GitLab supports:

* **Environments** – logical names like `dev`, `staging`, `prod`
* **Manual approvals** – use `when: manual` for human-triggered deployments
* **Protected environments** – restrict who can deploy to Prod
* **Variables per environment** – define different credentials/URLs for each

---

## 🚀 3. Example: Multi-Environment Docker Deployment to EC2

Here’s a **complete `.gitlab-ci.yml`** example:

```yaml
image: docker:latest

services:
  - docker:dind

variables:
  DOCKER_DRIVER: overlay2
  IMAGE_NAME: deepakyadav/devops-app
  IMAGE_TAG: $CI_COMMIT_SHORT_SHA
  DOCKER_BUILDKIT: 1

stages:
  - build
  - push
  - deploy

# 🔹 Build Docker Image
build_image:
  stage: build
  script:
    - docker build -t $IMAGE_NAME:$IMAGE_TAG .
    - docker tag $IMAGE_NAME:$IMAGE_TAG $IMAGE_NAME:latest
  artifacts:
    paths:
      - Dockerfile
    expire_in: 1h

# 🔹 Push Image to Docker Hub
push_image:
  stage: push
  script:
    - docker login -u "$DOCKER_USERNAME" -p "$DOCKER_PASSWORD"
    - docker push $IMAGE_NAME:$IMAGE_TAG
    - docker push $IMAGE_NAME:latest
  needs: ["build_image"]
  only:
    - main

# 🔹 Deploy to Dev
deploy_dev:
  stage: deploy
  image: alpine:latest
  environment:
    name: dev
    url: http://$DEV_HOST
  before_script:
    - apk add --no-cache openssh
    - echo "$SSH_PRIVATE_KEY" > private_key.pem
    - chmod 600 private_key.pem
  script:
    - ssh -o StrictHostKeyChecking=no -i private_key.pem $DEV_USER@$DEV_HOST "
        docker login -u $DOCKER_USERNAME -p $DOCKER_PASSWORD &&
        docker pull $IMAGE_NAME:latest &&
        docker stop devops-app || true &&
        docker rm devops-app || true &&
        docker run -d -p 80:80 --name devops-app $IMAGE_NAME:latest
      "
  needs: ["push_image"]
  only:
    - main

# 🔹 Deploy to Staging (manual approval)
deploy_staging:
  stage: deploy
  image: alpine:latest
  environment:
    name: staging
    url: http://$STAGING_HOST
  when: manual
  before_script:
    - apk add --no-cache openssh
    - echo "$SSH_PRIVATE_KEY" > private_key.pem
    - chmod 600 private_key.pem
  script:
    - ssh -o StrictHostKeyChecking=no -i private_key.pem $STAGING_USER@$STAGING_HOST "
        docker login -u $DOCKER_USERNAME -p $DOCKER_PASSWORD &&
        docker pull $IMAGE_NAME:latest &&
        docker stop devops-app || true &&
        docker rm devops-app || true &&
        docker run -d -p 80:80 --name devops-app $IMAGE_NAME:latest
      "
  needs: ["deploy_dev"]

# 🔹 Deploy to Production (manual approval, protected)
deploy_prod:
  stage: deploy
  image: alpine:latest
  environment:
    name: production
    url: http://$PROD_HOST
    on_stop: stop_prod
  when: manual
  before_script:
    - apk add --no-cache openssh
    - echo "$SSH_PRIVATE_KEY" > private_key.pem
    - chmod 600 private_key.pem
  script:
    - ssh -o StrictHostKeyChecking=no -i private_key.pem $PROD_USER@$PROD_HOST "
        docker login -u $DOCKER_USERNAME -p $DOCKER_PASSWORD &&
        docker pull $IMAGE_NAME:latest &&
        docker stop devops-app || true &&
        docker rm devops-app || true &&
        docker run -d -p 80:80 --name devops-app $IMAGE_NAME:latest
      "
  needs: ["deploy_staging"]
```

---

## 🧠 4. How It Works

| Stage              | Description                                         |
| ------------------ | --------------------------------------------------- |
| **build_image**    | Builds your Docker image once.                      |
| **push_image**     | Pushes the same image to Docker Hub.                |
| **deploy_dev**     | Automatically deploys to the Dev EC2 server.        |
| **deploy_staging** | Manually triggered after Dev succeeds (QA testing). |
| **deploy_prod**    | Manually triggered and protected (final release).   |

---

## 🔐 5. GitLab Environment Variables

In **GitLab → Settings → CI/CD → Variables**, set:

| Variable                              | Value                 |
| ------------------------------------- | --------------------- |
| `DEV_HOST`                            | EC2 IP of dev         |
| `STAGING_HOST`                        | EC2 IP of staging     |
| `PROD_HOST`                           | EC2 IP of prod        |
| `SSH_PRIVATE_KEY`                     | Your PEM file content |
| `DOCKER_USERNAME` / `DOCKER_PASSWORD` | Registry credentials  |

---

## 🧾 6. Best Practices

✅ **Build once, deploy many** – only build the image once and reuse it in all environments.
✅ **Use manual approvals** for Staging and Prod.
✅ **Protect the Prod environment** (GitLab → Deployments → Environments → Protect).
✅ **Use separate EC2 instances or clusters** per environment.
✅ **Store secrets in GitLab variables** — never in YAML directly.
