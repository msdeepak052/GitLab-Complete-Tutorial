# 22. GitLab Pipeline Optimization Techniques

## Quick Summary
- This is a grab bag: `rules`, `needs`, `parallel`/`matrix`, `cache`, `artifacts`, `include`, `tags`, `rules:changes`, `extends` — each cuts pipeline time or wasted compute a different way.
- The single highest-leverage change in most real pipelines is `needs:` — it turns a strictly sequential stage-by-stage pipeline into a DAG that runs jobs as soon as their actual dependencies finish.
- `rules`/`rules:changes` avoid running jobs at all when they can't possibly matter (wrong branch, unrelated files changed) — cheapest optimization there is (zero compute used).
- `cache`/`artifacts` avoid redoing expensive work (dependency installs, builds) across jobs and pipelines.
- `parallel`/`matrix` trade more concurrent runners for a shorter wall-clock time on a single expensive job (e.g. a big test suite).
- `extends` and YAML anchors both fight config duplication, but they are two different mechanisms — this file previously mislabeled a YAML-anchor example as `extends`, which is fixed here.
- For interviews: "how would you speed up a slow pipeline?" is one of the most common GitLab CI questions — this file is the answer key.

## Core Concepts

### `rules:` — conditional job execution
- Replaces the deprecated `only:`/`except:` for deciding *whether* a job runs at all.
- Evaluated top-to-bottom; first matching rule wins; if a rule has no `when:`, a match defaults to `when: on_success`.
- Common clauses: `if:`, `changes:`, `exists:`, `allow_failure:`, and per-rule `variables:` overrides.
- Zero-cost optimization: a job that never starts costs nothing, unlike a job that runs and gets cancelled.

### `needs:` — DAG execution for pipeline speed (this file's angle)
- Default GitLab behavior: stages run strictly in order, and a stage doesn't start until **every** job in the previous stage finishes — even unrelated ones.
- `needs:` lets a job declare its *actual* prerequisites and start the moment those finish, ignoring stage boundaries and any slow, unrelated sibling jobs.
- This is purely about **wall-clock pipeline duration** — for controlling *which artifacts* a job downloads, that's `dependencies:` (or `needs: - job: x, artifacts: true/false`), covered in file 14; don't conflate the two.
- `needs: - job: build_job, artifacts: true` (default `true`) also downloads that job's artifacts; `artifacts: false` skips the download for jobs that only need to wait, not consume output.
- `needs: [] ` (empty list) means "no dependencies — start immediately," useful for a lint job that doesn't need the build.
- Circular `needs:` graphs are rejected by GitLab at pipeline creation time.
- `needs:` can reference jobs in later-defined stages as long as the referenced job's stage runs before (or is unordered relative to) the current one — GitLab computes the DAG from the `needs:` graph, not file order.

### `parallel:` / `parallel:matrix:` — splitting work
- `parallel: N` runs N identical copies of a job, exposing `$CI_NODE_INDEX` / `$CI_NODE_TOTAL` so each instance can process a different slice.
- `parallel: matrix:` runs one job instance per combination of listed variables — useful for cross-version/cross-OS test matrices.
- Both consume more concurrent runner capacity to reduce wall-clock time — a resource/speed tradeoff, not a "free" optimization.

### `cache:` — reuse dependencies across pipeline runs
- Keyed by `cache: key:` (often `$CI_COMMIT_REF_SLUG` for per-branch caches); same key = shared cache across pipelines/jobs.
- `paths:` lists what to persist (e.g. `node_modules/`); `policy: pull-push` (default), `pull`, or `push` controls whether a job uploads, downloads, or both.
- Cache is best-effort — GitLab does not guarantee a cache hit; don't rely on it for correctness, only speed.

### `artifacts:` — pass build output between jobs in one pipeline
- `artifacts: paths:` marks files to upload after a job; later jobs in the same pipeline can consume them.
- `expire_in:` controls storage cost/cleanup — set it deliberately, default retention can otherwise pile up storage.
- Different from `cache:`: artifacts are pipeline-scoped output handed forward; cache is a speed optimization for repeated inputs.

### `include:` / child pipelines — modular, maintainable pipelines
- Splitting a monolithic YAML file doesn't by itself make a pipeline faster, but it enables per-service `rules:changes` gating (see file 21) which does.
- Full details (types, CI/CD Components, `trigger:` vs `include:`) live in file 21 — this file only covers it as one "avoid repetition / avoid unnecessary jobs" lever.

### `tags:` — matching jobs to the right runner
- Jobs only run on runners that have **all** the tags listed on the job.
- Prevents a Docker-only job from being picked up by a runner without Docker (which would just fail or hang), and lets you route heavy jobs to bigger runners.
- Not primarily a speed feature by itself, but avoids wasted failed/retried runs and lets you deliberately send expensive jobs to faster runners.

### `rules:changes:` — path-based conditional execution
- A `rules:` clause that only matches if the MR/commit touched matching paths — skips jobs entirely for unrelated changes (e.g. skip frontend build when only backend files changed).
- Big win in monorepos; combine with `include:`/`trigger:` for per-service fan-out (file 21, Lab 9).

### `extends:` — DRY job templates (the real keyword)
- `extends: .template_name` (or a list for multiple inheritance) makes a job inherit config from a hidden job (name starts with `.`, which GitLab never runs directly).
- Merge behavior: GitLab performs a **reverse deep merge** — hashes (like `variables:`) merge key-by-key, but scalar/array keys (like `script:`) are fully **overridden**, not concatenated, by whichever definition is "closest" to the final job (the job itself wins over `extends:` entries; later entries in an `extends:` list win over earlier ones).
- Works across files pulled in via `include:` — unlike YAML anchors, which only work within a single file.

### ⚠️ Deprecated / Changed — factual fix from the previous version
- The earlier version of this file had a section titled "extends" that actually showed `.default_job: &default_job` + `<<: *default_job` — that is **native YAML anchor/merge-key syntax**, not the GitLab `extends:` keyword. They look similar (both fight duplication) but are different mechanisms with different scoping rules. This file now shows a real `extends:` example (Lab 9) and keeps the anchor example (Lab 10) explicitly labeled as "an alternative to `extends` using native YAML anchors."
- `only:`/`except:` are officially deprecated; every job-level conditional example below uses `rules:`.

## Hands-On Labs

### Lab 1: `rules:` instead of `only:`/`except:` for conditional deploys
- **Goal:** Run a deploy job only on `main`, using current syntax.
- **`.gitlab-ci.yml`:**
```yaml
deploy_job:
  stage: deploy
  script:
    - echo "Deploying application..."
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```
- **Run it:** Push to `main`, then push to a feature branch.
- **Expected result:** Job appears and runs on `main`; job is absent entirely from the feature-branch pipeline (not just skipped — not created).
- **What this teaches:** `rules:` is the current, non-deprecated way to gate job creation; a non-matching job never consumes runner time.

### Lab 2: `needs:` to break stage-by-stage waiting
- **Goal:** Get a fast test job running the moment its one real dependency finishes, without waiting for the whole build stage.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - test
  - deploy

build_job:
  stage: build
  script:
    - echo "Building app..."
    - sleep 30

slow_unrelated_build:
  stage: build
  script:
    - sleep 120

unit_tests:
  stage: test
  script:
    - echo "Running unit tests..."
  needs: ["build_job"]
```
- **Run it:** Push, watch the pipeline graph/timing in CI/CD > Pipelines.
- **Expected result:** `unit_tests` starts right after `build_job` (~30s), not after `slow_unrelated_build` (~120s) finishes, even though both are in the `build` stage.
- **What this teaches:** `needs:` cuts wall-clock time by ignoring irrelevant siblings in the same stage — the core speed win.

### Lab 3: `needs:` with `artifacts: false` for wait-only dependencies
- **Goal:** Depend on a job's completion without downloading its (possibly large) artifacts.
- **`.gitlab-ci.yml`:**
```yaml
notify_slack:
  stage: test
  script:
    - echo "Build finished, notifying..."
  needs:
    - job: build_job
      artifacts: false
```
- **Run it:** Compare job duration/log with `artifacts: true` (default) vs `artifacts: false` when `build_job` has a large artifact.
- **Expected result:** `notify_slack` starts at the same time either way, but with `artifacts: false` it skips the artifact download step, shaving startup time.
- **What this teaches:** `needs:` timing and artifact transfer are separately tunable — don't pay for a download you don't need.

### Lab 4: `needs: []` for an independent, immediate job
- **Goal:** Run a lint job in parallel with build from the very start of the pipeline.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - test

lint:
  stage: test
  script:
    - echo "Linting (no dependency on build)..."
  needs: []

build_job:
  stage: build
  script:
    - echo "Building..."
```
- **Run it:** Push and watch the pipeline graph.
- **Expected result:** `lint` starts immediately at pipeline start, in parallel with `build_job`, despite nominally being in a later stage.
- **What this teaches:** `needs: []` fully detaches a job from stage ordering — the most aggressive DAG optimization for genuinely independent jobs.

### Lab 5: `parallel:` to split a test suite
- **Goal:** Cut test wall-clock time by running 4 shards concurrently.
- **`.gitlab-ci.yml`:**
```yaml
unit_tests:
  stage: test
  script:
    - echo "Running test suite chunk $CI_NODE_INDEX of $CI_NODE_TOTAL"
    - ./run_tests.sh --split $CI_NODE_INDEX/$CI_NODE_TOTAL
  parallel: 4
```
- **Run it:** Push, observe 4 separate `unit_tests 1/4` .. `4/4` jobs running concurrently.
- **Expected result:** Total test stage duration is roughly (single full run time / 4), assuming enough runner capacity.
- **What this teaches:** `parallel:` trades concurrent runner capacity for shorter wall-clock time on one expensive job.

### Lab 6: `parallel: matrix:` for a cross-version test matrix
- **Goal:** Test against multiple Node versions without duplicating the job.
- **`.gitlab-ci.yml`:**
```yaml
test_node:
  stage: test
  image: node:$NODE_VERSION
  script:
    - npm ci
    - npm test
  parallel:
    matrix:
      - NODE_VERSION: ["18", "20", "22"]
```
- **Run it:** Push, observe 3 job instances (`test_node: [18]`, `[20]`, `[22]`).
- **Expected result:** Each runs the same script against a different Node image, all in parallel.
- **What this teaches:** `matrix:` avoids copy-pasting near-identical jobs for each variable combination.

### Lab 7: `cache:` to skip re-downloading dependencies
- **Goal:** Speed up repeated `npm install` across pipeline runs on the same branch.
- **`.gitlab-ci.yml`:**
```yaml
build_job:
  stage: build
  script:
    - npm install
    - npm run build
  cache:
    key: ${CI_COMMIT_REF_SLUG}
    paths:
      - node_modules/
```
- **Run it:** Run the pipeline twice on the same branch without changing `package-lock.json`.
- **Expected result:** Second run's `npm install` step completes noticeably faster (cache hit logged in the job output).
- **What this teaches:** `cache:` is a best-effort speed optimization keyed per branch (or however you key it) — not guaranteed, not for correctness.

### Lab 8: `artifacts:` to avoid rebuilding downstream
- **Goal:** Share a build output with a test job instead of rebuilding it.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - test

build_job:
  stage: build
  script:
    - npm run build
  artifacts:
    paths:
      - dist/
    expire_in: 1 hour

test_job:
  stage: test
  needs:
    - job: build_job
      artifacts: true
  script:
    - ls dist/
```
- **Run it:** Push, inspect `test_job`'s log.
- **Expected result:** `dist/` exists in `test_job` without re-running the build script.
- **What this teaches:** `artifacts:` + `needs:` together avoid redundant work *and* cut waiting time.

### Lab 9: `extends:` — real multiple inheritance with deep merge
- **Goal:** DRY up two jobs that share an image and variables but differ in `script:`.
- **`.gitlab-ci.yml`:**
```yaml
.node_defaults:
  image: node:20
  variables:
    NODE_ENV: "test"

.docker_defaults:
  variables:
    DOCKER_DRIVER: overlay2

build_job:
  extends:
    - .node_defaults
    - .docker_defaults
  stage: build
  script:
    - npm ci
    - npm run build

test_job:
  extends: .node_defaults
  stage: test
  script:
    - npm test
```
- **Run it:** Push, check the CI Lint view (CI/CD > Editor > Lint) to see `build_job`'s fully merged config.
- **Expected result:** `build_job` ends up with `image: node:20`, both `NODE_ENV` and `DOCKER_DRIVER` variables merged together, and its own `script:` (not the templates' — because templates define no `script:` here). Multiple `extends:` entries merge left-to-right, with later entries and the job itself taking precedence on conflicts.
- **What this teaches:** This is the actual `extends:` keyword — hidden-job templates, multiple inheritance, deep merge of hashes like `variables:`, full override of scalars like `script:`.

### Lab 10: YAML anchors as an alternative to `extends`
- **Goal:** Achieve similar DRY-ness to Lab 9 using native YAML anchors instead of `extends:`.
- **`.gitlab-ci.yml`:**
```yaml
.default_job: &default_job
  image: node:20
  before_script:
    - npm ci

build_job:
  <<: *default_job
  stage: build
  script:
    - npm run build

test_job:
  <<: *default_job
  stage: test
  script:
    - npm test
```
- **Run it:** Push and confirm both jobs use `node:20` and run `npm ci` before their script.
- **Expected result:** Same practical outcome as `extends:` for this simple case.
- **What this teaches:** This is **not** `extends:` — it's a native YAML feature (anchor `&`, merge key `<<`, alias `*`). Key limitation vs. `extends:`: anchors only resolve within the *same file*, so they can't reach across `include:`d files the way `extends:` can.

### Lab 11: `rules:changes:` to skip unrelated jobs in a monorepo
- **Goal:** Only run the frontend build when frontend files actually changed.
- **`.gitlab-ci.yml`:**
```yaml
frontend_build:
  stage: build
  script:
    - npm install
    - npm run build
  rules:
    - changes:
        - frontend/**
```
- **Run it:** Push a commit touching only `backend/`, then one touching `frontend/`.
- **Expected result:** `frontend_build` is skipped (not created) for the backend-only commit, and runs for the frontend commit.
- **What this teaches:** Path-based `rules:changes:` is a zero-compute optimization in monorepos.

### Lab 12: `tags:` to route jobs to the correct/fastest runner
- **Goal:** Ensure a Docker-dependent job only lands on runners that actually have Docker.
- **`.gitlab-ci.yml`:**
```yaml
docker_build:
  stage: build
  script:
    - docker build -t myapp .
  tags:
    - docker
```
- **Run it:** Push with only a `docker`-tagged runner registered vs. an untagged runner.
- **Expected result:** Job stays "pending" if no runner with the `docker` tag is available; runs immediately once one is.
- **What this teaches:** `tags:` prevents jobs from being picked up by runners that can't actually execute them, avoiding wasted/failed runs.

### Lab 13: Combine everything into one optimized pipeline
- **Goal:** See the techniques compounding.
- **`.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - test
  - deploy

.node_defaults:
  image: node:20
  cache:
    key: ${CI_COMMIT_REF_SLUG}
    paths:
      - node_modules/

build_job:
  extends: .node_defaults
  stage: build
  script:
    - npm ci
    - npm run build
  artifacts:
    paths:
      - dist/
    expire_in: 1 hour
  tags:
    - docker

lint:
  extends: .node_defaults
  stage: test
  script:
    - npm run lint
  needs: []

unit_tests:
  extends: .node_defaults
  stage: test
  script:
    - npm test
  needs:
    - job: build_job
      artifacts: true

deploy_job:
  stage: deploy
  script:
    - echo "Deploying..."
  needs:
    - unit_tests
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```
- **Run it:** Push to `main`, watch the pipeline DAG graph.
- **Expected result:** `lint` starts immediately in parallel with `build_job`; `unit_tests` starts right after `build_job` without waiting on `lint`; `deploy_job` only exists on `main` and starts right after `unit_tests`.
- **What this teaches:** These techniques are additive — a real pipeline typically layers `rules`, `needs`, `cache`, `artifacts`, `extends`, and `tags` together, not just one at a time.

## Common Pitfalls
- Using `needs:` for artifact control when the actual goal is "reduce wait time" (or vice versa) — they're related but distinct: `needs:` = ordering/timing, `dependencies:`/`needs:artifacts` = what's downloaded.
- Assuming `cache:` guarantees a hit — it's best-effort; never make correctness depend on cache contents.
- Confusing YAML anchors (`&`/`*`/`<<`) with `extends:` — anchors are file-local and don't merge across `include:`s; `extends:` does.
- Forgetting `extends:` fully overrides array/scalar keys like `script:` rather than concatenating — a job extending a template and adding `script:` replaces the template's script entirely unless it's structured to avoid that.
- Over-using `parallel:`/`matrix:` on cheap jobs — it consumes more concurrent runner capacity for a job that wasn't the bottleneck.
- Leaving `expire_in:` unset on large artifacts — storage quietly grows.
- Still writing `only:`/`except:` in new pipelines instead of `rules:`.

## Interview Questions & Answers
- **Q: How would you speed up a pipeline that takes 20 minutes?**
  A: Profile first; typically: add `needs:` to break unnecessary stage-ordering waits, `cache:` dependency installs, `parallel:` the slowest test suite, and `rules:changes:` to skip jobs unaffected by the change.
- **Q: What's the difference between `needs:` and `dependencies:`?**
  A: `needs:` controls execution order/timing (DAG, can cross stages, can start earlier) and optionally artifact download; `dependencies:` (older keyword) only controls which artifacts a job receives, doesn't affect start timing.
- **Q: What's the difference between `cache:` and `artifacts:`?**
  A: `cache:` is a best-effort speed optimization for reusing inputs (e.g. `node_modules`) across pipelines/branches; `artifacts:` is guaranteed output handoff between jobs within one pipeline, also downloadable/browsable afterward.
- **Q: Is `extends:` the same as YAML anchors?**
  A: No — `extends:` is a GitLab CI keyword with deep-merge semantics that works across `include:`d files; YAML anchors (`&`/`*`/`<<`) are a native YAML feature limited to a single file.
- **Q: How does `extends:` handle multiple inheritance / conflicting keys?**
  A: Reverse deep merge — hash keys like `variables:` merge; scalar/array keys like `script:` are fully overridden by whichever source is closest to the final job (later `extends:` list entries win over earlier ones, the job itself wins over all).
- **Q: What does `rules:changes:` protect against?**
  A: Running jobs when the change couldn't possibly affect them — e.g. skipping a frontend build when only backend files changed. Zero compute cost since the job is never created.
- **Q: Why use `tags:` for optimization, not just correctness?**
  A: It routes expensive jobs to appropriately-sized/-equipped runners and prevents jobs silently queuing forever (or failing) on a runner that can't run them.
- **Q: Scenario: your `test_job` needs `build_job`'s output but not `lint_job`'s, and both run in the `build` stage — how do you speed this up?**
  A: Add `needs: [{job: build_job, artifacts: true}]` to `test_job`, and if `lint_job` has no dependency, give it `needs: []` too — both then run in parallel and `test_job` doesn't wait on `lint_job`.
- **Q: Scenario: pipeline duration barely changed after adding `needs:` everywhere — why?**
  A: Likely the true bottleneck is a single long job on the critical path (e.g. a slow test suite) — `needs:` only removes *waiting*, it can't shrink a job that's inherently slow; that needs `parallel:` or actual script optimization.
- **Q: What's `only:`/`except:` replaced by, and why does it matter for optimization?**
  A: `rules:`, which is more expressive (supports `changes:`, per-rule `variables:`, combinable conditions) and is the only actively maintained conditional-execution keyword.
